# 第 8 轮（灵感循环 R2）· BUDGET：电池管理是预算，跨物体泛化是物理，PEFT 是保先验

> 检索/复核日期：2026-10-25（UTC）。赛事身份不变：宇树 **UniBot 世界挑战赛**（unibot.unitree.com），G1 + Dex1，32 项桌面任务，通才单模型赛道，选手自部署 + 官方远程真机 API 评测。本文件延续第 7 轮状态；本轮是「灵感驱动研究循环」的第 2 轮，记为总第 8 轮。三个灵感词是「电池管理」「跨物体泛化」「参数高效微调」。我先核实了官方手册、榜单、数据集、提交接口和基座模型，得到一个不太舒服但重要的结论：**第 7 轮把"成功率与步骤分综合排序"当作目标函数，是错的；官方规则是成功率优先、步骤分只在成功率打平时作 tie-break。** 这改变了整个优化方向：不是"多拿步骤分"，而是"把整条任务做成"；不是"补最弱轴"，而是"先判断真实榜单是少数任务拖累还是共性能力不足"。在此基础上，我把三个词分别翻译成三个可执行的杠杆：电池管理 → **BMS 预算管理**（180s/320 runs 的时间与算力分配）；跨物体泛化 → **对象中心的物理泛化**（官方未见物品备注是定向换物清单）；PEFT → **保先验的参数预算**（视觉高秩、语言低秩、任务专家路由）。三者合成一个三层预算框架 **BUDGET-GPR**。

## 0. 本轮先核实：九个事实与一个修正

### 0.1 官方排名规则：成功率优先，步骤分只是 tie-break（第 7 轮需要修正）

官方参赛手册（中/英）明确：

- 每个任务执行 **10 次**，5 类泛化（位置/干扰物/背景/未见物品/人为干扰）**各 2 次**；32 个任务 → **320 次计分运行**；
- 每次真机执行 **最多 180 秒**，超时记失败；
- **实时榜单按 32 个任务的总平均成功率排序；成功率相同按总平均步骤分；仍相同则提交日期早的靠前**；
- 仅设通才模型赛道，**所有任务必须用同一个模型完成，不得混合多个模型**；模型类型不限（World Model / VLA 均可）；
- 选手自行部署，官方只做远程 API 调用；**推理延迟与动作内容会被记录**，并可能随结果展示；
- 另有**不计分单任务调试通道**（只测 1 个任务，不计入榜单）。

这修正了第 7 轮的一个关键假设：第 7 轮写"排名 = 成功率与步骤分综合排序"，并据此计算"终局放置 60% 步骤分"的总分增益。**实际上步骤分只在成功率完全相同时才起作用**。所以：

- 终局放置仍然是 **成功闸门**（成功 = 所有步骤完成），这个论点不变；
- 但"终局放置占 60% 步骤分"不能直接换成排名增益；**步骤分是诊断信号和 tie-break，不是第二目标**；
- 任何"只提高部分步骤、但不提高整条任务成功率"的改进，对排名的期望增益接近 0（除非恰好打平）。

这是本轮最重要的策略修正。

### 0.2 公开榜单：确实显示榜首 29.7%，但数据指纹可疑，只能当"早期预览"

榜单页现在渲染了 8 条记录：MolmoAct2/DexHacker 29.7%、WALL-OSS-0.5/Generalist Robotics 28.5%、DreamZero/World Model Lab 27.9%、Spirit-v1.5 25.9%、DM0 23.5%、π0.5 22.8%、GigaBrain-0 22.6%、GR00T N1.5 20.5%。这正是用户说的"榜首不到 30%"。

但我做了三项审计：

1. `leaderboard_data.json` 的 `generated_from` 仍是 `gen_leaderboard.py`；详情页 32 个任务全部写"测试视频占位，后续可替换为真实视频文件"；页面底部仍标"即将发布"。
2. 8 个模型的 **成功率与步骤分 Pearson r = 0.991**，"步骤分 − 成功率"差为 **6.9–10.4pp**，整体随成功率走高。真实的部分分通常不会这么干净地跟随成功率。
3. 32 个任务的平均成功率只在 **17.7%–30.3%** 之间，模型间标准差 2.5–9.5pp；每个任务的最强模型几乎是随机轮换。

结论：**这更像一份"早期预览/演示数据"，不能当作真实 SOTA 上限，也不能用来推断轴级瓶颈。** 但它的模型名是真实的 2026 模型族（MolmoAct2、Wall-OSS-0.5、DreamZero、π0.5、GR00T N1.5），所以也不能完全当假数据扔掉。正确用法是：**只当弱先验；真实判断必须用不计分单任务调试槽重测。** 第 7 轮把 +8.6pp 的"步骤分 − 成功率"差当"失败集中在后段"的证据，本轮应降级为不可用。

### 0.3 数据集：33,276 条 / 18.28M 帧 / 169.3 小时，32 个数据集全部在 2026-10-14 更新

HF collection 实测：32 个数据集，969–1,533 条/任务，合计 **33,276 条**、**18,282,246 帧**、30fps 下 **169.3 小时**。HangCup 1,043 条 / 194,564 帧；PickOutBatteries 993 条；StackBowls 979 条；PlugCharger 1,022 条。全部 `lastModified` 在 2026-10-14。

这说明全量数据已经落地，且比官方宣传的 32k 还多 1.3k。数据不是瓶颈；**如何用这 33k 覆盖 5 个泛化轴才是瓶颈**。

### 0.4 抽查任务均有 5 条英文复述，且数据来自多个采集 session

`meta/tasks.parquet` / episodes metadata 实测：抽查的 HangCup/StackBowls/ZipUp/PlugCharger 四个任务，`tasks` 字段都是 5 条英文复述用 `@` 连接；暂按 32×5 作为上界处理。例如 T11：`Pick out the batteries from the blocks and place them into the green box.@Take batteries out of blocks and put them in the green box.@...`。

episodes 的 `task_id` 前缀显示每个任务有多个采集 session：

- HangCup：6 个 session 前缀、3 个采集 ID、6 个日期（2026-05-06/07、06-02/03/04/24），1,043 条；
- PickOutBatteries：8 个 session 前缀、3 个采集 ID、8 个日期，993 条；
- StackBowls：4 个前缀、2 个采集 ID、4 个日期，979 条；
- PlugCharger：5 个前缀、2 个采集 ID、5 个日期，1,022 条。

这是好消息：数据有一定 session/日期多样性；也是坏消息：**同一任务的对象集合大概率是固定的**，因为官方"未见物品"备注说的是"缺少某物"。这直接引出 0.5。

### 0.5 官方"未见物品"备注，很可能就是"训练集缺少、评测时换入"的定向换物清单

32 个任务的 `generalization.unseen_object_3` 备注措辞高度一致：

- T01 HangCup：缺少红色杯子和塑料架子；
- T02 FruitCollection：缺少不同果篮；
- T03 PackDoll：缺少绿色和紫色娃娃；
- T04 FruitSorting：缺少其他款式的盘子；
- T10 PlugCharger：缺少其他颜色的插排；
- T11 PickOutBatteries：缺少黑色电池；
- T12 Unlock：缺少一把绿色锁；
- T27 StackBowls：除了塑料类型（即训练集只有塑料碗）。

最自然的解读是：**训练集只有一套固定对象，评测的"未见物品"轴会换入这些缺失的变体。** 也就是说，未见物品不是随机噪声，而是**系统性的对象替换分布偏移**：颜色、形状、材质、物理属性都可能变。这个解读尚未官方确认，但和 32 条备注的措辞、以及"未见物品"的定义完全一致。即使解读有误，这些对象变体也是合理的增强集。

实测 32 个任务里，**23 个** `unseen_object_3` 明确写了缺少/不同的对象变体，9 个留空（T08/T09/T15/T16/T19/T29/T30/T31/T32）。这条事实把"跨物体泛化"从"多收数据"变成了一个**有明确目标清单的数据工程问题**：我们知道要换什么。

### 0.6 官方 API：四路相机、关节/EE 双动作空间、chunk 与观测堆叠可配，延迟会被记录

提交模板 README（v2，2026-08-21）：

- 观测：4×RGB 480×640（左右高位 + 左右腕部）、双臂 7 维关节、EE 位姿（base 系，xyz+rpy）、夹爪开度、下半身 15 维、`observation.language` 单字符串；
- 自由度：`obs_delta_indices` 选键 + 每键堆叠帧；`image_resize` 自定；`action_chunk_size` 自定；动作空间 joint 或 ee 互斥；
- `reset()` 每 episode 一次；token 双处校验；
- 多端口：示例 N=3（8765–8767），可每端口独立进程或共享后端，但必须并发安全、状态隔离；
- **每步推理延迟与动作内容会被记录**，组织方可据此评估结果可信度；建议延迟平滑稳定、动作无异常离群。

注意：**观测里没有电池状态、没有力矩/触觉**。所以"电池管理"如果按字面理解，选手没有可观测变量；它只能是组织方侧的运维。这逼我把这个词翻译成"预算管理"（见 1.1）。

### 0.7 基座 WLA-1.0-Base：6B、2,500 小时、64 任务、Apache-2.0，官方微调默认"冻 VLM + 训 DiT"

UnifoLM-WLA-1.0-Base：6B，约 2,500 小时真机数据，64 个任务（桌面 + 全身），Apache-2.0。官方 `unifolm-wla` 的微调脚本默认：

- `trainer.freeze_modules: qwen_vl_interface`，只训 action expert（DiT）和 robot-state projector；
- 默认单卡 24GB；
- 支持 LoRA：VLM 和/或 action model，默认 `r=16, alpha=32`，target 是 q/k/v/o 投影；
- 可只训 action head 的 LoRA，也可同时训 VLM LoRA（需要更多显存）。

这很重要：**官方基线本身已经是"保先验"的参数高效方案**（VLM 冻结）。我们要做的不是"再加一个 LoRA"这么简单，而是回答"在哪一层、用多大秩、要不要任务路由"。

### 0.8 G1 的电池管理是真实的，但它是组织方侧变量

G1 官方规格：9000mAh 快拆电池、约 2 小时续航、13S 锂电、本地风冷、快拆热插拔（具体秒数未在公开页核对）；官方电池资料写有宇树自研 BMS。320 次运行 × 180 秒 = 最多 16 小时，一次完整评测必然涉及多次换电。**这是真实的"电池管理"约束，但选手无法控制**；选手能控制的是单次运行的推理延迟、动作时长和重试次数。所以本轮把"电池管理"翻译成"预算管理"，并用 T11（挑电池）作为字面意义上的金丝雀任务。

### 0.9 一个修正：第 7 轮的"综合排序"与"+8.6pp 弱先验"都要改

- 排名规则改为"成功率优先、步骤分 tie-break"；
- 公开榜单的 +8.6pp 步骤分差是演示数据的生成痕迹，不足以支撑"失败集中在后段"；
- 但"终局放置是成功闸门"仍然成立，因为成功定义就是所有步骤完成；
- 因此本轮的目标函数改为：**最大化 32 个任务的平均整条成功率**，步骤分只用于诊断和打平。

## 1. 三个灵感词，各自钉到可执行的杠杆

### 1.1 电池管理 → BMS：把 180 秒当成一块会耗尽的电池

字面电池不可控，但每个 episode 有一块"180 秒的电池"。BMS 的四个经典功能可以一一映射：

| BMS 功能 | 在 UniBot 里的映射 | 具体做法 |
|---|---|---|
| SoC 估算 | 剩余时间/剩余步骤估计 | `SoC_t = (180 - elapsed) / 180`；用演示时长分布估计 `T_rem` |
| 预留电量 | 终局放置/验证的保留时间 | 预留 `R` 秒（建议 20–30s），低于 `R` 进入 commit 模式 |
| 电芯均衡 | 32 个任务的预算分配 | 按"边际成功率/成本"分配数据、调试槽、重试预算 |
| 热管理/限流 | 延迟与算力节流 | 延迟 p99 超阈值时降 N、降分辨率、关验证；保持延迟平滑 |

这不是比喻游戏，而是直接对着评分结构：

- 成功率是主指标，超时 = 失败；所以"时间花在哪"直接决定成功；
- 终局放置是闸门，但接近/探索/重试会吃掉时间；BMS 保证最后一步有时间；
- 测试时验证/采样能提成功率（VeriVLA +14.7pp，+326ms/触发决策；VLA-ATTC 把 π0.5 失败率降 >50%），但不能无限制地花；BMS 决定"何时值得花"；
- 320 次运行、每次 180s，推理延迟还影响组织方的排期与可信度。

**关键洞察**：多数 VLA 的"重试/验证"是固定预算或固定阈值；UniBot 的成功是 all-or-nothing，且时间硬上限。把重试预算做成**状态相关**（越接近终局、越接近超时，越保守），比固定重试更优。

### 1.2 跨物体泛化 → 对象中心的物理泛化，不是外观泛化

2026 年的证据链：

- **ObjDream**（arXiv 2610.20223）：把观测组织成时序 object slots，身份与动态分通道，identity-guided routing 调制 VLM 注意力，并用 action-conditioned future object state 监督；在 LIBERO-Plus、RoboTwin 2.0 的 OOD 布局/ clutter/背景变化上提升。这说明"对象级结构"是对的方向。
- **Do VLAs Understand...**（arXiv 2610.06078）：七个 VLA 的线性探针显示，质量、易碎性、形变、摩擦、尺寸等**物理属性比语义类别/材质更难解码**；机器人预训练还会削弱语言流里的物理属性编码；把物体质量变大后，多数 VLA 仍用同样的抬升动作，成功率下降。这说明"跨物体"不只是换颜色/形状，**物理属性变化才是真难点**。
- **Pose6DAug**（arXiv 2606.20118）：只替换被操作物体、保留原轨迹/抓取接触/多视角几何，用 3D mesh + 6D pose + 视频 inpainting 生成增广；在 novel objects 上比 SOTA **+16.5%**，且不损 ID。这是"定向换物"的直接证据。
- **Object-centric residual RL**（Microsoft，2026-06）：用 object-centric state + proprio + 基座 VLA 动作训练轻量残差，纯仿真训练、零样本迁移真机，五个任务平均成功率 **42% → 76%**。这说明对象中心接口可以把"泛化"和"精确修正"分开。
- **MolmoAct2 / Wall-OSS-0.5** 等头部模型都在强调几何 grounding / 多 embodiment 预训练；但它们的 UniBot 分数仍在 30% 左右（如果榜单为真），说明"更大的 VLA"不是充分条件。

于是本轮的跨物体策略不是"再收 10 万条数据"，而是三件事：

1. **对象中心表示**：分割/跟踪物体，构造 functional slot（形状、可抓区域、相对容器位姿、物理属性 latent），而不是把整张图丢给 VLA；
2. **定向换物增广**：用官方 32 条未见物品备注做目标清单，从 33k 里挖对象、从 3D 资产库补变体，做 Pose6DAug 式替换；
3. **物理属性鲁棒控制**：对不确定物体用保守抓取/低速抬升/滑移检测；把"物理属性不确定"显式喂给 BMS 的 commit/verify 决策。

### 1.3 PEFT → 不是省算力，是"参数预算"与"保先验"

官方 WLA 微调默认冻 VLM、训 DiT。这已经是 PEFT 思路。下一步的关键不是"要不要 LoRA"，而是：

- **LoRA-SP**（arXiv 2603.07404，ICRA 2026）：VLA 的 intrinsic rank 远高于 LLM；小 rank（4/8）对 LLM 够，对 π0/SmolVLA 可能需要 **r≈128 或接近满秩**；固定 rank 在多任务下更不够；层级分配（视觉塔保留高容量、语言/动作剪枝）能把多任务成功率比标准 LoRA **+31.6%**，并匹配/超过全量微调。
- 这直接对应 UniBot：32 个任务、5 个泛化轴，**视觉/对象识别需要高容量，语言指令只有 160 条复述、低容量足够**。所以默认的 r=16 可能把容量放错了地方。
- 另一个问题是多任务干扰：32 个任务里有堆叠、插入、倾倒、拉链、布料，梯度会冲突。**共享 LoRA + 任务族专家路由（MoLE）** 是一个单 checkpoint 的解法：共享专家学通用操作，4–8 个任务族专家学差异，router 用指令嵌入/步骤相位。
- PEFT 还是**消融引擎**：8–16 个 LoRA 可以并行训练，几天内筛掉坏数据配方；全量微调做不到这个迭代速度。

所以 PEFT 在本轮不是"省显存"，而是三件事：**容量分配（rank budget）、任务路由（MoLE）、先验保持（OOD consistency）**。

## 2. 合成判断：三层预算 + 一个对象中心底座

把三个词放一起，得到一个比第 7 轮更完整的目标函数：

```text
maximize  (1/32) Σ_i p_i                       # 成功率优先，步骤分只是 tie-break
s.t.      p_i = P(整条任务成功 | 模型, 场景, 180s)
          模型 = 单一 checkpoint（PEFT/MoLE + 对象适配器）
          数据 = 官方 33k + 定向换物增广（不引入外部机器人数据）
          执行 = BMS 预算管理（180s 内分配验证/重试/收尾）
```

三层预算：

1. **训练预算（PEFT）**：参数花在哪？视觉高秩、语言低秩、任务族专家、对象适配器；
2. **任务预算（Portfolio）**：32 个任务，数据/调试/重试花在哪些任务？按边际成功率/成本分配；
3. **执行预算（BMS）**：180 秒内，验证/探索/重试/收尾各花多少？预留终局。

对象中心表示是共享底座：它同时服务策略（动作）、成功预测（BMS 的 p_t）、检索（ICR 的 key）和换物增广（OSA 的 mask/track）。

与第 7 轮的关系：

- **保留**：SSG 评分步骤图、PGL 放置目标阶梯、OPT 放置位姿迁移、ICR 检索、SVL 落点闭环、NRB 官方备注恢复、DebugLoop；
- **升级**：SSG 从"步骤分最大化"改为"成功门控 + 预算信号"；SVL 受 BMS 管；ICR/OPT 的 key 改成对象中心；GPR-VLA 加 PEFT/MoLE + 对象适配器；
- **新增**：BMS-EP（episode 预算）、BMS-PB（任务组合预算）、OCO（对象中心观察器）、OSA（定向换物增广）、PEFT-R（rank 分配/路由）、ATC（自适应测试时计算）；
- **修剪**：L2L 产学研降为可选（本轮不主推）；FLEET 只留工程检查单；全孪生/自由仿真/运行时 MPC/仿真 RL 继续砍；"步骤分作为第二目标"砍掉；"公开榜单当真实排名"砍掉。

## 3. 可证伪的五个假设

| # | 假设 | 检验 | 如果失败 |
|---|---|---|---|
| H1 | 真实榜单的 32 个任务不是少数零分拖累，而是普遍 20–30% 的共性能力不足 | 用 3 个 canary（T11/T27/T10）各 ≥30 次调试 + 任务级分布；10 次只做冒烟 | 若发现 5+ 个近零任务，转为 floor-raising |
| H2 | 官方未见物品备注是"训练缺少→评测换入"的清单；定向换物增广能提升未见物品轴 ≥10pp | 对象 held-out 离线 + ≥30 次 canary 或配对 A/B | 若解读错误，退回通用换物/背景增广 |

| H5 | BMS + ATC 在同等或更低平均延迟下提升整条成功率 ≥5pp | T11/T27/T10 的 ≥30 次 A/B；成功率/时间/p99 | 若只提步骤分不提成功率，关掉 ATC |

## 4. 风险与合规（先立后破）

- **单模型边界**：MoLE/对象适配器/验证头都必须在**同一个 checkpoint** 内；检索库是数据不是模型；确定性控制器（BMS/SVL）不算第二个模型。模型卡要写清楚。
- **外部数据**：官方手册只写"每队可获得 32 任务全部数据"，没有明确说外部数据是否允许。默认只用官方 33k + 由其派生的增广；3D 资产要逐个核许可；邮件问 `challenge_support@unitree.com`。
- **换物增广的物理真实性**：3D 替换可能产生"看起来对、抓起来不对"的样本；用抓取可行性/接触一致性 QA，拒绝率 >20% 就停。
- **对象备注解读**：`unseen_object_3` 的含义未官方解释；同时准备通用换物/背景增广兜底。
- **榜单不可靠**：公开榜单是早期预览；不要用它调参，最多用它选 canary。
- **延迟**：ATC 会加 300ms 级延迟；180s 预算内可承受，但 p99 要稳；延迟异常可能影响结果可信度。
- **过拟合 33k**：对象中心 + PEFT 的目的就是防这个；如果离线 OOD 不升，宁可退回官方基线 + 轻量 BMS。

## 1. 事实核对与修正

### 1.1 排名规则：成功率优先，步骤分只是 tie-break

官方参赛手册（中文）原文：

> “实时榜单按32个任务的 **总平均成功率** 进行排序，成功率相同时按 **总平均步骤分** 排序，若仍相同，则提交日期较早的模型排序靠前。”

英文版同义：

> “The real-time leaderboard is sorted by overall average success rate across all 32 tasks. In the event of a tie, the overall average step score is used as the differentiator.”

其他硬约束：

- 32 个任务，每个任务 10 次独立运行；5 类泛化（位置/干扰物/背景/未见物品/人为干扰）各 2 次；共 **320 次计分运行**。
- 每次真机执行最多 **180 秒**，超时记失败。
- 所有任务必须用 **同一个模型**；不得混合多个模型。模型类型不限（World Model / VLA 均可）。
- 选手自行部署；官方只做远程 API 调用；推理延迟与动作内容会被记录。
- 另有 **不计分单任务测试通道**，可用作调试，但成功率和步骤分不计入榜单。

**修正**：第 7 轮把“成功率与步骤分综合排序”当目标函数，据此计算“终局放置 60% 步骤分”的排名增益，这是错误的。终局放置仍然是成功闸门（成功=所有步骤完成），但 **只提高部分步骤、不提高整条成功率** 的改进，对排名的期望增益接近 0，除非恰好把成功率打平。

### 1.2 公开榜单：8 条记录，但仍是脚本生成的预览

`leaderboard_data.json` 当前渲染 8 条记录：

| 模型 | 团队 | 平均成功率 | 平均步骤分 | 步骤分−成功率 |

### 1.5 API、基座与 G1 的约束

**提交 API**（`unibot_submission` README）：

- 四路 RGB 480×640：`cam_left_high`、`cam_right_high`、`cam_left_wrist`、`cam_right_wrist`。
- 状态：双臂 7 维关节、左右 EE 位姿（base 系，xyz+rpy）、左右夹爪、`lower_body` 15 维；`observation.language` 单字符串，episode 内不变。
- 可配置：`obs_delta_indices` 选键+每键堆叠帧；`image_resize`；`action_chunk_size`；动作空间 joint / ee 互斥。
- `reset()` 每 episode 一次；token 双处校验。
- N 个评测机器人对应 N 个连续端口（示例 8765–8767）；每端口独立 episode/状态；共享后端必须并发安全、状态隔离。
- **每步推理延迟与动作内容会被记录**；延迟平滑、动作无异常离群是被建议的。

**关键缺失**：观测里**没有电池状态、没有力矩/触觉、没有深度图**。所以字面“电池管理”不是选手可观测变量；如果 OCO 需要深度/分割，必须用 checkpoint 内的学习头，或仅把外部模型当离线教师。

**WLA-1.0-Base**：

- 6B，约 2,500 小时真机数据，64 个任务（桌面 + 全身），Apache-2.0。
- 官方微调脚本默认 `trainer.freeze_modules: qwen_vl_interface`，只训 action expert（DiT）和 robot-state projector；默认单卡 24GB。
- 支持 LoRA：VLM 和/或 action model；默认 `r=16, alpha=32`，VLM target 为 `q_proj/k_proj/v_proj/o_proj`；action model target 为 `to_q/to_k/to_v/to_out.0/add_q_proj/add_k_proj/add_v_proj/to_add_out`。
- 官方基线本身就是“保先验”的参数高效方案；问题不是“要不要 LoRA”，而是“在哪层、多大秩、要不要任务路由”。

**G1 电池**：

- 9000mAh 快拆智能电池、13S 锂电、约 2 小时续航、宇树自研 BMS；本地风冷。官方产品页与开发者文档可核。
- 320 次 × 180 秒 = 最多 **16 小时**；按占位榜平均 44.02s 估算约 **3.9 小时**；2 小时续航意味着至少 2 次换电，极限情况 8 次。
- 这是真实的组织方侧约束，但选手无法读电池状态；选手能控的是推理延迟、动作时长、重试次数。**BMS 在本方案里是软件预算，不是电池控制。**

## 2. 定量分析：为什么不能“只修一个点”

### 2.1 目标函数

设任务 \(i\) 的 10 次运行成功率为 \(p_i\)，则：

```text
S = (1/32) Σ_i p_i
p_i = (1/10) Σ_j y_ij,  y_ij ∈ {0,1}
```

排名先比 \(S\)，只有 \(S\) 相同才比步骤分。于是：

```text
ΔS = (1/32) Σ_i Δp_i
```

**一个任务 +10pp → 总平均 +0.3125pp。** 想靠单点拿到 +3pp，需要该任务 +96pp，不现实。想靠 10 个任务各 +10pp，才有 +3.1pp。

### 2.2 统计噪声：一次 320 次评测只能分辨约 5pp

在 p≈0.30、320 次独立运行下：

```text
SE = sqrt(p(1-p)/320) = sqrt(0.21/320) ≈ 2.56pp
95% CI ≈ ±5.0pp
```

两个独立模型差值的 SE≈3.6pp，95% CI≈±7.1pp。因此：

- 榜首 29.7% vs 28.5% 的 1.2pp 差距 **不显著**。
- 一次正式跑看到 +3pp，不能可靠区分“真实提升”与“运气”。
- 不能把占位榜的任务均值当真实瓶颈；也不能用一次跑的结果决定砍/留组件。

**任务级更糟**：每个任务只有 10 次，p≈0.3 时 SE≈14.5pp，95% CI≈±28.4pp。任务级排名几乎不可用；必须做层次贝叶斯/部分池化，或增加试次。

### 2.3 对象轴的算术：23 个任务也只是 14.4% 的试次

| 改动 | 影响试次 | 总平均增益（若该改动 +Δ） |
|---|---:|---:|
| 1 个任务全部 10 次 | 10/320 | 0.03125 × Δ |
| 23 个明确任务的对象轴（2 次/任务） | 46/320 | 0.14375 × Δ |
| 全部 32 任务的对象轴（2 次/任务） | 64/320 | 0.20 × Δ |
| 全部 32 任务全部轴 | 320/320 | 1.00 × Δ |

代入数字：

- 23 个任务的对象轴 +20pp → **+2.9pp**。
- 全部对象轴 +10pp → **+2.0pp**。
- 9 个留空任务的对象轴 +10pp → **+0.56pp**。

所以“直接对着 20% 的未见物品轴去”只对 **全部 32 个任务** 才成立；只修 23 个明确任务，上限只有 +2.9pp。BUDGET-GPR 必须让 OCO/OSA 的收益外溢到位置、干扰物、背景、human 轴，而不是只做 23 个换物。

### 2.4 Canary 的功效：10 次试验不能证明 +10pp

不计分单任务通道如果只给 10 次，p≈0.3 时：

| 试次数 n | SE | 95% CI 半宽 |
|---:|---:|---:|
| 10 | 14.5pp | ±28.4pp |
| 30 | 8.4pp | ±16.4pp |
| 50 | 6.5pp | ±12.7pp |
| 100 | 4.6pp | ±9.0pp |

即使 30 次，也只能勉强看到 15pp 级效应。**第 7 轮/草稿里的“canary 真机 +10pp 才放行”在 10 次试验下不可检验。** 正确做法：

1. 向官方申请 **每个 canary ≥30 次**；能给 50–100 更好。
2. 如果只能 10 次，把它当 **冒烟测试/失败模式观察**，不作为 +5pp 的 Go/No-Go。
3. 用同场景配对 A/B / 多任务 canary 套件降低方差；报告置信区间，不报单点。
4. 正式跑仍是 320 次；把“+3pp 目标”写成期望，不写成保证。

### 2.5 时间预算：180s 很宽，BMS 的价值不是“省电”

- 中位 episode 5.9–15.5s；平均 18.3s；占位榜平均 44.02s。180s 上限对多数任务很宽。
- 320 次 × 180s = 16h 上限；按 44s 平均 ≈3.9h；G1 2h 续航 → 至少 2 次换电。
- 真正的时间风险是：长程任务（T16/T17/T31）、插入/对齐失败后的重试、ATC 验证开销、以及接近 180s 时的“最后一放”。
- BMS 的 reserve 建议 **15–25s（默认 20s，长程 30s）**；不是固定 30s。 
- ATC 每次触发约 +326ms 级（VeriVLA 口径）；5 次触发约 1.6s，180s 内可承受，但 p99 必须稳。
- BMS 必须在 **177s 前**进入 safe-hold，给超时留 2–3s 安全边界。

### 2.6 组合预算：按边际成功率/成本分配，不按“最弱轴”

32 个任务等权，但每个任务的失败原因、数据量、对象备注、调试成本不同。BMS-PB 的目标不是“补最弱轴”，而是：

```text
maximize  Σ_i E[p_i | data_i]
s.t.      Σ_i c_i ≤ B_data + B_debug + B_compute
```

其中 \(c_i\) 包含采集/增广/训练/调试成本。用层次 Beta-Binomial 估计 \(p_i\)，优先把预算给：

1. 明确对象变体、且当前 p 低/不确定性高的任务（T10/T11/T27 等）；
2. 终局步骤重、失败代价高的任务（T16/T17/T31）；
3. 能验证共享能力的任务（插入、堆叠、拉链、透明/布料边界）；
4. 不能只给一个 canary：一个任务只占 1/32，单点收益上限太低。

**结论**：BUDGET-GPR 的主线必须是“共享能力 + 多任务外溢”，canary 只用于诊断，不作为唯一优化目标。

### 3.2 BMS-EP：把 180 秒当成一块会耗尽的电池

BMS 的四个经典功能映射：

| BMS 功能 | UniBot 映射 | 实现 |
|---|---|---|
| SoC 估算 | 剩余时间/剩余步骤 | `SoC=(180-t-R)/(180-R)`；用演示分布估 `n_rem` |
| 预留电量 | 终局放置/验证 reserve | 默认 20s，长程 30s |
| 电芯均衡 | 32 任务组合预算 | BMS-PB |
| 热管理/限流 | 延迟/算力节流 | p99 超阈值时降分辨率/降 K/关 ATC |

**状态**：`t`（elapsed）、`step`、`p_t`（SSG 成功头）、`n_rem`、`retry_count`、`latency_p99`、`verify_cost`。

**动作**：`continue`、`verify`、`retry`、`regrasp`、`commit`、`safe_hold`。

```python
def bms_ep(t, step, p_t, n_rem, stats):
    reserve = 30.0 if step.long_horizon else 20.0
    step_p90 = stats.p90_step_time[step.id]
    verify_cost = 0.33
    slack = 180.0 - t - reserve - n_rem * step_p90

    if t >= 177.0:
        return "safe_hold"

    if step.is_terminal:
        if slack < step_p90 + 0.5:
            return "commit"
        if 0.25 <= p_t <= 0.80:
            return "verify"
        return "commit"

    if p_t < 0.25 and slack > step_p90 + 0.5:
        return "retry" if stats.retry_gain[step.id] > 0 else "commit"

    if p_t < 0.55 and slack > verify_cost + step_p90:
        return "verify"

    return "continue"
```

关键点：

- `reserve` 不是常数；长程任务留 30s，普通任务 20s。
- 终局步优先“commit 或 verify”，不在最后一放前做昂贵探索。
- `p_t` 低且余量足够才重试；否则保守完成当前步，避免把时间耗在抓取循环。
- `safe_hold` 在 177s 触发，保证不因推理延迟超 180s。
- BMS 不学习、不引入第二个模型；它是确定性控制器，必须在模型卡披露。

### 3.3 BMS-PB：32 任务组合预算

离线调度器，输入：

- 每个任务的当前成功率后验 `p_i ~ Beta(a_i,b_i)`（来自 canary/历史/离线代理）；
- 每个任务的增广/训练/调试成本 `c_i`；
- 任务权重 `w_i=1/32`；
- 总预算 `B`（GPU 小时、标注小时、调试槽、正式跑次数）。

目标：

```text
maximize  Σ_i w_i * E[p_i | b_i]
s.t.      Σ_i b_i ≤ B
```

简单可执行版：每轮选“期望边际增益/成本”最高的任务，执行后更新后验；每两周重排。不要用占位榜的任务均值做先验，只用它选 canary。

### 3.4 OCO：对象中心观察器（单 checkpoint 内）

**动机**：ObjDream 证明时序 object slots + identity routing + future object state 能提升 OOD 布局/杂波/背景；Do VLAs Understand 证明物理属性（质量、易碎、形变、摩擦、尺寸）比语义类别更难解码；只换外观不够，物理属性才是深水区。

**设计**：

- 输入四路 RGB + proprio + language；共享对象 query（K=16）跨视角聚合。
- 每个 slot 输出：
  - `h_k`：身份/外观 embedding；
  - `m_k`：mask logits；
  - `b_k`：2D box；
  - `r_k`：相对夹爪/容器的关系 token；
  - `v_k`：短时运动 token；
  - `φ_k`：物理属性 latent（尺寸/材质/可变形/易碎/摩擦的弱监督）。
- **identity-guided routing**：把 slot token 注入 VLM/DiT 的 token 序列，用 identity embedding 调制注意力，减少背景/杂波干扰。
- **future object state**：训练时用 action-conditioned 预测 `z_{t+Δ}` 监督；推理不做未来预测（ObjDream 的做法），避免延迟。
- **单模型边界**：在线只跑 checkpoint 内的 OCO 头；SAM2/检测器只作为离线教师生成伪标签，不参与推理。模型卡要写清教师模型与标签来源。
- **无深度**：API 没有深度图；OCO 先用 2D mask + 多视角 + EE 位姿 + 腕部视角学关系。若官方提供标定，再加 3D；不要假设有 depth。

**损失**：

```text
L_slot = λ_mask L_mask + λ_obj L_obj + λ_track L_track
       + λ_rel L_relation + λ_future L_future + λ_phys L_phys
```

其中 `L_future` 只在训练；`L_phys` 用可得的材质/尺寸标签或语言弱监督，不能伪造质量标签。

### 3.5 OSA：定向换物增广

**目标清单**：23 个明确 `unseen_object_3` 的任务（§1.4）；9 个留空任务用通用换物/背景增广兜底。

**OSA-lite（默认，2.5D，多视角一致）**：

1. 从官方 episode 里分割/跟踪目标物体与容器（离线教师）。
2. 对象 bank：按任务/外观/尺寸/可抓区域聚类；留出 20% 外观簇做 object-held-out。
3. 选同 affordance 的替换对象；对齐 2D 尺度/朝向/接触点。
4. 在四路视角同步替换；保留原动作轨迹、夹爪遮挡、接触时序；用 inpainting 补背景。
5. 保持原任务语言（或使用官方 5 条复述之一）；不引入新任务名。
6. QA：mask IoU、多视角一致性、接触保持、时序平滑、抓取可达；拒绝率 >20% 停。

**OSA-3D（可选，后置）**：mesh + 6D pose trajectory + 多视角渲染，接近 Pose6DAug；需要 3D 资产与许可，默认 OFF。Pose6DAug 的证据是 novel objects **+16.5%** 且不损 ID，但依赖物理一致的 3D 替换；2.5D 是低成本近似，必须用 QA 防止“看起来对、抓起来不对”。

**规模**：首轮 8 个任务 × 50–100 段 ≈ 400–800 段；扩到 23 个任务 × 50–100 段 ≈ 1.2–2.3k 段；加 9 个通用任务 ≈ 0.3k。相对 33k 真实数据约 5–10%，上限 25%。合成不能主导。

### 3.6 PEFT-R：参数预算、任务路由、先验保持

**基线**：官方 WLA 微调 = 冻 `qwen_vl_interface`，训 DiT action expert + projector；LoRA 默认 r=16/alpha=32。这个基线必须先复现。

**三层参数预算**：

| 层 | 建议 | 理由 |
|---|---|---|
| VLM 视觉流 | r=64/128（或 LoRA-SP 自适应） | 对象外观/几何变化需要高容量；LoRA-SP 指出 VLA 的 intrinsic rank 远高于 LLM |
| VLM 语言流 | r=8/16 | 只有 32 任务 × 5 复述，低容量足够，减少过拟合 |
| Action expert | r=32/64 或全量 | 动作精度是成功闸门；官方默认已训 DiT |
| 任务路由 | 4 个专家 + 1 共享，top-1/top-2 | 32 任务梯度冲突；单 checkpoint 内 MoLE |
| OOD 一致性 | 轻量正则 | clean/OSA 特征与动作一致，防换物过拟合 |

**MoLE 路由**：输入 = 指令 embedding + SSG 相位 + OCO 对象 token；4 个任务族专家（插入/堆叠、抓放/整理、可变形/拉链、工具/铰接），共享专家保通用；加 load-balancing loss，防专家塌缩。

**单模型审计**：所有专家、OCO、ATC 验证头、谓词头都在同一个 checkpoint；检索库是数据；BMS/SVL 是确定性代码。不得在推理时调用第二个 VLA/大模型。

**证据与边界**：LoRA-SP 在多任务真实机器人上比标准 LoRA 最高 **+31.6%**，并匹配/超过全量微调；但这是 π0/SmolVLA 的结果，不是 WLA。我们把它当 **rank 假设**，必须用 r=16/64/128/adaptive 消融验证。若全量微调更好且资源允许，回退全量 + OSA。

### 3.7 ATC：自适应测试时计算

**动机**：flow-based VLA 的噪声种子会产出不同质量的 chunk；固定单采样可能把一次坏动作变成不可逆失败。但 always-on 验证会拖垮延迟。

**设计**：

- 触发信号：两个初始 chunk 的 within-chunk 时序变化 + cross-sample 方差；或 SSG 成功头 `p_t∈[0.25,0.8]`。
- 触发后：采样 K=2–4 个候选 chunk；用 checkpoint 内的轻量 verifier 排序（输入 OCO future state、步骤相位、动作平滑度、夹爪时序）。
- 预算：BMS 只在 `slack > verify_cost + reserve` 时允许；每 episode 最多 5 次；总附加时间 ≤2s。
- 关闭条件：p99 >150ms，或只提高步骤分不提高成功率。
- 证据：VeriVLA 把 completion 50.8→65.5，每次触发 +326ms；VLA-ATTC 把 π0.5 在 LIBERO-LONG 的失败率降 >50%；DIRECT 证明“何时/何地花测试时算力”比固定 scaling 更省，最多降低 65% 延迟。

**注意**：ATC 不是“多采样一定更好”。如果 verifier 在 OOD 上不可靠，它会把预算花在错的动作上；必须用 object-held-out 和 canary 验证。

### 3.8 保留并升级的模块

| 模块 | 本轮定位 | 关键改动 |
|---|---|---|
| SSG v2 | 成功门控 + 相位标签 + 预算信号 | 不再最大化步骤分；32 任务步骤图；终局步=成功闸门；160 条复述匹配 |
| PGL v2 | 槽位/区域→2D 锚点→6D 位姿 | 锚点来自 OCO 对象/容器；训练/推理同渲染 |
| OPT v2 | 少样本释放位姿迁移 | 容器系 `H_i` 统计；key 改为对象中心；离散度驱动控制风格 |
| ICR v2 | 对象中心检索 | 键=对象关系+运动+相位；库=官方 33k；缓存编码控延迟 |
| SVL v2 | 落点 settle-verify | 缓放→0.5s 稳定/谓词校验→nudge/regrasp；受 BMS 管 |
| NRB v2 | 官方备注恢复 | human 备注剧本；9 个无对象备注任务用它兜底；可选 |

SSG 的事实基础：32 任务满分 100，终局步骤合计 **1275/3200=39.8%**，放置/插入/堆叠/闭合类约 **59.7%**。这些数字现在只用于“终局是闸门”和“时间/验证优先级”，不再用于“步骤分收益”计算。

### 3.9 单一 checkpoint 的接口

```text
obs ──► OCO ──► slot tokens ──┐
language ──► SSG ──► phase ───┤
                              ├─► GPR-VLA (WLA + PEFT-R/MoLE) ──► chunk
ICR.retrieve(object keys) ────┘
                              │
BMS-EP ──► allow/deny verify/retry ──► ATC / SVL
```

- OCO、SSG 谓词头、ATC verifier、policy/MoLE 是学习组件，必须同一 checkpoint。
- SSG 图、BMS、SVL、PGL 投影是确定性代码。
- ICR 是检索数据；训练时同步构建/采样，避免推理首次见 token 崩。
- 所有学习组件的输入输出在模型卡中披露；不把“检索库”伪装成模型。

### 3.10 损失

```text
L = L_flow
  + λ1 L_mask + λ2 L_obj + λ3 L_track + λ4 L_future + λ5 L_phys
  + λ6 L_step + λ7 L_ood + λ8 L_route + λ9 L_atc
```

| 项 | 含义 | 初始权重 |
|---|---|---:|
| L_flow | 动作 flow matching（WLA 原生） | 1.0 |
| L_mask/L_obj/L_track | OCO 分割/对象性/时序一致 | 0.1/0.1/0.05 |
| L_future | action-conditioned future object state（仅训练） | 0.05 |
| L_phys | 物理属性弱监督（仅在有标签时） | 0.01 |
| L_step | SSG 谓词/步骤 BCE | 0.2 |
| L_ood | clean/OSA 特征与动作一致性 | 0.05 |
| L_route | MoLE load balance | 0.01 |
| L_atc | verifier 排序/成功 BCE | 0.1 |

权重是起点，不是结论；用小规模消融定。

## 4. 数据引擎

### 4.1 对象 bank

- 从官方 33k 提取对象 track：离线教师分割 + 跟踪 + 人工抽检。
- 每个对象记录：任务、外观簇、尺寸、可抓区域、容器关系、出现时段、语言复述。
- 23 个明确备注任务优先；9 个留空任务用通用对象/背景增广。
- 留出 20% 外观簇作为 object-held-out；不能随机拆帧，否则泄漏。

### 4.2 object-held-out 划分

```text
train: 80% 对象外观簇 × 80% episode
val:   10% 对象外观簇 × 20% episode
test:  10% 对象外观簇（完全未见）
```

同时报告：

- ID（同对象、同任务、不同 episode）
- object-OOD（未见外观簇）
- task-OOD（若做跨任务迁移，单独报告，不混在一起）

### 4.3 OSA 规模与配比

| 桶 | 任务数 | 每任务段数 | 段数 |
|---|---:|---:|---:|
| 明确换物（OSA-lite） | 23 | 50–100 | 1,150–2,300 |
| 通用换物/背景 | 9 | 30 | 270 |
| 首轮试点 | 8 | 50–100 | 400–800 |
| 合计（扩展后） | 32 | — | 1,420–2,570 |

- 相对 33k 真实数据约 **4–8%**；可扩到 5–8k（15–25%），但合成不得超过 25%。
- 每段 1–3s；保留原动作与夹爪时序。
- 拒绝率 >20% 停；mask IoU <0.8、接触点偏移 >5mm、时序抖动超阈值都拒绝。

### 4.4 QA 与合规

- 自动 QA：mask/box 一致性、多视角重投影、接触保持、夹爪遮挡、动作平滑、语言匹配。
- 人工抽检 10%；每个任务至少 20 段。
- 物理真实性：2.5D 只改外观/几何，不改质量/摩擦；不要把“换色”说成“物理泛化”。
- 外部资产默认 OFF；3D mesh/贴图逐个核许可；教师模型只离线用，模型卡披露。
- 单模型边界：在线不加载 SAM/检测器/第二个 VLA。

## 5. 训练配方

### 5.1 阶段

| 阶段 | 数据 | 目标 | 退出条件 |
|---|---|---|---|
| 0 | 官方 33k | 复现 WLA 基线 | 真实 held-out 不降 |
| 1 | 官方 + OCO 伪标签 | 对象 slot/mask/track/future | mask IoU/跟踪达阈值 |
| 2 | 官方 + OSA-lite | 换物鲁棒 | object-held-out 代理指标 +10% 相对 |
| 3 | 官方 + OSA + PEFT-R | rank/MoLE/一致性 | ID 不降 >2pp，OOD 升 |
| 4 | + ATC verifier | 关键状态验证 | 离线排序 AUC 达标 |
| 5 | 全量 + 蒸馏/量化（可选） | 延迟 | p99 ≤150ms，理想 ≤100ms |

### 5.2 超参起点

| 项 | 值 |
|---|---|
| 基座 | WLA-1.0-Base 6B，bf16 |
| 冻结 | VLM 主干冻结（基线）；PEFT-R 只开 LoRA |
| LoRA | r=16 基线；视觉 64/128，语言 8/16，动作 32/64；alpha=2r |
| MoLE | 4 专家 + 共享；top-1；load balance 0.01 |
| 优化器 | AdamW；LoRA lr 1e-4；全量 2e-5；cosine；warmup 3% |
| batch | 64–128（按显存） |
| chunk | 16–32；控制 30Hz |
| 相机 | 4×480×640；可 resize 到 224/256 省延迟 |
| 算力 | 8×H100 级；官方 24GB 单卡只适合基线/小实验 |
| 早停 | 真实 held-out + object-OOD，不看占位榜 |

### 5.3 延迟

- 目标 `get_action` p99 ≤150ms；理想 ≤100ms。6B + 4 相机 + 对象头可能吃紧，优先 chunk≥16、图像 resize、共享后端批量。
- N 端口并发：每端口状态隔离；共享模型时做请求队列/批处理；p99 不能因并发翻倍。
- ATC 触发时 +300ms 级；BMS 保证总时间仍 <180s。
- 延迟异常会被官方记录；不要用“故意慢”规避超时或制造不可信轨迹。

## 6. 评测协议

### 6.1 三级评测

1. **离线（每天）**：object-held-out 的动作误差、释放位姿误差、mask/跟踪、成功头 AUC、ATC 排序 AUC、延迟。
2. **本地（每周）**：回放 + 小规模物理仿真（可选，只做接触/放置 sanity，不作为主回路）；失败模式挖掘。
3. **平台（版本门）**：不计分单任务 canary；正式计分跑 1–2 次。

### 6.2 Canary 套件

首选 5 个任务，覆盖不同失败模式：

- **T10 PlugCharger**：插入/对齐/力控。
- **T11 PickOutBatteries**：字面电池 + 精细抓取 + 物体变体。
- **T27 StackBowls**：堆叠/放置/非塑料变体。
- **T19 ZipUp**：可变形/闭合。
- **T20 PaperCupStacking**：轻物体/堆叠/纸杯变体。

每个 canary 尽量 ≥30 次；只能 10 次时只做冒烟，不做 +5pp 判定。记录：成功率、步骤分、时长、p50/p99 延迟、失败阶段、是否超时。

### 6.3 正式跑

- 计划 2 次（W7/W8）；若只允许 1 次，放 W8。
- 提交前 4h soak：N 端口并发、reset 隔离、健康检查、p99、异常动作检查。
- 预注册指标：总成功率、任务级成功率、对象轴、步骤分、时长、延迟；避免事后挑指标。

### 6.4 统计

- 任务级配对 bootstrap（按任务/场景重采样）；报告 95% CI。
- 一次 320 次跑的 CI≈±5pp；不要宣称 <3pp 的显著提升。
- 组件决策用离线 object-held-out + 30+ canary；正式跑只做最终确认。
- 若 CI 跨 0，不上线；若只提步骤分，不上线。

## 8. 创新点清单

> 状态：押注=本轮主线；支持=重要但非主线；升级=旧点改造；保留=沿用；可选=资源允许再做；砍=不做。

### I1 BMS-EP（新增，押注）
- 动机：180s 硬上限 + 全有或全无；固定重试/固定验证会浪费预算；观测无电池状态。
- 差异：把剩余时间、步骤、成功概率、延迟合成状态相关预算；终局 reserve；确定性控制。
- 可行性：只需时间戳、SSG、演示时长统计；无需训练。
- 资源：1 人周；CPU。
- 步骤：统计每步 p50/p90 → 实现控制器 → 离线回放校准 → 接 ATC/SVL。
- 风险：估算偏差/额外开销；用保守 p90 + safe-hold。
- 状态：押注。

### I2 BMS-PB（新增，支持）
- 动机：32 任务等权，数据/调试/算力有限；不能只修一个 canary。
- 差异：成本感知的 portfolio，不是“补最弱轴”。
- 可行性：离线优化；可与训练并行。
- 资源：低；1 人周。
- 步骤：后验估计 → 成本表 → 贪心/规划 → 双周重排。
- 风险：先验噪声；用保守区间，不追占位榜。
- 状态：支持。

### I3 OCO（新增，押注）
- 动机：ObjDream/物理属性证据表明对象级结构是 OOD 关键；纯图像 token 不够。
- 差异：对象 slot + identity routing + future state，全部在单 checkpoint；在线不用外部模型。
- 可行性：中等；需要离线教师标签；四视角可做。
- 资源：8×H100 级；2–3 周。
- 步骤：教师标签 → slot/mask/track → future/phys → 注入 VLM/DiT → 消融。
- 风险：分割噪声、单模型审计、无深度；先 2D/关系，不承诺 3D。
- 状态：押注。

### I4 OSA（新增，押注）
- 动机：23 个明确换物备注是免费的目标清单；Pose6DAug 证明定向换物 +16.5%。
- 差异：官方数据内的 2.5D 多视角替换 + QA；3D 后置；不做无许可资产。
- 可行性：中等；首轮 8 任务可落地。
- 资源：2–3 周；离线渲染/标注。
- 步骤：对象 bank → 8 任务试点 → QA → 23 任务扩展 → 配比消融。
- 风险：合成伪影/物理不一致；拒绝率 >20% 停。
- 状态：押注。

### I5 PEFT-R（新增，押注）
- 动机：官方 r=16 可能把容量放错；32 任务干扰；要保基座先验。
- 差异：视觉高秩/语言低秩/动作专家 + MoLE + OOD 一致性；单 checkpoint。
- 可行性：高；官方已支持 LoRA。
- 资源：8×H100 级；1–2 周。
- 步骤：复现基线 → rank 网格 → MoLE → 一致性 → 选配方。
- 风险：过拟合/延迟/审计；ID 降 >2pp 回退。
- 状态：押注。

### I6 ATC（新增，押注）
- 动机：flow 采样随机；关键状态一次坏 chunk 可能不可逆；固定 TTC 太贵。
- 差异：BMS 预算内触发；verifier 在 checkpoint 内；只在前景/终局用。
- 可行性：中等；需要 verifier 标签/离线排序。
- 资源：1–2 周；GPU 推理。
- 步骤：不确定性触发 → 候选排序 → 接 BMS → 延迟压测。
- 风险：延迟/验证器 OOD 不可靠；p99 超阈值关闭。
- 状态：押注。

### I7 SSG v2（升级，保留）

## 10. 八周计划
