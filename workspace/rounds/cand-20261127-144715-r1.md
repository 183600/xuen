## 1. 直觉与动机

### 1.1 灵感 1（ROS2）：ROS2 不是接口，是接口纪律

直觉：看到 ROS2 的第一反应是把策略包成 ROS2 节点。但 F20 说评测器只认 websocket/msgpack 的 PolicyService；把 ROS2 塞进计分路径，等于在 66ms 预算里加一次 DDS 发现、一次序列化、一个 daemon，换来的却是评测器看不见的东西。ROS2 真正值钱的是它逼你写清楚的四件事：**契约、生命周期、组合、可观测/可重放**。所以正确姿势是**双平面**：

- **计分面（data plane）**：纯 Python PolicyService，外部 schema 冻结，依赖最小，每端口状态隔离，确定性优先；
- **实验面（control plane）**：ROS2/DDS 只用于实验室——数据采集、机器人 bringup、TF2 坐标系、rosbag2 录制与回放、监控；
- 两面只通过一个**版本化 schema** 相接。

核心反直觉点：**把 ROS2 放进计分路径是负优化；把 ROS2 的契约纪律放进工程流程才是正收益。**

严谨定义（本轮最小形式）：

- 外部契约 `C_ext = (metadata 字段集, obs 键集与栈偏移, action 键集与形状, T_a, token 语义, reset 语义)`，用 schema hash 固化。
- 内部契约 `C_int = (policy → guard → action adapter)` 的版本化接口；允许实验面依赖 ROS2，禁止计分面在运行时 import ROS2。
- 契约漂移 `D = 1[C_ext(t) ≠ C_ext(t−1)]`；每次提交前必须 `D=0`，且官方 `example_env.py` + `run_client.py` 全通过。
- 可重放性：给定四元组 `(obs 流, checkpoint hash, config hash, seed)`，重放动作序列与原始序列的逐维最大绝对误差 `≤ ε`（float32 取 `1e-4`），否则视为不可重放。

### 1.2 灵感 2（技术路线图）：路线图不是甘特图，是风险退休顺序

直觉：I1–I9 是一张投资组合，不是一份计划。真正稀缺的不是想法，而是**串行验证能力**：一块 24GB GPU、一条单任务真机通道、一个数据工程师。把所有创新点并排画成甘特图是自欺；路线图应该是一张 DAG，边是依赖，节点是「风险退休事件」，每个事件有量化闸门。排序目标不是「功能多」，而是**每 GPU-周退休多少失败概率**、**每真机 episode 买到多少信息**。再叠加 F25：官方基座还在更新，路线图必须把「基座重定基」当成一个显式节点，而不是默默跟着跑。

核心反直觉点：**路线图的最大敌人不是时间不够，而是不可复现的实验——每次换基座/换数据都重建基线，等于每周从零开始。**

严谨定义：

- 路线图 `R = (V, E, w, c, g, ρ, τ)`：`V` 为工作包；`E` 为先后依赖；`w` 为工期（人周/GPU 周）；`c` 为资源向量（GPU、真机小时、人）；`g` 为闸门谓词（可自动判定的退出条件）；`ρ` 为该节点退休的风险质量；`τ` 为 TRL（1–9）。
- 关键路径 `CP = E 上按 w 加权的最长路径`；任何 CP 节点的 slip 直接推迟提交。
- 风险调整价值 `V(v) = P(g(v)=1) · Δscore(v) / cost(v)`；每轮只允许一个「在飞」的高风险节点，避免并行失败。
- 重定基闸：仅当新基座在 G1 回放基准上 `≥5%` 相对提升且无家族 `>2%` 退步，或解锁阻塞性能力，且迁移成本 `≤1 周`时，才允许切换；否则钉住 `B0 = UnifoLM-WLA-1.0-Base (2026-09-28)`。

### 1.3 统一：可执行的路线图 = ROS2 的回放纪律 × 数据引擎的假设

直觉：第 2 轮说胜负手在数据引擎；本轮补上它的执行边界——数据引擎的每个假设（孪生正迁移、增广有效、检索有用、合成示教可用）都必须能被一个可重放实验证伪。ROS2 的 bag/replay 提供「同一观测流可重复喂给不同 checkpoint」的基座；路线图提供「先证伪哪个假设」的顺序。于是路线图不再是文档，而是**可执行 DAG**：每个节点是一个 `(bag, config, checkpoint)` 三元组 + 一个闸门，跑完自动写进 I8 的注册表。

核心反直觉点：**路线图应该像 CI 一样被执行——节点失败自动阻断下游，而不是靠人记得上周跑过什么。**

# UniBot-V1 参赛创新点清单（第 3 轮 v1.2）

> 检索日期：2026-11-26（第 1 轮）、2026-11-27（第 2/3 轮）；来源见 §6。承接 v1.1：I6/I8 深化，I10/I11 新增，I4 改写，I7 修剪，其余维持。清单只增改不重置。

## 0. 创新点清单（每点：动机 / 与现有方案差异 / 技术可行性 / 所需资源 / 落地步骤 / 风险）

### I10 双平面契约架构（新） ★★★★★ TRL5
- **动机**：F20/F23——评测器只认 websocket/msgpack PolicyService，ROS2 是实验室侧能力。多数队伍要么把 ROS2 塞进计分路径（负优化），要么没有可重放基座（无法归因）。
- **与现有方案差异**：不是「用 ROS2 重写一切」，而是显式分离两个平面，并用 schema hash + CI 把外部契约冻结。
- **技术可行性**：高。外部契约已由官方 README/example_env 定义；内部适配层是纯 Python。
- **所需资源**：1 人周；无 GPU。
- **落地步骤**：
  1. 从 README/example_env 抽取 `C_ext`，生成 JSON Schema 与 hash；
  2. 定义 `ObsAdapter / ActionAdapter / PolicyRuntime` 三个内部接口；
  3. CI：每次提交跑官方 `example_env.py` + `run_client.py`，schema hash 变化即失败；
  4. 实验面：rosbag2 录制 → 转成同一 obs schema 的 replay 文件；
  5. 契约漂移看板（字段级 diff）。
- **风险**：过度冻结阻碍必要变更 → 版本号 + 迁移脚本；开发机无 ROS2 → 实验面可选，不阻塞计分面。

### I11 可执行技术路线图（新） ★★★★★ TRL6
- **动机**：I1–I9 是组合，不是计划；串行验证能力稀缺；官方基座移动（F25）。
- **形式化**：`R = (V, E, w, c, g, ρ, τ)`；目标 `max Σρ` s.t. 资源与依赖；关键路径按 `w` 最长路。
- **与现有方案差异**：甘特图按功能排；本点按「风险退休/成本」排，并把每个节点变成可自动判定的闸门。
- **技术可行性**：高。先做表格 + 脚本，不引入项目管理软件。
- **所需资源**：0.5 人周建表；每周 30 分钟复盘。
- **落地步骤**：①节点表（见 §2）；②闸门谓词脚本；③每周跑一次 DAG，失败节点阻断下游；④注册表回填。
- **风险**：过度规划/指标可游戏化 → 闸门只认可重放指标；进度乐观 → 用历史 slip 乘 1.5 缓冲。

### I6 v2 N 端口可靠性内核 ★★★★★ TRL6
- **动机**：F20/F22——N 端口并发、每端口状态隔离、延迟方差是显式可信度指标；参考 PolicyService 的同步路由会阻塞事件循环。
- **与 v1 差异**：v1 讲「共享 backend + 队列」；v2 给出进程/线程模型、每端口 EpisodeContext、deadline-aware 调度、生命周期与压测判据。
- **架构**：
  - 1 个推理后端（GPU，可多 CUDA stream）；N 个 websocket 端点；
  - 每端口一个 `EpisodeContext`（obs 环形缓冲、reset 代际、prior、进度状态、RNG），绝不共享；
  - 每端口 FIFO + 全局 deadline 调度器；同模型请求可跨端口连续批处理，但保持每端口顺序；
  - 生命周期：`start → warmup → ready → per-episode reset → active → drain → cleanup`；
  - 健康：`/healthz` + 每端口 last-seen + 队列深度 + p99。
- **关键判据**：p99 < 40ms（15Hz 预算 66ms 留余量）；jitter（p99−p50）< 10ms；0 次跨 episode 状态串扰；0 次 reset 丢失。
- **风险**：Python GIL/CUDA stream 争用 → 推理放独立线程/进程，端点只做序列化；公平性 → 每端口配额。

### I8 v3 可重放 L0 实验台 + 注册表 ★★★★★ TRL5
- **动机**：P11；L0 消融必须跨周可比。
- **组成**：
  1. `replay bag`：obs 流 + metadata + 时间戳 + 环境指纹；
  2. `replay runner`：同一 obs 喂给任意 checkpoint，输出动作与延迟；
  3. `fidelity`：与原始动作逐维最大误差、动作分布 KL、延迟偏差；
  4. `registry`：experiment_id, git hash, ckpt hash, config hash, bag id, offline metrics, real metrics, gate result。
- **G0 闸**：3 个任务 × 每任务 5 eps，replay fidelity 达标，基线分数可复现。
- **风险**：回放-在线 gap → 用 shadow run 校准；存储 → 只存 obs 指针 + 压缩帧。

### I4 v2 固定 T_a 下的相位化 chunk ★★★ TRL4
- **动机**：F21 否定了运行时自适应 chunk。
- **改写**：
  - 握手时声明全局 `T_a`（建议 4–8，按延迟预算与任务精度定）；
  - chunk 长度固定，但**内容**随相位变：接近段填满轨迹；接触段填「短残差 + 保持」；检测到人手/低置信时填「平滑保持/回退」；
  - 不再声称「干预态短 chunk」，改为「干预态短运动 + 长保持」。
- **风险**：保持动作被记为动作异常 → 保持段用当前位姿的平滑插值，速度/加速度界内；T_a 太小导致调用频率过高 → 用 p99 预算反推。

### I7 修剪（世界模型测试时前瞻）
- **修剪理由**：F20 的 N 端口并发 + 延迟方差，使 O(1–2) 次世界模型 rollout 的延迟与方差不可接受；TRL2；与 I5 数据引擎共用资产。
- **保留条件**：W6 shadow 显示 p99 余量 >30% 且 N 端口稳定；否则正式裁撤，资产转 I5。

### I1/I2/I3/I5/I9 增量
- **I1**：增广器接受 `seed`，每次增广写 replay id；考纲卡仍按 wiki。
- **I2**：数据 provenance（repo/commit/采集配置）；孪生家族 kill 判据（>2% 退步两次即剪）；重定基闸。
- **I3**：条件项；单模型边界未书面确认前只做 I3'（辅助监督），不上计分通道。
- **I5**：合成段带 replay id 与得分点标签；里程碑检测器置信门控。
- **I9**：检索库版本化；reset 一次性；阈值门控。
