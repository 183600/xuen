# 第 13 轮（新循环第 1 轮）· RUBRIC-TURN：把 94 个评分点当符号世界模型，把评测变成多轮对话

> 检索/复核日期：**2026-10-31（UTC）**。赛事身份已再次确认：宇树 **UniBot 世界挑战赛**（unibot.unitree.com），G1 + Dex1，32 项桌面任务，通才单模型赛道，选手自部署 + 官方远程真机 API。本轮灵感词是「多轮对话」「决策规划」「竞赛策略」。本轮不推倒第 10 轮 FACT-VLA、第 11 轮 GEO-RESIDUAL、第 12 轮 CHUNK-SERVO，而是在它们之上加一层：**用官方公开的 94 个评分点做符号世界模型，用 turn-level 决策规划决定“做哪一步、做多久、何时重试/止损”，用已知的人为干扰脚本做多轮修复，用竞赛组合决定把 320 trials 投到哪里。** 轮次编号说明：状态文件上一轮标为第 12 轮，用户称本轮为新循环第 1 轮；为保留历史，本轮标为“第 13 轮（新循环第 1 轮）”。

## 0. 先给结论：榜首 29.7% 仍是预览数据，真正的缺口是“评分点级进度 + 人为撤销 + 期权决策”

截至 2026-10-31，`leaderboard_data.json` 仍是 8 个模型的预览数据：MolmoAct2 29.7%、WALL-OSS-0.5 28.5%、DreamZero 27.9%、Spirit-v1.5 25.9%、DM0 23.5%、π-0.5 22.8%、GigaBrain-0 22.6%、GR00T N1.5 20.5%。但这份 JSON 的 `generated_from` 是 `gen_leaderboard.py`；每个模型的 `step_score` 与 `success_rate` 几乎完美线性（R²≈0.9999996–0.9999999，最大残差<0.006）；256 个任务成功率里有 241 个唯一值，只有 1 个是 10 的倍数；跨模型的任务成功率平均相关只有约 0.098。**这不是 10 次真机试验能产生的数据，而是预览/合成占位。** 页面静态 HTML 同时保留“即将发布 Coming Soon”的 fallback，runs.html 为空，详情页视频是“加载中”占位。结论：**不要把 29.7% 当真实 SOTA，也不要把榜单的任务排名当真实难度表。**

本轮真正的新信号不在榜单，而在任务页的 `tasks_v2/<slug>/info.json`。32 个任务 JSON 公开了 **94 个评分步骤** 及权重，还公开了每个任务的泛化备注，尤其是 `human_1_note` / `human_4_note`。这些备注不是泛泛的“人为干扰”，而是具体的编辑脚本：杯子向后/向右、网线移开、插口移开、叠完的毛巾翻开、拉上拉链后拉开、盖子拧回去、锁拿走、胶带向后/向右……这是一份**公开的对手剧本**。

把 94 个评分点按权重算一遍，会得到一个改变策略的算术：

| 任务步数 | 任务数 | 第一步权重均值 | 前两步累计均值 | 除最后一步外的“底仓”均值 | 最后一步均值 |
|---|---:|---:|---:|---:|---:|
| 2 步 | 11 | 50 | 100* | 50 | 50 |
| 3 步 | 14 | 30 | 60 | 60 | 40 |
| 4 步 | 5 | 25 | 50 | 75 | 25 |
| 5 步 | 2 | 20 | 40 | 80 | 20 |
| 全部 | 32 | **35.47** | **70.94*** | **60.16** | **39.84** |

\* 2 步任务的“前两步”就是整任务，不是最后一步之前的底仓；真正可比的“除最后一步外底仓”是 60.16 分。25/32 个任务前两步≥60 分，30/32 个任务前两步≥50 分。也就是说，**只要政策能稳定完成前面的步骤，就已经有一份不小的步骤分底仓；最后一步是额外的期权，不是全部。**

我的判断是：当前所有模型共享的瓶颈，已经从“动作级如何闭环”上移到了“评分点级如何决策”：

1. **进度缺口**：VLA 不知道官方评分点走到第几步；它只知道当前图像和任务语言。成功信号稀疏，步骤分信号稠密，但没人把它显式建模。
2. **修复缺口**：人为干扰经常不是把任务变难，而是**把已经完成的步骤撤销**（拉链拉开、毛巾翻开、盖子拧回、锁拿走、插头拔起、叠好的碗拿下来）。通用恢复策略会从头重做；评分点级修复只需要重做被撤销的那一步。
3. **目标缺口**：排名是“成功率优先、步骤分次之”。动作级 chunk 规划优化的是动作不确定性/未来想象，不是“这一步值多少分、失败会不会把底仓弄没、剩余 180 秒该重试还是收手”。最后一步应当被当作**廉价期权**：成功收益巨大，失败通常不扣分，真正的敌人是撤销与超时。

所以本轮押注 **RUBRIC-TURN**：

> 把官方 94 个评分点解析成带权重的符号任务图；每次 `get_action` 是一轮“对话”，政策维护“哪些评分点已完成/被撤销”的信念，决定下一子目标、执行多久、是否重试/修复；用公开的人为干扰备注做“检测→定位被撤销的评分点→最小修复”；用竞赛组合把成功率优先、步骤分次之的 lexicographic 目标落到 320 trials 的分配上。底层执行仍然交给 CHUNK-SERVO 的 5 步伺服，相位/编辑特征交给 FACT-VLA / GEO-RESIDUAL。**不新增第二个学习模型。**

一句话：**把“预测 1 秒的动作”再往上提一层，变成“读懂 94 个评分点、保护底仓、把最后一步当期权、被人改了只重做那一步”。**

## 1. 本轮新核实的事实（只列改变方案的）

### 1.1 榜单：仍是预览，且 1–2pp 的差距在 320 trials 噪声内

- 官方排行榜 JSON（2026-10-31 经 `r.jina.ai` 复核）仍是 8 个模型、32 个任务；`generated_from: gen_leaderboard.py`。
- 每模型 `step_score ~ success_rate` 线性回归 R²≈0.9999996–0.9999999，最大残差<0.006；成功率不是 10 次试验的整数倍；跨模型任务成功率平均 off-diagonal Pearson/Spearman 约 0.0975。**合成预览证据充分。**
- 即使榜单是真的，32 任务×10 次=320 trials 的平均成功率标准误约 **2.2–2.3pp**（按 p≈0.2–0.3 估算）；榜首 29.7% 与第二 28.5% 只差 1.2pp，在噪声内。**不要用一个预览榜的 1–2pp 差距指导工程。**
- 页面静态 HTML 仍含“即将发布 Coming Soon” fallback；`runs.html` 为空；详情页视频仍是“测试视频详情 加载中...”。没有新的真实评测结果。

**对方案的约束**：本轮不再花时间猜“榜首用了什么”，而是用公开评分点 + 单任务通道做自己的信号；榜单只当“大家都在 20–30%”这个粗先验。

### 1.2 规则：32×10、5 类泛化各 2 次、180 秒、单模型、N 端口

官方参赛手册（飞书 docx，2026-10-31 经 `r.jina.ai` 复核）确认：

| 项 | 规则 |
|---|---|
| 模型 | 所有任务须基于**同一模型**完成，不得混合多个模型；模型类型不限（World Model、VLA 均可） |
| 任务 | 32 项桌面任务 |
| 次数 | 每任务 10 次独立运行 |
| 泛化 | 5 类各 2 次：位置、干扰物、桌面背景、未见物品、人为干扰 |
| 时限 | 单次真机执行上限 **180 s**；超时记为失败，仍按执行情况算步骤分 |
| 排名 | 先比 32 任务总平均成功率；相同看总平均步骤分；再相同看更早提交 |
| 部署 | 评测跨 **N 台机器人**；提交须从 **8765** 起暴露 N 个连续端口；每端口独立交互，`reset()` 状态必须隔离 |
| 测试通道 | 另有**不计分的单任务测试通道**，可测单任务成功率/步骤分 |

**关键**：排名是 lexicographic，不是加权和。成功率是主序，步骤分只是 tie-break。但这不意味着步骤分不重要：当很多任务都是 0/10 或 1/10 时，成功率会大量打平，步骤分就是实际区分度；而且步骤分是比成功率更稠密、更低噪声的训练/选择信号。

### 1.3 API：23 维 joint / 21 维 EE；chunk 内无反馈；没有 done 信号

提交模板 README（2026-10-31 复核）给出：

| 项 | 规格 |
|---|---|
| 观测图像 | `cam_left_high`、`cam_right_high`、`cam_left_wrist`、`cam_right_wrist` 四路 RGB **480×640** |
| 本体 | 双臂关节 `[7]`、EE 位姿 `[6]`（xyz+rpy，base 系）、夹爪 `[1]`、`lower_body[15]`、语言 `str` |
| 动作空间 | `control_space` 仅 `"joint"` 或 `"ee"`，二者互斥 |
| 共享动作 | `action.left_gripper [1]`、`action.right_gripper [1]`、`action.pivot [7]` |
| joint 动作 | `action.left_arm [7]`、`action.right_arm [7]`；合计 **23 维**（7+7+1+1+7） |
| EE 动作 | `action.left_ee_pose_gripper_base [6]`、`action.right_ee_pose_gripper_base [6]`（绝对目标位姿）；合计 **21 维**（6+6+1+1+7） |
| chunk | `action_chunk_size` ≥1，固定；index 0 先执行，其余顺序执行，直到 evaluator 再次调用 `get_action` |
| 反馈 | **chunk 内不重新看世界、不打断**；只有 chunk 边界才有新观测 |
| done | **没有 done/stop 字段**；episode 由 evaluator 按成功/失败/180s 超时结束 |
| token | `metadata.token` 握手校验一次；每次 `get_action` 的 `meta.token` 都要匹配 |
| 缺失 | **没有 depth、camera_info、force/torque、tactile** |
| 监控 | 评测端逐调用记录延迟、波动、动作统计规律 |

这一节有两个对方案影响极大的推论：

1. **`action_chunk_size` 是反馈周期，不是普通推理参数。** chunk 内没有新观测，所谓“30Hz 视觉伺服”不可能由政策在 chunk 内完成；政策只能在每个 chunk 边界用新观测修正下一段。CHUNK-SERVO 的“5 步伺服”必须实现为“每 5 步（即 chunk=5）在边界上重规划/修正”，而不是“chunk=30 内的 30Hz 内环”。如果 chunk=8，反馈就是 3.75Hz；如果 chunk=30，反馈就是 1Hz。先前把“30 步规划 + 5 步伺服”理解成 chunk 内 30Hz 闭环是过度承诺；本轮把它修正为**“VLA 30 步意图 + chunk 边界 5 步修正”**。
2. **没有 done 信号，不能“安全停手”。** 政策不能主动结束 episode；只能继续发动作或让 evaluator 超时。因此“保住底仓就停”不是可执行策略；正确策略是**保护底仓、避免撤销风险、把最后一步当期权去尝试**，而不是停下来等 180 秒。

## 2. 诊断：三个缺口，以及“多轮对话”的正确落地

### 2.1 进度缺口：成功是稀疏的，步骤分是稠密的

一个任务只有成功/失败两个终局标签，但官方给了 2–5 个评分点。一个 3 步任务，前两步 60 分，最后一步 40 分；一个 5 步任务，前四步 80 分，最后一步 20 分。**如果政策只优化成功，它会把所有 trial 当成 0/1，浪费掉 60–80 分的稠密信号。**

RUBRIC-WM 的作用是把成功信号分解成 94 个可验证的子信号：抓住杯把、挂到标记位、网线插入端口、毛巾对折、拉链拉上、盖子拧开、锁打开、碗叠上……这些子信号可以直接用于：

- 训练：按评分点切前缀，教模型“当前这一步”而不是整任务；
- 选择：在单任务通道上比较两个 checkpoint 的“步骤完成曲线”，而不是只看 0/1；
- 决策：知道当前在第几步、下一步值多少分、失败会不会撤销上一步。

### 2.2 修复缺口：人为干扰是“撤销已完成步骤”，不是“把任务变难”

60 条人为干扰备注里，至少 11–13 条是明确的撤销/移除/回退：

- 拉上拉链后拉开（T19）；
- 叠完毛巾翻开（T16，两条）；
- 拧开盖子后拧回去（T14）；
- 笔盒合上后手动打开（T17）；
- 叠了第二个碗后拿下第二个（T27）；
- 中途把锁拿走（T12）；
- 插头拔起（T10）；
- 外壳盖移开（T29）；
- 零食放回传送带起点（T24，两条）。

其余大多是移动目标/容器/底座：杯子向后/向右、水果向前/向右、相框向上、试管向左/右、盘子向前、架子向左、网线/插口移开、胶带向后/向右、球拍向前/向左、电池底座/绿盒移动、书/架子移动、瓶子向左、纸杯移动、字母移动、碗向下、钉子移动……这些编辑的共同点是：**它们改变的是“评分点谓词”的真值，而不是任务语言。** 通用 VLA 会把它们当成分布外的新场景，从头试；评分点级修复可以：

1. 检测哪个已完成评分点的谓词从 1 变 0；
2. 定位被移动的物体/容器；
3. 只重做被撤销的那一步（最小修复集）；
4. 保留之前完成的步骤分。

这就是“多轮对话”的真正含义：**不是和 evaluator 聊天，而是把人为干扰当成对手的一轮“消息”，更新评分点信念，回一轮“修复动作”。**

### 2.3 目标缺口：最后一步是期权，不是必须避开的风险

排名先比成功率，再比步骤分。设一个任务已经完成前 \(k-1\) 步，底仓为 \(S_C\)，最后一步权重为 \(w_f\)，成功概率 \(p\)，失败导致撤销底仓的概率 \(q\)，撤销损失 \(\ell\)，尝试成本 \(c\)。尝试的期望价值：

\[
V_{\text{try}} = p\,(M+100) + (1-p)\,(S_C - q\ell) - c,
\qquad V_{\text{stop}} = S_C
\]

其中 \(M\) 是成功率的 lexicographic 权重（可以取 1000 或更大）。只要

\[
p\,(M+100-S_C) > (1-p)\,q\ell + c,
\]

就应该尝试。由于 \(M\) 很大，**只要 \(p>0\) 且 \(q\ell\) 不灾难性，尝试几乎总是占优**。真正的敌人不是“失败”，而是“失败把底仓撤销”或“尝试把 180 秒耗尽”。这解释了两件事：

- 为什么“保住步骤分就停”不是好策略（而且 API 没有 done，停不下来）；
- 为什么**修复人为撤销**比“提高单步精度”更划算：它直接降低 \(q\ell\)，把最后一步从“可能亏掉底仓”的赌博变成“低风险期权”。

### 2.4 “多轮对话”的三个 turn

| turn | 谁发起 | 政策看到什么 | 政策做什么 |
|---|---|---|---|
| **评测 turn** | evaluator | 新观测 + 固定语言指令 | 更新评分点信念，选下一子目标/动作 chunk |
| **人为 turn** | 人类干扰 | 物体/容器被移动、已完成步骤被撤销 | 检测回归，定位最小修复集，回修复动作 |
| **内部 turn** | 政策自己 | 当前图像/本体/历史 | 向同一 checkpoint 的 VLM 问“第 k 步完成了吗？”或做确定性谓词检查，更新 ledger |

API 没有对外文本通道；`observation.language` 是固定任务指令，不能向 evaluator 提问。所谓“对话”完全是内部的 turn-level 状态更新与子目标选择。这一点必须在方案里写清楚，避免被误解为 chatbot。

## 3. 方法：RUBRIC-TURN

### 3.1 三层架构：任务层 / 相位编辑层 / 控制层

```text
┌─────────────────────────────────────────────────────────────┐
│ L1  RUBRIC-TURN（本轮新增）                                  │
│  官方 94 评分点 → 符号任务图 → turn-level 决策规划           │
│  progress ledger / option value / human-turn repair          │
│  竞赛组合：success-first, step-score-second                  │
└───────────────────────────┬─────────────────────────────────┘
                            │ 子目标、修复目标、重试/提交预算
┌───────────────────────────▼─────────────────────────────────┐
│ L2  FACT-VLA + GEO-RESIDUAL（第 10/11 轮，保留）             │
│  相位特征 / 能力片段 / 编辑与回归检测 / 关键帧                │
└───────────────────────────┬─────────────────────────────────┘
                            │ 目标位姿、接触阶段、编辑分数
┌───────────────────────────▼─────────────────────────────────┐
│ L3  CHUNK-SERVO + DG-KEYFRAME（第 12 轮，保留）              │
│  5 步边界修正 / 相对目标检索 / 夹爪伺服 / 动作适配            │
└─────────────────────────────────────────────────────────────┘
```

- **L1 决定“做什么、做到哪一步、何时重试/修复”**；
- **L2 提供“现在是什么相位、场景有没有被编辑”的特征**；
- **L3 负责“最后几厘米怎么动”**。

三层都围绕同一个 VLA checkpoint；L1 的评分点状态机、谓词检查、修复宏都是确定性的；L2 若使用学习特征，仍在同一模型/LoRA 内；L3 的伺服无学习权重。**不新增第二个学习模型。**

### 3.2 RUBRIC-WM：把评分点解析成带权重的符号任务图

对任务 \(j\)，从 `info.json` 解析：

- 评分点 \(g_{j,1},...,g_{j,K_j}\)，权重 \(w_{j,i}\)，\(\sum_i w_{j,i}=100\)；
- 中文/英文描述；
- 完成谓词 \(c_{j,i}(s_t)\in\{0,1\}\)（确定性检查 + 可选 VLM 复核）；
- 前置关系 \(g_{j,i}\prec g_{j,i+1}\)（大多数任务是顺序的，但 4/5 步任务可能允许并行/重排；先用顺序图，单任务通道验证后放开）；
- 人为撤销边：若备注说“拉上后拉开”“叠完翻开”“盖上后打开”“拿走”，则 \(g_{j,i}\) 有一条“可被撤销”边，撤销后需要重做；
- 失败/不可达条件：目标物体被移出工作空间、目标容器被移走、关键物体缺失等。

**完成谓词的三层实现**：

1. **确定性几何/本体谓词**（首选，零学习、零延迟）：
   - `grasp`：夹爪开度 < 物体宽度 + margin，物体相对夹爪位移 > 阈值，腕部图像接触；
   - `lift`：物体 z 位移 > 阈值；
   - `hang/place/insert`：物体/夹爪相对目标区域的位置/姿态误差 < 阈值；插头尖端进入端口 ROI；
   - `open/close`：盖子角度、拉链头位置、锁角度；
   - `fold`：毛巾角点/边缘位置（变形物体用 VLM 兜底）；
   - `stack`：物体底部与下方物体顶部接触，高度差 < 阈值；
   - `sort`：物体进入正确区域/容器；
   - `push/pull`：物体沿轴位移 > 阈值。
2. **同 checkpoint VLM 复核**（歧义步骤）：给同一 WLA 的 VLM 输入当前图像 + “Has the robot completed the step: <step>? Answer yes/no.”，取 yes/no logit 或 3 次自一致性。只在评分点边界/每 2–3 个 chunk 调用，避免延迟。
3. **时序滤波**：每个评分点维护 \(b_i(t)=P(c_i=1)\)；完成是单调的（除非检测到撤销）；用滞回（连续 2 次通过才置 1，连续 2 次失败才置 0）抑制抖动。撤销检测触发“人为 turn”。

**离线标定**：用成功演示的最后帧作为正样本，评分点边界前的帧作为负样本，标定阈值；用任务 JSON 的步骤文本选择关键帧。离线可以用任意工具（包括另一个 VLM）做标注，但在线只用同一 checkpoint + 确定性谓词，避免单模型合规问题。

### 3.3 TURN-PLAN：每个 chunk 边界做一次小规模决策规划

在每个 chunk 边界 \(t\)，政策有：

- 评分点信念 \(b_t\)；
- 当前观测 \(o_t\)（四路图 + 本体 + 语言）；
- 剩余时间 \(T_{\text{rem}}\)；
- 当前子目标 \(g^\*\)（下一个未完成评分点，或修复目标）。

候选动作集：

- **VLA 候选**：用同一 WLA 生成 3–5 个 chunk，prompt 变体：
  - “Task: ... Current step: ... Completed: ... Execute the current step.”
  - “Recover step ... after the object moved.”
  - “Retry slowly / use the other arm.”
  - 不同噪声种子/温度（若模型支持）。
- **确定性宏候选**（CHUNK-SERVO / DG-KEYFRAME）：
  - `servo_to_grasp(object_pose)`、`lift`、`servo_to_target(target_pose)`、`insert`、`close_gripper`、`open_gripper`、`zip_pull`、`unfold`、`press`、`push`；
  - `hold`（短时安全保持，不是 180 秒停手）。
- **修复候选**：针对被撤销的评分点，调用对应的最小修复宏 + VLA “redo” prompt。

打分函数：

\[
U(a,h) = M\,\hat P(Y=1\mid b_t,a,h) + \sum_i w_i\,\hat P(c_i=1\mid b_t,a,h) - \lambda\,\hat P(\text{undo}\mid a,h) - \mu\,\text{cost}(h)
\]

- \(M\gg 100\)，近似 lexicographic；
- \(\hat P(Y)\) 用“剩余评分点完成概率的乘积”或 VLM 自一致性代理；
- \(\hat P(c_i)\) 来自谓词检查 + 时序滤波；
- \(\hat P(\text{undo})\) 来自接触风险、物体易碎/易倒、人为 turn 概率、动作幅度；
- \(\text{cost}(h)\) 是延迟/时间预算；\(h\le T_a\) 是本次提交的 chunk 长度（通常执行满 chunk，除非检测到状态变化需要截断）。

**决策规则**：

- 若检测到评分点回归 → 进入 `repair` 模式，选最小修复集，不重做整任务；
- 若当前评分点未完成且候选的 \(U\) 高于 `hold` → 执行最佳候选；
- 若所有候选的 \(U\) 都低于 `hold` 且时间充足 → 选一个低风险探索动作（换臂/换抓取点/换角度），不要空等；
- 若剩余时间不足以完成当前评分点 → 切到“保底仓”策略：只做低风险动作，避免撤销；但 API 没有 done，所以仍需继续发动作直到 evaluator 结束；
- 最后一步：按 §2.3 的期权公式，默认尝试；只有在 \(q\ell\) 很高（例如 FoldTowel 翻开、ZipUp 拉开）且修复宏不可用时才保守。

**为什么不是“又一个 adaptive chunking”**：候选生成可以复用 VLA，但决策变量是**评分点子目标**和**最小修复集**，不是 chunk 长度；优化目标是**官方步骤分 + 成功率的 lexicographic 期权**，不是动作不确定性/未来帧误差。chunk 长度只是执行参数，由延迟和反馈周期决定。

### 3.4 HUMAN-TURN：把 60 条公开备注变成有限的修复脚本

**离线**：

1. 解析 30 个任务的 60 条 human notes，归类为：
   - `move_target`：目标物体移动（杯子/水果/娃娃/试管/相框/球拍/电池/书/瓶子/纸杯/字母/碗/钉子/胶带/网线/插头/手机/耳机盒…）；
   - `move_receptacle`：目标容器/架子/底座/插口/盒子移动；
   - `undo_step`：撤销已完成步骤（拉链拉开、毛巾翻开、盖子拧回、笔盒打开、碗拿下来、锁拿走、插头拔起、外壳盖移开、零食放回起点）；
   - `remove_object`：关键物体被拿走（锁、外壳盖、第二个碗…）；
   - `extra_insert`：把另一头网线也插上（T05）；
   - `reset_object`：物体被放回起点（T24）。
2. 为每类写一个确定性修复宏：
   - `move_target` → 重新定位物体（头双目 + 腕部），更新 `object_pose`，重做抓取/放置；
   - `move_receptacle` → 重新定位容器/端口，更新 `target_pose`，重做对准/插入；
   - `undo_step` → 评分点回归 → 重做该评分点（拉链/折叠/拧盖/开盒/叠碗/开锁/插回/盖回）；
   - `remove_object` → 在工作空间搜索；找不到则失败；若是干扰物则忽略；
   - `extra_insert` → 定位第二个端口/网线端并插入；若不可达则当干扰物忽略；
   - `reset_object` → 重新抓取并放回目标。
3. **rollback 数据增强**：在成功演示的评分点边界，人工/仿真地施加逆向编辑（拉开、翻开、拧回、拿走、移动），生成“被撤销→修复”的片段；用这些片段微调同一 WLA 的 action expert，或在 CHUNK-SERVO 中用宏直接修复。注意：增强数据只用于训练/离线验证，不接触测试通道。

**在线**：

- 每个 chunk 边界做一次轻量检查：评分点谓词 + 物体/容器位姿 + 腕部图像变化；
- 若已完成评分点连续 2 次回归 → 判定人为 turn；
- 用最小修复集：只重做回归的评分点，不重做整任务；
- 若同一干扰重复出现（例如人反复拉开），修复宏提速/换手/换策略；若仍失败，回退 VLA 重规划；
- 记录每次修复的耗时/成功率，作为单任务通道的指标。

**为什么可行**：60 条备注是有限的、任务级的、公开的；大多数是刚体移动/撤销，确定性宏可以覆盖；变形物体（毛巾、拉链、笔盒）用 VLM/视觉兜底。**不需要第二个学习模型。**

### 3.5 ADAPTER-23D：WLA 54 维 → 挑战赛 23/21 维

挑战赛动作是 23 维 joint 或 21 维 EE；WLA 是 54 维相对 EE + 夹爪 + 手 + 腰/躯干/base/腿。适配方案：

| WLA action | 挑战赛映射 |
|---|---|
| 左 EE 相对位姿 `[0:6]` | 与当前左 EE 绝对位姿做 SE(3) 复合 → `action.left_ee_pose_gripper_base [6]` |
| 左夹爪 `[6:7]` | `action.left_gripper [1]` |
| 右手 `[7:13]` | 不用（Dex1 用 1 维夹爪） |
| 右 EE 相对位姿 `[13:19]` | 与当前右 EE 绝对位姿复合 → `action.right_ee_pose_gripper_base [6]` |
| 右夹爪 `[19:20]` | `action.right_gripper [1]` |
| 右手 `[20:26]` | 不用 |
| 腰 `[26:29]` | 可选映射到 `action.pivot[3:6]`；未标定则保持常量 |
| 躯干 `[29:32]` | 不用/常量 |
| base 平移/旋转 `[32:35]` | `action.pivot[0:3]`（vx, vy, angle_z） |
| base 位姿 `[35:41]` | 不用/常量 |
| height `[41:42]` | `action.pivot[6]`（height） |
| 腿 `[42:54]` | 不用/常量 |

- **EE 模式优先**：WLA 输出相对 EE，挑战赛要绝对 EE；复合是确定性的，且对 base 漂移更鲁棒。
- **pivot 语义未文档化**：先用数据集统计的常量（HangCup 的 `pivot_4≈0.15`、`height≈0.738`）或全零回退；在单任务通道上验证；tabletop 任务不需要走动，pivot 可以保持恒定，只用双臂。
- **状态适配**：挑战赛 `lower_body[15]` = 腿 12 + 腰 3，正好填 WLA state 的 `[32:35]` 腰 + `[48:54]/[54:60]` 腿；torso/d435/base 惯性/height 等缺失槽位填 0 并把 validity mask 置 0；EE 位姿用 xyz+rpy 转 rotation-6D；夹爪直接填。WLA 的 robot-state projector 支持 mask，缺失槽位不会污染。
- **观测选择**：WLA 需要 `cam_left_high` + 两个腕部；`cam_right_high` 可用于评分点谓词/头双目深度，不必全部喂给 WLA；用 `obs_delta_indices` 只发需要的键，降低带宽。
- **chunk/延迟**：`T_a` 是反馈周期。若 WLA 推理 ~200–400ms，`T_a=8–12`（267–400ms）是合理区间；`T_a=30` 是 1s 开环，接触任务风险大；`T_a=5` 反馈快但推理压力大。建议在单任务通道扫 5/8/12/30，选 p99 延迟不超时且成功率最高的点。**不要假设 30 步一定好，也不要假设 5 步一定可行。**

### 3.6 数据/训练：评分点前缀 + rollback 增强

1. **评分点切分**：成功演示 + `score_steps` → 每个评分点的起止帧。刚体任务用物体/夹爪轨迹 + 规则；变形/透明任务用离线 VLM 标注 + 人工抽检。产出 `(frame, step_id, completed_steps)`。
2. **前缀训练**：对每个演示，在每个评分点边界截断，训练模型从当前状态执行“下一步”；prompt 加 `[task instruction] [current step] [completed steps]`。这让模型见过部分完成状态、学会在评分点边界停/切换，而不是只模仿整条轨迹。
3. **rollback 增强**：在评分点边界施加逆向编辑（拉开、翻开、拧回、拿走、移动），训练“检测→修复”；可用仿真或人工回放。数据量不需要很大（每个任务几十到几百条），重点是覆盖 60 条备注的类型。
4. **负样本/失败数据**：公开数据全是成功；失败样本只能来自仿真或单任务通道的诊断日志。**不要用测试通道数据训练**（规则/诚信风险）；只用它做校准和选择。
5. **算力**：1×24GB GPU 做 LoRA/action-head 微调；WLA 冻结 VLM，只训 DiT action head + projector，成本可控；数据 33k episodes，预处理/切分是主要工作量。

## 4. 竞赛策略：成功优先、步骤分次之，最后一步是期权

### 4.1 排序目标的正确写法

官方排名是：

\[
\text{rank} = \text{sort}\big(\text{avg success rate},\ \text{avg step score},\ \text{earlier submission}\big)_{\text{lexicographic}}
\]

不是 \(0.7\times\text{success}+0.3\times\text{step}\)。因此政策的目标应是：

\[
\max\ \mathbb{E}[Y]\quad \text{subject to}\quad \max\ \mathbb{E}[S]\ \text{as tie-break}.
\]

在单任务层面，可以用 \(M=1000\) 的加权和近似：

\[
\max\ M\,P(Y=1)+S.
\]

这解释了为什么“只刷步骤分、不追成功”不是最优：成功率是主序。但也解释了为什么“最后一步的期权”很重要：它同时提高 \(P(Y)\) 和 \(S\)，而失败通常只损失时间，不损失底仓（除非撤销）。

### 4.2 320 trials 的噪声：1–2pp 的榜单差距不可信

每任务 10 次，真实成功率 \(p_t\)；观测 \(X_t\sim\text{Binomial}(10,p_t)\)。32 任务平均成功率：

\[
\bar X=\frac{1}{32}\sum_t \frac{X_t}{10},\qquad
\mathrm{Var}(\bar X)=\frac{1}{32^2}\sum_t \frac{p_t(1-p_t)}{10}.
\]

若 \(p_t\approx0.2\)，\(\mathrm{SE}(\bar X)\approx0.022\)，即 **2.2pp**；若 \(p_t\approx0.3\)，约 **2.3pp**。榜首 29.7% vs 第二 28.5% 的 1.2pp 差距在 1 个标准误内。**不要用预览榜的 1–2pp 差距做任务排序/架构选择。** 用单任务通道的配对 A/B、重复测量、bootstrap；步骤分通常比成功率更稠密，可作为更稳的选择信号。

### 4.3 任务组合：把工程投到“期权价值/成本”最高的任务

对每个任务估计：

- \(p_t\)：成功概率（Beta 后验，单任务通道 5–10 次给先验/更新）；
- \(s_t\)：期望步骤分；
- \(u_t\)：人为 turn 的可修复增益（有备注、易检测、宏可覆盖 → 高）；
- \(c_t\)：工程/算力/调试成本；
- \(r_t\)：风险（变形/透明/遮挡/长时序 → 高）。

优先级：

\[
\text{priority}_t \approx \frac{\partial\,\mathbb{E}[\text{rank}]}{\partial p_t}\,\Delta p_t + \frac{\partial\,\mathbb{E}[\text{rank}]}{\partial s_t}\,\Delta s_t \over c_t
\]

没有真实榜单时，用代理：\(\Delta p_t\) 来自单任务通道；\(\Delta s_t\) 来自评分点底仓（前两步≥60 的任务优先）；\(u_t\) 来自 60 条 human notes；\(c_t\) 来自任务步数/物体类型。

**具体建议**：

- **优先**：2–3 步任务（25 个），前两步权重高、最后一步是 40–50 分期权；有人为撤销备注的任务（T16、T19、T14、T12、T27、T10、T29、T24）；刚体、易检测、易修复。
- **次优先**：4–5 步任务中前几步刚体、最后一步易撤销的任务（T09、T15、T17、T18、T22、T28）；底仓 50–80 分。
- **谨慎**：变形/透明/遮挡任务（FoldTowel 的毛巾、ZipUp 的拉链、SyringWater 的注射器、PackiPhone 的透明壳）；评分点谓词和修复宏更难，先做离线/单任务验证。
- **不要**：按预览榜的任务排名分配工程；不要为每个任务训策略；不要碰测试通道训练。

### 4.4 人为轴：20% 的 trials，修复 ROI 最高

5 类泛化各 2 次，人为干扰占 2/10=20%。60 条备注中约 11–13 条明确撤销、40–45 条涉及移动（部分重叠）；如果能修复一半，理论上人为轴 +10–20pp，全局 +2–4pp——这比把基础策略从 29% 提到 31% 更确定，也更容易在单任务通道验证。**优先做“撤销类”修复**（T16、T19、T14、T17、T27、T12、T10、T29、T24），因为它们的评分点回归最明确；再做“移动类”重定位/重抓。

### 4.5 提交策略：先保底，再迭代；不要等完美

排名第三关键字是“更早提交”。若允许多次提交：先交一个 CHUNK-SERVO/基线安全版占位，再用单任务通道验证 RUBRIC-TURN 增量，过门后替换。若只允许一次：把 80% 工程放在“不会比基线差”的修复/评分点层，20% 放在激进期权；先在单任务通道做 5 任务×5 次的配对 A/B，过 G3 再提交。**不要用正式提交做探索。**

| 端口/并发 | N 端口状态串扰 | 每端口独立 ledger/server；reset 隔离；并发压测 |

| 任务 | 32 项桌面任务 |
| 次数 | 每任务 10 次独立运行 |
| 泛化 | 5 类各 2 次：位置、干扰物、桌面背景、未见物品、人为干扰 |
| 时限 | 单次真机执行上限 **180 s**；超时记为失败，仍按执行情况算步骤分 |
| 排名 | 先比 32 任务总平均成功率；相同看总平均步骤分；再相同看更早提交 |
| 部署 | 评测跨 **N 台机器人**；提交须从 **8765** 起暴露 N 个连续端口；每端口独立交互，`reset()` 状态必须隔离 |
| 测试通道 | 另有**不计分的单任务测试通道**，可测单任务成功率/步骤分 |

**对方案的硬约束**：

- 不能为每个任务加载不同的学习模型；评分点状态机/谓词/宏必须是确定性的，或使用同一 checkpoint 的特征/头。
- N 端口必须独立：每个端口一个 ledger、一个 history、一个模型会话；共享后端时要做请求隔离和并发控制。
- 单任务通道不计分，可用于 A/B 和门槛验证；不能用它训练（诚信风险）。

### 1.3 API 与 timing model（A）

提交模板 README（2026-10-31 复核）：

| 项 | 规格 |
|---|---|
| 观测图像 | `cam_left_high`、`cam_right_high`、`cam_left_wrist`、`cam_right_wrist` 四路 RGB **480×640** |
| 本体 | 双臂关节 `[7]`、EE 位姿 `[6]`（xyz+rpy，base 系）、夹爪 `[1]`、`lower_body[15]`、语言 `str` |
| 动作空间 | `control_space` 仅 `"joint"` 或 `"ee"`，二者互斥 |
| 共享动作 | `action.left_gripper [1]`、`action.right_gripper [1]`、`action.pivot [7]` |
| joint 动作 | `action.left_arm [7]`、`action.right_arm [7]`；合计 **23 维** |
| EE 动作 | `action.left_ee_pose_gripper_base [6]`、`action.right_ee_pose_gripper_base [6]`；合计 **21 维** |
| chunk | `action_chunk_size` ≥1，固定；index 0 先执行，其余顺序执行，直到 evaluator 再次调用 `get_action` |
| 反馈 | **chunk 内不重新看世界、不打断**；只有 chunk 边界有新观测 |
| done | **没有 done/stop 字段**；episode 由 evaluator 按成功/失败/180s 超时结束 |
| token | `metadata.token` 握手校验一次；每次 `get_action` 的 `meta.token` 都要匹配 |
| 缺失 | **没有 depth、camera_info、force/torque、tactile** |
| 监控 | 评测端逐调用记录延迟、波动、动作统计规律 |

**Timing model**：

- 控制频率 30Hz；一个 chunk 的物理时长 \(T_a/30\) 秒。
- 政策在 chunk 边界被调用一次；若 VLA 推理 \(L_{\text{vla}}\)、网络 \(L_{\text{net}}\)、规划 \(L_{\text{plan}}\) 的总和超过 \(T_a/30\)，机器人会在 chunk 之间停顿（evaluator 记录延迟）。
- 连续执行条件：

\[
\frac{T_a}{30} \ge L_{\text{vla}} + L_{\text{net}} + L_{\text{plan}}.
\]

- 例：\(T_a=8\) → 267ms；若 \(L_{\text{vla}}=250\)ms、\(L_{\text{net}}=50\)ms、\(L_{\text{plan}}=20\)ms，总 320ms > 267ms → 会停顿；\(T_a=12\) → 400ms，可连续；\(T_a=30\) → 1s，安全但开环。
- **chunk 大小是反馈周期，不是普通推理参数。** chunk 内无新观测，所以“30Hz 视觉伺服”只能在 chunk 边界以 30/\(T_a\) Hz 发生；\(T_a=5\) 是 6Hz 修正，\(T_a=8\) 是 3.75Hz，\(T_a=30\) 是 1Hz。
- 180s 的预算：\(T_a=8\) 时约 675 个 chunk；物理任务时间和推理延迟是约束，chunk 数量不是。政策有足够的重试机会，但要避免长时间 hold。

**RUBRIC-TURN 的不同点**：

## 2. 问题形式化

### 2.1 评分点图与打分

对任务 \(j\)：

- 评分点 \(g_{j,1},...,g_{j,K_j}\)，权重 \(w_{j,i}\)，\(\sum_i w_{j,i}=100\)；
- 完成谓词 \(c_{j,i}(s_t)\in\{0,1\}\)；
- 前置关系 \(g_{j,i}\prec g_{j,i+1}\)（默认顺序；4/5 步任务可能有并行/重排，先用顺序图，单任务通道验证后放开）；
- 撤销边 \(g_{j,i}\dashrightarrow g_{j,i}'\)：人为干扰可把已完成步骤置回未完成；
- 任务成功 \(Y_j=\prod_i c_{j,i}(s_T)\)（或官方成功谓词；本报告按“全部步骤完成=成功”理解，需单任务通道校验）；
- 任务步骤分 \(S_j=\sum_i w_{j,i} c_{j,i}(s_T)\)（按公开 `score_steps` 的加权和理解；若有前置依赖/不可累加，需按官方 evaluator 修正）。

**假设**：官方步骤分是评分点权重的加和。证据是任务 JSON 明确列出 `score_steps` 分数且合计 100，排行榜也有 `avg_step_score`。这是 B 级假设，必须用单任务通道验证：如果某个任务只能拿到“最后一步=100、前面=0”，说明不是简单加和，需改状态机。

### 2.2 Turn-level POMDP

- 状态 \(s_t\)：物体/容器位姿、夹爪、关节、评分点真值、人为编辑；
- 观测 \(o_t\)：四路 RGB + 本体 + 语言（只有 chunk 边界）；
- 动作 \(a_t\)：一个 chunk 的动作序列 + 选择的子目标/修复目标；
- 信念 \(b_t(i)=P(c_{j,i}=1)\)；
- turn 类型：
  - **评测 turn**：evaluator 返回新观测；
  - **人为 turn**：物体/容器被移动或已完成步骤被撤销；
  - **内部 turn**：政策用同一 checkpoint 的 VLM/确定性谓词复核进度。

政策的目标：

\[
\pi^\*=\arg\max_\pi\ \mathbb{E}\Big[\mathbf{1}[Y=1]\Big]\ \text{lexicographically before}\ \mathbb{E}\Big[\sum_i w_i c_i\Big].
\]

实现时用大常数 \(M\) 近似：

\[
\max\ M\,\mathbb{E}[Y]+ \mathbb{E}[S],\qquad M\gg 100.
\]

### 2.3 期权价值：最后一步该不该尝试

设已完成集合 \(C\)，底仓 \(S_C=\sum_{i\in C}w_i\)，最后一步权重 \(w_f\)，成功概率 \(p\)，失败导致底仓被撤销的概率 \(q\)，撤销损失 \(\ell\)，尝试成本 \(c\)。尝试与不尝试：

\[
V_{\text{try}}=p(M+100)+(1-p)(S_C-q\ell)-c,
\qquad V_{\text{stop}}=S_C.
\]

尝试条件：

\[
p(M+100-S_C)>(1-p)q\ell+c.
\]

由于 \(M\) 很大，**只要 \(p>0\) 且 \(q\ell\) 不灾难性，尝试几乎总是占优**。这意味着：

- 不要“保住底仓就停”；而且 API 没有 done，停不下来；
- 真正要优化的是 \(q\ell\)：减少“尝试失败导致撤销”的概率；
- 人为干扰是 \(q\) 的主要来源；HUMAN-TURN 修复直接降低 \(q\)，把最后一步从赌博变成期权；
- 若剩余时间不足（\(c\) 很大）或 \(q\ell\) 很高（例如 FoldTowel 被翻开、ZipUp 被拉开且修复宏不可用），才保守。

**数值例子**：3 步任务，底仓 60，最后一步 40，\(p=0.1\)，\(q=0.2\)，\(\ell=60\)，\(c=0\)，\(M=1000\)：

\[
V_{\text{try}}=0.1\times1100+0.9\times(60-12)=110+43.2=153.2,\quad V_{\text{stop}}=60.
\]

尝试明显占优。即使 \(p=0.02\)，\(V_{\text{try}}=22+0.98\times48=69.0>60\)。**低成功率也值得尝试，只要失败不把底仓弄没。**

### 2.4 Trial 噪声与组合

每任务 10 次，\(X_t\sim\text{Binomial}(10,p_t)\)。32 任务平均成功率：

\[
\bar X=\frac{1}{32}\sum_t\frac{X_t}{10},\qquad
\mathrm{Var}(\bar X)=\frac{1}{32^2}\sum_t\frac{p_t(1-p_t)}{10}.
\]

若 \(p_t\approx0.2\)，\(\mathrm{SE}(\bar X)\approx0.022\)；若 \(p_t\approx0.3\)，约 0.023。**2.2–2.3pp**。

单任务观测噪声更大：

| 真实 \(p\) | P(0/10) | P(≥1/10) | 若出现 1 次，观测成功率 |
|---:|---:|---:|---:|
| 0.02 | 0.817 | 0.183 | 10% |
| 0.05 | 0.599 | 0.401 | 10% |
| 0.10 | 0.349 | 0.651 | 10% |
| 0.20 | 0.107 | 0.893 | 10% |
| 0.30 | 0.028 | 0.972 | 10% |
| 0.40 | 0.006 | 0.994 | 10% |

**解读**：真实 \(p=0.05\) 也有 40% 概率出现 1/10（观测 10%），真实 \(p=0.10\) 有 65% 概率出现≥1/10。小改进可能让一个任务从 0/10 翻到 1/10；但单个任务的观测成功率非常粗。要用 32 任务平均 + 单任务配对 A/B + 步骤分（更稠密）来降噪。

### 3.1 三层架构


### 3.3 ProgressLedger：进度信念与回归检测

每个评分点维护：

```python
Belief = {
    "b": float,             # P(completed)
    "last_positive": int,   # chunk index
    "last_negative": int,
    "regressed": bool,
    "source": str,          # "geometry" | "vlm" | "prior"
}
```

更新规则：

1. **确定性谓词**：若通过，`logit += alpha`；若失败，`logit -= beta`；`b=sigmoid(logit)`。
2. **VLM 复核**：每 \(N_v\) 个 chunk 或评分点边界调用一次；yes/no logit 转成 likelihood，更新 `logit`。
3. **完成判定**：`b>0.8` 连续 2 次 → completed；`b<0.2` 连续 2 次 → not completed。
4. **回归检测**：已完成步骤连续 2 次 `b<0.5` → `regressed=True`，触发 HUMAN-TURN；记录回归的 step_id 和可能原因（物体/容器位姿变化、腕部图像变化）。
5. **人为 turn 确认**：若至少一个已完成步骤回归，且物体/容器位姿变化超过阈值，或 GEO-RESIDUAL 编辑分数超过阈值 → 确认人为 turn；否则可能是谓词抖动，继续观察。

**为什么用信念而不是硬状态**：视觉谓词会抖；VLM 会 hallucinate；人为干扰会让状态回退。信念 + 滞回 + 回归检测比硬编码状态稳。

### 3.4 TurnPlanner：候选生成与效用打分

```python
def plan_turn(obs, ledger, rubric, time_left):
    # 1. 更新进度
    ledger.update(obs, rubric)
    # 2. 检测人为 turn
    repair_targets = ledger.regressed_steps()
    if repair_targets:
        candidates = generate_repair_candidates(repair_targets, obs, rubric)
    else:
        step = ledger.next_uncompleted()
        candidates = generate_progress_candidates(step, obs, rubric)
    # 3. 加安全/保持候选
    candidates += [hold_candidate(obs, ledger)]
    # 4. 打分
    scored = [(c, utility(c, obs, ledger, rubric, time_left)) for c in candidates]
    # 5. 选择
    best = max(scored, key=lambda x: x[1])
    # 6. 若最佳低于 hold 且时间充足，选低风险探索
    if best[1] < utility(hold_candidate(obs, ledger), ...) and time_left > reserve:
        best = max(scored, key=lambda x: explore_value(x))
    return best[0]
```

**候选生成**：

- `generate_progress_candidates(step)`：
  - VLA prompt A：“Task: <instruction>. Current step: <step>. Completed: <list>. Execute the current step.”
  - VLA prompt B：“Retry the current step slowly; keep the gripper closed.”
  - VLA prompt C：“Use the other arm if the current arm is blocked.”
  - 3–5 个噪声种子/温度（若模型支持）。
  - 确定性宏：`servo_to_grasp`、`lift`、`servo_to_target`、`insert`、`close`、`open`、`zip`、`unfold`、`press`、`push`。
- `generate_repair_candidates(repair_targets)`：
  - 对每个回归步骤选对应修复宏；
  - VLA prompt D：“Recover step <k> after the object moved; re-localize and redo only this step.”
  - 若目标物体/容器移动：先 `re_localize`，再 `servo_to_grasp`/`servo_to_target`。
  - 若目标被拿走：`search_workspace`；找不到则返回 `fail_safe`（继续低风险动作，不强行抓空）。
- `hold_candidate`：短时保持（例如 3–5 步），不是 180 秒停手；用于避免在状态不确定时执行高风险动作。由于 API 没有 done，长时间 hold 只会浪费时间，不推荐。

**效用代理**：

```python
def utility(candidate, obs, ledger, rubric, time_left):
    p_success = estimate_success(candidate, ledger, rubric)       # 0..1
    p_complete = estimate_completion(candidate, ledger, rubric)   # sum w_i * b_i
    p_undo = estimate_undo(candidate, obs, ledger, rubric)        # 0..1
    cost = estimate_cost(candidate, time_left)                    # 0..1
    return 1000.0 * p_success + p_complete - 200.0 * p_undo - 50.0 * cost
```

- `estimate_success`：剩余步骤完成概率的乘积；若候选直接完成最后一步，乘上 VLM/谓词置信度；没有校准数据时用启发式。
- `estimate_completion`：当前 `b_i` + 候选对这些步骤的影响。
- `estimate_undo`：接触风险（物体易倒/易碎/变形）、动作幅度、是否靠近已完成区域、人为 turn 历史。
- `estimate_cost`：chunk 时长/剩余时间/VLM 调用。
- 权重 `1000/200/50` 是初始值，用单任务通道校准；`M=1000` 确保成功优先。

**chunk 截断**：如果在一个 chunk 执行前检测到评分点状态变化（例如上一次 chunk 后回归），不要执行旧计划的长尾；返回新计划的 chunk，或在旧 chunk 中把后半段替换为安全 hold。由于 evaluator 一次执行整个 chunk，政策只能在返回前决定；不能中途改。**所以“检测到变化”只能在 chunk 边界发生；chunk 内的变化要等下一个边界。**

**在线流程**：

1. 每个 chunk 边界更新 ledger；
2. 若 `regressed_steps` 非空 → 确认人为 turn；
3. 选最小修复集：只修复回归的步骤；如果回归步骤有前置依赖，修复最后一个回归步骤即可（前面的可能仍成立）；如果多个步骤回归，按拓扑顺序修复；
4. 执行修复宏；每个修复宏有超时（例如 15–25s）；
5. 修复后复核谓词；成功则回到 progress 模式；失败则回退 VLA re-plan 或 `fail_safe`；
6. 记录修复耗时/成功率，用于单任务通道和竞赛组合。

**rollback 增强**：

- 在成功演示的评分点边界，对物体/容器施加逆向编辑（拉开、翻开、拧回、拿走、移动），生成 `(pre_edit, edit, repair)` 片段；
- 训练同一 WLA 的 action expert 或校准修复宏；
- 每个任务 50–200 条增强即可覆盖主要类型；变形物体用仿真/人工回放。

**关键实现细节**：

- **EE 复合**：WLA 输出相对当前 EE 的 6D 增量；挑战赛要绝对目标。用 SE(3) 指数映射/四元数复合，避免欧拉角奇点。复合后再转 xyz+rpy 返回。
- **pivot 常量**：tabletop 任务不需要走动；`action.pivot` 先保持数据集均值/零。HangCup 的 `pivot_4≈0.15`、`height≈0.738` 说明不能全零；用每个任务/机器人的标定值，或先零再单任务通道验证。`pivot_3..5` 未文档化，保持常量最安全。
- **动作 shape**：joint 模式返回 23 维；EE 模式返回 21 维；每个 key 形状 `(T_a, dim)`，dtype `float32`；`meta.token` 每次都要带。
- **观测选择**：WLA 只用 `cam_left_high` + 两个腕部；`cam_right_high` 留给评分点谓词/头双目深度。`obs_delta_indices` 只声明需要的键；`image_resize` 可把 head 降到 240×320、wrist 降到 128×128/160×160，降低带宽。
- **历史**：`obs_delta_indices` 的 offset 是控制步，不是 chunk；`T_a=8` 时 `[-8,-4,0]` 覆盖前一个/半个 chunk；可用于进度估计，但不要假设有 chunk 内新观测。
- **端口隔离**：每个端口一个 `RubricTurnPolicy` 实例/ledger；共享 VLA 后端时，请求带 `port_id`/`episode_id`，`reset()` 清空该端口状态；并发压测。
- **p99 延迟**：VLA 推理是主成本；VLM 复核不要放在关键路径；确定性谓词优先；每 2–3 个 chunk 做一次 VLM；用缓存和异步。

### 3.7 实时预算

- 目标：p99 `get_action` ≤200ms（与第 12 轮一致）；若 WLA 6B 单次推理 >200ms，则用 \(T_a=12\)（400ms）并接受 3.3Hz 反馈；p99 包括 VLA + adapter + planner，不包括 VLM 异步。
- VLM 复核：\(L_{\text{vlm}}\) 若 300ms，不能每个 chunk 调用；每 \(N_v=4\) 个 chunk 一次，均摊 75ms；或只在该评分点边界调用。
- 安全余量：`T_a/30 - (L_vla+L_net+L_plan) ≥ 50ms`；不够就增大 \(T_a\) 或降分辨率/减模型。
- 180s：`T_a=12` 时 450 个 chunk；足够重试。不要用长时间 hold 消耗预算。

## 4. 伪代码

### 4.1 主循环

```python
class RubricTurnPolicy:
    def __init__(self, rubric, vla, servo, adapter, config):
        self.rubric = rubric
        self.vla = vla
        self.servo = servo
        self.adapter = adapter
        self.config = config
        self.ledger = ProgressLedger(rubric)
        self.history = []
        self.mode = "progress"          # progress | repair | fail_safe
        self.repair_targets = []
        self.step_count = 0

    def reset(self):
        self.ledger.reset()
        self.history.clear()
        self.mode = "progress"
        self.repair_targets = []
        self.step_count = 0
        return {"ok": True}

    def get_action(self, obs):
        self.history.append(obs)
        self.step_count += 1

        # 1) 进度更新（确定性谓词 + 可选 VLM）
        self.ledger.update(obs, self.rubric, self.config)
        regressed = self.ledger.regressed_steps()

        # 2) 人为 turn 检测
        if regressed and self.ledger.is_human_turn(obs):
            self.mode = "repair"
            self.repair_targets = minimal_repair_set(regressed, self.rubric)
        elif self.mode == "repair" and not regressed:
            self.mode = "progress"
            self.repair_targets = []

        # 3) 选候选
        if self.mode == "repair":
            candidates = self.generate_repair(self.repair_targets, obs)
        else:
            step = self.ledger.next_uncompleted()
            candidates = self.generate_progress(step, obs)
        candidates.append(self.hold_candidate(obs))

        # 4) 打分
        best = max(candidates, key=lambda c: self.utility(c, obs))
        if best.kind == "hold" and self.should_explore(obs):
            best = max(candidates, key=lambda c: self.explore_value(c, obs))

        # 5) 执行（chunk 边界修正）
        chunk = self.execute(best, obs)
        return self.adapter.to_api(chunk, self.config.token)
```

### 4.2 进度更新

```python
def update(self, obs, rubric, config):
    for step in rubric.steps:
        if step.predicate == "vlm_only" or self.should_verify(step):
            p = self.vlm_verify(obs, step)       # 0..1
        else:
            p = self.geometry_verify(obs, step)  # 0/1
        self.update_belief(step.step_id, p, source=...)

    # 回归检测
    for step in rubric.steps:
        b = self.belief[step.step_id]
        if step.step_id in self.completed and b < 0.5:
            self.negative_count[step.step_id] += 1
        else:
            self.negative_count[step.step_id] = 0
        if self.negative_count[step.step_id] >= 2:
            self.regressed.add(step.step_id)
            self.completed.discard(step.step_id)
```

### 4.3 最小修复集

```python
def minimal_repair_set(regressed, rubric):
    # 只修复回归步骤；若多个回归，按拓扑序
    order = topo_order(rubric)
    return [s for s in order if s in regressed]
```

## 5. 数据与训练

### 5.1 评分点切分

- **输入**：成功演示（parquet state/action + 四路视频）、任务 JSON 的 `score_steps`。
- **刚体任务**：用物体/夹爪轨迹 + 规则：
  - 抓取起点：夹爪开度下降 + 物体开始随夹爪移动；
  - 放置终点：物体/夹爪进入目标 ROI 且速度/夹爪开度稳定；
  - 插入终点：插头尖端进入端口 ROI；
  - 开/关：盖子角度/拉链头位置变化。
- **变形/透明**：离线 VLM 标注（Qwen2.5-VL/InternVL 等）+ 人工抽检；只用于训练/离线验证，不参与在线推理。
- **输出**：每个 episode 的 `step_boundaries = [t_0, t_1, ..., t_K]`；`(frame, step_id, completed_steps)`。
- **质量门**：G1 切分 F1≥0.75；刚体≥0.9；每个任务至少 50 条有效切分。

### 5.2 前缀训练

对每个 episode、每个评分点 \(k\)：

- 取 \(t_{k-1}\) 到 \(t_k\) 的片段作为“执行第 k 步”的目标；
- prompt：`Task: <instruction>. Current step: <step_k>. Completed: <steps 0..k-1>.`
- 图像：当前帧 + 短历史；
- 目标动作：该片段；
- 这样模型见过：
  - 从零开始；
  - 从部分完成状态开始；
  - 在评分点边界切换；
  - 最后一步的收尾。
- 训练：冻结 VLM，只训 DiT action head + projector（WLA 官方微调方式）；LoRA 可选；1×24GB GPU。

### 5.3 Rollback 增强

- 对每个评分点边界，施加逆向编辑：
  - 抓取后把物体移开 2–5cm；
  - 放置后把物体/容器移开；
  - 拉链拉上后拉开；
  - 毛巾叠好后翻开；
  - 盖子拧开后拧回；
  - 锁打开后拿走；
  - 碗叠好后拿下第二个；
  - 零食放回起点。
- 生成 `(pre_edit, edit, repair)` 片段；训练模型“检测到编辑→重做该步”。
- 增强量：每任务 50–200 条；优先覆盖 60 条 human notes 的类型。
- 不要用测试通道数据训练；不要用 unseen 测试集调参。

### 5.4 Prompt schema

```text
System: You are a robot policy. Execute the current scoring step.
Task: <official task instruction>
Current step: <step index + zh/en text>
Completed: <list of completed steps>
Last edit: <none | object moved | step undone | object removed>
Instruction: Execute the current step. If the step is already complete, keep the scene stable.
```

- 训练和推理使用同一 schema；推理时可加“recover”变体。
- 语言指令是固定的，不依赖外部对话；prompt 是内部 VLA 条件，不发给 evaluator。

### 5.5 数据划分与泄漏

- 按 episode/session/物体/背景分组划分，避免相邻帧跨 split。
- 公开数据全成功；失败/rollback 用仿真/增强。
- 单任务通道只做选择/校准，不训练；不把测试通道的失败帧加入训练。
- 评分点文本是公开的，不算泄漏；不要把测试任务的 `info.json` 备注硬编码成“看到某帧就执行某动作”；在线必须检测。

|---|---|---|---|

## 6. 竞赛策略

### 6.1 Lexicographic 目标

官方排名：

\[
\text{sort}\big(\text{avg success},\text{avg step score},\text{earlier submission}\big)_{\text{lexicographic}}.
\]

政策目标：

\[
\max\ M\,\mathbb{E}[Y]+\mathbb{E}[S],\qquad M\gg100.
\]

- 成功优先：不要为了步骤分牺牲成功；但最后一步的期权通常同时提高两者。
- 步骤分次之：当成功率打平（很多任务 0/10、1/10），步骤分是实际区分度。
- 更早提交：先交安全基线，再迭代；不要等完美。

### 6.2 Trial 噪声与任务优先级

- 320 trials 平均成功率 SE≈2.2–2.3pp；1–2pp 的榜单差距不可信。
- 单任务 10 次观测很粗：真实 p=0.05 有 40% 概率显示 1/10；真实 p=0.10 有 65% 概率≥1/10。
- 因此：
  - 不要因为单任务 0/10 就放弃；它可能是 p=0.05–0.1。
  - 不要因为单任务 1/10 就过度乐观；它可能是 p=0.05。
  - 用步骤分（更稠密）和配对 A/B 判断改进。
  - 用 Beta 后验/分层模型估计 \(p_t\)，不要把点估计当真值。

### 6.3 任务组合

| 层级 | 任务 | 特征 | 策略 |
|---|---|---|---|
| Tier 1 | T14,T19,T24,T10,T12,T27,T29 | 2–3 步；有明确撤销/重置备注；最后一步 40–50 分 | 优先 HUMAN-TURN 修复 + 期权尝试；单任务通道先验证 |
| Tier 2 | T01,T02,T03,T05,T08,T23,T30,T04,T06,T07,T11,T13,T20,T21,T25,T26 | 2–3 步；移动类备注；刚体为主 | 重定位/重抓宏；评分点底仓 50–60 分 |
| Tier 3 | T09,T15,T18,T22,T28 | 4 步；底仓 50、除最后一步 75；移动类备注 | 先做前 2–3 步底仓；最后一步期权；注意长时序 |
| Tier 4 | T16,T17 | 5 步；底仓 40、除最后一步 80；折叠/开盒，变形/长时序 | 只在谓词/VLM 可靠时上线；否则保留基线 |
| 观察 | T31,T32 | 无人为备注；T32 注射器（变形/透明风险） | 先看基础成功率/步骤分；不作为修复重点 |

**注意**：Tier 1 的“撤销类”最容易验证修复宏；Tier 2 的“移动类”数量最多；Tier 3/4 的“底仓”高但步骤多、风险大。先用单任务通道测 Tier 1，再扩到 Tier 2。

### 6.4 人为轴

- 人为干扰占 2/10=20%；修复 11–13 条撤销类中的一半，理论上人为轴 +10pp 左右，全局 +2pp。
- 优先顺序：撤销类（T16,T19,T14,T17,T27,T12,T10,T29,T24）→ 移动类（T01–T09,T11,T13,T15,T18,T20–T23,T25,T26,T28,T30）→ 混合/其他。
- 每个修复宏要有超时/回退；不要为了修复而把底仓弄没。
- 记录“修复成功/失败/超时”的混淆矩阵；用单任务通道估算 `u_t`。

### 6.5 单任务通道协议

1. 选 5 个 Tier 1 任务 + 2 个 Tier 2 任务；
2. 每个任务 5–10 次，配对 A/B：
   - A：CHUNK-SERVO 基线；
   - B：+ RUBRIC-TURN（评分点监控 + 修复 + 期权）；
3. 指标：成功率、步骤分、完成步数分布、p50/p99 延迟、修复次数/成功率、超时率；
4. 统计：配对 bootstrap/ McNemar（成功率）、Wilcoxon（步骤分）；不要只看均值；
5. 过 G3 才进正式提交；不过门就回退，不烧正式 trial。

### 6.6 提交策略

- 允许多次提交：先交安全基线占位（更早提交 tie-break），再交 RUBRIC-TURN 增量；每次提交前跑 32 任务干跑。
- 只允许一次：把工程集中在“不会比基线差”的评分点监控 + 修复；期权尝试只在 Tier 1 启用；保留基线回退开关。
- 不要用正式提交做探索；单任务通道先验证。
- 提交材料写清单模型合规：评分点状态机/谓词/宏无学习权重；VLM 复核用同一 checkpoint；没有第二个模型；没有测试通道训练。

## 7. 实验与门

### 7.1 离线

- **G0 解析**：32 任务、94 步、权重和=100、谓词映射覆盖≥90%、人工抽检 32 步。
- **G1 切分/进度**：刚体任务切分 F1≥0.9；变形任务≥0.75；进度 AUROC≥0.85；每个任务≥50 条切分。
- **消融**：确定性谓词 vs VLM 复核 vs 两者；不同阈值/滞回；不同 VLM 频率。

### 7.2 仿真/回放

- 用成功演示 + rollback 增强构建回放集；注入 60 条 human notes 的类型；
- 指标：人为 turn 检测延迟/召回/误报；修复成功率/耗时；最小修复 vs 从头重做；
- 通过：G2 检测≤200ms、修复≥70%、撤销类≥80%。

### 7.3 真机单任务

- 5–7 个任务 ×5–10 次；A/B 配对；
- 指标：成功率、步骤分、完成步数、p99 延迟、修复成功/超时、动作拒绝；
- 通过：G3 ≥3/5 任务 +10pp 成功率或 +10 步骤分；FoldTowel 不回归；p99≤200ms（或按 chunk 调整后不超时）。

### 7.4 32 任务干跑

- N 端口并发；每端口独立 ledger/reset；
- 检查 token、shape、dtype、pivot 常量、内存/显存、端口隔离；
- 通过：G5 无串扰、无泄漏、无超时增加。

### 7.5 消融

| 消融 | 问题 |
|---|---|
| RUBRIC-TURN vs CHUNK-SERVO | 评分点决策是否真的涨点？ |
| 修复 vs 无修复 | 人为轴是否涨？最小修复是否优于从头重做？ |
| 期权尝试 vs 保守 | 最后一步尝试是否提高成功率而不压步骤分？ |
| lexicographic vs success-only | 步骤分是否帮助 tie-break？ |
| 前缀训练 vs 整任务 | 评分点条件是否提高步骤完成？ |
| VLM 复核 vs 纯几何 | VLM 是否值得延迟？ |
| chunk 5/8/12/30 | 反馈周期 vs 延迟的最优点？ |

### 7.6 门表

| 门 | 通过标准 | 失败动作 |
|---|---|---|
| G0 | 32 任务/94 步/权重 100/谓词覆盖≥90% | 修 parser；歧义步骤 VLM-only |
| G1 | 刚体 F1≥0.9，变形≥0.75，AUROC≥0.85 | 只用确定性谓词；放弃变形任务 |
| G2 | 检测≤200ms；修复≥70%；撤销类≥80% | 砍在线修复；只保留离线 catalog |
| G3 | 5 任务×5 次：≥3 任务 +10pp 或 +10 步骤分；FoldTowel 不回归 | 回退基线；只保留监控 |
| G4 | p99≤200ms；timeout 不升；chunk 扫参有数据 | 加 chunk/降分辨率/减 VLM |
| G5 | N 端口隔离；reset 干净；内存不涨；动作校验全过 | 修 server；回退基线 |
| G6 | 消融支持因果 | 保留有效部分，砍无效部分 |
| G7 | 单模型合规；无测试训练；材料完整 | 回退 C1/C2 合规模式 |

### 7.7 Kill criteria

- G2 失败：不做在线自动修复；只做离线提示/人工复检；RUBRIC-TURN 退化为监控。
- G4 失败：增大 \(T_a\)、减少 VLM、降分辨率；仍失败则回退 CHUNK-SERVO。
- G3 失败：不提交 RUBRIC-TURN 版本；保留基线；把评分点用于诊断/数据选择。
- 任何合规疑问：退回纯确定性谓词 + 无 VLM 复核；确保单模型。

## 8. 风险与合规

| 风险 | 影响 | 缓解 |
|---|---|---|
| 单模型解释 | 被判定为第二个模型 | 评分点状态机/谓词/宏无学习权重；VLM 复核用同一 checkpoint；若质疑，退回纯确定性；提交材料写清楚 |
| 评分点语义歧义 | 进度估计错 | 人工抽检；阈值保守；歧义步骤 VLM+滞回；单任务通道验证 |
| 人为备注≠实际 | 修复错 | 在线检测；不 open-loop 照脚本；检测不到用 VLA 重规划 |
| chunk 内无反馈 | 过度承诺 30Hz 伺服 | 明确 chunk 边界修正；扫 5/8/12/30；p99 门 |
| 无 done 信号 | 不能安全停手/浪费时间 | 不做停手策略；避免撤销动作；时间预算内重试 |
| pivot 语义未文档化 | 动作被拒/机器人不动 | 常量/零回退；单任务通道验证；EE 模式优先 |
| VLM 复核延迟 | p99 超时 | 每 2–3 chunk 一次；小图；缓存/异步；确定性优先 |
| 变形/透明/遮挡 | 谓词/修复失败 | 降优先级；VLM+腕部；单任务验证；失败回退 |
| 评测噪声 | 1–2pp 假阳性 | 配对 A/B；bootstrap；320 SE≈2.2pp；不追预览榜 |
| 数据泄漏/诚信 | 取消资格 | 只用公开训练数据；测试通道只做选择；不训练测试数据 |
| 时间预算 | 180s 不够修复+尝试 | 剩余时间感知；优先高权重步骤；避免长 hold |
| 端口/并发 | N 端口状态串扰 | 每端口独立 ledger/server；reset 隔离；并发压测 |
| 动作 shape/dtype | 被 evaluator 拒绝 | 用 `example_env.py` 校验；unit test；token 每次带 |
