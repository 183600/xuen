## 1. 两个灵感的第一性原理

### 灵感 1 ·「场景驱动创新」→ 竞争单元不是「一个通用策略」，而是「场景族作战单元」

**直觉**：32 个任务看起来是 32 个独立问题，但它们其实按**接触工况**聚成少数几个族：把杯子挂上钩、把试管插进架、把毛巾折起来、把电池抠出来——决定成败的不是物体名字，而是「刚性抓放 / 插入连接 / 可变形 / 序列装配」这几种物理交互模式。通用策略把有限容量平均分给所有族，等于**在每个族都只做到中等**；而各族难度差异越大，平均主义的损失越大（L14）。官方 11 月新增的数据也正好按这些族在铺（折衣→可变形、组装凳子→序列装配、做三明治→刚性归置），说明「按场景族组织能力」与数据生产方向同构。

**严谨定义（U19 场景族）**：记场景族 `F = (R, C, Π, φ)`，其中 `R` 为接触工况（刚性/柔性/流体/连接器），`C` 为容器或关节结构（平面/挂具/抽屉/插槽/传送带），`Π` 为成功谓词模板（到点、插入深度、折叠覆盖率、装配顺序完整），`φ` 为该族的主导失败模式（抓点失配/对位误差/状态歧义/顺序错乱）。32 个挑战任务按主族映射为 4 族（见产物区 §1 表），交叉标签另记。**假设 H1**：按 `R,C` 分族比按物体名/外观聚类更能预测失败模式（E634 直接检验，失败则该假说降级）。

**策略含义**：把第 2–3 轮已经建好的通用栈（IP-09 伺服、IP-13 状态层、IP-02 介入、IP-06 评测）保留为**公共地基**，在其上按族挂**专业化轻量件**（LoRA/头/不变式模板/安全包络），由**场景路由器**在测试时选择——这就是「场景族作战单元」。它不推翻通用策略，而是把「一个策略打天下」改为「一族一套作战配置」。

### 灵感 2 ·「应用落地」→ 落地不是「做出模型」，而是「场景卡闭合」

**直觉**：实验室 demo 与可交付系统之间隔着五道坎——**场景覆盖、延迟预算、安全/可恢复、数据飞轮、可验收**。落地的标志不是「跑通一个视频」，而是「对某个场景族能说清：它在什么条件下可靠、失败时怎么退回、拿什么指标验收、下一批数据从哪来」。比赛恰好是一个受控的落地测试：任务冻结、按步骤计分、单 checkpoint + 自部署软件。因此「落地」应被工程化为**场景卡**：一族的全部承诺写在一张可执行、可验收、可回滚的卡上。

**严谨定义（U20 场景卡 / U21 场景编译）**：
- `Card_F = {family, task_ids, specialist_id, waypoint_skeleton, invariant_set, safety_envelope(延迟/工作空间/动作幅度), acceptance(success, step_score, latency, safety), known_failures, fallback=generic}`；
- `compile(ℓ, o0) = instantiate(template_{route(ℓ,o0)}, bind(ℓ,o0))`；路由置信度低于 `TAU_ROUTE` 时返回 `generic card`（P15 可回滚）。卡的每个字段都必须能被 E634–E638 中某一条判据检验，**不可检验的字段不许写进卡**（P14）。

**策略含义**：把 IP-17 做成「落地闭环」而不是又一层模型：场景缺口挖掘（用官方新增场景集 + 数字孪生场景）→ 族索引数据飞轮 → 族专业化 → 场景卡验收 → 回滚。落地由此从叙事变成**可审计的产物**。

### 灵感交叉 · 场景族 × 状态层 = 真正可部署的作战单元

第 3 轮的 IP-13 状态层是**族无关**的地基（目标是谁、在哪、卡没卡住）；本轮的场景族是**族相关**的顶层（该用哪套成功谓词、哪套安全包络、哪套介入优先级）。二者不是竞争关系：状态层给每张卡提供统一的「世界状态」输入，场景卡决定「读哪些状态、按哪套判据判通过」。这也解释了为什么单纯堆状态层不够——**同一套卡方门限不能同时服务插入（亚毫米）和折衣（厘米级容差）**，必须由场景卡把容差、不变式、安全阈值实例化。

## 2. 研究问题（新增 Q13–Q15，接 Q1–Q12）

- **Q13（场景族的可检验性）**：32 个挑战任务能否被 4 个接触工况族稳定划分，且族标签比物体名更能解释/预测失败模式？（E634；这是整套方案的前置门槛）
- **Q14（场景路由与专业化收益）**：从指令 + 首帧能否把任务路由到正确族（含弃权到通用），路由 + 族专业化相对单一通用策略的分数增益是否大于路由错误的期望损失（L15）？（E635）
- **Q15（场景卡的落地校准）**：场景卡预测的验收指标（成功率/步骤分/延迟/安全）能否在留出任务上被校准（误差 ≤ ε），数字孪生场景能否作为场景卡的前置验收环境？（E636/E637）

## 3. 设计原则（新增 P13–P15，接 P1–P12）

- **P13（场景先于模型）**：任何新组件必须写明它服务哪个场景族、针对哪个主导失败模式；不服务任何具体族的「通用增强」默认不上线（只在离线评测里)。判据：一张「组件 × 场景族」责任矩阵。
- **P14（落地以卡验收）**：组件「落地」的定义是拥有一张场景卡，且卡上每个承诺都有 E 编号可检、有回退路径；研究性组件只许离线存在。
- **P15（可回滚部署）**：任何族专业化件都必须带一开关退回 generalist；路由置信度 < `TAU_ROUTE` 一律弃权到通用卡；宁可少赚专业化收益，不可因误路由亏分（L15）。

## 4. 清单处置（深化 / 修剪 / 新增）

- **新增**：IP-16 ScenarioCompiler + ScenarioRouter（P0，MVP 后第一，取代第 3 轮把 IP-13 当第一扩展的排序）；IP-17 ScenarioLandingLoop 场景卡注册表 + 验收门 + 数据飞轮（P1）。

- **退化链**：Level-1.7 新增——**路由失败 → 通用卡（P15），状态层按第 3 轮 Level-1.6 退化，系统仍可跑**。

## 5. 本轮最大风险

**最大风险是「场景族」可能是伪结构**：如果 E634 证明 32 个任务无法被接触工况族稳定划分、或族标签并不比物体名更好地预测失败模式，那么整套路由器、场景卡与族专业化就退化为昂贵的规则外挂，收益还不如把算力全押在单一通用策略上——因此 E634 必须作为**前置门槛先跑**，不过门就整轮回撤到「只保留场景卡作为文档规范」的最小形态。

## 6. 下一轮迭代计划（深化与修剪，不推倒重来）

- **待外部事件**：榜单开放 48h 内复核 F2/F5（任务级榜单）；规则手册可读版关闭 Q3/Q4/Q9/Q12 的合规悬置（Q9 跨 episode 状态仍只问一次）。

## 4. 新增 IP 详述

### IP-16 · ScenarioCompiler + ScenarioRouter（P0，新）

- **动机**：32 任务聚成 4 个接触工况族，族间难度差异大、族内共享失败模式；单一通用策略把容量平均分配，损失约等于族间性能离散度（L14）。场景路由是**最低成本的结构先验**：不新训基座，只在已有栈前加一个薄决策层。
- **与现有方案差异**：teaser 榜（待复核假设）与常规 VLA 都是「一个策略吃所有任务」；本方案在**同一条策略通路上按族选专家/适配器/验证模板**，且带**弃权**（P15）——不确定就退回通用，避免误路由亏分。
- **技术可行性**：高。路由器输入=指令文本嵌入 + 首帧若干检测/场景特征（可复用 IP-13 检测器）；输出=4 族 + 弃权；可用逻辑回归/小 MLP/最近邻，样本可由「32 任务名 + 新增场景集任务名」自动打标扩展到数百条。场景卡是模板实例化，无训练。
- **资源**：算力极小（一次前向，且只编译一次/事件触发）；数据=任务名与元数据 + IP-06 标注；接口=无新增字段（全部策略内部，合规安全）。
- **落地步骤**：①用 §1.2 表生成族标签与模板（本产物即初版 schema）；②路由器最小实现 + 弃权阈值 `TAU_ROUTE`；③`compile(ℓ,o0)` 生成场景卡；④把卡上的 `specialist_id` 接到 IP-01 专家、`invariant_set` 接到 IP-09/U17、`safety_envelope` 接到伺服限幅；⑤E634 先验证族有效，再 E635 验证路由收益；⑥事件触发重编译（大光流/断言连续失败）。
- **风险**：族是伪结构（E634 前置门槛）；路由误判（L15 盈亏点 + 弃权）；族模板过拟合任务名（用留出任务/新增场景集验证）。

### IP-17 · ScenarioLandingLoop 场景卡注册表 + 验收门 + 数据飞轮（P1，新）

- **动机**：「应用落地」的核心不是再训一个模型，而是闭合五个环：场景覆盖、延迟预算、安全/可恢复、数据飞轮、可验收。官方 11 月新增的场景集与数字孪生场景，正好提供了**挑战外**的验证与补给面。
- **组成**：①**场景卡注册表**（每族一张卡，版本化、可回滚）；②**验收门**（成功率/步骤分/延迟 P99/安全违规四门）；③**回滚开关**（一键回通用卡，P15）；④**数据飞轮**（官方新增场景集按族打标 → 缺口最大的族优先补给 → 进 IP-12 课程）；⑤**孪生预验收**（`small_warehouse_digital_twin` 等场景先跑卡，再上真机）。
- **与现有方案差异**：常规做法把「数据/训练/评测」当三条独立流水线；本方案用**场景卡**把它们绑在同一族的同一份承诺上，卡不达标就不许上线，杜绝「demo 能跑但不可交付」。
- **技术可行性**：高。注册表是配置/元数据系统；验收门复用官方评分口径与 IP-06；数据飞轮只需打标脚本 + 课程接口；孪生场景已由官方资产提供。
- **资源**：近零训练；主要成本是打标与回放基础设施（复用 IP-06/IP-13）。
- **落地步骤**：①场景卡 schema（见 U20）与注册表；②四门验收脚本；③回滚开关接入主循环；④官方 11 月场景集按族打标（§1.3 表）；⑤在孪生场景上做前置验收（E636）；⑥数据杠杆计量（E637）。
- **风险**：**自证偏差**（自己定卡自己验收）→ 用留出任务 + 官方真机回放交叉验证；族-数据错配 → 打标双人复核 + 留出族；卡字段膨胀 → P14「不可检验不许进卡」。

## 8. 推导（新增引理 L14–L16；L1–L13 沿用第 1–3 轮）

**引理 L14（场景族分解的收益上界）** 设通用策略在族 `f` 上的成功率为 `p_f`，族权重 `w_f`（Σw_f=1），则其对全体任务的期望成功率 `p_g = Σ w_f p_f`。若族专业化件能把族 f 提到 `q_f`，则增益 `G = Σ w_f(q_f − p_g) ≥ Σ w_f(p_f − p_g) = 0`，且 `G = 0` 当且仅当所有 `p_f` 相等（加权方差为零）。⇒ **专业化的潜在收益恰等于通用策略的族间性能离散度**：任务越异质（插入 vs 归置难度差越大），分解越值钱；同质任务分解无收益。这给出 E634 的量化判据：先测 `Var_w(p_f)`，离散度小就根本不值得做族专业化。∎

**引理 L15（路由错误的代价与弃权阈值）** 设正确路由的每任务增益为 `Δ`、误路由相对通用策略的损失为 `Δ'`（`Δ,Δ' > 0`），路由器精度 `a`。启用路由的期望净收益 `E = aΔ − (1−a)Δ'`；令 `E>0` 得**盈亏平衡精度** `a* = Δ'/(Δ+Δ')`。若允许弃权到通用（弃权无增益无损），则仅需 `a_route·Δ > (1−a_route)·Δ'` 在**被路由的那部分**成立，门槛进一步降低。⇒ 路由器必须先估 `a` 与 `Δ/Δ'` 再决定是否上线；`a < a*` 时路由关闭，只保留场景卡文档。∎

**引理 L16（场景数据的边际杠杆与预算分配）** 设族 f 的分数对新增数据量 `n` 的边际改善 `∂score_f/∂n` 递减（凹函数），单位数据成本 `cost_f`。在总预算 B 下最大化 `Σ_f score_f(n_f)` 的一阶条件是各族**边际收益/成本相等**；故应优先把数据给 `fail_mass_f × leverage_f / cost_f` 最大的族（`fail_mass_f`=该族失败占比，`leverage_f`=可迁移性）。⇒ 11 月新增的 Fold_Clothes（C 族，1000 eps）与 Assemble_Stool（D 族，1000 eps）若对应族失败占比高、且与挑战族同构，则是最优投放点；否则（跨本体/域差大）杠杆低，应先做小样本迁移探针再决定。∎
