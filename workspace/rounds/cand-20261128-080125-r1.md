### 第 1 轮灵感驱动研究记录（新循环 · 承接第 6 轮 CADVS-v6）

**灵感词**：并发推理、模型预测控制

**继承关系**：第 6 轮 CADVS-v6（IP-497~500）在「七硬门不增」前提下，用 GGC / MCTM / STM 把提议约束到「几何可达、空间连通、语义可解释」的亚族，并以软因子链 η_g·η_topo·η_interp·η_cmd 只收紧、不放松证书边界。但 v6 的全部正确性证明仍隐含两个未经审计的**时间假设**：**(T1) 证书只对一个「此刻」的快照负责，不承诺未来**——它认证一条轨迹，却不保证轨迹终点之后仍存在可被认证的延续；**(T2) 认证是串行且上下文静止的**——提议、门评估、记忆固化、情感更新被默认可按任意顺序、在稳定快照上完成。本轮两个灵感词恰好各补一个时间维度：**模型预测控制**补上「向前看的时域」，**并发推理**补上「同时发生的并行时间」。v7 不新增硬门，而是把证书从「点证书」升级为**带租约与版本的前瞻证书**。

**直觉与动机**：

1. **模型预测控制 → 证书要有「未来」，而不只是「此刻」**。直觉上，v6 像一个只看脚下台阶的登山者：每一步都被证明安全，却可能一步步走进再也无法认证的悬崖（**认证陷阱 / certified trap**）。MPC 的核心教训不是「优化一条轨迹」，而是「只提交一个有可行延续的计划，然后滚动重规划」——**递归可行性（recursive feasibility）**。做法：每条被提交的滚动时域计划 π 必须以一个**终端不变集 X_f** 收尾，且存在一个离线认证过的备份控制器 κ_f，使 X_f 在扰动管下保持不变。于是任何时刻都存在一个「退一步」的合规动作；若某步找不到以 X_f 收尾的计划，就不提交，而是执行 κ_f 一步（它本身把状态留在 X_f 内）。关键洞见：**递归可行性不是新门，而是对既有 kc_plan / kc_loop 证书载荷的加厚**——门数不变，只要求计划证书携带「终端见证」W_H。

2. **模型预测控制 → 用「管」把模型误差变成显式约束收紧**。直觉：滚动时域依赖模型 f，模型错了，预测就偏。tube MPC 不去猜真实扰动，而是用可证明的误差管半径 r_k 收紧约束：名义轨迹离约束边界至少 r_k，真实轨迹就仍在约束内。做法：对每个既有门的裕度减去 L_i·r_H（Lipschitz 常数 × 管半径），并入 v6 已有的阈值收紧；随机 / 未建模扰动再用**并行场景采样 + 场景优化界**转成概率证书。关键洞见：**鲁棒性表现为「对既有门的加性收紧」，而不是新增一道鲁棒门**。

3. **并发推理 → 危险不是「算得慢」，而是「旧快照解锁新承诺」**。直觉：把认证想成一本多人同时记账的账本。v6 的单调性证明默认一个人顺序记账；一旦多个推理线程并发读-改-写，就可能出现「门评估用旧记忆版本，提交时记忆已被固化线程改写」——证书对版本 v 成立，却被当成对 v+1 成立。安全上最危险的从来不是延迟，而是**陈旧证书通过了本不该通过的承诺**。做法：上下文快照不可变并带版本号 v；证书 = (claim, margin, v, 租约 [t0, t0+H])；提交是一次 **CAS（compare-and-swap）**：只有 version(c) 仍为 v、未过期、且终端见证成立，才允许提交，否则中止重算或 fail-closed 回退。关键洞见：**并发只能收紧不能放松**——并行分支的结果按合取（meet）合并（可交换、单调），唯一需要定序的是提交点（线性化点）。

4. **并发推理 → 从「串行想清楚再做」到「并行竞速 + 验证后提交」**。直觉：串行地「提一个、证一个、不行再提」浪费了 MPC 需要的多分支时域。并发让 B 条时域分支在同一不可变快照上同时提议、同时评估，先被证明安全且递归可行的分支先赢，其余剪枝。但必须诚实：并发不是免费的正确性；若分支共享同一份错误模型，它们会一起错。因此竞速只发生在**提议层**，**提交层仍是单写者、带版本校验**。

**关键洞见总述**：v6 回答「提议如何符合物理 / 空间 / 意图」；v7 回答「当提议是滚动时域、认证是并发执行时，证书如何在时间上仍然有效」。七硬门 kc_evidence_forged_v5 及其在 v5 中追加的 kc_plan / kc_loop 全部原样复用，数量与语义冻结；本轮新增的只有：
- IP-501 CHP（并发时域提议器），
- IP-502 CVC（并发验证与版本化提交），
- IP-503 RFG（递归可行性守卫，折叠进 kc_plan / kc_loop），
- IP-504 RSC（鲁棒管 + 并行场景证书），
- IP-505 EFA-v7（租约 / 可行性 / 鲁棒软因子链）。

**形式化目标（增量）**：

1. **CHP（Concurrent Horizon Proposer）**：<br>
   - 不可变上下文快照 c^{(v)} = (M_v, ŝ_v, E_v, p_v)，版本 v ∈ ℕ；同一版本对所有并发分支只读<br>
   - 计划 π = (u_0,…,u_{H−1}) ∈ U^H，名义 rollout x̂_0=p_v, x̂_{k+1}=f(x̂_k,u_k)；B 条分支并行生成，各自携带 (branch_id, v)<br>
   - 分支生成由 FMPP 条件于 c^{(v)} 与分支种子；粗门（kc_ee / kc_bal 的低成本裕度）为负者立即剪枝

2. **CVC（Concurrent Verification & Commit）**：<br>
   - 门证书 Cert_i(x̂; c^{(v)}) = (pass_i, m_i, v)，m_i 为归一化裕度；prepare 阶段并行评估全部硬门<br>
   - 证书束 Bundle_b = (plan_b, {Cert_i}_i, W_H, v, t0)；只有所有硬门通过且 W_H 非空才成为候选<br>
   - 提交是单写者 CAS：commit(b) 为真 ⟺ version(c_now)=v ∧ now ≤ t0+H ∧ W_H 在当前上下文仍有效；否则中止、重验或回退<br>
   - 线性化点 = 提交点；并行分支只以合取（meet）汇入候选集，因此任意交错等价于某个提交串行序

3. **RFG（Recursive Feasibility Guard，折叠进 kc_plan / kc_loop）**：<br>
   - 终端集 X_f 与备份控制器 κ_f：∀x∈X_f, f(x,κ_f(x))⊕W ⊆ X_f（离线证明，缓存证明 id）<br>
   - 计划可行 ⟺ 沿 rollout 所有门（含鲁棒收紧）通过 ∧ x̂_H ∈ X_f；终端见证 W_H = (x̂_H, cert_id(κ_f), proof_id, r_H)<br>
   - kc_plan′ = kc_plan ∧ (W_H ≠ ⊥)；kc_loop′ = kc_loop ∧（每次重规划前 W_H 对观测状态仍有效）——只加厚载荷，不新增门<br>
   - 若无任何分支给出 W_H：不提交，执行备份动作 κ_f(p) 一步

4. **RSC（Robust Scenario Certificate）**：<br>
   - 有界扰动 ‖w‖≤w_max；误差管 e_0=0, e_{k+1}=A_k e_k + w_k，r_k = Σ_{j<k}‖A‖^{k−1−j}·w_max<br>
   - 鲁棒裕度 m_i^rob = m_i − L_i·r_H，要求 m_i^rob ≥ τ_i^v6（加性收紧，并入既有阈值）<br>
   - 随机 / 未建模扰动：N 个场景并行采样，全通过则用场景优化界 N ≥ (2/ε)(ln(1/β)+d) 给出 P(violation)≤ε（置信 1−β）<br>
   - 场景合取可交换、可结合，故并行评估不改变证书强度

5. **EFA-v7 软因子链**：ECS_v7 = ECS_v6 · η_lease · η_feas · η_robust，其中<br>
   - η_lease = 1 + κ_lease·(t−t0)/H ∈ [1, 1+κ_lease]（租约越老越保守）<br>
   - η_feas = 1 + κ_feas·(1 − ρ_H)，ρ_H = min(1, d(x̂_H, ∂X_f)/δ_f)（终端越贴边界越保守）<br>
   - η_robust = 1 + κ_rob·(r_H / r_max) ∈ [1, 1+κ_rob]<br>
   - 阈值 τ_i^v7 = γ_i·τ_i^v5·Π_factor_i^v6 · η_lease·η_feas·η_robust + L_i·r_H；乘积 ≤ 1.3 设计上限

6. **形式化定义（单步执行流）**：给定指令 L、目标 ρ_target、版本化上下文存储 𝒞：<br>
   - c^{(v)} = 𝒞.snapshot()；<br>
   - Π = CHP.propose(c^{(v)}, B)；<br>
   - Surv = {π ∈ Π : RSC.scenarios_ok(π,c^{(v)}) ∧ CVC.prepare(π,c^{(v)}) ≠ ⊥}；<br>
   - 按 ECS_v7 降序对 Surv 的证书束做 CVC.commit；首个成功者取 u_0 执行，其余丢弃；<br>
   - 若全灭：执行 κ_f(p_v)（备份步），状态由不变性留在 X_f；<br>
   - Exec_CADVS-v7 = {x : 以有效 (v, 租约, W_H, 鲁棒裕度) 提交}，且 Exec_v7 ⊆ Exec_v6 ⊆ … ⊆ Exec_v29

**本轮最大风险**：**安全—活性坍缩（safety–liveness collapse）**——递归可行性可以用一个极小、极保守的终端不变集 X_f 换取；于是系统永远「安全」，却只能反复执行备份控制器或原地微动，任何单步证书都合格，而任务永远不推进。fail-closed 的硬门在结构上**无法察觉**这种「每一步都对、整体不动」的失效。

## 0. 增量定位与继承关系（在 CADVS-v6 / IP-497~500 基础上扩展）

### 0.1 本轮问题

v6 的证书是**点证书**：认证一条轨迹在其提交瞬间的合法性。它有两个未被审计的时间假设：

- **T1（时域缺口）**：不承诺「终点之后仍可认证」。一条轨迹可以逐步合格，却把系统带进不可再认证的状态（认证陷阱）。
- **T2（并发缺口）**：认证被默认为串行且上下文静止。并发读-改-写会让「对版本 v 成立」的证书在版本 v+1 上被提交（陈旧证书解锁新承诺）。

v7 用**模型预测控制**补 T1（滚动时域 + 递归可行性），用**并发推理**补 T2（不可变快照 + 版本化 CAS 提交）。硬门数量与语义冻结，只加厚既有门的证书载荷。

## 2. 关键算法骨架

### IP-501 CHP：并发时域提议器

```python
@dataclass
class ConcurrentHorizonProposer:
    """CHP：在同一不可变快照上并行生成 B 条长度 H 的滚动时域计划。
    红线：分支只读快照；不得在生成期写任何共享状态。"""
    fmpp: FlowMatchingProposalPolicyKernel
    H: int = 10
    B: int = 8
    n_workers: int = 8

    def propose(self, snap: ContextSnapshot) -> list[HorizonPlan]:
        v = snap.version

        def branch(b: int) -> HorizonPlan:
            seed = mix_seed(v, b)
            us = self.fmpp.sample_horizon(snap.immutable_view(), H=self.H, seed=seed)
            x_hat = rollout(self.fmpp.f, snap.pose, us)
            return HorizonPlan(us=us, x_hat=x_hat, branch=b, version=v)

        with ThreadPool(self.n_workers) as pool:
            plans = list(pool.map(branch, range(self.B)))
        # 粗门剪枝：低成本裕度为负者直接丢弃
        return [p for p in plans if coarse_margin(p) >= 0.0]
```

### IP-502 CVC：并发验证与版本化提交

```python
@dataclass
class ConcurrentVerifier:
    """CVC：并行门评估 + 单写者 CAS 提交。
    线性化点 = commit；prepare 的结果永远绑定快照版本 v。"""
    gates: GateSet              # 七硬门 + kc_plan/kc_loop，语义冻结
    rfg: RecursiveFeasibilityGuard
    H: int = 10

    def prepare(self, plan: HorizonPlan, snap: ContextSnapshot,
                rsc: RobustScenarioCertifier) -> CertBundle | None:
        margins = {}
        for name, gate in self.gates.items():
            # RSC 提供加性收紧量 L_i * r_H
            m = gate.margin(plan.x_hat, snap, tighten=rsc.tighten(name, self.H))
            if m < gate.tau:
                return None                      # 任一硬门不过 → 该分支出局
            margins[name] = m
        w_h = self.rfg.terminal_witness(plan, snap)
        if w_h is None:
            return None                          # 无终端见证 → 不构成可提交候选
        return CertBundle(plan=plan, margins=margins, W_H=w_h,
                          version=snap.version, t0=now())

    def commit(self, bundle: CertBundle, store: VersionedContextStore) -> bool:
        # 单写者；这就是线性化点
        with store.commit_lock:
            if store.version != bundle.version:
                return False                     # 陈旧读：快照已被改写 → 中止
            if now() > bundle.t0 + self.H:
                return False                     # 租约过期 → 中止
            if not self.rfg.witness_valid(bundle.W_H, store.current):
                return False                     # 终端不变性在当前上下文失效
            store.append_commit(bundle)          # 原子追加提交记录
            return True
```

### IP-503 RFG：递归可行性守卫（折叠进 kc_plan / kc_loop）

```python
@dataclass
class RecursiveFeasibilityGuard:
    """RFG：终端不变集 + 备份控制器；只加厚既有门载荷，不新增门。"""
    X_f: TerminalSet               # 离线构造：控制不变集
    kappa_f: BackupController      # 离线认证：X_f 在 W 下不变
    delta_f: float = 0.2           # 终端深度归一化尺度

    def terminal_witness(self, plan: HorizonPlan,
                         snap: ContextSnapshot) -> TerminalWitness | None:
        xH = plan.x_hat[-1]
        if not self.X_f.contains(xH):
            return None
        if not self.kappa_f.invariance_proof.valid():
            return None
        return TerminalWitness(xH=xH, kappa_id=self.kappa_f.cert_id,
                               proof_id=self.kappa_f.invariance_proof.id,
                               r_H=plan.r_H)

    def feasible_margin(self, plan: HorizonPlan) -> float:
        depth = self.X_f.distance_to_boundary(plan.x_hat[-1])
        return min(1.0, depth / self.delta_f)

    def backup_step(self, x):
        # 保证 f(x, kappa_f(x)) ⊕ W ⊆ X_f
        return self.kappa_f(x)
```

### IP-504 RSC：鲁棒管 + 并行场景证书

```python
@dataclass
class RobustScenarioCertifier:
    """RSC：确定性误差管（加性收紧）+ 随机场景（并行合取 + 场景界）。"""
    A_norm: float
    w_max: float
    L: dict[str, float]           # 各门 Lipschitz 常数
    N_scen: int = 32
    eps: float = 0.05
    beta: float = 0.01
    dim: int = 6

    def tube_radius(self, H: int) -> float:
        return self.w_max * sum(self.A_norm ** k for k in range(H))

    def tighten(self, gate_name: str, H: int) -> float:
        return self.L[gate_name] * self.tube_radius(H)

    def scenarios_ok(self, plan: HorizonPlan, sampler, gates,
                     snap: ContextSnapshot) -> bool:
        def one(s: int) -> bool:
            w = sampler.sample(s)
            x = rollout_with_disturbance(plan.us, snap.pose, w)
            return all(g.margin(x[k], snap, 0.0) >= g.tau
                       for k in range(len(x)) for g in gates.values())

        with ThreadPool(self.n_workers) as pool:
            oks = list(pool.map(one, range(self.N_scen)))
        if not all(oks):
            return False
        # 场景优化 / VC 型样本复杂度界
        need = (2.0 / self.eps) * (math.log(1.0 / self.beta) + self.dim)
        return self.N_scen >= need
```

### IP-505 EFA-v7：硬门不变 + 租约/可行性/鲁棒软因子

```python
@dataclass
class EvidenceForgingAssemblerV7:
    v6: EvidenceForgingAssemblerV6
    chp: ConcurrentHorizonProposer
    cvc: ConcurrentVerifier
    rfg: RecursiveFeasibilityGuard
    rsc: RobustScenarioCertifier
    store: VersionedContextStore
    k_lease: float = 0.1
    k_feas: float = 0.1
    k_rob: float = 0.1

    def select(self, L, t_now, context) -> tuple[bool, Action | None, str]:
        snap = self.store.snapshot()             # 不可变快照 + 版本 v
        plans = self.chp.propose(snap)

        bundles = []
        for p in plans:
            if not self.rsc.scenarios_ok(p, context.sampler,
                                         self.v6.gates, snap):
                continue
            b = self.cvc.prepare(p, snap, self.rsc)
            if b is not None:
                bundles.append(b)

        # 软评分只决定尝试顺序，不改变可提交性
        bundles.sort(key=lambda b: self.ecs_v7(b, snap), reverse=True)
        for b in bundles:
            if self.cvc.commit(b, self.store):
                return True, b.plan.us[0], 'FORGED_CCRH_V7'

        # 无任何分支可提交 → 备份控制器一步（fail-closed，仍留在 X_f）
        return True, self.rfg.backup_step(snap.pose), 'SAFE_BACKUP_V7'

    def ecs_v7(self, b: CertBundle, snap: ContextSnapshot) -> float:
        eta_lease = 1.0 + self.k_lease * (now() - b.t0) / self.chp.H
        eta_feas = 1.0 + self.k_feas * (1.0 - self.rfg.feasible_margin(b.plan))
        eta_robust = 1.0 + self.k_rob * (b.plan.r_H / self.rsc.w_max)
        return (self.v6.ecs_v6(b.plan.x_hat, b.plan.n_flow, snap.s_emo,
                               self._v6_factors(b))
                * eta_lease * eta_feas * eta_robust)
```

### 集成流水线（v6 → v7）

```
离线/慢时域：
  终端不变集 X_f 构造（分钟~小时级）：在收紧约束下求控制不变集，附 SOS/区间证明
  备份控制器 κ_f 认证：∀x∈X_f, f(x,κ_f(x))⊕W ⊆ X_f，缓存 proof_id
  误差管表 r_k 与各门 Lipschitz 常数 L_i 标定
  场景采样器与样本复杂度参数 (ε, β) 标定

在线准入（异步，数十毫秒）：
  c^{(v)} = store.snapshot()                     # 不可变、带版本
  CHP.propose(c^{(v)}) ──▶ B 条时域计划（并行）
       ├─ RSC.scenarios_ok（N 场景并行）──▶ 全通过才继续
       └─ CVC.prepare（门并行）──▶ 证书束（含 W_H, v, t0）
  按 ECS_v7 降序 CVC.commit（单写者 CAS）
       ├─ 成功 ──▶ 执行 u_0，滚动移位重规划
       └─ 全灭 ──▶ κ_f(p) 备份一步（留在 X_f）

在线控制环（目标 < 0.6 ms）：
  EFA-v7 只消费预计算的证书束与提交记录；硬门调用链路不变
```

## 3. 复杂度分析（增量更新）

| 模块 | 时间复杂度 | 空间复杂度 | 关键参数 | 实时性 |
|---|---|---|---|---|
| CHP.propose | O(B·H·n)/W 并行 | O(B·H·n) | B=8, H=10, W=8 | 准入时域 ~5–20 ms |
| CVC.prepare | O(B·G)/W 并行 | O(B·G) | G≈9 | ~1–3 ms |
| CVC.commit | O(1) + 锁 | O(1) | — | < 0.05 ms |
| RFG.terminal_witness | O(n) | O(1) | — | < 0.01 ms |
| RSC.scenarios_ok | O(N·H·n)/W 并行 | O(N·H·n) | N=32 | ~10–30 ms |
| EFA-v7.select 软因子 | O(1) | O(1) | — | < 0.05 ms |

**端到端**：准入路径并行化后 P99 ≈ 20–35 ms（异步，不影响控制环）；控制环仍为 O(1) 消费预计算证书，P99 ≈ 0.6 ms（维持 v6 目标）。内存上，版本化快照按需保留，提交后旧版本可回收，稳态 O(#in-flight versions)。

## 4. 正确性论证（增量）

### 定理 11（版本化提交的线性化 / 陈旧证书不可能）

**陈述**：任意并发执行中，若 `commit(b)` 在时刻 t* 返回真，则 b 的全部门裕度均在版本 v = version(c_{t*}) 上计算、租约未过期、终端见证有效；因此被提交计划在 t* 的上下文下满足全部硬门。推论：不存在陈旧证书被提交；任意交错等价于某个提交串行序。

**证明**：`commit` 持有单写者锁，先比较 `store.version == bundle.version`，再检查 `now ≤ t0+H`，再检查 W_H 对当前上下文有效；快照不可变，故证书束是 v 的函数。任一检查失败即中止，证书束被丢弃或在新版本上重验。候选合并为合取（meet），可交换、单调。故提交成功蕴含「同一版本 + 未过期 + 见证有效」。∎

### 定理 12（递归可行性 / 无认证陷阱）

**陈述**：假设 (i) 每个被提交计划都以 X_f 收尾并携带 W_H；(ii) κ_f 使 X_f 在 W 下不变；(iii) 误差管收紧覆盖真实误差。则从任一被提交状态出发，下一步都存在被认证的动作序列；若重规划全灭，备份步 κ_f 仍把状态留在 X_f。因此系统不会进入「认证可行集为空」的状态。

**证明**：标准 MPC 归纳。t 时刻提交计划 π 满足 x̂_H ∈ X_f。执行 u_0 后，若重规划成功则归纳继续；若全灭，应用 κ_f，由 (ii) 后继 ∈ X_f，且把 π 的移位尾部与备份拼接即得名义+管意义下的可行计划。对 t 归纳。∎

### 定理 13（场景证书的并行合取）

**陈述**：若独立采样 N ≥ (2/ε)(ln(1/β)+d) 个场景且全部通过，则真实违反概率 ≤ ε 的概率至少 1−β。并行评估得到同一合取（与顺序无关），故并发不削弱该界。

**证明**：场景优化 / VC 型样本复杂度界；合取运算可交换、可结合，故 map（并行采样）后 reduce（全通过）与串行结果一致。∎

### 定理 14（单调收紧与严格退化）

**陈述**：Exec_CADVS-v7 ⊆ Exec_CADVS-v6。当 η_lease=η_feas=η_robust=1、r_H=0、且无并发（单分支、版本不变）时，v7 精确退化为 v6。

**证明**：η_lease,η_feas,η_robust ≥ 1，r_H ≥ 0 ⇒ τ_i^v7 ≥ τ_i^v6，门不放松；提交额外增加版本/租约/见证三条件；RFG 只加厚 kc_plan/kc_loop 载荷。故执行集只收缩。退化条件使所有新增量归零、提交条件恒真，恢复 v6 语义。∎

### 诚实声明

- **X_f 的保守性直接决定活性**：不变集越大越好，但可证不变集在接触/摩擦等非光滑动力学下往往很小；本方案无法在结构上消除「安全但不前进」。
- **误差管线是线性上界**：非线性强接触下 r_k 可能爆炸，导致门被过度收紧、可用分支锐减。
- **场景界依赖可交换性**：分布漂移（新地形、新负载）会破坏 i.i.d. 假设，ε 界失效；需在线有效性监测（见 R65）。
- **并发正确性是模型级**：CAS 只保证逻辑线性化，不防止内存模型层面的撕裂读、伪共享与编译器重排；必须配合 TLA+/PlusCal 模型检验与确定性重放。
- **版本抖动**：高更新率下 CAS 频繁失败，可能引发「重验风暴」；需有界重试与退避，极端时退回单分支保守模式。

## 7. 本轮最大风险（最终确认）

**一句话**：**安全—活性坍缩**——递归可行性可以用一个极小、极保守的终端不变集 X_f 换取；于是系统永远「安全」，却只能反复执行备份控制器或原地微动，任何单步证书都合格，而任务永远不推进。fail-closed 的硬门在结构上无法察觉这种「每一步都对、整体不动」的失效。
