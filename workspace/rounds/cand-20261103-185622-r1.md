# 第 16 轮（研究线累计；本轮灵感循环第 2 轮）· CAM-ZEST：把「胜任力门控」做成中间件，解耦信任信号的生产与消费，面向人形机器人全身协调的可组合降级

> 检索/复核日期：**2026-11-03（UTC）**。赛事身份不变：宇树 **UniBot 世界挑战赛**（unibot.unitree.com），G1 + Dex1，32 项桌面任务，通才单模型赛道。本轮三个词是「中间件」「人形机器人」「创新点提炼」。**不推倒**第 10–15 轮；CAM-ZEST 是 ZEST-VLA 之上的**中间件层**：把第 15 轮内嵌在 PolicyService 里的信任门、残差计算、FALLBACK 语法、复检逻辑抽离为可热插拔、可多端口复用、可独立版本的 **Competence-Aware Middleware (CAM)**，并把创新点显式登记到 **Innovation Registry**。

## 0. 先给直觉：第 15 轮把「胜任力」算出来了，但锁在单进程里

第 15 轮 ZEST-VLA 做了三件事：
1. **生产信任信号**：三个自监督残差 → conformal/CUSUM → 信任门（TRUST/FALLBACK/HOLD）+ 软胜任力 `c_t`。
2. **消费信任信号**：VOI-MAP 调度器读 `c_t` 和门控模式，决定 SERVO/LOOK/VLA/FALLBACK/COMMIT/HOLD。
3. **执行降级**：FALLBACK 走手工几何原语语法，通过 WAVE-SERVO 执行。

问题在于：**这三件事耦合在同一个 PolicyService 进程里**。
- 真机评测是 **N 端口并发**（每端口独立 websocket、独立 VLA 调用、独立 reset）。第 15 轮要求「每个端口独立维护地图、信念、预算、CUSUM、模式」；这在工程上意味着 **N 份重复代码、N 份独立校准、N 份无法共享的统计功力**。
- **人形机器人 G1** 不只是双臂：它有腰、腿、全身 23–29 个自由度。桌面任务主要用双臂，但 **移动操作**、**全身协调**、**站立平衡** 也是隐性需求。如果以后要把「走到桌前」也纳入同一套信任门，不能把腿部的残差、腰部的 CUSUM、双臂的 FALLBACK 再写一遍新 PolicyService。
- **创新点提炼** 第 15 轮只在文档里；没有机器可读的注册表。评审、复现、消融、迁移学习都要靠人工对着 markdown 找。

所以本轮的直觉是：**把「胜任力门控」做成中间件**。不改变第 15 轮的数学，只改变它的**部署拓扑**和**接口契约**：

> **CAM（Competence-Aware Middleware）是一个独立进程/库，暴露标准 gRPC/ZeroMQ 接口：**
> - **上游（生产者）**：任意残差计算器（双臂、腰、腿、全身）、任意 CUSUM 参数、任意几何原语语法。
> - **下游（消费者）**：任意调度器（VOI-MAP、导航栈、全身控制器）、任意执行器（WAVE-SERVO、腿部 MPC、全身 QP）。
> - **中间状态**：信任门模式、软胜任力、残差向量、校准分位数、版本号——全都**可序列化、可迁移、可共享**。
> - **创新点注册表**：每个残差通道、每个门控参数、每个原语、每个假设（H1–H5）都有唯一 ID、版本、证据等级、证伪条件，**自动生成创新点清单**。

一句话押注：

> **第 15 轮把「胜任力」算对了；本轮把它「装对地方」：抽离为中间件，统一接口，跨端口共享校准，面向全身自由度可组合，并把创新点显式登记。不改数学，只改拓扑——这才是工程能上真机的前提。**

三个可验证创新点（增量）：

1. **中间件化的胜任力总线**：把残差计算、conformal/CUSUM、FALLBACK 语法、复检逻辑封装为 `CAM Core` + `CAM Adapters`；单进程多端口共享校准集、CUSUM 状态、原语成功率；热插拔残差通道、热加载语法规则。**G13 验证「多端口共享校准不退化、热插拔不崩」。**
2. **面向人形全身的可组合降级**：定义 **Body-Part Trust Scope**（部位级信任域）：双臂、腰、腿各自有残差、CUSUM、FALLBACK；支持 **Cross-Part Gating**（跨部位门控，如「腿部不信任 → 双臂只 HOLD」）和 **Whole-Body Fallback Graph**（全身降级图，如「双臂 FALLBACK + 腰对齐 + 腿站立」）。**G14 验证「移动操作任务上跨部位门控有效、不引入死锁」。**
3. **机器可读的创新点注册表**：`innovation_registry.yaml` 记录每个创新点的 ID、符号定义、假设、证据等级、证伪条件、消融对照、版本依赖；CI 自动检查「是否有未注册的创新点声明」「是否有未证伪的假设」「是否有版本漂移」。**G15 验证「注册表完整性检查通过、自动生成的创新点清单与论文一致」。**

三个词怎么落地：

| 词 | 落地 | 不做什么 |
|---|---|---|
| **中间件** | 把 ZEST 核心逻辑抽离为 `cam_core` (Rust/Go) + `cam_py` (Python bindings) + gRPC/ZeroMQ 接口；PolicyService 变薄，只做观测→动作映射 | 不重写残差数学；不引入分布式一致性协议（单机多进程足够）；不做服务发现/注册中心（静态配置） |
| **人形机器人** | 引入 Body-Part Trust Scope、Whole-Body Fallback Graph；复用双臂残差通道模板到腰/腿；G1 真机验证移动操作 | 不做全身 MPC/平衡控制器（那是 L2 事）；不承诺解决行走稳定性；只做「信号生产/消费的标准化」 |
| **创新点提炼** | `innovation_registry.yaml` + `scripts/check_registry.py` + CI gate；每轮必须显式声明增量创新点、关联假设、证据等级 | 不做自动论文生成；不替代人类判断；只做「可追溯、可校验、可消融」的结构化记录 |

## 1. 研究日志：为什么要中间件化

### 1.1 第 15 轮留下的三个「工程债」

```text
E1. 端口隔离 = 代码复制：N 端口 = N 套 CUSUM、N 套校准、N 套原语成功率统计。
E2. 部位耦合 = 扩展难：双臂残差写死在 PolicyService；加腰/腿要改核心调度循环。
E3. 创新点隐性 = 审计难：H1–H5、残差定义、消融对照散落在 markdown 里；CI 无法自动检查。
```

E1 是最痛的：官方评测 **N 个并发端口**，每端口独立 reset、独立 VLA 调用。第 15 轮方案里 `ZestPolicy` 是类实例，每端口 `new` 一份。校准集 `q_α` 每端口各算一遍（浪费）、CUSUM 状态不共享（无法利用其他端口的 ID 证据）、`g_prim` 原语成功率各自统计（样本极少）。真机上 **端口间是同分布的**——同一个 VLA、同一个环境、同一套任务——**校准集完全可以共享，CUSUM 先验可以共享，原语成功率可以共享**。

E2 是扩展性债：G1 是人形机器人。现在只做桌面双臂，但赛事规则没禁止「走到桌前」「调整站姿」「双臂协同搬运重物」。如果把腿部纳入，**腿部的残差（足底压力、ZMP、关节扭矩）、腿部的 CUSUM、腿部的 FALLBACK（站立平衡原语）**，不能再写在双臂的 `select_action` 里。需要**部位级隔离 + 跨部位协调**。

E3 是科学债：第 15 轮写了 H1–H5、三个残差、消融表，**但这些都不是机器可读的**。换人、换轮、做消融时，靠人工对着文档核对「这轮是不是动了 r_geo」「H3 到底证伪没」。一个严谨的研究循环，**创新点必须是结构化数据，能被 CI 校验**。

### 1.2 三个新判断

1. **中间件不是「加层」，是「解耦生产与消费」**。第 15 轮的 `ZestPolicy` 既生产信任信号（残差→CUSUM），又消费信任信号（调度器读 `c_t`/mode）。CAM 把生产侧做成 **Residual Providers**（可插拔：双臂残差、腿部残差、腰部残差、甚至外部视觉模块），把消费侧做成 **Trust Consumers**（VOI-MAP 调度器、导航栈、全身 QP 控制器），中间用 **Trust Bus**（gRPC/ZeroMQ topic）连接。生产侧不关心谁消费，消费侧不关心怎么生产，**只关心契约**：`TrustSignal{mode, c_t, residuals[], timestamp, version}`。

2. **人形机器人的「部位」是天然的信任隔离单元**。双臂操作、腰部对齐、腿部站立/行走，各有各的残差分布、各自的 OOD 模式、各自的 FALLBACK 原语。但它们**不是独立的**——双臂抓重物需要腰配合、腿部移动需要双臂收敛。**Cross-Part Gating** 正是中间件层要解决的：腿部 `mode=FALLBACK` 时，双臂自动禁用 `SERVO` 只允许 `HOLD`/`LOOK`；腰部 `c_t` 低时，双臂的 `P_succ(SERVO)` 乘以腰部的 `c_t`。这在单体 PolicyService 里会写成 `if leg.mode == FALLBACK: arm.allowed.remove(SERVO)`——**耦合在业务逻辑里，扩展一次改一遍**。中间件层把它做成 **策略规则引擎**：`rule: if part(leg).mode == FALLBACK then part(arm).allow -= SERVO`，热加载、可审计、可测。

3. **创新点注册表是「可证伪」的工程化前提**。第 15 轮 H4 合成实验证伪后剪枝了 Beta 后验——**这是好事，但靠人工记在文档里**。如果有一个 `innovation_registry.yaml`，里面写：
```yaml
- id: "ZEST.beta_posterior"
  status: "falsified"
  evidence: "exp/zest_sim.py: H4 CI crosses zero"
  superseded_by: "ZEST.cusum_recheck"
  round: 15
```
下一轮新人一来 `cat registry.yaml` 就知道「Beta 已死、CUSUM+复检存活」，不用读十万字 markdown。CI 还能自动检查：**「主算法引用的创新点必须在注册表里且 status != falsified」「每个假设必须有证伪条件」「消融对照必须注册」**。这才是「创新点提炼」的工程落地。

### 1.3 与第 15 轮的关系

| 层 | 第 15 轮 ZEST-VLA | 第 16 轮 CAM-ZEST |
|---|---|---|
| 部署 | PolicyService 进程内类 | 独立进程 `cam_core` + gRPC/ZeroMQ + Python bindings |
| 端口共享 | 无（每端口独立实例） | **校准分位数、CUSUM 先验、原语成功率、语法规则全共享** |
| 部位支持 | 仅双臂（硬编码） | **Body-Part Trust Scope**：双臂/腰/腿可插拔，统一接口 |
| 跨部位协调 | 无（或硬编码 if-else） | **Cross-Part Gating Rules**：热加载、可审计、可测 |
| 创新点记录 | Markdown 文档 | **`innovation_registry.yaml` + CI 校验** |
| 残差计算 | 内嵌在 `compute_residuals()` | **Residual Provider 插件**：双臂/腰/腿/外部视觉独立开发 |
| FALLBACK 语法 | 硬编码在 `plan_primitives()` | **Primitive Registry**：版本化、热加载、域检查插件化 |
| 校准流程 | 离线脚本手跑 | **CAM Calibration Service**：自动采集、分位数计算、版本发布 |

**保留**：第 15 轮所有数学（残差定义、conformal/CUSUM、软胜任力、VOI 调度公式、几何原语语法、失败模式分类、命题 1–8、合成实验框架）。
**升级**：从「单进程单部位」→「中间件多端口多部位」；从「隐性创新点」→「显式注册表 + CI 校验」。
**剪枝**：不做分布式一致性（单机多进程足够）；不做服务发现（静态配置）；不引入新数学。

## 2. 机制草图（形式化见产物区）

### 2.1 CAM 总线契约

**TrustSignal**（核心消息，所有消费者订阅）：
```protobuf
message TrustSignal {
  string port_id = 1;           // 端口标识
  string part_id = 2;           // 部位：arm_left, arm_right, waist, leg_left, leg_right, whole_body
  TrustMode mode = 3;           // TRUST / FALLBACK / HOLD / PROBE
  float c_t = 4;                // 软胜任力 [0,1]
  repeated Residual residuals = 5;  // 各通道归一化残差
  int64 timestamp_us = 6;       // 单调递增
  string version = 7;           // CAM 版本号
  string calibration_version = 8; // q_α 版本
}

enum TrustMode { TRUST=0; FALLBACK=1; HOLD=2; PROBE=3; }
message Residual { string name = 1; float z_score = 2; float raw = 3; float scale = 4; }
```

**ResidualProvider 接口**（生产者实现，每部位一个）：
```protobuf
service ResidualProvider {
  rpc ComputeResiduals(ResidualRequest) returns (ResidualResponse);
  rpc GetSchema(Empty) returns (ResidualSchema);  // 通道名、尺度估计器类型、权重
}
```

**TrustConsumer 接口**（消费者实现，如 VOI-MAP、导航栈）：
```protobuf
service TrustConsumer {
  rpc OnTrustSignal(TrustSignal) returns (ActionAdm); // 返回允许动作集
  rpc GetPolicy(Empty) returns (TrustPolicy);         // 该消费者的门控策略
}
```

**PrimitiveRegistry 接口**（FALLBACK 语法管理）：
```protobuf
service PrimitiveRegistry {
  rpc PlanPrimitives(PrimitivePlanRequest) returns (PrimitivePlan);
  rpc CheckDomain(DomainCheckRequest) returns (DomainCheckResponse);
  rpc ReportOutcome(PrimitiveOutcome) returns (Empty); // 更新 g_prim
}
```

### 2.2 多端口共享状态

CAM 进程维护 **共享只读状态**（热加载、版本化）：
- `q_α`：校准分位数，来自 **Calibration Service**（离线/在线混合）。
- `CUSUM_Prior`：`α, k, h` 的先验分布（用其他端口的 ID 数据做经验贝叶斯）。
- `PrimitiveStats`：`g_prim` 先验 + 在线更新（所有端口汇聚）。
- `GrammarRules`：几何原语语法规则（热加载，版本化）。
- `CrossPartRules`：跨部位门控规则（热加载，可审计）。

**每端口每部位私有状态**（CAM 进程内隔离，不跨端口共享）：
- `S_b`：CUSUM 统计量。
- `mode`：当前信任模式。
- `fallback_dwell`：驻留计数。
- `surprise_window`：滑动窗口惊讶率。

**关键点**：共享状态是**只读+版本化**的，私有状态是**完全隔离**的。这既利用了端口间的同分布性（共享校准、先验、原语统计），又保证了端口间无干扰（CUSUM 状态、模式独立）。

### 2.3 Body-Part Trust Scope 与 Cross-Part Gating

定义 **部位集合** `P = {arm_l, arm_r, waist, leg_l, leg_r, whole_body}`。

每个部位 `p ∈ P` 有独立的：
- `ResidualProvider_p`：计算该部位的残差向量 `r^p`。
- `CUSUM_p`：`S^p_b = max(0, S^p_{b-1} + e^p_b - α^p - k^p)`。
- `mode^p ∈ {TRUST, FALLBACK, HOLD, PROBE}`。
- `c^p_t`：软胜任力。
- `FallbackPrimitives_p`：该部位的几何原语库（双臂用第 15 轮语法，腰用 `ALIGN/ROTATE`，腿用 `STAND/STEP/BALANCE`）。

**Cross-Part Gating Rule**（示例，YAML 热加载）：
```yaml
rules:
  - id: "leg_fallback_disarms_arms"
    condition: "part(leg_l).mode == FALLBACK or part(leg_r).mode == FALLBACK"
    action:
      - "part(arm_l).allow -= SERVO"
      - "part(arm_r).allow -= SERVO"
      - "part(arm_l).allow -= FALLBACK"
      - "part(arm_r).allow -= FALLBACK"
  - id: "waist_low_competence_penalizes_arms"
    condition: "part(waist).c_t < 0.5"
    action:
      - "part(arm_l).c_t *= part(waist).c_t"
      - "part(arm_r).c_t *= part(waist).c_t"
  - id: "whole_body_hold_on_any_hold"
    condition: "any p: part(p).mode == HOLD"
    action:
      - "all p: part(p).allow = {HOLD}"
```

**执行语义**：CAM 核心每控制周期（5 步块边界）评估所有规则，生成各部位的 `allowed_actions^p`，发布 `TrustSignal`。消费者（VOI-MAP 调度器、腿部 MPC）读取各自部位的 `allowed_actions` 做决策。

### 2.4 Whole-Body Fallback Graph

当多部位同时进入 FALLBACK，需要**协调执行顺序、同步点、安全回退**。定义 **Fallback Graph** `G = (V, E)`：
- `V`：原语节点，带部位标签、`precondition`、同步约束。
- `E`：依赖边（顺序）、同步边（并行等待）、冲突边（互斥资源）。

示例：移动操作「走到桌前 → 双臂抓取 → 走回目标 → 放置」的全身降级图：
```yaml
graph:
  nodes:
    - id: "nav_to_table"     part: leg   prim: "NAVIGATE"    sync: "pre_grasp"
    - id: "waist_align"      part: waist prim: "ALIGN"       sync: "pre_grasp"
    - id: "arm_l_reach"      part: arm_l prim: "REACH"       sync: "pre_grasp"
    - id: "arm_r_reach"      part: arm_r prim: "REACH"       sync: "pre_grasp"
    - id: "dual_grasp"       part: arms  prim: "DUAL_GRASP"  deps: ["pre_grasp"]
    - id: "nav_to_target"    part: leg   prim: "NAVIGATE"    deps: ["dual_grasp"]
    - id: "dual_place"       part: arms  prim: "DUAL_PLACE"  deps: ["nav_to_target"]
  edges:
    - ["nav_to_table", "pre_grasp"]  # 顺序
    - ["waist_align", "pre_grasp"]
    - ["arm_l_reach", "pre_grasp"]
    - ["arm_r_reach", "pre_grasp"]
    - ["pre_grasp", "dual_grasp"]    # 同步汇聚
    - ["dual_grasp", "nav_to_target"]
    - ["nav_to_target", "dual_place"]
```

CAM 的 `FallbackExecutor` 按拓扑序调度，**同步点阻塞直到所有前驱完成**，冲突边互斥。这比第 15 轮的单部位线性队列强得多：它天然支持**全身协调降级**。

```math
\sigma^p_k = \text{MAD}_W(\{r^p_{k,b-W+1}, ..., r^p_{k,b}\}) + \epsilon_k
```

### 2.3 CUSUM 与信任门（每端口每部位独立，参数来自共享先验）

共享先验：`Prior = (α_0, k_0, h_0, Σ_α, Σ_k, Σ_h)` —— 用其他端口的 ID 数据做经验贝叶斯估计。
每端口每部位可微调：`α^p_{π} = α_0 + δ_α` 等（δ 很小，在线估计）。

CUSUM 递推（同第 15 轮，仅加部位/端口下标）：
```math
e^p_{π,b} = \mathbb{1}[s^p_{π,b} > q^p_α], \quad s^p = \sum_k w^p_k z^p_k
```
```math
S^p_{π,b} = \max(0, S^p_{π,b-1} + e^p_{π,b} - α^p_π - k^p_π)
```
```math
mode^p_{π,b} =
\begin{cases}
TRUST & S^p_{π,b} \le h^p_π \land mode^p_{π,b-1} \neq FALLBACK \\
FALLBACK & S^p_{π,b} > h^p_π \\
PROBE & mode^p_{π,b-1} = FALLBACK \land dwell^p_{π,b} \ge r^p \\
TRUST & mode^p_{π,b-1} = PROBE \land e^p_{π,b} = 0 \\
FALLBACK & mode^p_{π,b-1} = PROBE \land e^p_{π,b} = 1 \\
HOLD & \text{安全触发/预算耗尽}
\end{cases}
```
软胜任力：
```math
c^p_{π,b} = 1 - \frac{1}{W} \sum_{i=0}^{W-1} e^p_{π,b-i}
```

### 2.4 Cross-Part Gating Rules（热加载、可审计）

规则集 `R = {r_1, ..., r_M}`，每条规则：
```math
r_j = (id_j, \text{condition}_j, \text{action}_j, \text{priority}_j)
```
- `condition_j`：布尔表达式，原子谓词为 `part(p).mode == M`、`part(p).c_t < θ`、`part(p).allow ∋ A`。
- `action_j`：原子操作集合，`part(p).allow += A`、`part(p).allow -= A`、`part(p).c_t *= factor`、`part(p).mode := M`。
- `priority_j`：整数，高优先级后执行（覆盖低优先级）。

**评估算法**（每控制周期）：
```python
def evaluate_cross_part_rules(rules, part_states):
    # part_states: {p: {mode, c_t, allow, ...}}
    allow = {p: set(base_allow[p]) for p in P}  # 基础允许集来自各部位自身 mode
    c_t = {p: part_states[p].c_t for p in P}
    mode = {p: part_states[p].mode for p in P}
    
    for rule in sorted(rules, key=lambda r: r.priority):
        if eval_condition(rule.condition, part_states):
            for action in rule.actions:
                apply_action(action, allow, c_t, mode)
    return allow, c_t, mode
```

### 2.5 Whole-Body Fallback Graph（全身降级图）

图 `G = (V, E)`，节点 `v ∈ V`：
```math
v = (id, part, primitive, args, precond, sync_group, deps, conflicts)
```
- `part ∈ P`：所属部位。
- `primitive`：原语名（来自 `PrimitiveRegistry`）。
- `args`：参数绑定（来自语义地图 `M`）。
- `precond`：前置条件（目标可见、可达、自由空间、夹爪空闲等）。
- `sync_group`：同步组 ID（同组节点并行，汇聚后继续）。
- `deps`：顺序依赖（前驱节点 ID 列表）。
- `conflicts`：互斥资源（如同一夹爪、同一末端执行器）。

边 `E` 隐含在 `deps`、`sync_group`、`conflicts` 中。

**调度算法**（拓扑序 + 同步屏障 + 互斥锁）：
```python
class FallbackExecutor:
    def __init__(self, graph, primitive_registry):
        self.graph = graph
        self.registry = primitive_registry
        self.completed = set()
        self.running = {}
        self.locks = {resource: Lock() for resource in all_resources}
    
    def step(self, part_states, obs):
        # 1. 找可运行节点：前驱完成、同步组就绪、前置条件满足、资源可获取
        ready = []
        for v in self.graph.nodes:
            if v.id in self.completed or v.id in self.running:
                continue
            if not all(d in self.completed for d in v.deps):
                continue
            if v.sync_group and not self._sync_group_ready(v.sync_group):
                continue
            if not v.precond.check(obs, part_states):
                continue
            if not self._try_acquire_locks(v.conflicts):
                continue
            ready.append(v)
        
        # 2. 启动就绪节点（按优先级/部位并行）
        for v in ready:
            self._launch_primitive(v, part_states, obs)
        
        # 3. 检查运行中节点是否完成
        for v_id, handle in list(self.running.items()):
            if handle.is_done():
                self.completed.add(v_id)
                self._release_locks(handle.conflicts)
                del self.running[v_id]
        
        return len(self.completed) == len(self.graph.nodes)
```

### 2.7 校准服务

**离线校准**（赛前）：
- 在 `K` 个已知 ID 任务上，每任务 `E` 个 episodes，收集全端口、全部位的残差分数 `s^p`。
- 计算每部位 `q^p_α = Quantile_{1-α}(s^p)`，发布版本 `v_cal`。

**在线校准**（评测中，可选）：
- 每端口每部位维护 ID 残差滑动窗口（用 `mode=TRUST` 且 `c_t > 0.9` 的块）。
- 定期重新计算 `q^p_α`，若变化 > 阈值则发布新版本 `v_cal'`（热加载，不中断推理）。

**经验贝叶斯先验**（共享 CUSUM 参数）：
- 收集所有端口 ID 下的 `e_b` 序列，估计 `α` 的后验分布 `Beta(a, b)`。
- 取后验均值作为 `α_0`，方差作为 `Σ_α`；同理 `k, h`。
- 新端口启动时初始化 `α^p_π = α_0`，运行中可微调。

### 2.8 创新点注册表

`innovation_registry.yaml`（见 §1.3 机制草图），配合 `scripts/check_registry.py`：

**CI 校验规则**：
1. **完整性**：主算法引用的每个创新点 ID 必须在注册表中且 `status != falsified`。
2. **假设关联**：每个创新点必须有 `hypothesis_refs`，每个假设必须有 `falsification` 条件。
3. **证据等级一致性**：`evidence_level=C` 的创新点必须有对应的门 `Gxx` 验证计划。
4. **版本依赖**：`depends_on` 指向的创新点版本必须 ≤ 当前版本。
5. **消融对照**：`ablation_refs` 中的每个对照必须在实验脚本中实现。
6. **无孤儿假设**：注册表中每个假设必须被至少一个创新点引用。

```rust
// CAM Core 主循环（Rust 伪代码，实际用 tokio + tonic gRPC）
async fn cam_main() {
    // 1. 加载共享状态
    let shared = Arc::new(RwLock::new(load_shared_state()));
    
    // 2. 启动 gRPC 服务
    let grpc_server = start_grpc_server(shared.clone());
    
    // 3. 启动 ZeroMQ Pub/Sub（TrustSignal 广播）
    let zmq_pub = start_zmq_publisher();
    
    // 4. 每端口每部位状态机（并发任务）
    for port in ports {
        for part in PARTS {
            let shared = shared.clone();
            let zmq_pub = zmq_pub.clone();
            tokio::spawn(async move {
                run_part_state_machine(port, part, shared, zmq_pub).await;
            });
        }
    }
    
    // 5. 校准服务后台任务
    tokio::spawn(calibration_service(shared.clone()));
    
    // 6. 原语注册表后台任务
    tokio::spawn(primitive_registry_service(shared.clone()));
    
    // 7. 等待信号
    wait_for_shutdown().await;
}

async fn run_part_state_machine(port: PortId, part: PartId, shared: SharedState, pub: ZmqPublisher) {
    let mut state = PartPrivateState::new();
    let mut calib = shared.read().calibration.get(&part).cloned();
    let mut prior = shared.read().cusum_prior.get(&part).cloned();
    
    loop {
        // 等待 ResidualRequest（来自 PolicyService）
        let req = wait_residual_request(port, part).await;
        
        // 1. 计算残差（调用 ResidualProvider 插件）
        let residuals = call_residual_provider(part, &req).await;
        
        // 2. 归一化（用共享 MAD 尺度或本地滑动 MAD）
        let z_scores = normalize_residuals(residuals, &state.mad_windows);
        
        // 3. 计算融合分数
        let s = fuse_scores(z_scores, &part_weights(part));
        
        // 4. CUSUM 更新
        let surprise = (s > calib.q_alpha) as u8;
        state.surprise_window.push(surprise);
        state.cusum = (state.cusum + surprise as f32 - prior.alpha - prior.k).max(0.0);
        
        // 5. 模式更新（含复检）
        state.mode = update_mode(state.mode, state.cusum, surprise, &prior);
        
        // 6. 软胜任力
        state.c_t = 1.0 - state.surprise_window.mean();
        
        // 7. 发布 TrustSignal
        let signal = TrustSignal {
            port_id: port,
            part_id: part,
            mode: state.mode,
            c_t: state.c_t,
            residuals: z_scores.into_iter().map(|(n, z)| Residual { name: n, z_score: z, ... }).collect(),
            timestamp_us: now_us(),
            version: CAM_VERSION,
            calibration_version: calib.version,
        };
        pub.publish(&signal).await;
        
        // 8. 定期同步共享状态（校准版本、先验、原语统计）
        if should_sync() {
            let new_shared = shared.read().clone();
            calib = new_shared.calibration.get(&part).cloned().unwrap_or(calib);
            prior = new_shared.cusum_prior.get(&part).cloned().unwrap_or(prior);
        }
    }
}
```

### 3.2 PolicyService（薄客户端）

```python
class ThinPolicyService:
    def __init__(self, port_id, cam_grpc_addr, cam_zmq_addr):
        self.port_id = port_id
        self.cam_stub = CAMStub(grpc_channel(cam_grpc_addr))
        self.zmq_sub = zmq_subscribe(cam_zmq_addr, f"trust.{port_id}.*")
        self.part_obs_splitter = PartObservationSplitter()
        self.allowed_actions = {p: set() for p in PARTS}
        self.c_t = {p: 1.0 for p in PARTS}
        self.mode = {p: "TRUST" for p in PARTS}
    
    def get_action(self, obs):
        # 1. 分发观测到各部位
        part_obs = self.part_obs_splitter.split(obs)
        
        # 2. 请求残差计算（异步，非阻塞）
        for part in PARTS:
            if self.mode[part] in {"TRUST", "PROBE"}:
                self.cam_stub.ComputeResiduals.future(ResidualRequest(
                    port_id=self.port_id, part_id=part, obs=part_obs[part]
                ))
        
        # 3. 消费最新 TrustSignal（从 ZeroMQ 缓存读取）
        self._consume_latest_signals()
        
        # 4. 评估跨部位规则（本地也有规则副本，或从 CAM 获取）
        self._evaluate_cross_part_rules()
        
        # 5. 每部位决策
        actions = {}
        for part in PARTS:
            actions[part] = self._decide_part_action(part, part_obs[part])
        
        # 6. 合并动作（双臂同步、全身协调）
        return self._merge_actions(actions, obs)
    
    def _decide_part_action(self, part, obs):
        allowed = self.allowed_actions[part]
        c_t = self.c_t[part]
        mode = self.mode[part]
        
        if mode == "HOLD" or not allowed:
            return HoldAction()
        
        if "SERVO" in allowed and mode == "TRUST":
            return ServoAction(self.vla_plan[part])
        
        if "FALLBACK" in allowed and mode == "FALLBACK":
            return FallbackAction(self.primitive_queue[part])
        
        if "LOOK" in allowed:
            return LookAction(self._compute_look_target(part))
        
        if "VLA" in allowed:
            return VLARequestAction()
        
        return HoldAction()
    
    def _consume_latest_signals(self):
        while self.zmq_sub.has_message():
            signal = self.zmq_sub.recv()
            part = signal.part_id
            self.mode[part] = signal.mode
            self.c_t[part] = signal.c_t
            self.residuals[part] = signal.residuals
    
    def _evaluate_cross_part_rules(self):
        # 本地评估 CrossPartRules（从 CAM 热加载缓存）
        part_states = {p: {"mode": self.mode[p], "c_t": self.c_t[p], "allow": self.allowed_actions[p]} for p in PARTS}
        allow, c_t, mode = evaluate_cross_part_rules(self.cross_part_rules, part_states)
        self.allowed_actions = allow
        self.c_t = c_t
        self.mode = mode
```

## 4. 性质、复杂度与正确性

### 4.1 中间件不改变第 15 轮数学性质

**命题 9（数学等价性）**：对于任意端口 `π`、部位 `p`，若 `ResidualProvider_p` 实现与第 15 轮 `compute_residuals` 相同的函数 `ϕ_p`，共享 `q_α` 与第 15 轮离线校准值相同，CUSUM 参数 `α, k, h` 与第 15 轮相同，则 CAM Core 产生的 `TrustSignal` 序列与第 15 轮 `ZestPolicy` 单进程版本逐块完全一致。

**证明**：CAM Core 的每部位状态机正是第 15 轮 `ZestPolicy.on_block_finished` 的逻辑抽离；输入相同（观测、动作、地图、上一计划）、参数相同、递推相同，输出必然相同。网络传输只增加延迟，不改变数值。∎

**推论**：第 15 轮命题 1–8（标签无关性、ID 假警报控制、OOD 检测延迟、安全降级、ID 非退化、瞬态恢复、零样本组合条件保证、OOD-G 不可检测性、早期中止成本上界）全部保持。

### 4.2 多端口共享校准的统计性质

**命题 10（共享校准的方差降低）**：设 `N` 个端口 ID 残差分数 `s_{π,b} ~ F_ID` 独立同分布。第 15 轮每端口独立取 `n` 样本分位数 `q_{α,π}`，方差 `Var(q_{α,π}) ≈ α(1-α) / (n f(q_α)^2)`。CAM 共享校准汇聚 `Nn` 样本取 `q_{α,shared}`，方差 `Var(q_{α,shared}) ≈ α(1-α) / (Nn f(q_α)^2) = Var(q_{α,π}) / N`。

**证明**：经验分位数渐近正态性，样本量乘 `N` 方差除 `N`。∎

**边界**：要求端口间 ID 分布**可交换**（同一 VLA、同一环境、同一任务分布）。若某端口系统性分布漂移（如相机去焦），共享校准反而有害。缓解：在线监控各端口 ID 惊讶率，若某端口显著偏离则回退独立校准。

### 4.3 跨部位门控的安全性

**命题 11（Cross-Part Gating 单调性）**：设基础允许集 `base_allow(p, mode)` 关于 `mode` 单调：`TRUST ⊇ PROBE ⊇ FALLBACK ⊇ HOLD`（动作集包含关系）。Cross-Part Rules 只做 `allow -= A`、`c_t *= factor (≤1)`、`mode := HOLD`。则最终允许集 `allow(p) ⊆ base_allow(p, mode(p))`。

**证明**：规则动作仅删除动作、降低胜任力、强制 HOLD，不增加动作。∎

**推论**：跨部位门控**只会更保守**，不会引入第 15 轮没有的不安全动作。安全性继承第 15 轮命题 4。

### 4.4 全身降级图的活性

**命题 12（Fallback Graph 无死锁充分条件）**：若 `G = (V, E)` 满足：
1. `deps` 构成 DAG（无循环依赖）。
2. 每个 `sync_group` 内节点无 `conflicts` 互斥（或互斥资源可预分配）。
3. 每个节点的 `precond` 在有限步内可满足（环境不主动对抗）。
则 `FallbackExecutor` 保证在有限步内完成所有节点或明确报告不可满足前置条件。

**证明**：DAG 拓扑序保证顺序依赖无循环；同步组内并行节点无互斥保证可同时推进；前置条件有限步可满足保证每个节点最终可启动。∎

**工程约束**：图构建时静态检查 DAG、互斥冲突；运行时监控节点超时，超时则标记失败、释放锁、触发上层重规划。

### 4.5 创新点注册表 CI 校验的完备性

**命题 13（CI 校验捕获所有声明违规）**：设注册表 `R`、主算法代码 `C`、实验脚本 `E`。CI 规则 1–6 在 `R, C, E` 上运行。若 CI 通过，则：
- `C` 中引用的每个创新点 ID 存在于 `R` 且 `status != falsified`。
- `R` 中每个创新点有 `hypothesis_refs`，每个假设有 `falsification`。
- `R` 中 `evidence_level=C` 的创新点有对应门 `Gxx`。
- `R` 中版本依赖无环、版本号单调。
- `E` 中实现了 `R` 中所有 `ablation_refs` 对照。
- `R` 中无孤儿假设。

**证明**：CI 规则直接编码上述条件，遍历 AST/正则匹配代码中的创新点引用、实验脚本中的消融函数名。∎

**边界**：CI 只能检查**显式引用**（如 `innovation_id("CAM.trust_bus")` 标注）。若代码隐式实现了未注册的创新点，CI 无法捕获。缓解：代码审查时强制要求显式标注。

**脚本**：`exp/cam_sim.py`（扩展第 15 轮 `zest_sim.py`）。

**生成模型**：
- `N=10` 端口，每端口 `E=100` ID episodes，`E=50` OOD-E episodes。
- 端口间 ID 分布同分（`F_ID` 相同），但有 `10%` 端口有轻微系统性偏移（模拟相机去焦）。
- 共享校准：汇聚所有端口 ID 样本取 `q_α`。
- 独立校准：每端口各取自己的 ID 样本取 `q_α`。
- 指标：ID 假警报率、OOD-E 检测延迟、分位数估计方差。

**预期结果（合成）**：
| 指标 | 独立校准 | 共享校准 | 判读 |
|---|---:|---:|---|
| ID 假警报率 (无偏移端口) | 11.8% | 10.2% | 共享更好 |
| ID 假警报率 (偏移端口) | 12.1% | 15.6% | 共享更差（需检测偏移回退） |
| 分位数方差 | 0.023 | 0.002 | 共享降低 10x |
| OOD-E 检测延迟 | 2.1 块 | 2.0 块 | 相当 |

**缓解策略验证**：加入「端口偏移检测」（监控各端口 ID 惊讶率，若 > `α + 3σ` 则标记该端口回退独立校准）。验证检测准确率 > 90%、不误伤正常端口。

### 5.5 合成实验：跨部位门控

**场景**：移动操作任务「走到桌前 → 抓取 → 走回目标 → 放置」。
- 腿部：`NAVIGATE` 原语，偶尔 OOD-E（地形未建图、动态避障失败）触发 `FALLBACK`（`STAND`/`REPLAN`）。
- 腰部：`ALIGN` 原语，配合双臂抓取。
- 双臂：`REACH`/`GRASP`/`PLACE`。

**基线**：无跨部位门控（腿部 FALLBACK 时双臂继续 SERVO）。
**实验组**：启用 `leg_fallback_disarms_arms` 规则。

**指标**：任务成功率、碰撞率、双臂在腿部 FALLBACK 期间的 SERVO 执行次数。

**预期**：实验组成功率 +15pp、碰撞率 -80%、双臂误动作归零。

## 6. 风险与合规

### 6.1 单模型合规

| 模式 | 做法 | 风险 |
|---|---|---|
| C1 确定性几何 | CAM Core 全是确定性函数 + 在线一维统计 | 最低 |
| C2 符号 backchannel | TrustSignal、CrossPartRules 都是符号/标量 | 低 |
| C3 同 checkpoint 特征 | ResidualProvider 可复用 VLA encoder（如需视觉残差） | 低–中 |
| 禁止 | 第二个学习模型、在线权重更新、训练失败检测器 | 高 |

**关键声明**：CAM 不训练任何新参数；共享校准是**统计量汇聚**，不是学习；Cross-Part Rules 是**手工/配置规则**，不是学习策略；Primitive Registry 是**手工控制器库**，不是第二个策略网络。完全符合单模型规则。

### 6.2 风险表

| 风险 | 影响 | 缓解 |
|---|---|---|
| **中间件延迟超标** | 真机关键路径 p99 > 2ms 导致控制不稳 | **in-process 模式默认**；gRPC 仅调试；压测前对比 |
| 共享校准遭遇异质端口 | 个别端口相机/标定差导致共享校准有害 | 在线偏移检测 + 自动回退独立校准 |
| 跨部位规则冲突/死锁 | 规则优先级设计不当导致允许集振荡 | 静态分析规则冲突；运行时监控模式切换频率 |
| Fallback Graph 死锁 | 依赖图有环、同步组互斥 | 构建时 DAG 检查；运行时超时熔断 |
| Primitive Registry 热加载竞态 | 执行中换语法导致原语参数错 | 版本化 + 双缓冲：只在原语边界切换版本 |
| 创新点注册表维护成本高 | 研发被文档工作拖累 | CI 自动化覆盖 90%+ 检查；仅关键节点人工审计 |
| 零拷贝序列化复杂 | Rust-Python 边界零拷贝难调试 | 用 `pyo3` + `numpy` 数组零拷贝；必要时退回 `memcpy` |
| 部位级残差前端未就绪 | 腰/腿残差 Provider 真机未集成 | 分阶段：先双臂 CAM 化（G17/G18），再加腰/腿（G19） |

### 6.3 已知失效模式

| 场景 | 会发生什么 | CAM 行为 | 结果 |
|---|---|---|---|
| 单端口相机去焦（系统性偏移） | 该端口 ID 残差分布右移 | 偏移检测触发 → 该端口回退独立校准 | 其余端口继续受益共享校准 |
| 腿部导航 OOD-E（动态障碍物） | 腿部 `mode=FALLBACK`，触发 `STAND` | Cross-Part Rule 禁用双臂 `SERVO/FALLBACK` | 双臂安全 HOLD，避免移动中抓取碰撞 |
| 腰部对齐失败（扭矩过大） | 腰部 `c_t` 降至 0.3 | Rule `waist_low_competence_penalizes_arms` 降低双臂 `c_t` | 双臂调度器倾向 `LOOK`/`VLA` 重规划，不盲目执行 |
| 双臂 FALLBACK 中 Primitive Registry 热加载 | 新语法版本发布 | 双缓冲：当前原语队列跑完再切版本 | 无执行中断，版本切换平滑 |
| 评测中发现新 OOD-G 类型 | VLA+地图共同 grounding 错，残差正常 | 无法检测（命题 7 边界） | 只能靠外部语义检查/任务清单，CAM 无法解决 |

## 8. 一句话押注

**第 15 轮把「胜任力」算对了；本轮把它「装对地方」：抽离为中间件，统一接口，跨端口共享校准，面向全身自由度可组合，并把创新点显式登记。不改数学，只改拓扑——这才是工程能上真机的前提。**

## 9. 本轮最大的风险

**中间件引入的额外跳转（gRPC/ZeroMQ）在真机关键路径上可能超出延迟预算（p99 > 2ms），导致不得不退回 in-process library，从而失去「多进程共享状态、热插拔、跨语言」的核心优势。** 这是典型的「架构纯度 vs 实时性」权衡，必须在 G13 真机压测前用 `cam_core` 的 in-process 模式和 gRPC 模式对比延迟分布，提前做决定。
