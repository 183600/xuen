# 第 4 轮（新循环）· DEADLINE-PLAN：把 180 秒、N 个端口和里程碑预算当成一等约束

> 检索/复核日期：**2026-10-29（UTC）**。赛事身份已再次核实：宇树 **UniBot 世界挑战赛**（unibot.unitree.com），G1 + Dex1，32 项桌面任务，通才单模型赛道，选手自部署 + 官方远程真机 API；不是 PLM UniBot，也不是 OpenUniBot。状态文件基线仍是第 12 轮 CHUNK-SERVO；本轮是新循环第 4 轮，不推倒它，而是在它上面加一层「时间/资源/计划」：CHUNK-SERVO 决定「怎么在 5 步内闭环」，DEADLINE-PLAN 决定「H 选多大、每个 chunk 真正执行几步、什么时候重规划、什么时候放弃，以及 N 个端口如何共享一张 GPU 而不让任何一个端口饿死」。

## 0. 先给结论：榜首不到 30%，缺的不只是最后 3 厘米，还有「预算」这一层

截至 2026-10-29，官网首页、排行榜页、运行记录页都显示「即将发布 / Coming Soon」；详情页 32 个任务视频全部是「测试视频占位，后续可替换为真实视频文件」。此前榜单 JSON 里的 8 个模型——MolmoAct2 29.7%、WALL-OSS-0.5 28.5%、DreamZero 27.9%、Spirit-v1.5 25.9%、DM0 23.5%、π0.5 22.8%、GigaBrain-0 22.6%、GR00T N1.5 20.5%——只能当**预览上限/难度信号**，不能当 live SOTA，也不能反推任务难度表。这个判断本轮再次成立。

但「榜首不到 30%」这件事仍然有意义：头尾只差 9.2pp，说明这不是某个架构领先，而是所有模型共享同一个瓶颈。第 12 轮把这个瓶颈定位为「最后 3 厘米的开环执行」，这说对了一半。另一半是：

1. **时间预算没有被建模。** 每个 trial 上限 **180 秒**，超时记失败；32 任务 ×10 次 = 320 trials。VLA 不知道现在第几步、还剩多少秒、下一步值不值得赌。
2. **算力/网络预算没有被建模。** 评测跨 **N 台机器人**，提交要从 **8765** 起暴露 N 个连续端口；不同端口可能同时调用。共享一张 GPU 时，batch、排队、图像预处理、网络抖动会把 p99 延迟放大；官方明确记录每次 `get_action` 的延迟和波动，作为结果可信度的一部分。
3. **成功预算没有被建模。** 任务不是一条指令，而是 2–5 个里程碑；最后一个里程碑失败，前面全白做。模型没有「这一步成功概率多高、要不要先恢复、要不要换顺序」的显式决策。

所以本轮的押注是 **DEADLINE-PLAN**：

> 用 33k 成功演示离线建「里程碑图 + 时长/成功分布」；用保形/贝塔下界把每个里程碑的成功概率变成可用的风险预算；在线用一个小规模动态规划决定「继续 / 重规划 / 恢复 / 放弃」；用一个机器人时间调度器把 N 个端口的 chunk 请求排成不饿死的批次；用一个每端口独立、CPU 轻量、带看门狗的嵌入式运行时保证 p99。

一句话：**把「成功率」从一个模型指标，变成一个由计划、期限和调度共同决定的系统指标。**

三个灵感词怎么落到方案里：

| 灵感词 | 落到哪里 | 不做什么 |
|---|---|---|
| **成功率** | 里程碑级成功概率 + 保形/贝塔下界 + 机会约束 DP；用单任务通道做配对 A/B | 不把预览榜单当 SOTA；不用 +1–2pp 做结论 |
| **任务规划** | 2–5 节点里程碑图 + 计划修复 + 恢复原语；VLA 只负责运动先验 | 不做 32 个任务各一个策略；不做完整 TAMP 求解器 |
| **嵌入式系统** | 每端口实时 supervisor + 共享 GPU 的机器人时间调度 + 静态内存/看门狗/p99 | 不把「嵌入式」误解成在 G1 MCU 上跑 6B；不做 30Hz 广域网伺服 |

## 1. 本轮核实/修正的事实（只列会改变方案的）

### 1.1 榜单：仍是预览，不是 live SOTA

本轮用 `r.jina.ai` 渲染官网，得到的状态是：

- 首页排行榜区：**「即将发布 Coming Soon」**，没有 8 行数据。
- 排行榜页：同样是「即将发布 Coming Soon」。
- 运行记录页：仍显示 `256 / 256` 条预览记录，但每条都是同一个 8 模型 ×32 任务的合成表。
- 详情页 `details.html?model=MolmoAct2&user=DexHacker`：32 个任务视频全部写「测试视频占位，后续可替换为真实视频文件」。
- 直接抓 `leaderboard_data.json`：返回的是 SPA 反爬占位页，不再是 JSON；说明这个 JSON 已经不是稳定公开接口。

此前第 12/13 轮直接读过 `leaderboard_data.json`，并做过三项检验：`generated_from = gen_leaderboard.py`；`step_score ~ success_rate` 的 R² > 0.999999；8 个模型的 32 维任务成功率两两平均相关只有 0.098。这些检验本轮无法重跑（JSON 被反爬页替换），但页面状态和详情页占位足以支持同一个结论：**29.7% 是预览/难度信号，不是 live SOTA**。

### 1.2 规则：32 任务、10 次/任务、5 类泛化各 2 次、180 秒、N 端口

官方参赛手册（飞书 docx，2026-10-29 通过 `r.jina.ai` 重新抓取）明确：

- 所有任务须基于**同一模型**完成，不得混合多个模型一起测试；模型类型不限（World Model、VLA 均可）。
- 32 个任务，每个任务 10 次独立运行；5 类泛化各 2 次：位置、干扰物、桌面背景、未见物品、人为干扰。
- 单次真机执行上限 **180 秒**，超时记失败，并按执行情况计算步骤分。
- 排名先看 32 任务**总平均成功率**，相同看**总平均步骤分**，再相同看**更早提交**。
- 评测跨 **N 台机器人**；提交须从 **8765** 起暴露 N 个连续端口；每端口独立交互，`reset()` 状态必须隔离。
- 另有**不计分的单任务测试通道**，可用于单任务成功率/步骤分验证。

**对方案的约束**：DEADLINE-PLAN 必须是每端口独立、CPU 轻量、不抢 GPU 的 supervisor；不能是第二个策略模型；单任务通道是唯一敢做配对 A/B 的地方。

### 1.3 API：chunk 示例是 8，不是 30；H 是全局固定参数

提交模板 README（2026-10-29 复核）给出：

| 项 | 规格 |
|---|---|
| 观测图像 | `cam_left_high`、`cam_right_high`、`cam_left_wrist`、`cam_right_wrist` 四路 RGB **480×640** |
| 本体 | 双臂关节 `[7]`、EE 位姿 `[6]`（xyz+rpy，base 系）、夹爪 `[1]`、下身体 `[15]`、语言 `str` |
| 动作空间 | `control_space` 仅 `"joint"` 或 `"ee"`，二者互斥 |
| 共享动作 | `action.left_gripper [1]`、`action.right_gripper [1]`、`action.pivot [7]` |
| EE 动作 | `action.left_ee_pose_gripper_base [6]`、`action.right_ee_pose_gripper_base [6]`（**绝对目标位姿**，xyz+rpy，base 系） |
| chunk | `action_chunk_size ≥ 1`，**固定**；index 0 先执行，其余顺序执行，直到 evaluator 再次调用 |
| token | `metadata.token` 握手校验一次；每次 `get_action` 的 `meta.token` 都要匹配 |
| 缺失 | **没有 depth、camera_info、force/torque、tactile** |
| 监控 | 评测端逐调用记录延迟、波动和动作统计规律，作为结果可信度的一部分 |

**本轮最重要的接口修正**：README 的示例是 **`action_chunk_size: 8`**，不是 30。官方 WLA 的默认 `chunk_size=30` 是**模型侧 action horizon**（30 步 @30Hz，覆盖 1 秒），不是挑战赛 API 的 chunk 大小。选手要在 metadata 里自己选一个**全局固定**的 H，evaluator 每 H 步调用一次 `get_action`。

这带来两个硬约束：

1. **反馈周期是 `H/f_c`，不能按阶段变。** 你可以在 H 步的 chunk 里只让前 k 步「真正运动」，后 H−k 步保持/刹车；但 evaluator 仍然要等 H 步才再次调用。**能自适应的是「有效运动前缀 k」，不是 API 的 H。**
2. **H 是全局控制参数，不是推理超参数。** H=5 时反馈 167ms，但 N 个端口的请求率是 `N·f_c/H`；H=30 时请求率低，但接触段基本开环。H 的选择必须和 N、GPU 吞吐、网络 RTT 一起算。

这是第 12 轮 CHUNK-SERVO 需要修正的地方：它把「5 步执行块」当成可以按阶段切换的参数；实际上 H 是全局的，能按阶段切换的是「chunk 内执行多少步」和「什么时候重规划」。

### 1.5 头部方案：四种路线，同一个「系统层」缺口

| 模型家族 | 公开路线 | 优势 | 与本轮相关的瓶颈 |
|---|---|---|---|
| **MolmoAct2** | Ai2 的 action reasoning model；Molmo 2-ER + action expert + adaptive depth reasoning；大规模双臂数据；强调 3D 空间推理、推理加速、无 per-task 微调 | 3D/空间语义强；推理快；双臂 | 仍是开环 chunk；没有里程碑/期限决策；最后接触与恢复 |
| **WALL-OSS-0.5** | X Square 的 4B VLA（3B VLM + action expert）；公开材料称 15 个真机任务 60.5% average task progress | 预训练直接可用；progress 高 | progress ≠ success；没有期限/调度层；4B 的实时性 |
| **DreamZero** | 14B Wan2.1 video-diffusion world-action model；预测未来视频再出动作 | 长程预测/规划 | 14B 推理重；世界模型不直接解决接触力/毫米级对齐；长 chunk 更危险 |
| **π0.5** | Physical Intelligence 的开放世界泛化 VLA | 语义/新场景泛化 | 接触密集任务的精度；远程部署延迟 |
| **GigaBrain-0** | 世界模型生成数据 + VLA；用世界模型降真机数据依赖 | 数据效率/泛化 | 生成数据的物理保真度；最后 3 厘米 |
| **GR00T N1.5** | NVIDIA 通用人形 VLA | 生态/embodiment | 任务特定精度；数据覆盖 |

共同点不是「模型不够大」，而是：

- **都是 action chunk 开环执行**；chunk 内不看新图，也不检查「这一步成没成」。
- **都没有显式的里程碑状态**；任务是否完成、哪一步被撤销、下一步该保哪一步，模型不知道。
- **都没有期限/预算管理**；180 秒对模型是一个外部常量，不是一个可分配的资源。
- **都没有多端口实时调度**；N 个端口共享一张 GPU 时，谁先推理、谁可以等、谁快饿死了，模型不关心。

所以头部的差距不在「再大 2B」，而在**执行层之上的系统层**。

### 1.6 近期工作：调度、期限、保形、子任务，四块拼图都有人做，但没人拼在一起

本轮检索到的、会改变方案的近期工作：

1. **VLA-HWBench（arXiv 2610.34717，2026-10-26）**：在 Jetson AGX Thor 和 AMD Ryzen AI Max+ 上测 18 个开源 VLA，做七阶段延迟拆解。结论：**action-generation strategy 比模型大小更重要**；延迟在 Jetson 上差 **82×**、AMD 上差 **157×**；参数量最多解释 15% 的延迟方差；「长 chunk + 少 flow-matching 步」能跟上控制，token-by-token 解码不行；4-bit 权重 + kernel fusion 让 π0.5/GR00T N1.7 快 2.6–2.9×；优化后 CPU 预处理反而从 12% 涨到 39%。这直接支持「H 和推理步数是控制参数」。
2. **Armory / Action Chunk Scheduling（Georgia Tech，2026-07）**：10 台机器人共享策略服务器，提出在**机器人时间**而非请求时间做 one-step lookahead 调度。它明确指出 **EDF 会饿死「快机器人」**——快机器人大部分时间没有紧迫 deadline，于是被反复降级、停住。这和 UniBot 的 N 端口场景几乎同构。
3. **RACE（ICLR 2026）**：把策略输出改成「期望状态轨迹」，做时间最优规划和异步推理的 Best-of-N。传送带任务上，15Hz base 成功率 0.03，45Hz base 0.27，RACE 0.63；2.5× 速度下 RACE 仍有 0.53。说明**执行时序/规划层可以把成功率翻倍**，不只是模型层。
4. **ReconVLA（arXiv 2604.16677）**：把保形预测直接用在 VLA 的 action token 上，得到与执行质量和任务成功相关的校准不确定性，并做失败检测，不需重训。它证明「成功概率可以被校准」，但没有做里程碑规划。
5. **ACPS / Task-Aware Conformal State Estimation（NeurIPS 2026 Workshop）**：CMBSα 给感知状态估计提供覆盖率保证，ACPS 在感知不确定性下做 anytime confidence-maximizing plan search，给计划成功率证书。它证明「保形 + 任务规划」可行，但没有接 VLA chunk 和多端口服务。
6. **FineART（arXiv 2609.36416）**：40,543 episodes / 1,718 h / 533,913 subtasks；mid-training 在子任务标注上把空间指令跟随从 32.0% 提到 100.0%；有人类逐步子任务提示时，未见长程任务从 16.0% 提到 76.0%。它证明**显式子任务结构**对长程任务价值巨大，但它是另一个数据集/机器人，不是 UniBot。
7. **A2C2（arXiv 2509.23224）/ VLA-Corrector（arXiv 2607.01804）**：前者是每控制步运行的轻量 chunk 修正头，后者是 latent-space 视觉监控 + 检测到漂移才截断重规划；两者都在解决「chunk 内开环」，但都引入了一个学习模块，单模型合规性需要额外论证。CHUNK-SERVO 的确定性伺服是更保守的路线。

**缺口**：调度（Armory）、期限/时间最优（RACE）、保形成功（ReconVLA/ACPS）、子任务结构（FineART）四块都有人做，但没有人在「单模型 + 无深度/力 + N 端口 + 180 秒 + 官方远程 API」的约束下把它们拼成一个**可提交的系统**。DEADLINE-PLAN 就是拼这个缺口。

### 1.7 为什么现在能做

- **官方 WLA 基座**：6B、约 2,500 h 真机、64 任务、二指/五指、单张 24GB GPU 可微调；默认 `action_horizon=30`、`target_fps=30`、`num_inference_timesteps=4`、`image_size=[336,448]`；冻结 VLM，只训 DiT action head + robot-state projector；支持 LoRA。不要从零训 6B/14B。
- **33k 成功演示**：不只做 imitation，也能做里程碑时长分布、关键帧/目标图、恢复原语库。
- **腕部彩色内参 32/32**：2D 伺服/目标图对齐不用先标定；头双目可做 PBVS 兜底。
- **单任务通道**：不计分，但能跑真实 A/B；这是唯一能校准「成功概率」和「失败时间」的地方。
- **官方仿真**：`unitree_sim_isaaclab`、`unitree_mujoco` 足够搭 N 端口的风洞，不需要训练大策略。

## 2. 诊断：三个没有被建模的预算

### 2.1 时间预算：180 秒不是常量，是分布

把一次 trial 写成：

```text
t=0: reset → 第一次观测
t=0..180: 策略在线，evaluator 每 H 步调用一次 get_action
t=180: 超时，记失败
```

如果失败主要发生在最后 20% 的时间（接触/插入/拉拉链），那么「期限管理」比「更大模型」更值钱；如果失败主要发生在最开始 20%（感知/抓取），那么期限管理没用。**这个分布目前没人公开测过**，所以本轮把它列为 P0 诊断：先用单任务通道测 5 个任务的失败时间/里程碑，再决定是否投 DEADLINE-PLAN。

### 2.2 算力/网络预算：N 端口共享一张 GPU，p99 是成功率的隐形杀手

设：

- `f_c`：控制频率（README 未写死；本报告默认 30Hz，必须实测）；
- `H`：全局 `action_chunk_size`；
- `N`：端口数/机器人数；
- `τ`：网络 RTT + 图像传输 + 推理的等效延迟；
- `Θ`：GPU 服务器每秒能返回的 chunk 数（取决于 batch、分辨率、去噪步数）。

则每个端口的请求周期是 `P = H/f_c`，总请求率是 `N/P = N·f_c/H`。系统可行的必要条件是：

```text
N·f_c/H ≤ Θ
```

一个具体的例子：

| 配置 | P | N=4 总请求率 | 如果 Θ=15 chunks/s | 结果 |
|---|---:|---:|---:|---|
| H=5, f_c=30 | 167ms | 24/s | 15/s | **不可行**，端口会饿死 |
| H=8, f_c=30 | 267ms | 15/s | 15/s | 临界，p99 很容易超 |
| H=15, f_c=30 | 500ms | 8/s | 15/s | 可行，但接触段开环 500ms |
| H=30, f_c=30 | 1s | 4/s | 15/s | 很稳，但接触段基本开环 |

这张表说明：**H 不是「越小越好」**。H=5 对接触最友好，但可能把服务器压垮；H=30 对服务器最友好，但把接触段变成开环。正确做法是：先测 `Θ` 和 `τ`，再选一个**全局 H**，然后用「chunk 内有效前缀 k」在接触段刹住，用调度器保证 N 个端口都不饿死。

### 2.3 成功预算：最后一个里程碑失败，前面全白做

把任务写成里程碑序列 `m=1..M`（M≈2–5）。一次 trial 的成功概率近似：

```text
P(success) = Π_m P(m succeeds | m-1 succeeded, time remaining)
```

如果每个里程碑单独 80% 成功，5 个里程碑的联合成功率只有 `0.8^5 ≈ 32.8%`。这正好落在「榜首不到 30%」的量级。**不是每个里程碑都要 99%，而是要在最后一个里程碑之前知道自己还剩多少预算、要不要先恢复。**

更关键的是：VLA 在成功演示上训练，没见过「失败后怎么恢复」。它会把一个已经失败的里程碑继续做下去，直到超时。DEADLINE-PLAN 的价值就是：在里程碑级别检测「这一步没成」，然后用预算决定「再试一次 / 换顺序 / 先恢复 / 放弃」。

### 2.4 一个反直觉的推论：成功率是调度问题

如果两个端口的任务一个在接触段、一个在搬运段，它们对延迟的敏感度不同。接触段的 chunk 晚 100ms 可能就撞了；搬运段的 chunk 晚 300ms 只是慢一点。固定 round-robin 会把接触段端口拖死；EDF 又会饿死「大部分时间不紧迫」的快端口。**按阶段加权的机器人时间调度**，比「给每个端口平均分 GPU」更接近成功率的真实目标。

## 3. 方法：DEADLINE-PLAN

### 3.1 总架构

```text
                    ┌──────────────────────────────────────────┐
                    │  Evaluator (N ports 8765..8765+N-1)      │
                    └───────────────┬──────────────────────────┘
                                    │ websocket: obs / action chunk
                                    ▼
        ┌────────────────────────────────────────────────────────┐
        │  Per-port RT Supervisor (CPU, one process per port)    │
        │  ├─ milestone detector (deterministic keyframes/pose)  │
        │  ├─ success table + conformal lower bound              │
        │  ├─ deadline DP (continue/replan/recover/abort)        │
        │  ├─ phase-prefix selector (k ≤ H)                      │
        │  ├─ plan cache (30-step VLA plan)                      │
        │  └─ action adapter (WLA 54D → API 21D)                 │
        └───────────────┬────────────────────────────────────────┘
                        │ async request + deadline + phase
                        ▼
        ┌────────────────────────────────────────────────────────┐
        │  Shared VLA Server (GPU, one model copy)               │
        │  ├─ robot-time lookahead scheduler                     │
        │  ├─ batch inference (TensorRT/FP8, CUDA graphs)        │
        │  ├─ per-port session isolation                         │
        │  └─ latency/queue/action logging                       │
        └────────────────────────────────────────────────────────┘
```

- **唯一学习模型**：VLA（官方 WLA 微调 action head）。
- **确定性/统计层**：里程碑检测、成功表、DP、调度、看门狗；无学习权重。
- **数据资产**：33k 成功演示 → 里程碑时长分布、关键帧、恢复原语；不是第二个模型。
- **共享 GPU**：一张卡只放一份 VLA 权重；N 个 supervisor 只做轻量 CPU 计算。

### 3.2 MILESTONE-GRAPH：把任务拆成 2–5 个可观测节点

对每个任务定义一个有向无环图 `G=(V,E)`，节点是里程碑，边是可行顺序。以三个任务为例：

```text
HangCup:       approach → grasp → lift → align → hang
PlugEthernet:  grasp cable → align plug → insert → release
Toolbox:       pick tool → place in box → ... → close lid → lock
```

每个节点 `v` 存：

- `d_v`：时长分布（中位数、p90），来自成功演示；
- `p_v(s)`：在状态 `s` 下的成功概率，来自校准表；
- `pre_v` / `post_v`：可观测的前置/后置条件（夹爪开合、EE 相对位姿、目标在腕部图中的位置、受器状态）；
- `rec_v`：失败后的恢复原语（retreat / re-approach / re-grasp / re-place）。

**里程碑检测器是确定性的**：用关键帧描述子（ORB/颜色/SSIM）、EE 相对位姿、夹爪宽度、目标在图像中的 ROI 变化来判断。它不需要第二个学习模型；置信度低时回退 VLA，不触发重规划。

### 3.3 CONFORMAL-BUDGET：把成功概率变成可用的下界

不要用一个黑箱「成功预测器」。默认用**小表 + 贝塔下界**：

```text
特征离散化：
  milestone_id × phase × time_bin × visual_residual_bin × gripper_bin
统计：
  每个 bin 用 Beta(α0 + successes, β0 + failures) 后验
  p_lower = Beta 后验的 α 分位数（例如 5%）
```

如果表太稀疏，用**逻辑回归**（10–20 个特征）替代；如果还要更强，用**保形预测**：

```text
校准集 D_cal = {(x_i, y_i)}，y_i ∈ {0,1}
nonconformity: s_i = p_hat(x_i) - y_i
q = Quantile_{1-α}(s_i)
p_lower(x) = clip(p_hat(x) - q, 0, 1)
```

覆盖保证：在可交换性假设下，`P(p_true ≥ p_lower) ≥ 1-α`。分布漂移时（未见物品/背景），用**分组保形**（按任务/阶段分组）或**自适应保形**，并只把下界用于「继续 vs 重规划」的软决策，不用于安全关键动作。

**合规性**：这是统计校准层，不是策略；不加载第二个学习模型。若官方对「模型」作最宽解释，退到 C1（只用离线表）或 C2（只用确定性启发式）。

### 3.4 PHASE-PREFIX：H 固定，chunk 内只执行 k 步

这是本轮对 CHUNK-SERVO 的关键修正：

```text
metadata.action_chunk_size = H   # 全局固定，例如 8
每个 chunk:
  k = phase_prefix(phase, p_lower, time_left)
  actions[0:k]   = VLA plan 的前 k 步（或叠加伺服修正）
  actions[k:H]   = hold / brake / keep gripper
  return actions[0:H]
```

- **H 是全局的**：不能按阶段改；它由 `N·f_c/H ≤ Θ` 和接触精度共同决定。
- **k 是阶段自适应的**：接触段 `k=3`，预接触 `k=5`，搬运 `k=H`；后 H−k 步保持/刹车，避免在接触段盲推。
- **代价**：每个 chunk 浪费 `(H−k)/f_c` 秒；如果 H=8、k=3、30Hz，浪费 167ms。一个 20 chunk 的任务浪费 3.3s，相对于 180s 可接受；换来的是一次接触失败可能省下的整个 trial。
- **重规划**：VLA 仍然按 30 步规划；每 H 步重新请求一次；plan cache 保证 `get_action` 不等 GPU。

为什么不是「H=5 全局」？因为 H=5 让 N=4 的请求率变成 24/s，可能超过 GPU 吞吐；H=8 是官方示例，也是更稳的折中。为什么不是「H=30 全局」？因为接触段 1 秒开环，最后 3 厘米必输。**H=8 + k=3 是「接口可行」和「接触安全」的折中。**

### 3.5 ROBOT-TIME-SCHED：按机器人时间调度，而不是按请求到达时间

每个端口有一个动作队列，剩余 `q_i` 步；它的**饥饿时刻**是：

```text
d_i = t_now + q_i / f_c
```

服务器维护每个端口的队列镜像、在飞 chunk、执行 horizon 和网络延迟。调度时，对候选 batch `B` 打分：

```text
score(B) = Σ_{i∈B} w_i · 1[ t_now + d_infer(|B|) + margin ≤ d_i ]
w_i = 1 + β · criticality(phase_i)
```

- `criticality`：接触段 > 预接触 > 搬运；接触段的 chunk 更值钱。
- `d_infer(|B|)`：实测的 batch 推理时间曲线；不是线性。
- 候选 batch 用 one-step lookahead 枚举（N≤8 时 2^N≤256，CPU 可承受）；N 更大时用 least-laxity-first 贪心。
- **admission control**：队列太长时，低 criticality 的端口可以等；高 criticality 的端口优先。
- **graceful degradation**：服务器迟到时，搬运段可以用**缓存 chunk**（staleness < 阈值）；接触段必须 hold，不能执行过期动作。

Armory 的教训是：EDF 会饿死「快机器人」，因为它大部分时间没有紧迫 deadline。机器人时间 lookahead 把「未来会不会饿死」纳入打分，而不是只看当前 deadline。

### 3.6 嵌入式运行时：每端口一个实时 supervisor

- **进程隔离**：每个端口一个 supervisor 进程，独立 `reset()`、独立 plan cache、独立里程碑状态；共享 GPU server 只保存 per-port session。
- **实时性**：`SCHED_FIFO` 优先级、CPU 亲和、`mlockall`、静态环形缓冲、热路径不分配内存；Python MVP 用 `uvloop` + 预分配 numpy，正式版用 C++/Rust。
- **看门狗**：GPU 超时 → 返回安全 hold chunk（最后安全位姿、零速度、保持夹爪）；连续超时 → 降级到缓存 plan；绝不返回 NaN/错误形状。
- **p99 预算**：`p99 ≤ H/f_c − margin`；H=8、30Hz 时是 267ms，margin 50ms → p99≤217ms；H=5 时是 167ms，margin 30ms → p99≤137ms。
- **日志**：每次调用的延迟、batch 大小、队列深度、chunk 大小、里程碑、`p_lower`、动作统计；既用于评测可信度，也用于离线校准。

## 4. 合规性：VLA 是唯一学习模型

| 模式 | 做法 | 风险 | 建议 |
|---|---|---|---|
| **C1 离线标注** | 里程碑/成功表只离线生成；线上只有 VLA + 查表 | 最低 | 保守首选 |
| **C2 确定性控制器** | 里程碑检测、DP、调度、看门狗都是几何/统计/控制律 | 低；需向官方说明 | 主推 |
| **C3 同 checkpoint 特征** | 成功表的特征用 VLA 同一 checkpoint 的 encoder，不加载第二个模型 | 低–中；需说明 | 需要强特征时用 |

**禁止**：加载第二个学习策略/残差网络/独立视觉编码器做在线决策；为每个任务训一个策略；用在线 ASR/TTS 增加延迟（API 也没有音频）。

## 5. 实验与门

### 5.1 P0 诊断（先做，决定是否继续）

在单任务通道选 5 个任务（PlugInEthernet、HangCup、ZipUp、StackBowls、FoldTowel），每个跑 10 次基线，记录：

- 失败时间（相对 180s 的百分比）；
- 失败里程碑（approach/grasp/lift/align/insert/release）；
- 失败原因（感知/抓取/接触/超时/人为干扰）；
- 每次 `get_action` 的延迟 p50/p99；
- 实际控制频率 `f_c`。

**Go/No-Go**：

- 如果 ≥50% 失败发生在最后 30% 时间或最后 1–2 个里程碑 → 投 DEADLINE-PLAN。
- 如果 ≥50% 失败发生在最前 30% 时间或抓取阶段 → 先修感知/抓取，不投调度。
- 如果 p99 延迟已经 <50ms 且 N=1 → 调度收益有限，先做里程碑规划。
- 如果 p99 >200ms 或 N≥4 → 调度是刚需。

## 6. 预期收益与竞赛策略

### 6.1 算术

- 总分 `S = (1/32) Σ p_t`；320 trials 下，`p≈0.25` 的单次标准误约 2.42pp；不要用 +1–2pp 做结论。
- 如果调度/期限把超时率从 10% 降到 5%，受影响 trial 约 +5pp；摊到 32 任务约 +1–2pp。
- 如果接触任务（19 个）各 +5pp，全局 +3.0pp；各 +10pp，全局 +5.9pp。
- 人为干扰轴占 20%；如果恢复把 human 轴 +10pp，全局 +2pp。
- **保守合计 +2–4pp；乐观 +5–8pp**。这些是设计目标，不是承诺；G3/G5 不过就不提交。

### 6.2 任务组合

- **A 档（调度/期限优先）**：ToolboxStorage、PackBag、StorePaddle、ArrangeTestTubes、PlugInEthernet、HangCup、ZipUp、StackBowls、Unlock、PourOutMedicine。特征：长程、多里程碑、接触密集、容易超时。
- **B 档（VLA 优先）**：FruitCollection、FruitSorting、ColorArrangement、OrganizeBookshelf、FoldTowel、SpellRobot、ConveyorSorting。特征：语义/变形/动态，调度收益低。
- **C 档（观察）**：单任务通道里 `p_t` 接近 0 且失败在早期感知/抓取的任务；不投调度。

优先级：

```text
priority_t = q_t · Δ_t / cost_t
```

`q_t` = 失败发生在最后 30% 时间/最后 1–2 个里程碑的比例；`Δ_t` = 调度/期限的条件增益；`cost_t` = 工程成本。先做 A 档中 `q_t` 最高、`cost_t` 最低的 3–5 个。

### 6.3 提交节奏

1. **W0**：官方 WLA + API adapter + H=8 基线；单任务通道跑通 1 个任务，确认 `f_c`、`pivot`、token、延迟。
2. **W1**：P0 诊断；如果 Go，做里程碑图和成功表。
3. **W2–W3**：DP + 前缀 + 看门狗；单任务 A/B。
4. **W4**：调度器 + N=4 干跑；p99/饿死/内存。
5. **W5**：32×10 干跑；最终提交；保留回退开关。
6. 若允许多次提交：先交安全基线锁「更早提交」tie-break；若只允许一次：W5 后交最终版。

## 7. 风险与剪枝

| 风险 | 影响 | 缓解 |
|---|---|---|
| 里程碑分割错 | 错误重规划 | 只用 2–5 个粗节点；低置信度回退 VLA |
| 成功表分布漂移 | 保形覆盖失效 | 分组/自适应保形；只做软决策 |
| 单模型解释 | 被判第二个模型 | C1/C2/C3；表/DP/调度无学习权重 |
| 调度开销 | 增加延迟 | one-step lookahead；N≤8；C++/Rust |
| Python GIL | p99 抖动 | 每端口独立进程；uvloop；热路径 C++ |
| 端口串扰 | 状态污染 | 每端口 session；独立 reset；共享内存只读 |
| 过期 chunk | 接触段盲推 | 接触段 hold；搬运段 staleness 检查 |
| 预览榜单误导 | 方向错误 | 单任务通道；配对 A/B；不反推难度 |
| 时间不够 | 32 任务铺太大 | 先 5 任务；A 档 3–5 个；B/C 档保留基线 |

**明确不做**：

- 不从零训 VLA/World Model（官方 WLA 已做完）。
- 不做完整 sim-to-real 策略训练（只做调度/期限风洞）。
- 不做第二个学习模型/残差策略（单模型风险）。
- 不做 6D 物体位姿网络（透明/变形不可靠）。
- 不做力/触觉闭环（API 没有）。
- 不做 30Hz 广域网伺服（RTT 不允许）。
- 不做 32 个任务各一个策略（规则禁止）。
- 不把预览榜单当 SOTA/难度表。

## 8. 一句话押注

**先用 H=8 的全局 chunk + 里程碑图 + 保形成功下界 + 机器人时间调度，把「超时/接触失败/端口饿死」这三类系统损失压下去；如果 P0 诊断显示失败主要发生在最后 30% 时间，这就是当前最值得押注的 2–4pp。**

# 第 4 轮产物 · DEADLINE-PLAN 技术报告

> 检索/复核日期：**2026-10-29（UTC）**。对象：宇树 **UniBot 世界挑战赛**（G1 + Dex1，32 项桌面任务，通才单模型赛道，选手自部署 + 官方远程真机 API）。本报告是第 4 轮想法区「DEADLINE-PLAN」的工程化产物；不替换第 12 轮 CHUNK-SERVO，而是把它从「控制层」推进到「时间/资源/计划层」。

## 0. 结论与边界

### 0.1 一句话结论

官方 WLA 的 30 步 action horizon 是吞吐优势，也是接触精度的结构性弱点；但挑战赛 API 的 `action_chunk_size` 是**全局固定**的（模板示例 **8**），所以真正的控制变量不是「30 还是 5」，而是「H 选多大、chunk 内真正执行几步、什么时候重规划、N 个端口怎么调度」。DEADLINE-PLAN 用「里程碑图 + 保形成功下界 + 机会约束 DP + 机器人时间调度 + 每端口实时 supervisor」，把成功率从模型指标变成系统指标。

### 0.2 证据等级

| 等级 | 含义 | 本报告中的例子 |
|---|---|---|
| A | 官方文档、提交模板、数据集元数据、官网页面直接核实 | 规则、API、33,276 eps、WLA `action_horizon=30`、官网「即将发布」 |
| B | 我们在公开数据/网页上做的分析，可复现 | 腕部内参 32/32、H/请求率可行性表、失败时间诊断设计 |
| C | 设计假设，需 G0–G7 验证 | 里程碑 F1≥0.8、保形覆盖 ±2%、调度 +5pp |

### 0.3 本轮不做什么

- 不从零训 VLA/World Model；官方 WLA 已开源 6B 基座。
- 不做完整 sim-to-real 策略训练；数字孪生只做调度/期限风洞。
- 不做第二个学习模型/残差策略；里程碑检测、DP、调度、看门狗都是确定性/统计层。
- 不做 6D 物体位姿网络；用里程碑关键帧 + 相对位姿 + 局部特征。
- 不做力/触觉闭环；API 没有。
- 不做 30Hz 广域网伺服；RTT 不允许。
- 不做 32 个任务各一个策略；规则禁止，且不泛化。
- 不把预览榜单当 live SOTA、任务难度表或失败分布。

### 1.2 规则（A）

官方参赛手册（飞书 docx，2026-10-29 通过 `r.jina.ai` 抓取）核实：

| 项 | 规则 |
|---|---|
| 模型 | 所有任务须基于**同一模型**完成，不得混合多个模型一起测试；模型类型不限 |
| 任务 | 32 项桌面任务 |
| 次数 | 每任务 10 次独立运行 |
| 泛化 | 5 类各 2 次：位置、干扰物、桌面背景、未见物品、人为干扰 |
| 时限 | 单次真机执行上限 **180 s**；超时记失败，并按执行情况计算步骤分 |
| 排名 | 先比 32 任务总平均成功率；相同看总平均步骤分；再相同看更早提交 |
| 部署 | 评测跨 **N 台机器人**；提交须从 **8765** 起暴露 N 个连续端口；每端口独立交互，`reset()` 状态必须隔离 |
| 测试通道 | 另有**不计分的单任务测试通道**，可用于单任务成功率/步骤分验证 |

**对方案的约束**：DEADLINE-PLAN 必须是每端口独立、CPU 轻量、不抢 GPU 的 supervisor；不能是第二个策略模型；单任务通道是唯一敢做配对 A/B 的地方。

### 1.3 API（A）

提交模板 README（2026-10-29 复核）给出：

| 项 | 规格 |
|---|---|
| 观测图像 | `cam_left_high`、`cam_right_high`、`cam_left_wrist`、`cam_right_wrist` 四路 RGB **480×640** |
| 本体 | 双臂关节 `[7]`、EE 位姿 `[6]`（xyz+rpy，base 系）、夹爪 `[1]`、下身体 `[15]`、语言 `str` |
| 动作空间 | `control_space` 仅 `"joint"` 或 `"ee"`，二者互斥 |
| 共享动作 | `action.left_gripper [1]`、`action.right_gripper [1]`、`action.pivot [7]` |
| EE 动作 | `action.left_ee_pose_gripper_base [6]`、`action.right_ee_pose_gripper_base [6]`（**绝对目标位姿**，xyz+rpy，base 系） |
| chunk | `action_chunk_size ≥ 1`，**全局固定**；index 0 先执行，其余顺序执行，直到 evaluator 再次调用 |
| token | `metadata.token` 握手校验一次；每次 `get_action` 的 `meta.token` 都要匹配 |
| 缺失 | **没有 depth、camera_info、force/torque、tactile** |
| 监控 | 评测端逐调用记录延迟、波动和动作统计规律，作为结果可信度的一部分 |

**本轮最重要的接口修正**：README 的示例是 **`action_chunk_size: 8`**，不是 30。官方 WLA 的默认 `chunk_size=30` 是**模型侧 action horizon**（30 步 @30Hz，覆盖 1 秒），不是挑战赛 API 的 chunk 大小。选手要在 metadata 里自己选一个**全局固定**的 H，evaluator 每 H 步调用一次 `get_action`。

两个硬约束：

1. **反馈周期是 `H/f_c`，不能按阶段变。** 你可以在 H 步的 chunk 里只让前 k 步「真正运动」，后 H−k 步保持/刹车；但 evaluator 仍然要等 H 步才再次调用。**能自适应的是「有效运动前缀 k」，不是 API 的 H。**
2. **H 是全局控制参数，不是推理超参数。** H=5 时反馈 167ms，但 N 个端口的请求率是 `N·f_c/H`；H=30 时请求率低，但接触段基本开环。H 的选择必须和 N、GPU 吞吐、网络 RTT 一起算。

**观测/语言适配**：挑战赛 `*_ee_pose_gripper_base` 是 xyz+rpy；WLA server 的 `*_ee_6d` 实际是 **xyz+rot6d（9 维）**，obs adapter 必须做 rpy→rot6d。图像映射为 `cam_left_high` + 左右腕部三路；`cam_right_high` 只用于双目深度/伺服。语言方面，WLA server 用 `unnorm_key`/固定 prompt，不直接吃挑战赛的 `observation.language`；需要把 32 任务语言映射到 WLA 的任务 key（或空 prompt），并在单任务通道验证。

**动作适配**：WLA 输出 54 维相对动作（EE 相对 xyz+rotvec、gripper、灵巧手、腰、躯干、base、腿）；挑战赛 `ee` 模式要 21 维（左右 EE 绝对位姿各 6 + 左右夹爪各 1 + pivot 7）。adapter 必须：

1. 把 WLA 每个未来动作 compose 到 **plan-time 当前 EE** 的 base 系绝对位姿；
2. 把整个 30 步 compose 成绝对目标，再按 H 切片；
3. 校验 TCP/夹爪长度偏移（平移 ≤1cm、旋转 ≤2°）；
4. 校验 `pivot` 的 7 维语义；不匹配时先返回全零 pivot，只验证双臂。

### 1.6 头部方案的做法与瓶颈（A+B）

| 模型家族 | 公开路线 | 优势 | 与本轮相关的瓶颈 |
|---|---|---|---|
| **MolmoAct2** | Ai2 的 action reasoning model；Molmo 2-ER + action expert + adaptive depth reasoning；大规模双臂数据；强调 3D 空间推理、推理加速、无 per-task 微调 | 3D/空间语义强；推理快；双臂 | 仍是开环 chunk；没有里程碑/期限决策；最后接触与恢复 |
| **WALL-OSS-0.5** | X Square 的 4B VLA（3B VLM + action expert）；公开材料称 15 个真机任务 60.5% average task progress | 预训练直接可用；progress 高 | progress ≠ success；没有期限/调度层；4B 的实时性 |
| **DreamZero** | 14B Wan2.1 video-diffusion world-action model；预测未来视频再出动作 | 长程预测/规划 | 14B 推理重；世界模型不直接解决接触力/毫米级对齐；长 chunk 更危险 |
| **π0.5** | Physical Intelligence 的开放世界泛化 VLA | 语义/新场景泛化 | 接触密集任务的精度；远程部署延迟 |
| **GigaBrain-0** | 世界模型生成数据 + VLA；用世界模型降真机数据依赖 | 数据效率/泛化 | 生成数据的物理保真度；最后 3 厘米 |
| **GR00T N1.5** | NVIDIA 通用人形 VLA | 生态/embodiment | 任务特定精度；数据覆盖 |

共同点：

- 都是 action chunk 开环执行；chunk 内不看新图，也不检查「这一步成没成」。
- 都没有显式的里程碑状态；任务是否完成、哪一步被撤销、下一步该保哪一步，模型不知道。
- 都没有期限/预算管理；180 秒对模型是一个外部常量，不是一个可分配的资源。
- 都没有多端口实时调度；N 个端口共享一张 GPU 时，谁先推理、谁可以等、谁快饿死了，模型不关心。

### 1.7 近期工作（A/B）

1. **VLA-HWBench（arXiv 2610.34717，2026-10-26）**：18 个开源 VLA，Jetson AGX Thor + AMD Ryzen AI Max+，七阶段延迟拆解。结论：action-generation strategy 比模型大小更重要；延迟差 82×（Jetson）/157×（AMD）；参数量最多解释 15% 的延迟方差；「长 chunk + 少 flow-matching 步」能跟上控制，token-by-token 解码不行；4-bit 权重 + kernel fusion 让 π0.5/GR00T N1.7 快 2.6–2.9×；优化后 CPU 预处理从 12% 涨到 39%。
2. **Armory / Action Chunk Scheduling（Georgia Tech，2026-07）**：10 台机器人共享策略服务器，在**机器人时间**而非请求时间做 one-step lookahead 调度。明确指出 **EDF 会饿死「快机器人」**——快机器人大部分时间没有紧迫 deadline，于是被反复降级、停住。和 UniBot 的 N 端口场景几乎同构。
3. **RACE（ICLR 2026）**：把策略输出改成「期望状态轨迹」，做时间最优规划和异步推理的 Best-of-N。传送带任务上，15Hz base 成功率 0.03，45Hz base 0.27，RACE 0.63；2.5× 速度下 RACE 仍有 0.53。说明执行时序/规划层可以把成功率翻倍。
4. **ReconVLA（arXiv 2604.16677）**：把保形预测直接用在 VLA 的 action token 上，得到与执行质量和任务成功相关的校准不确定性，并做失败检测，不需重训。证明「成功概率可以被校准」，但没有做里程碑规划。
5. **ACPS / Task-Aware Conformal State Estimation（NeurIPS 2026 Workshop）**：CMBSα 给感知状态估计提供覆盖率保证，ACPS 在感知不确定性下做 anytime confidence-maximizing plan search，给计划成功率证书。证明「保形 + 任务规划」可行，但没有接 VLA chunk 和多端口服务。
6. **FineART（arXiv 2609.36416）**：40,543 episodes / 1,718 h / 533,913 subtasks；mid-training 在子任务标注上把空间指令跟随从 32.0% 提到 100.0%；有人类逐步子任务提示时，未见长程任务从 16.0% 提到 76.0%。证明显式子任务结构对长程任务价值巨大，但它是另一个数据集/机器人。
7. **A2C2（arXiv 2509.23224）/ VLA-Corrector（arXiv 2607.01804）**：前者是每控制步运行的轻量 chunk 修正头，后者是 latent-space 视觉监控 + 检测到漂移才截断重规划；两者都在解决「chunk 内开环」，但都引入了一个学习模块，单模型合规性需要额外论证。
8. **Jetson-PI（arXiv 2607.12659）/ LiteVLA-Edge（arXiv 2603.03380）**：前者在 Jetson Orin 上把控制频率提高 8.66×/5.41×；后者在 Jetson AGX Orin 上做到 150.5ms 端到端（6.6Hz）的 ROS2 部署。说明边缘部署可行，但 150ms 对 30Hz 接触控制仍然偏慢。

**缺口**：调度（Armory）、期限/时间最优（RACE）、保形成功（ReconVLA/ACPS）、子任务结构（FineART）四块都有人做，但没有人在「单模型 + 无深度/力 + N 端口 + 180 秒 + 官方远程 API」的约束下把它们拼成一个**可提交的系统**。

### 1.8 未核实/未解决

- GPU 吞吐 `Θ`（取决于模型、batch、分辨率、去噪步数；必须实测）。
- 官方 94 个评分点/3200 分的任务介绍表（本轮 CAPTCHA；按 B 级先验）。
- 是否允许多次提交、提交次数上限（需邮件确认）。
- 官方 WLA 与挑战赛 API 的 `pivot` 语义是否完全一致。
- 挑战赛 32 任务是否都包含在 WLA 的 64 任务训练集中。

## 2. 问题形式化

### 2.1 成功率与预算

总分：

```math
S = \frac{1}{32}\sum_{t=1}^{32} p_t,\qquad
p_t = \frac{1}{10}\sum_{j=1}^{10} y_{t,j},\quad y_{t,j}\in\{0,1\}.
```

320 trials 下，若 `p≈0.25`，单次标准误：

```math
\mathrm{SE}(S)\approx \sqrt{\frac{p(1-p)}{320}}\approx 0.0242.
```

配对 A/B 的方差取决于任务内相关；同一初始条件的 A/B 成功高度相关时，配对差值方差可显著降低。报告必须给配对差值的 bootstrap 置信区间，而不是只报两个平均值。

人为干扰轴：

```math
\Delta S_{\mathrm{human}} = \frac{2}{10}\,\Delta p_h = 0.2\,\Delta p_h.
```

即 human 轴成功率 +10pp → 全局 +2pp。

时间预算：每个 trial 上限 `T=180s`；策略在 `t=0` 重置，`t=T` 超时。一次 trial 的成功概率是「在 T 内完成所有里程碑」的概率，而不是「每一步都像演示」的概率。

### 2.2 里程碑图

对任务 `t` 定义有向无环图：

```math
G_t=(V_t,E_t),\qquad V_t=\{0,1,\dots,M_t\},
```

`0` 是起始，`M_t` 是完成。每个节点 `v` 存：

- `p_v(s)`：在状态 `s` 下完成该里程碑的概率；
- `d_v`：时长分布（中位数、p90）；
- `c_v`：该里程碑对应的过程分/信用；
- `pre_v`、`post_v`：可观测前置/后置条件；
- `rec_v`：失败恢复原语。

一次 trial 的联合成功率近似：

```math
P(\text{success}) = \prod_{m=1}^{M} p_m(s_m).
```

如果每个 `p_m=0.8`、`M=5`，联合只有 `0.328`；这正好落在「榜首不到 30%」的量级。**不是每个里程碑都要 99%，而是要在最后一个里程碑之前知道自己还剩多少预算、要不要先恢复。**

### 2.3 成功概率的校准

#### 2.3.1 贝塔表（默认，C2）

把特征离散化：

```text
x = (milestone_id, phase, time_bin, visual_residual_bin, gripper_bin)
```

每个 bin 用 Beta 后验：

```math
p \sim \mathrm{Beta}(\alpha_0 + n_{\mathrm{succ}},\ \beta_0 + n_{\mathrm{fail}}),
\qquad
p_{\mathrm{lower}} = Q_{\alpha}(p).
```

`Q_α` 是 Beta 分布的 α 分位数（例如 5%）。先验 `α0=β0=1`（均匀）；样本少时下界自然保守。

#### 2.3.2 保形预测（可选，C3）

校准集 `D_cal={(x_i,y_i)}`，`y_i∈{0,1}`。预测器 `p_hat(x)`（逻辑回归/梯度提升/查表）。非一致性分数：

```math
s_i = p_{\mathrm{hat}}(x_i) - y_i.
```

取 `q = Quantile_{1-α}({s_i})`，则：

```math
p_{\mathrm{lower}}(x) = \mathrm{clip}(p_{\mathrm{hat}}(x) - q,\ 0,\ 1).
```

在可交换性假设下，`P(p_true ≥ p_lower) ≥ 1-α`。分布漂移时（未见物品/背景），用**分组保形**（按任务/阶段分组）或**自适应保形**，并只把下界用于「继续 vs 重规划」的软决策，不用于安全关键动作。

**合规性**：这是统计校准层，不是策略；不加载第二个学习模型。若官方对「模型」作最宽解释，退到 C1（只用离线表）或 C2（只用确定性启发式）。

### 2.4 期限与 chunk 模型

设：

- `f_c`：控制频率（假设 30Hz，必须实测）；
- `H`：全局 `action_chunk_size`；
- `N`：端口数；
- `τ`：网络 RTT + 图像传输 + 推理的等效延迟；
- `Θ`：GPU 服务器每秒能返回的 chunk 数。

反馈周期：

```math
T_{\mathrm{fb}} = \frac{H}{f_c} + \tau.
```

总请求率：

```math
\Lambda = \frac{N f_c}{H}.
```

可行必要条件：

```math
\Lambda \le \Theta.
```

| 配置 | `T_fb`（τ=50ms） | N=4 请求率 | 如果 Θ=15 | 结果 |
|---|---:|---:|---:|---|
| H=5, f_c=30 | 217ms | 24/s | 15/s | **不可行**，端口会饿死 |
| H=8, f_c=30 | 317ms | 15/s | 15/s | 临界，p99 很容易超 |
| H=15, f_c=30 | 550ms | 8/s | 15/s | 可行，但接触段开环 550ms |
| H=30, f_c=30 | 1050ms | 4/s | 15/s | 很稳，但接触段基本开环 |

**有效运动前缀**：在 H 步 chunk 内，只让前 `k` 步真正运动：

```math
a_{\mathrm{cmd}}[0:k] = \mathrm{VLA\ plan}[0:k] \circ \mathrm{servo},
\qquad
a_{\mathrm{cmd}}[k:H] = \mathrm{hold/brake}.
```

`k` 按阶段选：

| 阶段 | k | 理由 |
|---|---:|---|
| 搬运/自由空间 | H | 精度要求低，追求吞吐 |
| 预接触 | 5 | 开始降速/对齐 |
| 接触/插入 | 3 | 防止盲推，给下一次调用留安全余量 |
| 回撤/恢复 | 5 | 避免碰撞 |

代价：每个 chunk 浪费 `(H−k)/f_c` 秒；H=8、k=3、30Hz 时浪费 167ms。一个 20 chunk 的任务浪费 3.3s，相对于 180s 可接受；换来的是一次接触失败可能省下的整个 trial。

### 2.5 队列调度目标

每个端口 `i` 有一个动作队列，剩余 `q_i` 步；饥饿时刻：

```math
d_i = t_{\mathrm{now}} + q_i/f_c.
```

服务器维护每个端口的队列镜像、在飞 chunk、执行 horizon 和网络延迟。对候选 batch `B` 打分：

```math
\mathrm{score}(B) = \sum_{i\in B} w_i \cdot
\mathbf{1}\left[t_{\mathrm{now}} + d_{\mathrm{infer}}(|B|) + \mathrm{margin} \le d_i\right],
```

```math
w_i = 1 + \beta \cdot \mathrm{criticality}(\mathrm{phase}_i).
```

- `criticality`：接触段 > 预接触 > 搬运；接触段的 chunk 更值钱。
- `d_infer(|B|)`：实测的 batch 推理时间曲线；不是线性。
- 候选 batch 用 one-step lookahead 枚举（N≤8 时 `2^N≤256`，CPU 可承受）；N 更大时用 least-laxity-first 贪心。
- **admission control**：队列太长时，低 criticality 的端口可以等；高 criticality 的端口优先。
- **graceful degradation**：服务器迟到时，搬运段可以用缓存 chunk（staleness < 阈值）；接触段必须 hold，不能执行过期动作。

Armory 的教训是：EDF 会饿死「快机器人」，因为它大部分时间没有紧迫 deadline。机器人时间 lookahead 把「未来会不会饿死」纳入打分，而不是只看当前 deadline。

### 2.6 假设与可辨识性

DEADLINE-PLAN 只在以下条件同时满足时启用：

1. 里程碑可观测（视觉/本体/夹爪信号至少一个可靠）；
2. 里程碑检测器置信度高于阈值；
3. 成功表有足够校准样本（单任务通道/扰动 rollout）；
4. 延迟和 GPU 吞吐已实测；
5. 任务属于 A 档（长程/接触密集/多里程碑）；
6. 单模型合规（C1/C2/C3）。

任一条不满足 → 回退 VLA 开环 + 固定 H；不硬做 DP/调度。

## 3. 系统设计

### 3.1 进程/端口拓扑

```text
                    ┌──────────────────────────────────────────┐
                    │  Evaluator (N ports 8765..8765+N-1)      │
                    └───────────────┬──────────────────────────┘
                                    │ websocket: obs / action chunk
                                    ▼
        ┌────────────────────────────────────────────────────────┐
        │  Per-port RT Supervisor (CPU, one process per port)    │
        │  ├─ milestone detector (deterministic keyframes/pose)  │
        │  ├─ success table + conformal lower bound              │
        │  ├─ deadline DP (continue/replan/recover/abort)        │
        │  ├─ phase-prefix selector (k ≤ H)                      │
        │  ├─ plan cache (30-step VLA plan)                      │
        │  └─ action adapter (WLA 54D → API 21D)                 │
        └───────────────┬────────────────────────────────────────┘
                        │ async request + deadline + phase
                        ▼
        ┌────────────────────────────────────────────────────────┐
        │  Shared VLA Server (GPU, one model copy)               │
        │  ├─ robot-time lookahead scheduler                     │
        │  ├─ batch inference (TensorRT/FP8, CUDA graphs)        │
        │  ├─ per-port session isolation                         │
        │  └─ latency/queue/action logging                       │
        └────────────────────────────────────────────────────────┘
```

- 每个端口一个 `PolicyService` 实例，独立 `reset()`、独立 plan cache、独立里程碑状态。
- supervisor 是 CPU 线程/进程，不阻塞 websocket；VLA 请求异步、可批处理。
- 共享 VLA server 用 session ID 区分端口；模型权重只有一份，不违反单模型。
- GPU 6B bf16 约 12GB；一张 24GB/40GB GPU 可服务多个端口，具体并发取决于 batch 和序列长度。

**帧/TCP 风险**：WLA 的 EE 帧与挑战赛的 `*_ee_pose_gripper_base` 帧可能差一个 TCP/夹爪长度偏移；必须用 `example_env.py` 的观测和真实数据做一次手眼/工具坐标校准（平移 ≤1cm、旋转 ≤2°）。这是 G6 的第一验证项。

### 3.3 状态机

```text
INIT ──first obs──▶ PLAN ──plan ready──▶ EXEC
  ▲                   ▲                    │
  │                   │                    ├─ milestone ok ──▶ NEXT
  │                   │                    │
  │                   │                    ├─ milestone fail/timeout ──▶ RECOVER
  │                   │                    │                              │
  │                   │                    │                              ├─ recovered ──▶ EXEC
  │                   │                    │                              └─ budget low ──▶ HOLD/ABORT
  │                   │                    │
  │                   └── replan ◀─────────┴─ scene changed / undo detected
  │
  └──────────────────────────────────────────────────────────────
任意状态 ──task success / max steps──▶ DONE
```

- `EXEC`：正常执行，`k` 按阶段选；VLA plan 异步刷新。
- `NEXT`：里程碑完成，推进到下一个节点；如果任务完成，`DONE`。
- `RECOVER`：里程碑失败/超时/场景变化；先停，再重定位；目标可见 → 更新 goal；不可见 → VLA 重规划。
- `HOLD/ABORT`：预算不足或安全风险；返回安全 hold；不硬做。
- `DONE`：任务成功/最大步数；清理状态，等待 `reset()`。

### 3.4 `get_action` 伪代码

```python
class DeadlinePlanPolicy:
    def get_action(self, obs):
        self._tick(obs)
        self._update_milestone(obs)
        self._maybe_request_plan(obs)

        if self.plan is None:
            # cold start: synchronous VLA, safe hold if timeout
            self.plan = self.vla.predict(obs)
            self.plan_idx = 0

        phase = self._phase()
        p_lower = self.success_table.lower(self._features(obs, phase))
        k = self._phase_prefix(phase, p_lower, self._time_left())

        if self._should_replan(phase, p_lower):
            self._request_plan(obs, phase)
        if self._should_recover(obs):
            self._start_recover(obs)

        a_ff = self.plan[self.plan_idx : self.plan_idx + k]
        if self.mode == "SERVO" and self.goal is not None:
            delta = self.servo.compute(obs, self.goal)
            a_ff = compose_relative(a_ff, delta)

        a_cmd = self._pad_to_H(a_ff, k)  # hold/brake for k..H
        self.plan_idx += k
        if self.plan_idx >= len(self.plan):
            self.plan_idx = 0
            self.plan = None

        return self.adapter.to_api(a_cmd, obs, self.token)
```

`_maybe_request_plan`：

```python
def _maybe_request_plan(self, obs):
    if self._future is not None and not self._future.done():
        return
    if self._future is not None:
        self.plan = self._future.result()
        self.plan_idx = 0
        self._future = None
    if self.plan is None or self.plan_age >= self.plan_ttl:
        snapshot = copy_obs(obs)
        self._future = self.executor.submit(self.vla.predict, snapshot)
```

规则：

- VLA 永远不阻塞 `get_action`（除冷启动）；plan 过期就用旧 plan + 伺服。
- 每个 chunk 只做一次里程碑检查；检查失败不影响返回合法动作。
- 任何异常 → 返回上一组合法 chunk 或安全 hold；绝不返回 NaN/错误形状。

### 3.5 规划器伪代码

```python
def plan_action(m, tau, features, table):
    # m: current milestone index; tau: remaining seconds
    if m == M:
        return ("done", 1.0)
    if tau <= MIN_TIME[m]:
        return ("abort", 0.0)

    best = None
    for a in ACTIONS:  # continue, replan, recover
        p = table.lower(features, m, a)
        d = table.duration_p90(m, a)
        if tau < d:
            continue
        if a == "continue":
            nxt = m + 1 if p > 0 else m
            val = p * V(nxt, tau - d) + (1 - p) * V(m, tau - d - REC_TIME)
        elif a == "replan":
            val = p * V(m + 1, tau - d) + (1 - p) * V(m, tau - d - REC_TIME)
        else:  # recover
            val = p * V(m, tau - d) + (1 - p) * V(m, tau - d - REC_TIME)
        if best is None or val > best[1]:
            best = (a, val)
    return best
```

复杂度：`O(M·T/Δt·|A|)`；M≤5、T=180、Δt=1s、|A|=3 → 2700 次操作；每个端口 1–5Hz 运行，CPU 可忽略。

### 3.6 调度器伪代码

```python
def schedule(ports, now):
    # ports: list of {id, q_remaining, phase, criticality, last_chunk}
    candidates = []
    for B in subsets(waiting_ports, max_batch):
        t_done = now + infer_time(len(B)) + MARGIN
        score = 0.0
        for i in B:
            d_i = now + ports[i].q_remaining / FC
            if t_done <= d_i:
                score += 1.0 + BETA * ports[i].criticality
        candidates.append((score, B))
    best = max(candidates, key=lambda x: x[0])
    dispatch(best[1])
```

- N≤8 时枚举 `2^N`；N>8 时用 least-laxity-first + batch 贪心。
- `infer_time(b)` 用离线测的曲线（batch 1/2/4/8）。
- 如果 `score==0`（所有候选都赶不上），优先服务 criticality 最高的端口，并让低 criticality 端口用缓存/等待。
- 记录每次调度的 batch、延迟、饿死次数；用于离线调参。

### 3.7 嵌入式运行时

| 项 | 设计 |
|---|---|
| 进程 | 每端口一个 supervisor；共享 GPU server 独立进程 |
| 调度 | `SCHED_FIFO` 优先级 80；CPU 亲和到隔离核；`mlockall` |
| 内存 | 启动时预分配环形缓冲；热路径不 `malloc`/不建 Python 对象 |
| IPC | 共享内存 ring + `epoll`/websocket；请求带 deadline/phase/session |
| 看门狗 | GPU 超时 → 安全 hold；连续超时 → 缓存 plan；绝不返回 NaN |
| p99 | `p99 ≤ H/f_c − margin`；H=8/30Hz → 217ms；H=5/30Hz → 137ms |
| 日志 | 每次调用：延迟、batch、队列深度、chunk、里程碑、`p_lower`、动作统计 |
| 隔离 | 每端口 session；独立 `reset()`；共享内存只读；不共享可变状态 |

**Python MVP**：`uvloop` + 预分配 numpy + `orjson`；把里程碑检测/DP/调度放到 C++ 扩展或 Rust/PyO3。**正式版**：C++17/Rust supervisor；GPU server 用 TensorRT/FP8 + CUDA graphs。

## 4. 离线管线

### 4.1 里程碑分割

对每个任务人工定义 2–5 个里程碑，用任务描述 + 成功演示关键帧：

| 任务 | 里程碑 |
|---|---|
| HangCup | approach → grasp → lift → align → hang |
| PlugInEthernet | grasp cable → align plug → insert → release |
| ZipUp | grasp zipper → align → pull → release |
| StackBowls | grasp bowl → lift → align → stack → release |
| FoldTowel | grasp corner → fold → smooth → place |

关键帧选择：

- 接触任务：首次接触前 1–3 帧 + 接触稳定后 1 帧；
- 挂/叠/插入：目标进入腕部视野且夹爪距离 <5cm 的帧；
- 拉链/锁：夹爪咬合前的帧；
- 变形任务：不建精确里程碑，只建相位/语义节点，调度不启用。

**检测器**：用关键帧描述子（ORB/颜色/SSIM）+ EE 相对位姿 + 夹爪宽度 + 目标 ROI 变化。置信度低 → 回退 VLA，不触发重规划。

### 4.2 时长/成功分布

- 时长：从成功演示统计每个里程碑的中位数、p90；按任务/物体/位置分箱。
- 成功概率：所有演示都是成功的，直接统计会有偏；必须用**扰动 rollout** 和**单任务通道失败**来估计失败率。
- 扰动方式：物体位置偏移、受器偏移、背景替换、干扰物、目标被移动/拿走、夹爪初始开合变化。
- 先验：`Beta(1,1)`；每个 bin 至少 5 个样本才启用；否则回退到任务级/阶段级表。

### 4.3 保形校准

| 项 | 设计 |
|---|---|
| 校准集 | 单任务通道失败/成功 + 扰动 rollout + 离线回放 |
| 特征 | 里程碑、阶段、剩余时间、视觉残差、夹爪宽度、动作 chunk 统计、延迟、端口负载 |
| 非一致性 | `p_hat - y` 或 `|p_hat - y|` |
| 覆盖率 | 目标 90%/95%；分组（任务/阶段）检查 |
| 漂移 | 自适应保形/分组保形；只做软决策 |
| 报告 | 覆盖率、Brier、AUROC、预测集大小 |

### 4.4 恢复原语

- `retreat`：沿接近方向回撤 2–5cm；
- `re-approach`：重新对齐目标，降速；
- `re-grasp`：张开夹爪、后退、重新抓；
- `re-place`：把物体放回桌面/起点，重新开始当前里程碑；
- `re-order`：如果任务有多个物体，换下一个更容易的物体（DP 决定）。

执行方式：

1. 用 VLA 的 phase prompt（同一模型，不同输入）：例如 "the cup slipped; pick it up again"；
2. 用确定性伺服（CHUNK-SERVO）执行短回撤/对齐；
3. 两者都不行 → 回退 VLA 开环，不硬做。

### 4.5 规模估算

- 32 任务 ×3 里程碑 ≈ 96 个节点；
- 每个节点 5–10 个关键帧 → 约 1k 张图；
- 128×128 JPEG 约 5–10KB → <20MB；
- 成功表/时长表 <10MB；
- 索引/元数据 <100MB；
- 总 <200MB，可随提交包分发或预加载。

## 5. 实验设计

### 5.1 P0 诊断（先做，决定是否继续）

在单任务通道选 5 个任务（PlugInEthernet、HangCup、ZipUp、StackBowls、FoldTowel），每个跑 10 次基线，记录：

- 失败时间（相对 180s 的百分比）；
- 失败里程碑（approach/grasp/lift/align/insert/release）；
- 失败原因（感知/抓取/接触/超时/人为干扰）；
- 每次 `get_action` 的延迟 p50/p99；
- 实际控制频率 `f_c`。

**Go/No-Go**：

- 如果 ≥50% 失败发生在最后 30% 时间或最后 1–2 个里程碑 → 投 DEADLINE-PLAN。
- 如果 ≥50% 失败发生在最前 30% 时间或抓取阶段 → 先修感知/抓取，不投调度。
- 如果 p99 延迟已经 <50ms 且 N=1 → 调度收益有限，先做里程碑规划。
- 如果 p99 >200ms 或 N≥4 → 调度是刚需。

### 5.2 离线

| 实验 | 数据 | 指标 | 门 |
|---|---|---|---|
| 里程碑分割 | 5 任务人工标注 | 边界 F1 | G0 |
| 成功表校准 | 扰动 rollout + 单任务通道 | 覆盖率、Brier、AUROC | G1 |
| DP 规划 | 回放 100 条演示 + 注入扰动 | 成功率、超时率 | G2 |
| 恢复原语 | 失败演示/仿真 | 恢复成功率、时间 | G2 |

### 5.3 仿真

| 实验 | 变量 | 指标 | 门 |
|---|---|---|---|
| 收敛/期限 | H、N、τ | 成功率、超时率 | G2 |
| 调度 | round-robin / EDF / lookahead | p99、饿死次数、GPU 利用率 | G2 |
| 扰动 | 位置/遮挡/背景/目标移动/人手 | 恢复率、检测延迟 | G4 |

| 项 | 设计 |
|---|---|
| 任务 | PlugInEthernet、HangCup、ZipUp、StackBowls、FoldTowel |

| 通过 | ≥3/5 任务 +10pp；FoldTowel 不回归 >5pp |

### 5.5 多端口干跑

| 项 | 设计 |
|---|---|
| 端口 | N=4（与评测一致） |
| 任务 | 32×2（干跑，不提交） |
| 指标 | 端口隔离、reset 干净、内存不涨、p99、饿死次数 |
| 门 | 无串扰；p99≤217ms（H=8）；内存稳定 |

### 5.6 消融

1. 成功表 on/off。
2. DP on/off。
3. 有效前缀 k on/off（k=H vs 阶段 k）。
4. 调度 on/off（round-robin vs robot-time lookahead）。
5. 恢复原语 on/off。
6. 保形 vs Beta 表 vs 启发式。
7. H=5/8/15/30。
8. 目标检测器：关键帧 vs 纯本体。

### 5.7 统计

- 配对 A/B：同一初始条件，`Δ_t = p_on - p_off`；5 次/任务只能看方向，不能看显著性。
- 汇总 5 任务用 bootstrap；报告 95% CI。
- 若 CI 跨 0，继续测或放弃；不要用 +1–2pp 做结论。
- 320 trials 的 SE≈2.42pp；任何小于 2pp 的全局提升都需要更多重复/配对设计。

## 8. 创新点清单（动机/差异/可行性/资源/步骤/风险）

### 8.1 DEADLINE-DP：机会约束的里程碑规划

- **动机**：VLA 不知道剩余时间、里程碑进度、失败后是否值得再试；一个晚期失败浪费整个 trial。
- **与现有方案的差异**：CHUNK-SERVO 只做 5 步几何闭环；RUBRIC-HEAD/TURN-SERVO 做评分点/回合，但没做期限预算；RACE 做时间最优轨迹，但没做里程碑级成功概率；ACPS 做保形规划，但没接 VLA chunk。DEADLINE-DP 把「剩余时间 × 里程碑成功下界 × 恢复成本」放进一个小 DP。
- **技术可行性**：M≤5、T=180、Δt=1s → 2700 次操作；CPU 1–5Hz；不需要第二个模型。
- **所需资源**：33k 演示（时长分布）、单任务通道/扰动 rollout（成功校准）、CPU。
- **落地步骤**：P0 诊断 → 5 任务里程碑图 → Beta 表 → DP 回放 → 单任务 A/B → 32 任务扩展。
- **风险**：里程碑检测错、成功表漂移、DP 过于保守；用粗节点、分组保形、只做软决策缓解。

### 8.2 PHASE-PREFIX：H 固定，chunk 内只执行 k 步

- **动机**：API 的 H 是全局固定的；接触段需要短反馈，但全局 H=5 可能压垮 N 端口服务器。用「有效运动前缀」在接触段刹住，兼顾接口可行与接触安全。
- **与现有方案的差异**：CHUNK-SERVO 假设可以按阶段改 chunk；实际不能。PHASE-PREFIX 把「H 全局、k 阶段自适应」拆开，是对 API 的正确建模。
- **技术可行性**：只需在返回的 H 步动作里填充 hold/brake；不需要改 evaluator；代价是每 chunk 浪费 `(H−k)/f_c` 秒。
- **所需资源**：无额外数据；只需阶段检测（里程碑图）和 H 选择实验。
- **落地步骤**：H=8 基线 → 阶段 k 表 → 单任务 A/B → 扫 H=5/8/15。
- **风险**：hold/brake 可能被 evaluator 当成异常动作；需要确认 hold 动作的合法性/平滑性；用官方 `example_env.py` 验证。

### 8.3 ROBOT-TIME-SCHED：机器人时间 lookahead 调度

- **动机**：N 端口共享 GPU；round-robin 会拖死接触端口，EDF 会饿死快端口；官方记录延迟波动，调度直接影响成功率和可信度。
- **与现有方案的差异**：Armory 做机器人时间调度，但没接里程碑/成功表；UniBot 选手多数只做「一端口一进程」或「共享模型 + 简单队列」。ROBOT-TIME-SCHED 把阶段 criticality 和成功预算纳入 batch 打分。
- **技术可行性**：N≤8 时枚举 `2^N`；CPU 可承受；`d_infer(b)` 可离线测。
- **所需资源**：N=4/8 GPU 实测、batch 延迟曲线、CPU 调度器。
- **落地步骤**：测 `Θ`/`τ` → 实现 round-robin/EDF/lookahead → N=4 干跑 → 单任务/多任务 A/B。
- **风险**：调度开销、GPU 争用、端口串扰；用 C++/Rust、每端口 session、只读共享内存缓解。

### 8.4 EMBED-RT：每端口实时 supervisor

- **动机**：p99 抖动、Python GIL、内存分配、看门狗缺失，会让接触段在关键时刻卡住；官方明确记录延迟和波动。
- **与现有方案的差异**：多数提交是「Python 服务 + 模型直接返回」；EMBED-RT 把 supervisor 做成嵌入式实时进程，GPU server 只做推理。
- **技术可行性**：30Hz 控制、N≤8、CPU 轻量；C++/Rust 或 Python+uvloop 都可 MVP。
- **所需资源**：CPU 核、实时优先级、共享内存、日志。
- **落地步骤**：Python MVP → 延迟剖析 → C++/Rust 热路径 → p99 门。
- **风险**：实时优先级在容器/云主机不可用；用 CPU 亲和 + 预分配 + 看门狗兜底。

### 8.5 FAILURE-AUDIT：失败时间/里程碑审计

- **动机**：不知道失败发生在哪，就无法决定投感知、接触还是调度；榜单是预览，不能反推。
- **与现有方案的差异**：多数团队只报成功率；FAILURE-AUDIT 把「失败时间、失败里程碑、失败原因、延迟」做成结构化日志，作为数据飞轮。
- **技术可行性**：单任务通道即可；每任务 10 次；人工/自动标注。
- **所需资源**：5 任务 ×10 次真机；日志/视频。
- **落地步骤**：P0 诊断 → 失败分类 → 更新任务组合 → 复测。
- **风险**：样本少、标注主观；用配对/重复实验缓解。

### 8.6 CONFORMAL-CAL：分组保形成功校准

- **动机**：成功表在不同物体/背景/干扰下会漂移；需要一个有覆盖保证的下界，避免 DP 过度乐观。
- **与现有方案的差异**：ReconVLA 校准 action token 不确定性，但不做里程碑规划；ACPS 做状态估计保形，但不接 VLA chunk。CONFORMAL-CAL 把保形用在里程碑成功概率上，并做分组校准。
- **技术可行性**：校准集来自单任务通道/扰动 rollout；逻辑回归/查表；CPU 轻量。
- **所需资源**：失败样本（关键）、分组标签、校准脚本。
- **落地步骤**：Beta 表 → 分组保形 → 覆盖率检查 → DP 集成。
- **风险**：可交换性不成立、失败样本不足；用自适应保形 + 保守先验 + 只做软决策缓解。

## 9. 风险与合规

### 9.1 单模型合规的三种模式

| 模式 | 做法 | 风险 | 建议 |
|---|---|---|---|
| **C1 离线标注** | 里程碑/成功表只离线生成；线上只有 VLA + 查表 | 最低 | 保守首选 |
| **C2 确定性控制器** | 里程碑检测、DP、调度、看门狗都是几何/统计/控制律 | 低；需向官方说明 | 主推 |
| **C3 同 checkpoint 特征** | 成功表的特征用 VLA 同一 checkpoint 的 encoder，不加载第二个模型 | 低–中；需说明 | 需要强特征时用 |

**禁止**：加载第二个学习策略/残差网络/独立视觉编码器做在线决策；为每个任务训一个策略；用在线 ASR/TTS 增加延迟（API 也没有音频）。

### 9.2 风险表

| 风险 | 影响 | 缓解 |
|---|---|---|
| 里程碑分割错 | 错误重规划 | 只用 2–5 个粗节点；低置信度回退 VLA |
| 成功表分布漂移 | 保形覆盖失效 | 分组/自适应保形；只做软决策 |
| 单模型解释 | 被判第二个模型 | C1/C2/C3；表/DP/调度无学习权重 |
| 调度开销 | 增加延迟 | one-step lookahead；N≤8；C++/Rust |
| Python GIL | p99 抖动 | 每端口独立进程；uvloop；热路径 C++ |
| 端口串扰 | 状态污染 | 每端口 session；独立 reset；共享内存只读 |
| 过期 chunk | 接触段盲推 | 接触段 hold；搬运段 staleness 检查 |
| hold/brake 非法 | 动作被拒 | 用官方 `example_env.py` 验证；保持平滑/限幅 |
| `pivot` 语义不一致 | 动作被拒/机器人不动 | 先返回全零 pivot；单任务通道验证 |
| 预览榜单误导 | 方向错误 | 单任务通道；配对 A/B；不反推难度 |
| 时间不够 | 32 任务铺太大 | 先 5 任务；A 档 3–5 个；B/C 档保留基线 |
| 评测噪声 | +1–2pp 假阳性 | 配对 A/B、bootstrap、重复实验；SE≈2.4pp |
