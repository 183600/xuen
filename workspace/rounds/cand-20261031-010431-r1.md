# 第 13 轮 · REL-OS：把 320 次真机 trial 当成可靠性工程——先修「能不能稳定交付」，再谈「模型有多强」

> 检索/复核日期：**2026-10-31（UTC）**。赛事身份不变：宇树 **UniBot 世界挑战赛**（unibot.unitree.com），G1 + Dex1，32 项桌面任务，通才单模型赛道，选手自部署 + 官方远程真机 API。本轮是新一轮灵感循环第 1 轮，三个词是「**成功率**」「**可靠性**」「**机器人操作系统**」。本轮不推倒第 10 轮 FACT-VLA、第 11 轮 GEO-RESIDUAL、第 12 轮 CHUNK-SERVO；而是补上它们共同缺的系统层：**CHUNK-SERVO 决定「最后 3 厘米要不要闭环」，REL-OS 决定「这个闭环在 N 个端口、有限推理算力、10 次/task 的抽样噪声下能不能稳定交付」。**

## 0. 先给结论：30% 不是能力天花板，是可靠性天花板；而 5 步 chunk 在 N 端口下可能根本排不上队

截至 2026-10-31，官网排行榜经 `r.jina.ai` 抓取仍显示 8 个模型：MolmoAct 29.7%、WALL-OSS-0.5 28.5%、DreamZero 27.9%、Spirit-v1.5 25.9%、DM0 23.5%、π0.5 22.8%、GigaBrain-0 22.6%、GR00T N1.5 20.5%。但同一页面也标注「即将发布」，最新搜索快照的表格甚至是空的；这些数字只能当**历史预览**，不能当实测 SOTA。真正会改变方案的是五个结构性事实：

1. **320 次 trial 的统计噪声约 ±5pp。** p≈0.28 时 `SE=sqrt(0.28×0.72/320)=2.5pp`，95% CI ±4.9pp；8 个模型头尾只差 9.2pp。也就是说，榜单上的名次大部分在噪声里，追 +1–2pp 的模型改动没有意义，只有机制性的大幅增益才可信。
2. **10 次/task 的后验区间宽得惊人。** 0/10 的 95% Beta 区间是 [0.2%, 28.5%]，10/10 是 [71.5%, 99.8%]。一个任务看起来「完全不会」或「完全会」，都可能只是 10 次抽样的结果；工程分配必须用分层后验/下限置信界，而不是点估计。
3. **参考 PolicyService 把任何异常变成致命错误。** `get_action` 抛异常 → server 把 traceback 作为文本帧发回，然后以 `CloseCode.INTERNAL_ERROR` 关闭连接；参考客户端只在握手阶段重连，mid-episode 不重连。一次 NaN/形状错误/超时，可能直接终结一个 trial。全量评测约 `320×100=32,000` 次调用；0.1% 的 per-call 异常率就是 ~32 次故障，按 S=30% 估算可吃掉 ~3pp；1% 可吃掉 ~30pp。
4. **N 端口共享一个大模型时，固定 5 步 chunk 可能不可调度。** 设单次推理服务时间 S、控制频率 f=30Hz、端口数 N、chunk 长度 H，则每个端口的执行间隔 A=H/f；闭环稳定的必要条件是 `S < A/(N-1)`，即 `H > f·S·(N-1)`。S=80ms 时：N=3 → H_min≈4.8（H=5 刚好在稳定边界），N=8 → H_min≈16.8（H=5 必然排队）。合成仿真里 N=8、H=5、S~80ms 的 p99 响应延迟约 650ms、100% 的 chunk 在返回时已经过期；这比 CHUNK-SERVO 想替代的 1s 开环好不了多少。**短 chunk 不是免费的；它消耗的是 GPU 的实时预算。**
5. **官方数据已经补上了腕部内参。** 当前 HF 版本（HangCup `lastModified 2026-10-14`）在 `camera_params.wrist_left/right.color` 中给出了内参与畸变，推翻了第 12 轮「腕部无内参」的假设；这删掉了一项原计划的标定工作，但也意味着不能再用旧版元数据做方案假设，所有离线管线必须按当前版本重跑。

所以本轮的押注是 **REL-OS**：

> 不换更大的模型，而是把现有 VLA 包进一个 **fail-operational 的 per-port 运行时**：异常防火墙保证任何故障都退化成安全 hold 而不是断连；风险加权调度把短 chunk 留给正在接触的端口、把长 chunk 留给运输中的端口；缓存 VLM 特征的快速动作头把单次服务时间压到足以支撑短 chunk；值门控恢复只在期望收益为正时干预；分层 Beta 后验把工程投到「地板任务」而不是已经 80% 的任务。

一句话：**先把「成功率」当成系统可靠性指标，而不是模型能力指标。**

三个可验证创新点（不是三个宏大名目）：

1. **PORT-OS**：每端口生命周期 + 异常防火墙 + 动作盾 + 看门狗 + 状态隔离 + 结构化回放；目标是把协议/运行时故障率压到 0，p99 开销 <10ms。
2. **RISK-SCHED + CFAH**：风险加权 EDF 调度 + 按风险自适应 chunk + 缓存 VLM 特征的快速动作头；目标是在 N=3/8 下把 p99 陈旧率压到 <5%，同时保留接触段的短 chunk。
3. **VGR + REL-ALLOC**：确定性故障信号 + 反事实值门控 + 180s 时间预算内的重试/回退；分层 Beta-Binomial + 下限置信界 + 配对序贯检验，把 320 trials 的工程预算投到期望增益最大的任务。

三个灵感词怎么落到方案里：

| 灵感词 | 落到哪里 | 不做什么 |
|---|---|---|
| **成功率** | 320-trial 统计噪声、10 次/task 后验、分层 Beta、抬地板、步骤分保护 | 不追 +1–2pp 的噪声级改动；不把预览榜单当 SOTA |
| **可靠性** | fail-operational 运行时、异常防火墙、动作盾、看门狗、值门控恢复、无回归约束 | 不做第二个学习模型；不做不可逆的高风险干预 |
| **机器人操作系统** | per-port lifecycle、风险加权 EDF、共享推理后端、截止时间/陈旧动作、缓存特征动作头、可观测/回放 | 不把 ROS2 塞进提交接口；不引入 MoveIt 全栈；不依赖 ROS2 运行时 |

## 1. 本轮新核实的事实（只列会改变方案的）

### 1.1 规则：32×10、5 类泛化各 2 次、180s、单模型、N 端口、单任务不计分通道

官方参赛手册（2026-10-31 经 `r.jina.ai` 复核，§1.1–§2.2）明确：

- 32 个任务，每个任务 **10 次独立运行**；5 类泛化各 2 次：位置、干扰物、桌面背景、未见物品、人为干扰。
- 单次真机执行上限 **180 s**；超时记失败，并按执行情况计算步骤分。
- 排名先看 32 任务**总平均成功率**；相同看总平均步骤分；再相同看**更早提交**。
- 所有任务须基于**同一模型**完成，不得混合多个模型；模型类型不限（World Model、VLA 均可）。
- 评测跨 **N 台机器人**；提交须从 **8765** 起暴露 N 个连续端口；每端口独立交互，`reset()` 状态必须隔离。
- 另有**不计分的单任务测试通道**，可用于单任务成功率/步骤分验证。

**对方案的约束**：REL-OS 必须是每端口独立、CPU 轻量、不抢 GPU 的确定性运行时；不能是第二个策略模型；单任务通道是唯一敢做 A/B 的地方。

### 1.2 API 与运行时：四路 RGB、无深度/力/触觉、N 端口、延迟与动作规律会被记录

提交模板 README（2026-10-31 复核 raw 版本）给出：

- 观测：`cam_left_high`、`cam_right_high`、`cam_left_wrist`、`cam_right_wrist` 四路 RGB 480×640；双臂关节 `[7]`、EE 位姿 `[6]`（xyz+rpy，base 系）、夹爪 `[1]`、下身体 `[15]`、语言 `str`。
- `metadata` 字段：`control_space`、`obs_delta_indices`、`image_resize`、`action_chunk_size`、`token`；`obs_delta_indices` 同时决定**发哪些观测**和**叠几帧**。
- 动作：`joint` 或 `ee` 互斥；`action_chunk_size` 固定；index 0 先执行，其余顺序执行，直到 evaluator 再次调用 `get_action`；**chunk 内没有新观测，也没有打断机制**。
- 没有 depth、camera_info、force/torque、tactile。
- 部署：N 个连续端口从 8765 起；每端口独立、稳定完成整条交互；官方给出两种实现：每端口独立 server（最稳）或共享模型后端（省资源，需自行处理并发与状态隔离）。
- **§6 交互质量与成绩可信度**：评测端逐步记录每次 `get_action` 的响应时延、波动和返回动作的统计规律，并可能随成绩一起展示；要求时延平滑稳定、动作格式规范、无异常离群值、避免不规律交互模式。

**关键推论**：参考 server 的 `get_action` 是同步调用；如果推理阻塞，单端口会卡住；共享后端如果不做线程/进程隔离，N 个端口会互相阻塞。延迟抖动和动作异常不只是工程问题，可能直接影响成绩可信度。**运行时是评分面的一部分。**

### 1.4 官方基线：WLA 6B / 2,500h / 64 任务 / 默认 chunk 30 / 24GB 微调

- **UnifoLM-WLA-1.0**：6B 参数，约 2,500 小时真机数据，64 个任务（桌面 + 全身），支持二指夹爪和五指灵巧手；2026-09-28 开源 Base 权重、微调代码、模型服务器。
- 动作专家默认 `target_fps=30`、`chunk_size=30`，覆盖约 `[0, 29/30]` 秒；4 步扩散去噪；微调时冻结 VLM（`qwen_vl_interface`），只训 DiT action head + robot-state projector，默认单张 **24GB** GPU。
- 提交模板的 `ExamplePolicy` 默认 `action_chunk_size=8`，且示例堆叠 4 帧图像、3 帧状态。**官方自己的示例也没有用 30 步；chunk size 是提交侧的控制参数，不是模型常量。**
- 统一动作空间 54 维、状态 60 维；挑战赛 `ee` 动作是 2×6 EE + 2×1 gripper + 7 pivot。adapter 仍需处理「WLA 相对 EE → 挑战赛绝对 EE」和 `pivot` 语义，但这不是本轮重点；本轮假设第 12 轮的 adapter 已验证。

**战略结论**：不要再从零训 6B/14B；把官方 WLA 基座拿来做 action-head 微调/缓存特征推理，把省下的算力投到**运行时、调度、恢复和评测统计**。

### 1.5 榜单：8 个预览模型，但页面同时标注「即将发布」

2026-10-31 的抓取出现两种状态：

- `r.jina.ai` 抓取的 `leaderboard.html` 仍显示 8 个模型（MolmoAct 29.7% … GR00T N1.5 20.5%）。
- 同一页面的末尾标注「即将发布」；搜索快照的表格是空的；`runs.html` 也是「即将发布」。

结合第 12 轮已经做过的取证（`leaderboard_data.json` 的 `step~success` 回归 R²>0.999999、每任务成功率不是 10% 的整数倍、32 个任务视频是占位符），本轮的判断是：

> **29.7% 只能作为「赛事方预览/难度信号」，不能作为 SOTA、任务难度表或失败分布。** 本轮不从榜单名次挖创新点，只从规则、API、数据和公开模型家族的技术路线里挖。

### 1.6 参考 server 的故障行为：一个异常就可能终结一个 trial

从 `policy/web_policy.py`（2026-10-31 读取）确认：

- `PolicyService._on_connection` 对每个请求调用 `route(request)`；`get_action` 是同步的。
- 任何 handler 异常 → `await socket.send(traceback.format_exc())`，然后 `await socket.close(code=CloseCode.INTERNAL_ERROR, ...)`，并重新抛出。
- 服务端和客户端都设置 `ping_interval=None, ping_timeout=None`；没有应用层心跳/截止时间。
- 客户端 `RemotePolicy._handshake` 只在 `ConnectionRefusedError` 时每 5 秒重试；**mid-episode 没有重连逻辑**。
- `/healthz` 只是一个 HTTP liveness 探针，不检查模型是否卡住、动作是否合法、状态是否泄漏。

**结论**：提交侧必须自己实现「异常防火墙 + 截止时间 + 安全回退 + 状态隔离」。这不是可选的工程优化，而是防止一次异常吃掉一个 trial 的必要条件。

### 1.7 近期工作：失败检测/恢复很热，但「何时干预」和「运行时调度」仍是空白

- **失败检测/恢复**：RoboFailRing（ACL 2026）用失败记忆检索做及时检测；FLARE（CVPR 2026）用 Retry/Reset 范式；VLA-Corrector（arXiv 2609.06508）用 stage-aware verifier + prompt recovery；ProbeAct（arXiv 2606.09740）用 hidden-state probe + CBF；FailureSpot（arXiv 2609.04277）用 action-derived weak supervision 做时间戳级检测；CycleVLA（arXiv 2601.02295）做 subtask backtracking。
- **运行时监控的价值边界**：RESCUE（arXiv 2610.13516）指出，监控器的检测精度不等于干预价值；在 stop-and-reset 模型下，即使理想检测器也只能承受 **2.0–3.3%** 的误报率，否则不必要的重置会抵消收益。**这直接否决了「检测到异常就重置」的粗暴方案。**
- **测试时扩展**：MG-Select（ICLR 2026 / arXiv 2510.05681）用同一 VLA 的条件掩码分布做 verifier-free 选优；RoboMonkey（PMLR 2025）用采样 + 验证器；TokenPB（arXiv 2603.18091）用同一 checkpoint 的 bucket token 自验证。**这些工作证明「同一模型多采样 + 选优」可行，但都假设算力无限；在 N 端口共享 GPU 时，必须把采样预算纳入调度。**
- **运行时保证/OS**：SOTER（arXiv 1808.07921）的 RTA 模式（先进控制器 + 安全控制器 + 决策模块）；fallback-safe MPC（arXiv 2309.08603）；ROS 2 lifecycle/watchdog（Nav2 Lifecycle Manager、ros-safety software_watchdogs、ros2_medkit graph_watchdog）；K8s + ROS2 的分布式故障缓解（arXiv 2410.18825）。**这些给出了「fail-operational」的设计语言，但还没有人把它落到 UniBot 的 N 端口提交运行时上。**
- **评测统计**：RoboLab 的 Beta  credible interval；SureSim（arXiv 2510.04354）用 PPI 结合仿真和真机；PhAIL（arXiv 2605.29710）用 time-to-success CDF；「Beyond Binary Success」（arXiv 2603.13616）用 anytime-valid sequential testing。**10 次/task 的官方设置下，这些统计工具不是可选项，而是防止把噪声当结论的必需品。**

### 1.8 为什么现在能做

- 官方 WLA 基座 + 24GB 微调：不用从零训。
- 官方示例 `action_chunk_size=8`：说明短 chunk 是官方预期内的用法，不是异端。
- 腕部内参已发布：G0 标定工作量大幅下降。
- 33k 成功演示 + 180s 余量：可以离线校准失败信号和重试价值。
- 参考 server 代码公开：可以精确知道异常/延迟/状态隔离的边界。
- N 端口、共享后端、延迟/动作规律记录：官方直接把「运行时可靠性」写进了接口和可信度条款。

## 2. 诊断：三个「不是模型」的故障源

把一次失败拆开，除了「模型不会」，还有三类系统性故障：

```text
t0: evaluator 调用 get_action
      │
      ├─ A. 协议/运行时故障：异常、NaN、形状错、端口串扰、reset 不干净
      │     → server 断连 / evaluator 拒绝动作 / 状态污染
      │
      ├─ B. 排队/陈旧动作：N 端口共享 GPU，短 chunk 导致请求率 > 服务率
      │     → 返回的 chunk 已经过期，机器人执行的是「旧世界的动作」
      │
      └─ C. 误干预/回退：检测到异常就重置/重试，但重置成本 > 继续执行
            → 把本来能成功的 trial 打断，或把已完成的子目标破坏
```

对应的可靠性工程语言：

| 故障源 | 可靠性机制 | 度量 |
|---|---|---|
| A 协议/运行时 | 异常防火墙、动作盾、看门狗、状态隔离、监督进程 | 协议故障率、p99 开销、跨端口污染次数 |
| B 排队/陈旧 | 风险加权 EDF、自适应 chunk、缓存特征动作头、截止时间回退 | p99 响应延迟、chunk 陈旧率、deadline miss |
| C 误干预 | 反事实值门控、时间预算、可逆动作、无回归约束 | 干预精确率、误报率、每次干预的期望增益 |

**这三个故障源都不需要换更大的模型，但都能直接吃掉成功率。** 这就是本轮把「可靠性」放在「能力」前面的原因。

## 3. 方法：REL-OS

### 3.1 总架构

```text
                    ┌────────────────────────────────────────────┐
                    │  Evaluator (N ports 8765..8765+N-1)        │
                    └───────────────┬────────────────────────────┘
                                    │ websocket: obs / action chunk
                                    ▼
        ┌──────────────────────────────────────────────────────────┐
        │  Per-port PolicyService (CPU)                            │
        │  ├─ Lifecycle: INIT→READY→ACTIVE→DEGRADED→SAFE_HOLD→DONE │
        │  ├─ Exception firewall (never propagate)                 │
        │  ├─ Action shield (shape/dtype/NaN/limits/continuity)    │
        │  ├─ Deadline watchdog (hold if inference misses)         │
        │  ├─ Per-episode state (reset barrier, no shared mutable) │
        │  └─ Telemetry: latency, action stats, transitions, MCAP  │
        └───────────────┬──────────────────────────────────────────┘
                        │ async, per-port queue, risk score
                        ▼
        ┌──────────────────────────────────────────────────────────┐
        │  Risk-aware inference scheduler (shared GPU backend)     │
        │  ├─ risk-weighted EDF / aging / deadline fallback        │
        │  ├─ adaptive chunk H_i per port                          │
        │  ├─ optional best-of-N only when slack                   │
        │  └─ full VLA + cached-feature action head (CFAH)         │
        └───────────────┬──────────────────────────────────────────┘
                        │
                        ▼
        ┌──────────────────────────────────────────────────────────┐
        │  VGR (value-gated recovery)                              │
        │  ├─ deterministic failure signals                        │
        │  ├─ counterfactual value gate + 180s time budget         │
        │  └─ retry / backtrack / hold / replan (same VLA)         │
        └──────────────────────────────────────────────────────────┘
```

- **唯一学习模型**：VLA（官方 WLA 微调 action head）；CFAH 是同一 checkpoint 的推理拆频，不是第二个模型。
- **确定性控制器**：动作盾、看门狗、调度器、值门控、视觉伺服；无学习权重。
- **数据资产**：33k 成功演示 → 失败信号阈值/重试价值/目标库；不是第二个模型。
- **数字孪生**：只做延迟/增益/扰动风洞，不训练策略。

### 3.2 PORT-OS：fail-operational 的 per-port 生命周期

状态机：

```text
INIT ──metadata/reset──▶ READY ──first obs──▶ ACTIVE
  ▲                        │                    │
  │                        │                    ├─ exception/NaN ──▶ SAFE_HOLD
  │                        │                    ├─ deadline miss ──▶ DEGRADED
  │                        │                    ├─ failure signal ─▶ RECOVER
  │                        │                    └─ task done ──────▶ DONE
  │                        │                                           │
  └────────────────────────┴──────── reset ◀──────────────────────────┘
```

规则：

- `SAFE_HOLD`：返回当前 EE 绝对位姿（`ee` 模式）或当前关节（`joint` 模式）+ 当前夹爪 + 零 pivot；这是**永远合法**的动作，不会因为模型异常而断连。
- `DEGRADED`：推理超时/延迟抖动 > 阈值；返回上一组安全 chunk 或 hold，记录 deadline miss；下一次请求优先恢复。
- `RECOVER`：VGR 触发；只在值门控通过时进入；有最大重试次数和总时间预算。
- `DONE`：任务成功/最大步数；清理状态，等待 `reset()`。
- **异常防火墙**：`get_action` 外层 `try/except BaseException`（至少 `Exception`），任何异常都不得穿透到 `PolicyService`；返回安全动作并记录。
- **动作盾**：检查 key 集合、shape、dtype、NaN/Inf、关节/EE 限位、chunk 内跳变、夹爪范围；非法动作替换为 hold，而不是让 evaluator 拒绝。
- **状态隔离**：每端口独立 policy 实例；共享模型只读；reset 清空历史、plan cache、goal、VGR 计数器；不允许全局可变状态。
- **监督进程**：每端口一个进程（或进程池），supervisor 检测 crash 并重启；重启后 `reset()` 必须干净；不要在一个进程里共享可变 episode 状态。

### 3.3 RISK-SCHED：把 chunk 长度当成调度资源

定义：

- 端口 i 的风险 `r_i ∈ [0,1]`：接触距离、夹爪闭合、任务阶段、最近失败信号、剩余时间。
- 端口 i 的 chunk `H_i`：风险高 → 短（5–10）；风险低 → 长（20–30）。
- 端口 i 的截止时间 `d_i`：`H_i/f - margin`；超过则返回 hold，避免陈旧动作。
- 调度优先级：`π_i = r_i + aging·wait_i`；aging 防止低风险端口饿死。
- 共享后端只允许一个（或少量）高风险的短 chunk 端口同时运行；其他端口排队或降级为长 chunk。

**容量规则**（本轮最重要的工程结论）：

```text
闭环稳定必要条件：S < A/(N-1)，A = H/f
=> H_min ≈ f · S · (N-1)
```

| S（单次推理） | N=3 | N=8 |
|---:|---:|---:|
| 20 ms | H_min≈1.8 | H_min≈4.2 |
| 40 ms | H_min≈3.6 | H_min≈8.4 |
| 80 ms | H_min≈4.8 | H_min≈16.8 |
| 120 ms | H_min≈7.2 | H_min≈25.2 |

含义：

- 如果 N=3、S=80ms，H=5 只是**刚好**稳定；H=8–10 更安全。
- 如果 N=8、S=80ms，H=5 **不可调度**；必须 H≥17，或把 S 降到 <24ms（H=5），或多卡。
- 如果官方 N 未知，提交侧应在启动时测量 S，并按 `H_min+margin` 选择 chunk；这比拍脑袋固定 5 步可靠。
- 短 chunk 的收益必须扣除排队延迟：`D_i = W_i + S_i`；如果 `D_i` 接近 1s，短 chunk 就失去了意义。

### 3.4 CFAH：缓存 VLM 特征的快速动作头

目的：把 S 从 80–150ms 降到 20–40ms，使 N=8/H=5 或 N=3/H=5 有足够余量。

做法（不新增学习模型）：

1. 低频（每 K 步，如 K=30）跑 VLM/视觉编码器，缓存任务/场景特征 `z_t`。
2. 高频（每个 chunk）只跑 DiT action head + robot-state projector，条件为 `z_t` + 当前本体 + 腕部图像特征。
3. 如果 `z_t` 过期超过阈值（场景变化/人为干扰），强制刷新 VLM；否则用缓存。
4. 这是官方 WLA 的推理拆频：VLM 冻结、action head 已训练；不需要新 checkpoint，也不违反单模型。
5. 如果 CFAH 在某个任务上掉点，回退到全模型低频推理；CFAH 是**性能选项**，不是唯一路径。

### 3.5 VGR：值门控恢复，而不是「检测到就重置」

信号（确定性，无学习权重）：

- 动作层：冻结（连续 chunk 几乎相同）、振荡（方向反复）、跳变（chunk 间距离过大）、NaN/限位。
- 本体层：夹爪闭合但 EE 不动（空抓/滑移）、EE 位移与指令方向相反、关节速度饱和。
- 几何层：第 11 轮的 `d_t, n_t, r_static, r_grasp, edit_score`；目标被移动/拿走/遮挡。
- 任务层：官方 rubric 子目标（如 HangCup 抓把手/挂上；ToolboxStorage 收 2 个/收完/合盖/上锁）；进度回退检测（human 轴「拉上再拉开」）。

值门控：

```text
干预收益 ≈ (p_rec - p_cont) · ΔV - C_time - (1-p_rec) · C_regression
```

- `p_rec` 用离线校准的保守下限；`p_cont` 是继续执行的估计成功率。
- 只有在 `干预收益 > 0` 且 `剩余时间 > 重试时间 + 安全余量` 时才干预。
- 误报预算参考 RESCUE：stop-and-reset 下理想检测器也只能承受 2–3% 误报；所以默认动作是**继续 + 降速/保守伺服**，不是重置。
- 干预优先级：继续 > 降速/hold > 重试当前子目标 > 回退一个子目标 > 重规划。**越靠后越贵，越要严格的证据。**
- 无回归约束：已完成子目标进入「保护集」；后续动作如果会穿过/扰动保护集，限速或拒绝。

### 3.6 可观测与回放

- 每次 `get_action` 记录：时间戳、端口、obs hash、动作统计（min/max/mean/std/NaN）、推理时间、队列等待、状态迁移、VGR 决策、异常。
- 用 MCAP/rosbag2 风格（或简单 JSONL + 视频关键帧）做 episode 回放；失败样本进入 failure corpus。
- 离线回放可以复现「哪一次调用、哪一个动作、哪一个信号」导致失败；这是把 320 trials 变成可学习数据的唯一方式。
- 监控指标：协议故障率、p50/p95/p99 延迟、deadline miss、chunk 陈旧率、VGR 触发率/精确率、每任务成功率、步骤分。

## 4. 创新点清单（动机 / 与现有方案差异 / 可行性 / 资源 / 落地步骤 / 风险）

### I1 · PORT-OS：fail-operational 的 per-port 运行时

- **动机**：参考 server 任何异常都会断连；没有应用层心跳/截止时间；N 端口/状态隔离是官方硬要求；评测端记录延迟与动作规律。一次异常可能吃掉一个 trial；0.1% per-call 异常率约等于 -3pp。
- **与现有方案的差异**：第 10–12 轮都在模型/控制层；I1 是系统层。它不加载第二个模型，不改变策略，只在策略外面加确定性外壳。它借用 ROS2 lifecycle/watchdog 的设计模式，但不把 ROS2 放进提交路径。
- **技术可行性**：高。纯 Python/asyncio/进程；不需要 GPU；可用官方 `run_server.py`/`example_policy.py` 直接包。
- **所需资源**：1 名工程师 1–2 周；CPU；故障注入脚本；N 端口压测环境。
- **落地步骤**：① 包 `SafePolicy`；② 异常防火墙；③ 动作盾；④ deadline watchdog；⑤ per-port state/reset 屏障；⑥ supervisor + `/readyz`；⑦ 故障注入（异常/NaN/错形状/延迟/端口串扰）；⑧ 32×10 干跑。
- **风险**：hold 动作可能打断正在进行的接触；动作盾可能误杀合法动作；supervisor 重启会丢 episode 状态。缓解：hold 只用于异常/超时；动作盾只做硬约束；重启只作为最后手段。

### I2 · RISK-SCHED + CFAH：把短 chunk 留给真正需要的端口

- **动机**：固定 5 步 chunk 在 N 端口下可能排队到 >600ms；短 chunk 的收益被队列延迟吃掉；接触端口和运输端口对延迟的需求不同。
- **与现有方案的差异**：第 12 轮把 chunk size 当固定控制参数；I2 把它当成**可调度的实时资源**，并引入 CFAH 降低 S。它不改变模型语义，只改变推理频率和输入缓存。
- **技术可行性**：中。调度器/风险评分容易；CFAH 需要官方 WLA 的 action head 和一次性能剖析；最坏情况回退全模型。
- **所需资源**：1×24GB GPU；N 端口压测；延迟 trace；1 名工程师 2–3 周。
- **落地步骤**：① 测 S 分布（全模型/CFAH，batch=1..N）；② 实现风险评分与 EDF；③ 自适应 H；④ CFAH 原型；⑤ 离线 trace 回放 + 合成仿真；⑥ 单任务通道 A/B；⑦ 全量干跑。
- **风险**：CFAH 掉点；单模型合规解释；批处理增大首请求延迟；风险评分不准。缓解：CFAH 只作为可选路径；保留全模型回退；batch 窗口 ≤5ms；风险评分用保守阈值。

### I3 · VGR + REL-ALLOC：只做值为正的干预，只投期望增益最大的任务

- **动机**：失败检测已经很多，但「检测到就重置」会亏（RESCUE 2–3% 误报预算）；180s 给重试留了时间；10 次/task 的噪声让 +1–2pp 不可信；human 轴会撤销已完成子目标。
- **与现有方案的差异**：第 11 轮 GEO-RESIDUAL 做检测/几何，第 12 轮 CHUNK-SERVO 做伺服；I3 做**决策**：是否干预、干预哪一层、何时放弃。REL-ALLOC 把 `q_t×Δ/cost` 升级为分层 Beta + 下限置信界 + 序贯配对检验。
- **技术可行性**：中高。信号是确定性的；阈值可离线校准；单任务通道可 A/B；统计工具现成（scipy）。
- **所需资源**：1 名工程师 2 周；5 个代表任务的单任务通道；历史评测日志；离线回放。
- **落地步骤**：① 定义信号与阈值；② 在成功演示 + 扰动回放上标定；③ 实现 VGR 状态机/行为树；④ 单任务 A/B（servo off/on, VGR off/on）；⑤ 分层 Beta + LCB 选任务；⑥ 序贯停止规则；⑦ 全量前复核。
- **风险**：误报/漏报；重试成本；任务特定阈值；统计模型错配。缓解：保守下限；可逆动作；按任务族共享先验；用 held-out session 校准。

## 5. 与第 10/11/12 轮的关系：保留、升级、剪枝

**保留**：

- FACT-VLA 的相位化 BC、CAC 柔顺执行、EGP 证据门控；
- GEO-RESIDUAL 的动作条件化残差、米制表面距离、编辑检测；
- CHUNK-SERVO 的双频执行、演示检索相对目标、数字孪生标定；
- 官方 WLA 基座、33k 演示、官方 rubric、单任务通道。

**升级**：

- 固定 5 步 chunk → **风险自适应 chunk + 调度**；短 chunk 只在有算力余量时使用；
- 失败检测 → **值门控恢复**；默认继续，只有期望收益为正才干预；
- 任务组合 `q_t×Δ/cost` → **分层 Beta + LCB + 序贯检验**；把 10 次/task 的噪声纳入决策；
- 「最后 3 厘米」→ **「最后 3 厘米 + 运行时 3 毫秒」**；异常/超时/状态污染同样是得分点；
- 腕部标定 G0 → **用发布内参 + 重投影抽检**；省下的时间投到运行时和调度。

**剪枝**：

- 不做从零训 VLA/World Model（官方 WLA 已做完）；
- 不做完整 sim-to-real 策略训练（只做控制器风洞）；
- 不做第二个学习模型/残差策略（单模型风险；用确定性控制器）；
- 不做 6D 物体位姿网络（透明/变形不可靠；用相对目标 + 局部对齐）；
- 不做力/触觉闭环（API 没有）；
- 不把 ROS2 塞进提交接口（只借设计模式）；
- 不假设 5 步 chunk 永远优于 30 步（取决于 N、S、任务阶段）；
- 不追 +1–2pp 的榜单噪声（320 trials 的 SE≈2.5pp）；
- 不做 32 个任务各一个策略（规则禁止，且不泛化）。

## 7. 风险与合规

| 风险 | 影响 | 缓解 |
|---|---|---|
| 单模型解释 | 被判定为第二个模型 | 运行时/CFAH/伺服都是确定性或同一 checkpoint；提交材料写清楚 |
| N 未知/变化 | 固定 H 不可调度 | 启动测 S；按 H_min+margin 自适应；保留多卡/长 chunk 回退 |
| 参考 server 异常断连 | 一个 trial 直接失败 | 异常防火墙；hold 永不让异常穿透 |
| 动作盾误杀 | 合法动作被替换 | 只做硬约束；灰度/单任务验证；记录 veto 原因 |
| VGR 误干预 | 把成功 trial 打断 | 值门控 + 保守下限 + 可逆动作；误报预算 <3% |
| CFAH 掉点 | 成功率下降 | 单任务 A/B；掉点即回退全模型 |
| 延迟抖动 | 成绩可信度下降 | deadline 调度；p99 监控；降分辨率/长 chunk |
| 统计过拟合 | 把噪声当结论 | 分层先验；session 分组；预注册门；配对检验 |
| 端口状态污染 | 跨 episode 串扰 | 每端口独立实例；reset 屏障；共享模型只读 |
| 评测语义未知 | 超时/重连行为不确定 | 单任务通道实测；保守 fallback；保留回滚开关 |

## 8. 一句话押注

**先把 VLA 包进一个 fail-operational 的 per-port 运行时，用风险加权调度把短 chunk 留给接触中的机器人、把长 chunk 留给运输中的机器人，用值门控只做期望收益为正的恢复，用分层 Beta 后验把工程投到地板任务——在 320 次 trial 的噪声里，只有系统可靠性带来的大幅增益是可信的。**

# REL-OS 技术报告：把 UniBot 真机评测当成可靠性系统

> 检索/复核日期：**2026-10-31（UTC）**。本报告是第 13 轮想法区「REL-OS」的产物：事实核对、可靠性形式化、系统设计、伪代码、仿真结果、实验门与风险。它不重复第 10–12 轮的模型/控制细节，只补系统层。所有外部事实均标注来源与检索日期；无法稳定复核的数字明确标为 C 级。

## 0. 摘要与证据等级

**一句话**：UniBot 当前的首要瓶颈不是「模型不够大」，而是 **320 次真机 trial 的可靠性工程**——协议/运行时故障、N 端口共享推理造成的 chunk 陈旧、以及「检测到异常就重置」的误干预，都会直接吃掉成功率；在 10 次/task 的抽样噪声下，只有机制性的大幅增益才可信。

**证据等级**：

| 级别 | 含义 | 本报告中的例子 |
|---|---|---|
| **A** | 官方规则/接口/代码、HF 数据元数据、可复算的统计 | 32×10、180s、N 端口、四路 RGB、`action_chunk_size`、33,276 集、腕部内参、Beta 区间 |
| **B** | 官方 README/模型卡/公开文档，但可能随版本变化 | WLA 6B/2,500h/64 任务/chunk 30/24GB、示例 chunk 8、榜单预览数字 |
| **C** | 合成仿真、文献外推、工程估算 | S=80ms、N=8 的 p99 延迟、CFAH 20–40ms、VGR 阈值、故障损失 pp |

**不声称**：

- 不声称榜单 29.7% 是实测 SOTA；官网同时标注「即将发布」，搜索快照表格为空。
- 不声称 S=80ms 是官方测量；这是 6B 模型 + 四路 RGB + 30Hz 的量级假设，必须用 G1 实测替换。
- 不声称 CFAH/调度器一定涨点；它们是可证伪的工程假设，失败就回退。
- 不声称 320 trials 的 +1–2pp 是真实提升；SE≈2.5pp，95% CI≈±4.9pp。

### 1.3 参考 server 的故障行为

来源：`policy/web_policy.py`（2026-10-31 读取）。

```python
# 行为摘要，不是逐行复制
async def _on_connection(socket, path):
    ...
    try:
        response = route(request)          # get_action 同步执行
        await socket.send(response)
    except Exception:
        await socket.send(traceback.format_exc())
        await socket.close(code=CloseCode.INTERNAL_ERROR, ...)
        raise
```

- `get_action` 在 server 的事件循环里同步执行；推理阻塞会卡住该端口。
- 任何 handler 异常 → 把 traceback 文本发回客户端 → 以 `INTERNAL_ERROR` 关闭连接。
- `ping_interval=None, ping_timeout=None`：没有应用层心跳/超时。
- 客户端 `RemotePolicy._handshake` 只在 `ConnectionRefusedError` 时每 5 秒重试；mid-episode 没有重连。
- `/healthz` 只是 HTTP liveness，不检查模型/动作/状态。

**推论**：提交侧必须自己实现异常防火墙、动作盾、截止时间和状态隔离；否则一次异常可能直接终结一个 trial。

## 3. 可靠性形式化

### 3.1 成功率分解

把任务 t 的成功率拆成「模型能力」和「系统可靠性」：

\[
p_t = (1-\epsilon_t)\, q_t
\]

- \(q_t\)：在没有协议/运行时故障时，模型完成任务的概率。
- \(\epsilon_t\)：一次 trial 中至少发生一次致命协议/运行时故障的概率。

若每次 `get_action` 独立地以概率 \(e\) 抛异常，一次 trial 约 \(m\approx100\) 次调用：

\[
\epsilon_{\text{trial}} = 1-(1-e)^m \approx m e
\]

在 S=30%、320 trials、每次故障杀死一个 trial 的**最坏假设**下：

| per-call 异常率 e | 期望故障数（32,000 calls） | 失败 trial 占比 | 成功率损失 |
|---:|---:|---:|---:|
| 0.01% | 3.2 | 1% | **0.3 pp** |
| 0.03% | 9.6 | 3% | **0.9 pp** |
| 0.1% | 32 | 10% | **3 pp** |
| 0.3% | 96 | 30% | **9 pp** |
| 1% | 320 | 100% | **30 pp** |

**注意**：这是最坏情况；如果 evaluator 容忍重连或异常不杀 trial，损失更小。但参考客户端 mid-episode 不重连，所以「异常 → trial 失败」是合理默认。**0.1% 的 per-call 异常率就足以吃掉 3pp；1% 足以吃掉全部成功率。** 异常防火墙的优先级高于任何模型改进。

### 3.2 抽样噪声

官方每任务 10 次、32 任务，总 trials=320。若整体成功率 p≈0.28：

\[
\mathrm{SE}(S)=\sqrt{\frac{p(1-p)}{320}}=2.51\text{pp},\qquad
95\%\ \mathrm{CI}\approx\pm4.92\text{pp}
\]

8 个预览模型头尾只差 9.2pp，约 1.9 个 CI 宽度；**大部分名次在噪声里**。

单任务 10 次的 Beta(1,1) 后验 95% 区间：

| 成功 k/10 | 95% 下限 | 95% 上限 |
|---:|---:|---:|
| 0 | 0.23% | 28.49% |
| 1 | 2.28% | 41.28% |
| 2 | 6.02% | 51.78% |
| 3 | 10.93% | 60.97% |
| 4 | 16.75% | 69.21% |
| 5 | 23.38% | 76.62% |
| 6 | 30.79% | 83.25% |
| 7 | 39.03% | 89.07% |
| 8 | 48.22% | 93.98% |
| 9 | 58.72% | 97.72% |
| 10 | 71.51% | 99.77% |

**结论**：不能因为一个任务 0/10 就放弃，也不能因为 10/10 就重仓；用 LCB 和序贯检验做决策。

### 3.3 串行子目标与重试

若一个 trial 有 K 个串行子目标，每个成功率 r：

\[
p_{\text{trial}}=\prod_{k=1}^{K} r_k
\]

允许每个子目标一次重试，则：

\[
r'_k = 1-(1-r_k)^2
\]

| 单步 r | 无重试 K=5 | 一次重试 K=5 | 增益 |
|---:|---:|---:|---:|
| 0.70 | 0.168 | 0.624 | +45.6pp |
| 0.80 | 0.328 | 0.815 | +48.7pp |
| 0.90 | 0.590 | 0.951 | +36.1pp |
| 0.95 | 0.774 | 0.988 | +21.4pp |

**结论**：在 180s 预算内，trial 内重试的期望收益很大；但前提是能检测到子目标失败且重试是安全的。这直接支持 VGR，但也要求值门控（不是所有失败都值得重试）。

### 3.4 容量/排队：短 chunk 不是免费的

模型：

- 每个端口执行完一个 H 步 chunk 后，发下一个请求；执行时间 \(A=H/f\)。
- 单个共享推理服务器，服务时间 S（均值），一次服务一个请求。
- 每个端口最多一个未完成请求（闭队列）。
- 服务器利用率 \(\rho = N S/(A+W+S)\)；稳定条件 \(\rho<1\)，最坏 \(W\to\infty\) 时化为：

\[
S < \frac{A}{N-1}
\quad\Longleftrightarrow\quad
H > f\,S\,(N-1)
\]

因此：

\[
H_{\min}\approx f\,S\,(N-1)
\]

| S | N=3 | N=8 |
|---:|---:|---:|
| 20 ms | 1.8 | 4.2 |
| 40 ms | 3.6 | 8.4 |
| 80 ms | 4.8 | 16.8 |
| 120 ms | 7.2 | 25.2 |

- N=3、S=80ms：H=5 刚好在稳定边界；H=8–10 更安全。
- N=8、S=80ms：H=5 不可调度；必须 H≥17，或 S<24ms（H=5），或多卡。
- 如果官方 N 未知：启动时测 S，按 \(H_{\min}+\text{margin}\) 选择 chunk；不要拍脑袋固定 5 步。
- 反馈延迟 \(D_i=W_i+S_i\)；若 \(D_i\) 接近 1s，短 chunk 的收益被排队吃掉。

**这是本轮最重要的工程结论**：第 12 轮的 5 步 chunk 在 N=3 时可能成立，在 N=8 时可能反而制造陈旧动作；chunk 长度必须与 N、S、任务阶段一起调度。

### 3.5 值门控

定义：

- \(p_{\text{cont}}\)：继续执行的估计成功率。
- \(p_{\text{rec}}\)：干预后的估计成功率（保守下限）。
- \(\Delta V=V_{\text{succ}}-V_{\text{fail}}\)：成功/失败的价值差。
- \(C_{\text{time}}\)：干预消耗的时间/机会成本。
- \(C_{\text{regression}}\)：干预把已完成子目标破坏的代价。

干预的期望收益：

\[
G=(p_{\text{rec}}-p_{\text{cont}})\Delta V
  - C_{\text{time}}
  - (1-p_{\text{rec}})\,C_{\text{regression}}
\]

只有当 \(G>0\) 且剩余时间 \(T_{\text{left}}>T_{\text{intervene}}+T_{\text{margin}}\) 时才干预。

**误报预算**：RESCUE（arXiv 2610.13516）在 stop-and-reset 模型下发现，即使理想检测器也只能承受约 **2.0–3.3%** 的误报率；超过这个预算，不必要的重置会抵消收益。所以默认动作是「继续 + 降速/保守伺服」，不是「检测到就重置」。

干预层级（越靠后越贵）：

```text
继续 → 降速/保持 → 重试当前子目标 → 回退一个子目标 → 重规划
```

### 3.6 可靠性记账

每任务后验：

\[
y_{t,i}\sim\mathrm{Bernoulli}(p_t),\qquad
p_t\sim\mathrm{Beta}(\alpha_t,\beta_t)
\]

按任务族/难度共享先验：

\[
\alpha_t=\mu_{g(t)}\kappa_{g(t)},\qquad
\beta_t=(1-\mu_{g(t)})\kappa_{g(t)}
\]

看到 k 次成功、n 次失败后：

\[
p_t\mid y\sim\mathrm{Beta}(\alpha_t+k,\ \beta_t+n-k)
\]

决策用下限置信界：

\[
\mathrm{LCB}_t=\mathrm{Beta}^{-1}(0.05;\alpha_t+k,\beta_t+n-k)
\]

任务分配（抬地板）：

\[
t^*=\arg\max_t \frac{\max(0,\tau-\mathrm{LCB}_t)\cdot \Pr(\text{improve})}{\text{cost}_t}
\]

配对 A/B：同一任务/初始条件配对，用 McNemar 检验或配对 bootstrap；序贯测试用 alpha spending，避免「测到显著就停」的乐观偏差。

**含义**：10 次/task 的官方设置下，点估计不可靠；用 LCB 做保守决策，用序贯检验控制误报。这把「工程时间」当成有限资源分配问题。

## 4. 系统设计

### 4.1 拓扑

```text
Evaluator (N ports 8765..8765+N-1)
   │  websocket
   ▼
Per-port PolicyService (CPU, one process per port)
   ├─ Lifecycle / Exception firewall / Action shield / Deadline watchdog
   ├─ Per-episode state / reset barrier / telemetry
   └─ async queue (one outstanding request)
        │
        ▼
Risk-aware scheduler (shared GPU backend)
   ├─ risk-weighted EDF + aging + deadline fallback
   ├─ adaptive chunk H_i
   └─ full VLA + cached-feature action head (CFAH)
        │
        ▼
VGR (value-gated recovery)
   ├─ deterministic signals
   ├─ counterfactual value gate + 180s budget
   └─ retry / backtrack / hold / replan
```

### 4.2 生命周期

```text
INIT ──metadata/reset──▶ READY ──first obs──▶ ACTIVE
  ▲                        │                    │
  │                        │                    ├─ exception/NaN ──▶ SAFE_HOLD
  │                        │                    ├─ deadline miss ──▶ DEGRADED
  │                        │                    ├─ failure signal ─▶ RECOVER
  │                        │                    └─ task done ──────▶ DONE
  │                        │                                           │
  └────────────────────────┴──────── reset ◀──────────────────────────┘
```

- `READY`：metadata 已注册，等待 `reset()`；`reset()` 必须清空历史/缓存/计数器。
- `ACTIVE`：正常推理；每次请求检查 deadline。
- `SAFE_HOLD`：异常/非法动作；返回当前 EE 绝对位姿 + 当前夹爪 + 零 pivot（`ee`），或当前关节 + 当前夹爪 + 零 pivot（`joint`）。
- `DEGRADED`：推理超时/延迟抖动；返回上一组安全 chunk 或 hold；下次请求优先恢复。
- `RECOVER`：VGR 触发；有最大重试次数和总时间预算。
- `DONE`：任务成功/最大步数；等待 reset。

### 4.3 动作盾（Action Shield）

检查顺序：

1. **key 集合**：`ee` 必须有 `left_ee_pose_gripper_base`、`right_ee_pose_gripper_base`、`left_gripper`、`right_gripper`；`joint` 必须有 `left_arm`、`right_arm`、`left_gripper`、`right_gripper`。
2. **shape/dtype**：EE `[6]`、gripper `[1]`、joint `[7]`、pivot `[7]`；float32/float64；batch 维一致。
3. **NaN/Inf**：任一非有限值 → 替换为 hold。
4. **限位**：EE 位置/姿态、joint 限位、gripper [0,1]；超限 → 裁剪或 hold（可配置）。
5. **chunk 连续性**：相邻步的 EE 位移/关节差超过阈值 → 拒绝该 chunk（或降速重采样）。
6. **动作统计**：min/max/mean/std/NaN 计数写入 telemetry；评测端 §6 会看动作规律。

**原则**：动作盾只做硬约束，不做「风格」判断；所有 veto 记录原因，便于离线分析误杀。

### 4.4 风险加权调度

风险评分（示例，需校准）：

\[
r_i = w_1\cdot \text{contact}_i + w_2\cdot \text{gripper}_i + w_3\cdot \text{stage}_i
    + w_4\cdot \text{recent\_failure}_i + w_5\cdot \text{time\_pressure}_i
\]

- `contact`：EE 与目标/桌面的距离（来自第 11 轮几何）。
- `gripper`：夹爪闭合/负载（来自本体）。
- `stage`：任务阶段（接近/抓取/运输/放置）。
- `recent_failure`：最近 VGR 信号。
- `time_pressure`：剩余时间/预计完成时间。

调度：

```text
priority_i = risk_i + aging * wait_i
choose argmax priority_i
if now + S_est > deadline_i: return hold / degrade
```

- 高风险端口优先拿短 chunk；低风险端口拿长 chunk。
- 同一时刻只允许少量高风险短 chunk 端口；其余排队或降级。
- 截止时间按 `H_i/f - margin`；不确定时用保守估计。
- 批处理窗口 ≤5ms，避免首请求延迟。

### 4.5 CFAH（缓存 VLM 特征的快速动作头）

目标：把 S 从 80–150ms 降到 20–40ms（C 级假设，需 G1 实测）。

```text
每 K 步（如 K=30）：
    z_t = VLM(images, language)          # 低频、全模型
每步/每个 chunk：
    a = DiT_action_head(z_t, proprio, wrist_feature)  # 高频、轻量
    if scene_changed or wrist_changed or stale(z_t):
        refresh z_t
```

- 同一 checkpoint：VLM 冻结，action head 已训练；不是第二个模型。
- 腕部图像变化快时，`z_t` 可能过期；用腕部特征/几何变化触发刷新。
- 如果 CFAH 掉点，回退全模型低频推理；CFAH 是性能选项，不是唯一路径。
- 需要 G1 测 S 分布、G3 测成功率；没有实测不写「已加速」。

### 4.6 VGR（值门控恢复）

信号：

| 层 | 信号 | 计算 |
|---|---|---|
| 动作 | 冻结 | 连续 chunk 的 EE/关节差 < ε |
| 动作 | 振荡 | 方向符号反复切换 ≥ k 次 |
| 动作 | 跳变 | chunk 间距离 > 阈值 |
| 本体 | 空抓/滑移 | 夹爪闭合但 EE 不动 / 位移与指令相反 |
| 本体 | 饱和 | 关节速度/力矩（无力矩，用速度）饱和 |
| 几何 | 目标丢失/移动 | 第 11 轮 `d_t, n_t, r_static, r_grasp, edit_score` |
| 任务 | 子目标回退 | rubric 进度下降（human 干扰） |

状态机：

```text
MONITOR ──signal──▶ EVALUATE ──G>0 & time──▶ INTERVENE
   ▲                    │                         │
   │                    └─G≤0 / no time──▶ MONITOR│
   └──────────── success/failure ◀────────────────┘
```

干预：

- **降速/保持**：最便宜；用于不确定/轻度异常。
- **重试当前子目标**：回到最近的安全 waypoint；用相对目标/视觉伺服。
- **回退一个子目标**：仅当证据强、且不会破坏保护集。
- **重规划**：最贵；只在剩余时间充足时。
- **无回归约束**：已完成子目标进入保护集；后续轨迹穿过保护集 → 限速/拒绝。

### 4.7 可观测与回放

- 每次调用记录：timestamp、port、obs hash、action stats、inference time、queue wait、state transition、VGR decision、exception。
- 存储：JSONL + 关键帧视频；或 MCAP/rosbag2 风格。
- 回放：能复现「哪一次调用、哪一个动作、哪一个信号」导致失败。
- 指标：协议故障率、p50/p95/p99 延迟、deadline miss、chunk 陈旧率、VGR 触发率/精确率、每任务成功率/步骤分。
- 失败样本进入 failure corpus；不是训练第二个模型，而是校准阈值/值门控。

## 5. 伪代码

### 5.1 SafePolicy 外壳

```python
class SafePolicy:
    def __init__(self, inner, cfg):
        self.inner = inner
        self.guard = ActionGuard(cfg)
        self.state = PerEpisodeState(cfg)
        self.telemetry = Telemetry(cfg)
        self.vgr = ValueGatedRecovery(cfg)

    @property
    def metadata(self):
        return self.inner.metadata

    def reset(self):
        self.state.reset()
        self.telemetry.reset_episode()
        self.vgr.reset()
        return self.inner.reset()

    def get_action(self, obs):
        t0 = monotonic()
        try:
            self.state.observe(obs)
            if self.state.mode == "SAFE_HOLD":
                return self.guard.hold(obs)
            if self.state.mode == "DEGRADED":
                return self.guard.hold_or_last(obs)
            action = self.inner.get_action(obs)
            action = self.guard.sanitize(action, obs)
            self.state.update(obs, action)
            self.telemetry.record(t0, obs, action, self.state)
            return action
        except BaseException as e:
            self.telemetry.exception(e)
            self.state.enter_safe_hold()
            return self.guard.hold(obs)
```

### 5.2 ActionGuard

```python
class ActionGuard:
    def sanitize(self, action, obs):
        if not self.keys_ok(action):
            return self.hold(obs, reason="keys")
        if not self.shapes_ok(action):
            return self.hold(obs, reason="shape")
        if has_nonfinite(action):
            return self.hold(obs, reason="nan")
        action = clip_limits(action)
        if not self.continuity_ok(action):
            return self.hold(obs, reason="jump")
        return action

    def hold(self, obs, reason="hold"):
        if self.control_space == "ee":
            return {
                "left_ee_pose_gripper_base": obs["state.left_ee_pose_gripper_base"],
                "right_ee_pose_gripper_base": obs["state.right_ee_pose_gripper_base"],
                "left_gripper": obs["state.left_gripper"],
                "right_gripper": obs["state.right_gripper"],
                "pivot": zeros(7),
            }
        return {
            "left_arm": obs["state.left_arm"],
            "right_arm": obs["state.right_arm"],
            "left_gripper": obs["state.left_gripper"],
            "right_gripper": obs["state.right_gripper"],
            "pivot": zeros(7),
        }
```

### 5.3 RiskScheduler

```python
def dispatch(requests, gpu, now):
    for r in requests:
        r.priority = r.risk + AGING * (now - r.arrival)
    while gpu.free and requests:
        r = max(requests, key=lambda x: x.priority)
        if now + estimate_service(r) > r.deadline:
            r.port.degrade(reason="deadline")
            requests.remove(r)
            continue
        gpu.submit(r)
        requests.remove(r)
```

### 5.4 VGR

```python
def decide(signals, time_left):
    if not is_failure(signals):
        return CONTINUE
    if time_left < RETRY_TIME + MARGIN:
        return CONTINUE
    p_rec = lower_bound_recovery(signals)
    p_cont = estimate_continue(signals)
    gain = (p_rec - p_cont) * DELTA_V - C_TIME - (1 - p_rec) * C_REGRESSION
    if gain <= 0:
        return CONTINUE
    if signals.severity == "mild":
        return SLOW_OR_HOLD
    if signals.recoverable:
        return RETRY
    return BACKTRACK
```

## 6. 仿真结果

### 6.1 设置

- 单服务器、非抢占、闭队列；N 个端口；每个端口一个未完成请求。
- 服务时间 \(S\sim\mathrm{LogNormal}\)，均值 80ms，CV 0.30；敏感度测试 S=20/40/80/120ms。
- 控制频率 f=30Hz；chunk H=5/10/20/30；执行时间 A=H/f。
- 调度：风险加权 + aging；风险随机生成，仅用于比较策略。
- 仿真时长 5,000s；seed=0；合成数据，**不是真机结果**。
- 指标：
  - `p99_delay`：请求从到达到返回的 p99 延迟。
  - `stale`：返回延迟 > A 的请求比例（下一个 chunk 没赶上）。
  - `high_risk_p99`：高风险端口的 p99 延迟。

### 6.2 结果

| 配置 | p99 延迟 | 陈旧率 | 解释 |
|---|---:|---:|---|
| N=1, H=5 | 151 ms | 0.4% | 单端口也会有尾部延迟 |
| N=3, H=5 | 203 ms | 4.6% | 刚好在稳定边界 |
| N=3, H=10 | 171 ms | 0.0% | 更安全 |
| N=3, H=20 | 161 ms | 0.0% | 长 chunk 更稳 |
| N=8, H=5 | 650 ms | 100% | **不可调度** |
| N=8, H=10 | 484 ms | 32.8% | 仍不可调度 |
| N=8, H=20 | 229 ms | 0.0% | 可用 |
| N=8, H=30 | 186 ms | 0.0% | 最稳 |
| N=8, 1×H5 + 7×H30 | 249 ms | 2.7% | 只留一个短 chunk 端口 |
| N=8, 1×H8 + 7×H30 | 224 ms | 0.0% | 短 chunk 稍长即可 |
| N=8, 2×H5 + 6×H30 | 422 ms | 100% | 两个短 chunk 端口就过载 |
| N=8, 2×H10 + 6×H30 | 295 ms | 0.0% | 短 chunk 放到 10 即可 |
| N=8, H=5, S=20ms | 57 ms | 0.0% | CFAH 若真能到 20ms |
| N=8, H=5, S=40ms | 242 ms | 33.3% | 40ms 仍不够 8×5 |
| N=8, H=10, S=40ms | 114 ms | 0.0% | 40ms + H=10 可行 |
| N=8, H=20, S=120ms | 550 ms | 0.1% | 长 chunk 容忍慢模型 |

### 6.3 解释

1. **公式和仿真一致**：N=8、S=80ms 时 H_min≈16.8；H=20 才稳定，H=5/10 都过载。
2. **短 chunk 的「并发预算」很小**：N=8 时最多 1 个 H=5 端口，或 2 个 H=10 端口；再多就过载。
3. **CFAH 的价值**：若 S 真能到 20ms，N=8/H=5 的 p99 只有 57ms；若只能到 40ms，H=5 仍不够，需要 H=10。
4. **不要迷信 H=5**：在 N=3 时 H=5 可行；在 N=8 时 H=5 是灾难。chunk 长度必须和 N/S 一起选。
5. **调度器只能缓解，不能创造容量**：风险加权可以把短 chunk 留给高风险端口，但总服务需求不能超过服务器容量。

## 7. 实验设计

### E0 · 协议故障注入

- 对象：`SafePolicy` + 参考 server；N=3/8 模拟端口。
- 注入：异常、NaN、Inf、错 shape、错 dtype、2s 延迟、跨端口状态污染、reset 后旧状态。
- 样本：每个故障类型 200 次；共 ~1,400 次。
- 指标：逃逸到 server 的异常数、trial 中断数、p99 开销、hold 动作合法性。
- 通过：0 逃逸；p99 开销 <10ms；hold 100% 合法。

### E1 · 容量剖析

- 对象：官方 WLA 全模型 vs CFAH；目标 GPU（24GB）。
- 变量：batch=1..N；N=1/3/8；H=5/10/20/30；S 分布。
- 样本：每配置 200 次请求；记录 p50/p95/p99。
- 指标：S 分布、p99、deadline miss、H_min 预测误差。
- 通过：H_min 公式预测 p99 误差 <20%；deadline miss <1%。
- 失败：加 chunk/降分辨率/多卡/关 CFAH。

### E2 · 调度器回放

- 对象：FIFO vs EDF vs 风险加权 EDF。
- 输入：E1 的延迟 trace + 合成风险轨迹。
- 样本：5,000s × 10 seeds。
- 指标：p99 延迟、陈旧率、高风险端口 p99、低风险端口饥饿时间。
- 通过：p99 陈旧 <5%；高风险 p99 <250ms；无端口饥饿 >2s。
- 失败：回退 FIFO + 固定 H=8–10。

### E3 · VGR 校准与单任务 A/B

- 离线：33k 成功演示 + 扰动回放；标定冻结/振荡/滑移/目标丢失阈值。
- 在线：5 个代表任务（HangCup、ToolboxStorage、ZipUp、FoldTowel、一个未见物品任务）；单任务不计分通道；每配置 20 trials。
- 对比：servo off/on；VGR off/on；只 hold vs 允许 retry。
- 指标：检测 AUROC、误报率、干预精确率、成功率、步骤分、恢复时间。
- 通过：AUROC≥0.85；误报≤5%；干预精确率≥70%；3/5 任务 +10pp；FoldTowel 不回归 >5pp。
- 失败：只保留 hold/降速；不做 retry。

### E4 · 可靠性记账回测

- 输入：历史评测日志/仿真后验；按 session 分组。
- 对比：点估计 vs Beta 后验 vs 分层 Beta；均匀分配 vs 抬地板 vs `q_t×Δ/cost`。
- 指标：校准误差（预测 vs 实际）、下限覆盖率、同预算下的任务地板/平均成功率。
- 通过：校准误差 <5pp；同预算下地板提升；序贯检验 α 控制在 5%。

### E5 · 32×10 干跑

- 对象：完整提交包；N 端口；180s/任务。
- 指标：协议故障、p99 延迟、chunk 陈旧、内存/句柄泄漏、每任务成功率/步骤分。
- 通过：0 协议故障；p99 <500ms；内存稳定；reset 干净。
- 失败：回退基线；逐项定位。

### E6 · 提交合规

- 单模型：VLA 一个 checkpoint；CFAH 同 checkpoint；运行时/伺服确定性。
- 文档：说明 CFAH 不是第二个模型；说明动作盾/调度器不改策略语义。
- 回滚：保留全模型/固定 chunk 的提交分支。

## 9. 风险与合规

| 风险 | 影响 | 缓解 |
|---|---|---|
| 单模型解释 | 被判定为第二个模型 | 运行时/CFAH/伺服都是确定性或同一 checkpoint；文档写清楚 |
| N 未知/变化 | 固定 H 不可调度 | 启动测 S；按 H_min+margin 自适应；长 chunk/多卡回退 |
| 参考 server 异常断连 | 一个 trial 直接失败 | 异常防火墙；hold 永不让异常穿透 |
| 动作盾误杀 | 合法动作被替换 | 只做硬约束；单任务灰度；记录 veto 原因 |
| VGR 误干预 | 把成功 trial 打断 | 值门控 + 保守下限 + 可逆动作；误报预算 <3% |
| CFAH 掉点 | 成功率下降 | E3 A/B；掉点即回退全模型 |
| 延迟抖动 | 成绩可信度下降 | deadline 调度；p99 监控；降分辨率/长 chunk |
| 统计过拟合 | 把噪声当结论 | 分层先验；session 分组；预注册门；配对检验 |
| 端口状态污染 | 跨 episode 串扰 | 每端口独立实例；reset 屏障；共享模型只读 |
| 评测语义未知 | 超时/重连行为不确定 | 单任务通道实测；保守 fallback；回滚开关 |
| 回放/遥测开销 | 影响延迟 | 异步写；采样；关键帧；p99 预算 <5ms |
