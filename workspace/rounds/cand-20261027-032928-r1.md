# 第 8 轮 · SKILL-GRAPH：评分步骤不总是一条线，而是一张加权 AND-OR 技能图（有时是链）

> 检索/复核日期：2026-10-27（UTC）。赛事身份确认不变：用户所指是宇树科技的 **UniBot 世界挑战赛**（unibot.unitree.com），G1 + Dex1、32 项桌面任务、通才单模型赛道、选手自部署 + 官方远程真机 API 评测；检索未发现更匹配的其他 UniBot。本轮三个灵感词是「能耗优化」「知识图谱」「ROS」。我先给结论：**知识图谱是唯一值得升级为主轴的词；能耗优化应降级为“分数感知的算力/时延分配”，ROS 应降级为“离线几何监督 + 数据采集”，两者都不要硬塞进在线关键路径。** 主判断也从第 7 轮的“终局放置是唯一闸门”修正为：**榜首 29.7% 是“任务状态混叠 + 技能间干扰 + 终端接触失败 + 抓取/夹持失败”四件事叠加；官方评分步骤给出的不总是一条线性流程，而是带权重的 AND-OR 子目标图（有分支就 AND-OR，有依赖就链）。把这张图编译成可执行技能图（ETSG），在一个 checkpoint 内做技能条件化路由，把数据、算力和验证集中到“抓取/夹持”与“终端接触”两族技能上，比继续堆放置模块更可能突破 30% 天花板。**

## 0. 本轮先核实：榜单仍是“预览态”，但足够重排优先级

> 重要限定：榜单页仍写 Coming Soon，JSON 自述由脚本生成，8 个模型的平均时长都挤在 43.7–45.2s，数值过于平滑；**这份快照很可能是演示/占位数据**。上面的统计只用来生成假设，不用来断言“真实榜首方案”。真正的结论要等官方榜和调试槽。

## 1. 三个灵感词，先各自“去魅”

### 1.1 知识图谱：唯一值得升级为主轴的词

第 7 轮的 SSG 是一条线性状态机 `s0→s1→…→sk`。但官方 `score_steps` 不一定是执行顺序：T06 ColorArrangement 的三个放置目标（红最右、绿中间、黄最左）可建模为彼此独立（除非初始布局占住目标位），列表顺序不是物理依赖；T10 PlugCharger 的插入依赖“抓插排”和“抓插头”两个独立前置；T27 StackBowlsThree 则是碗 1→碗 2→碗 3 的链。**评分步骤是“带权重的子目标谓词”，不是“时间序列”；图要按物理依赖建，有分支就 AND-OR，有依赖就链。** 正确的表示是 **加权 AND-OR 图**：

- 节点 = 子目标（subgoal），带官方权重 `w_i`、技能标签 `skill_i`、谓词 `π_i`、前置条件 `Pre_i`、效果 `Eff_i`；
- 成功 = 所有必需子目标的 AND；
- 步骤分 = 已完成子目标权重之和；
- 边 = 物理依赖（先抓后放、先开盖后倒药、先叠碗 1 再叠碗 2），不是固定顺序；
- 干扰 = 图上的编辑（移动对象、撤销子目标、替换对象、加干扰物），恢复 = 重新满足被破坏的谓词。

这张图直接解决四个问题：

1. **任务状态混叠**：长程任务中相同的观测对应不同阶段；图给当前子目标一个显式坐标（TaskAnchor 用里程碑坐标把 π0.5 在 RMBench 提升 65pp、RoboMemArena CSR +35.5pp，只加 ~2ms 延迟，[S12]）。
2. **技能路由**：每个子目标自带技能标签，不需要学一个隐式路由器；这给技能条件化 MoE 提供免费监督（MAST-VLA 用 skill-conditioned LoRA-MoE 在 CALVIN 拿到 Avg. Len 4.65，[S13]；AtomicVLA 用 atomic skill MoE 在真机长程 +18.3%，[S14]）。
3. **检索与数据**：检索键可以按“技能 + 对象角色 + 关系”约束，而不是全局外观；5 个泛化轴可以变成 5 类图编辑，而不是随机增广。
4. **诊断**：每个子目标都有谓词，离线就能算 per-subgoal success；这正是第 7 轮缺的“钱丢在哪一步”的仪表盘（MetaFine 用 compositional task graph 做 per-stage 诊断，[S15]）。

**与通用场景图/知识图谱的区别**：我们不需要重建整个 3D 场景，也不需要 LLM 在线规划。ETSG 是**官方评分 schema 的编译产物**，任务图部分是确定性的、零感知误差；只有“对象/容器当前位姿”这一小块需要视觉估计。这样既拿到结构先验，又避免通用 KG 的脆弱性。

### 1.2 能耗优化：降级为“分数感知的算力/时延分配”

在这个赛事里，“能耗”不是电费，而是**每单位延迟/能量换来的分数**。官方会记录每步时延及其波动，N 台机器人并发；模型越重（DreamZero 14B/7Hz），算力越可能成为约束。2026 年的证据表明 VLA 推理有大量冗余：

- A1 的 budget-aware 自适应推理：动作一致性触发早退 + 层间截断 flow matching，最多降 76.6% backbone 计算、72% 每 episode 延迟，成功率只掉 1–2pp（[S16]）。
- Decoupled Early Exits 把 backbone 深度、action expert 深度、denoising 步数做成三个可联合配置的算力轴，延迟 −79.2%、FLOPs −31.8%，平均成功率 +5.6%（[S17]）。
- ActTune 用动作类别/层/权重敏感度做精度分配 + GPU 工作点选择，每成功任务能耗最多 −76.8%，延迟增加 <10%（[S18]）。
- EcoVLA/VLA-ULAP 则从 device-edge 协同/超轻本地预测器角度降能耗与时延（[S19][S20]）。

但**能耗优化本身不会提高 OOD 成功率**。它唯一正确的用法是：**把省下来的算力，重新分配到评分权重最高、当前最不确定的步骤上**——终局接触和抓取闸门。也就是把“均匀推理”改成“分数感知的 anytime 推理”。这值得做，但它是**二阶杠杆**；如果 profiling 显示算力/时延不紧，就应该关掉，别让它变成新的 FLEET。

另外有一个次要的“物理能量”解释：堆叠/倾倒的稳定性可以用势能/支撑多边形/质心做 verifier，作为 SVL 的一项检查。这个可以做，但只是终端工具链的一个小模块，不是主线。

### 1.3 ROS：降级为“离线几何监督 + 数据采集”

官方在线接口是 WebSocket + msgpack，不是 ROS。选手的策略服务器在外部，评测器连进来；ROS 2 不在评测链路上。把 ROS 塞进在线推理只会增加序列化、节点发现和延迟不确定性。ROS 的正确位置是：

- **离线/进程内几何监督**：用 G1 URDF + Pinocchio/KDL 做 FK/IK、关节限位、工作空间、自碰撞、桌面近似碰撞、chunk 平滑度检查；在返回动作前做一次确定性过滤。这能减少“动作不可达/自碰撞/抖动”的低级失败，尤其是插入和堆叠。
- **数据采集与回放**：用 ROS 2 bag + `unitree_ros2`/`ros2_control` 采集实验室数据，再转成 LeRobot v3（官方 schema），服务于第 7 轮的 L2L 数据农场。
- **开发期验证**：用 ROS 2 的 TF2/可视化做相机外参、坐标系和轨迹回放；评测期不需要 ROS 运行时。

2026 年的工程证据也支持“策略服务器与 ROS 解耦”：VLAgents 用统一 policy server + 共享内存/压缩流，vla.cpp 用无 PyTorch 的 C++ runtime，Isaac ROS Deploy 用 Triton/ONNX 做确定性部署（[S21][S22][S23]）。**结论：ROS 是工程倍增器，不是研究主线；本轮只保留 RGS（ROS 2 Geometric Supervisor）作为可插拔模块。**

## 2. 主判断：把 SSG 升级成 ETSG，把“放置优先”修正为“双闸门 + 技能路由”

### 2.1 第 7 轮哪里对、哪里不够

第 7 轮最硬的证据仍然成立：

- 终局步骤合计 1275/3200 = **39.8%**；放置/插入/堆叠/闭合/倾倒类步骤约 **59.7%**；32/32 任务的成功闸门都是终局步骤（[S24]）。
- 榜单快照的步骤分−成功率 gap 也支持“多数失败发生在后段”。

但第 7 轮把失败过度归因于“终局放置”，忽略了两件事：

1. **抓取/夹持也是闸门**：DisconnectEthernet、PickOutBattery、Unlock 这些任务的 gap 小，但 8 模型均值只有约 20–27%，榜首也只有 21–24%；它们的损失在第一步，不在最后一步。
2. **模型间干扰**：8 个模型的任务排名相关性很低，说明“一个稠密策略硬扛 32 任务”会互相干扰；这不是靠一个更强的放置模块能解决的。

所以本轮把目标从“终局放置”改成**两族技能 + 一个路由**：

- **Acquisition 族**：grasp / pick / hold / unplug / extract；决定“能不能开始”。
- **Terminal 族**：place / insert / stack / close / zip / hang / pour / fold；决定“能不能收尾”。
- **ETSG 路由**：决定当前该调用哪个技能、哪个子目标、哪个验证谓词；把 32 个任务的长尾映射到 8 个共享技能上。

### 2.2 技能条件化不是“每任务 LoRA”

第 7 轮砍掉了“每任务 LoRA”，这是对的。本轮提的是**技能级**条件化：

- 32 个任务 × ~1k 演示 = 32k；但“抓取”出现在 32/32 任务，“放置”出现在 24+ 任务，“闭合/拉链”约 8 个，“插入”约 4 个，“堆叠”约 3 个，“倾倒/注射”约 2 个，“折叠”1 个。
- 按技能重排后，头部技能有上万条演示，尾部技能只有 1–3k；这比按任务切分更数据高效。
- 技能专家共享同一个 VLM 主干和 action expert，只在 FFN/动作头上做低秩专家；**一个 checkpoint，top-1 路由**。这符合“单模型”的精神；如果审计不接受 MoE，就退化为“技能 token + 里程碑坐标”的稠密模型（TaskAnchor 式），仍然是一个模型。

这正好对应公开证据：MAST-VLA 的 skill-conditioned LoRA-MoE 在 CALVIN 长程 SOTA；AtomicVLA 的 SG-MoE 在真机长程 +18.3%；TaskAnchor 的里程碑坐标用 2ms 换来巨大长程增益。三条证据指向同一个结论：**不是模型不够大，而是模型不知道“现在处于哪个技能阶段”**。

### 2.3 预期收益与可证伪点

- 若技能路由能捕获 oracle 空间的 1/3：+2.9pp。
- 若终端接触专家把 terminal subgoal 成功率 +10pp：按终局权重 39.8%、到达终局率 q≈0.6（第 7 轮估计）估算，**步骤分**约 +2.4pp；按成功率口径上限 +6pp，现实 +3–5pp；若同时改善抓取，合计 +4–6pp。
- 若 GECE 把 5 轴 OOD 各 +3–5pp：按轴权重，总分再 +1–2pp。
- **目标：从 29.7% 推到 35–38%（+5–8pp）；保守目标 33–35%（+3–5pp）。**
- **可证伪点**：如果 E3（技能路由）在 SLDH 上没有把 terminal/acquisition 子目标成功率提高 ≥5pp，或者 E4（图编辑数据）在 5 轴上没有 ≥3pp 且 ID 回归 >1pp，则主线不成立，回退到第 7 轮的 SSG+PGL+OPT+SVL。

## 4. 为什么不是“再堆一个放置模块”

第 7 轮的 PGL/OPT/SVL 仍然要做，但它们解决的是“终端接触的几何精度”，解决不了：

- **抓取闸门**：如果第一步没抓住，终局工具再强也没有机会。
- **任务状态混叠**：同一个画面在不同阶段需要不同动作；没有显式阶段坐标，模型会“回到上一步”或“提前收尾”。
- **技能间干扰**：32 个任务的视觉/动作分布差异大，一个稠密策略会在任务间平均化；技能专家把它们解耦。
- **数据不对称**：终局接触任务只有少数几个（插入 4、堆叠 3、闭合 8），但每个都是高权重闸门；需要按技能重采样，而不是按任务均匀采样。

所以本轮的火力分配是：

```text
技能图 + 路由（ETSG/SGR-VLA）        35%
终端工具链（PGL/OPT/SVL/GCR）         25%
数据引擎（SLDH/GECE/L2L）             25%
算力/几何/部署（SCG/RGS/FLEET 检查单） 15%
```

## 6. 风险与合规（先立后破）

- **单模型审计**：技能 MoE 可能被质疑“是不是多个模型”。对策：一个 checkpoint、共享主干/共享 action expert、top-1 路由、模型卡写清；若仍不接受，退化为技能 token + 里程碑坐标的稠密模型。
- **榜单快照不可靠**：页面 Coming Soon、脚本生成；所有数字只作方向性先验，绝不用来选模型或断言真实榜首方案。
- **图感知误差**：ETSG 的任务图部分是确定性的；对象/容器位姿需要视觉估计，透明/布料/小件会错。对策：分桶回退；只在刚体任务做图编辑与位姿迁移。
- **官方备注噪声**：T27 描述红/绿/蓝三碗，但 `human_1_note` 写“粉色碗”，说明备注可能模板复用/跨任务串写；GECE 必须先做对象/任务一致性检查，不一致的备注只做弱先验。
- **技能标签噪声**：官方步骤文本到技能标签是人工/规则映射；对策：双人标注 10% 抽检，路由用软标签/共享专家兜底。
- **SCG 没有收益**：如果算力不紧，SCG 只会增加复杂度；对策：先 profiling，p99/能耗不紧就关闭。
- **ROS 外参/延迟**：相机外参不一定可得；ROS 2 只做离线和进程内过滤，不进在线关键路径。
- **外部数据合规**：L2L 数据默认 OFF；邮件确认后再开。
- **统计噪声**：若 320 trials、p≈0.3，SE≈2.56pp；+3pp 需要配对种子/bootstrap，不能只看一次跑分。

## 7. 一句话押注

**把官方评分步骤编译成加权 AND-OR 技能图，并在一个 checkpoint 内做技能条件化专家路由，把数据和算力集中到“抓取/夹持”与“终端接触”两族技能上——这是比继续堆放置模块更可能把 30% 天花板抬到 35%+ 的方向。**

## 2. ETSG：从线性 SSG 到加权 AND-OR 技能图

### 2.1 为什么线性状态机不够

第 7 轮的 SSG 假设 `s0→s1→…→sk` 是固定顺序。但官方 `score_steps` 是**评分谓词**，不是执行顺序：

- T06 ColorArrangement：三个放置目标（红最右、绿中间、黄最左）可建模为彼此独立（除非初始布局占住目标位）；列表顺序不是物理依赖，可以先放黄色再放红/绿，只要最终三个谓词都满足。线性状态机会把“列表顺序”误当“唯一顺序”。
- T10 PlugCharger：步骤 1“抓住插排”、步骤 2“抓住插头”、步骤 3“把插头插到插排中”；步骤 1/2 相互独立，步骤 3 依赖两者——这是一张**菱形 AND 图**，不是链。
- T27 StackBowlsThree：步骤 1“把碗 1 放到中间”、步骤 2“把碗 2 叠到碗 1 上”、步骤 3“把碗 3 叠到碗 2 上”；这是一条链，步骤 2 依赖 1，步骤 3 依赖 2。ETSG 保留这条链，不强行画成 AND-OR。
- 人为干扰：`human_*` 会把已完成的对象移走/撤销；线性状态机只能“重跑整个任务”，图可以只失效被破坏的谓词，保留其他进度。

所以 ETSG 不是“所有任务都必须 AND-OR”，而是“按物理依赖建图：有分支就 AND-OR，有依赖就链；官方列表顺序只作为默认执行顺序的一个候选”。

图状态/技能图的先例：MomaGraph 用图状态抽象长程操作 [S25]，MoMaStage 用图状态/记忆处理阶段切换 [S26]；VLM-KG 把 VLM 与知识图谱结合 [S27]；CodeGraphVLP/GraSP-VLA 用图约束视觉-语言-动作先验 [S28][S29]。我们的差异是：ETSG 的图来自**官方评分 schema**，不是从视频自动构建；任务图部分零感知误差，只有对象/容器位姿需要估计。

### 2.2 形式化

定义任务

```text
T = (V, E, s0, Pre, Eff, π, w, Skill)
```

- `V = {v_1..v_k}`：子目标节点；`w_i` 为官方权重（总和 100）。
- `s0`：初始状态（夹爪开/合、对象位姿、容器开/闭、任务进度）。
- `Pre_i`：前置谓词集合；`Eff_i`：效果谓词集合。
- `π_i`：子目标完成谓词（可观测/可估计）。
- `E ⊆ V×V`：物理依赖边；`(u,v)` 表示 `Eff_u` 是 `Pre_v` 的必要条件。
- `Skill: V → {grasp, extract, place, insert, stack, close, pour, fold}`。

执行时，**可执行集合**：

```text
Eligible(s) = { v ∈ V : Pre_v ⊆ s, π_v(s)=false, 未被阻塞 }
```

任务成功：

```text
Success = ∧_{v∈V} π_v(s_final)
StepScore = Σ_{v∈V} w_v · 1[π_v(s_final)]
```

关键点：`Eligible` 是偏序，不是全序；同一个任务可能有多条合法执行顺序。图只约束物理依赖，不约束“官方列表顺序”。

### 2.4 谓词 DSL

| 谓词 | 含义 | 估计方式 | 典型任务 |
|---|---|---|---|
| `holding(hand, obj)` | 夹爪夹住对象 | 夹爪宽度 + 视觉 + 触觉（无触觉则视觉） | 32/32 |
| `on(a, b)` | a 在 b 上方/表面 | 3D 关系 + 支撑 | 堆叠/放置 |
| `inside(a, c)` | a 在容器 c 内 | 容器检测 + 3D 包含 | 收纳 |
| `inserted(plug, socket)` | 插头进入插座 | 相对位姿 + 接触 | T10/T26 |
| `closed(zipper/lid)` | 拉链/盖子闭合 | 视觉状态分类 | T09/T19/T23 |
| `upright(obj)` | 对象直立 | 姿态角 | T14/T32 |
| `stacked(a, b)` | a 稳定叠在 b 上 | 位姿 + 支撑多边形 | T20/T27 |
| `poured(src, dst)` | 倾倒完成 | 目标容器内容变化 | T14/T32 |
| `stable(obj)` | 放置稳定 | 质心/支撑多边形/短时不动 | 终端 |

谓词实现为 Python callable + 感知适配器；返回 `(bool, confidence)`。低置信时回退到“视频/人工/调试槽”标签，不硬判。

### 2.5 编译流程

```text
for each task:
  1. 解析 tasks_v2/<slug>/info.json：语言、score_steps、权重、generalization 备注
  2. 规则 + LLM 抽取：每个 step 的对象角色、技能标签、谓词、前置/效果
  3. 人工复核 10%（重点：插入/闭合/倾倒/折叠）
  4. 从 5 条演示视频中定位每个子目标的完成帧（弱监督）
  5. 构建 E/V/Pre/Eff；用依赖检测消除环（若有环，说明谓词粒度太粗）
  6. 生成 5 条英文复述的别名；语言 embedding 做任务识别
  7. 用 1–2 个调试槽任务校准谓词阈值
```

### 2.6 执行语义（部分序 + 重试 + 恢复）

```python
while not success(state):
    eligible = [v for v in V
                if pre(v) <= state and not done[v] and not blocked[v]]
    if not eligible:
        recover_or_break()
        continue
    v = argmax(eligible, key=lambda x: w[x] * (1 - P_success[x]) * criticality[x])
    skill = Skill[v]
    action = policy(obs, skill=skill, milestone=coord(v), language=lang)
    action = geometric_filter(action)
    execute(action, chunk)
    ok, conf = verify(predicate[v], obs)
    if ok and conf > tau:
        done[v] = True
        for u in descendants(v):
            invalidate_if_pre_broken(u)
    else:
        retry[v] += 1
        if retry[v] > 2:
            repair(v)          # re-grasp / re-place / re-approach
```

- `criticality`：终端闸门 1.5，抓取闸门 1.2，其他 1.0。
- `repair`：先 PGL/OPT/SVL 微调；再 GCR 检索同技能 demo；最后回退到 shared expert。
- 人为干扰：`human_*` 事件发生时，重新验证所有已完成谓词；只失效被破坏的节点，不重置整图。

### 2.7 与 SSG 的差异

| 维度 | SSG（第 7 轮） | ETSG（本轮） |
|---|---|---|
| 结构 | 线性状态机 | 加权 AND-OR 偏序图 |
| 顺序 | 固定 | 物理依赖决定，可多序 |
| 权重 | 用于优先级 | 用于价值/算力/采样 |
| 验证 | 终局为主 | 每子目标谓词 |
| 干扰 | 整任务重跑 | 局部失效/恢复 |
| 数据 | 官方备注剧本 | 图编辑 + 备注 + 未见物 |
| 诊断 | task-level | subgoal/skill/axis-level |

## 3. SGR-VLA：单 checkpoint 的技能条件化路由

### 3.1 总览

```text
                    ┌──────────────────────────────┐
language ──────────►│  Shared VLM backbone (6B)     │
                    │  WLA-1.0-Base (primary)       │
skill token ───────►│  + LoRA-MoE (8 experts + 1)   │
milestone coord ───►│  + shared flow action expert  │
4×RGB + proprio ───►│  + progress head              │
                    └──────────────┬───────────────┘
                                   │ action chunk
                    ┌──────────────▼───────────────┐
                    │ GCR retrieval (graph keys)   │
                    │ PGL anchors / OPT pose       │
                    │ SVL settle-verify            │
                    │ RGS geometric filter (opt.)  │
                    └──────────────┬───────────────┘

```

### 3.2 技能分类（8 类）

| 技能 | 典型子目标 | 覆盖任务（粗） | 数据量（粗） | 闸门角色 |
|---|---|---|---|---|
| `grasp` | 抓住/夹起/握住 | 32/32 | 32k | Acquisition |
| `extract` | 拔出/取出/拧开 | 5–7 | 5–8k | Acquisition |
| `place` | 放到/归位/排列 | 24+ | 24k+ | 终端/中间 |
| `insert` | 插入/插头/穿孔 | 4 | 4–6k | Terminal |
| `stack` | 叠碗/叠杯/垒积木 | 3 | 3–4k | Terminal |
| `close` | 拉拉链/关盖/合盒 | ~8 | 8–10k | Terminal |
| `pour` | 倒药/倒水/注射 | 2 | 2–3k | Terminal |
| `fold` | 折衣服/折纸/整理 | 1–2 | 1–2k | Terminal |

> 覆盖/数据量是**粗分类**，用于说明长尾不平衡，不是官方统计。`grasp` 几乎每个任务都有；`insert/stack/pour/fold` 是尾部但高权重闸门。

### 3.3 单 checkpoint 架构

- **主干**：WLA-1.0-Base 6B（首选，G1/Dex1 先验）；挑战者 MolmoAct2-Think（快照榜首，但空间扰动弱项）；回退 π0.5（生态成熟）。三选一，不集成。
- **技能条件化**：在最后 N 层 FFN 插入 LoRA（rank 16–32），K=8 个技能专家 + 1 个 shared expert；top-1 路由。Router 输入 = 技能 embedding + 里程碑坐标 + 语言 CLS + 视觉 pooled token。
- **共享 action expert**：flow matching 动作头，所有技能共享；技能只调制特征，不复制动作头。这样“一个模型”更纯粹，参数量也更省。
- **进度头**：辅助预测当前子目标完成度/剩余步数；用 SLDH 弱标签训练。
- **里程碑坐标**：`coord(v) = (task_embedding, node_index/k, normalized_progress)`；TaskAnchor 式注入，不改主干结构。[S12]
- **参数量估算**：6B 主干 + 8×~20–30M LoRA（合计 ~0.2B）+ ~0.3B action expert；**激活参数约 6.1B**（估算，需按实际实现校准）。单模型、单 checkpoint。

### 3.4 路由

```python
def route(skill, graph_state, lang, visual):
    # 1) 图给出技能；这是确定性路由，不学任务分类器
    if skill in SKILLS:
        s = skill
    else:
        s = "shared"
    # 2) 模型内部 top-1 选 LoRA expert
    logits = router(skill_emb[s], coord(graph_state), lang_cls, visual_pool)
    e = argmax(logits)
    if entropy(logits) > tau_ent:
        e = shared_expert          # 不确定时回退共享专家
    return e
```

- **不做 learned task classifier**：任务识别用语言 embedding + 图匹配；避免 32 类分类器在 OOD 语言上崩。
- **软回退**：路由熵高/技能标签缺失 → shared expert；保证单模型在异常输入下仍可运行。
- **负载均衡**：训练时加 router load-balance loss；推理时允许不均衡（终端技能本来就该多算）。

### 3.5 训练目标

```text
L = L_flow
  + 0.1 · L_progress          # 子目标完成度
  + 0.05 · L_route            # 技能/专家路由（若有硬标签）
  + 0.1 · L_graph_consistency # 背景/干扰不变，位置/对象等变
  + 0.1 · L_recovery          # 人为干扰后的恢复
  + 0.05 · L_pose             # 终端相对位姿（PGL/OPT 监督）
```

- `L_flow`：flow matching / 动作 chunk 回归（按主干原配方）。
- `L_progress`：子目标完成度 + 剩余步数（辅助头）。
- `L_graph_consistency`：见 §5.4；只在有图编辑对时启用。
- `L_recovery`：`human_*` 前后配对；恢复动作应重新满足被破坏谓词。
- `L_pose`：PGL/OPT 生成的终端位姿监督；只在刚体任务启用。

### 3.6 单模型合规与安全回退

| 方案 | 描述 | 合规风险 | 性能预期 |
|---|---|---|---|
| A（首选） | 单 checkpoint + 8 技能 LoRA-MoE + 共享 action expert | 中（需说明单模型） | 最高 |
| B（安全） | 单 checkpoint + 技能 token + 里程碑坐标，无 MoE | 低 | 中高 |
| C（保守） | 单 checkpoint + 稠密 LoRA，仅图路由 | 最低 | 中 |

**决策规则**：先做 B（便宜、可解释），确认图路由有效后再上 A；若审计不接受 A，保留 B。A 的模型卡必须写明：一个 checkpoint、共享主干、共享 action expert、top-1 路由、无任务级模型切换。

## 4. SLDH：步骤级诊断（先知道钱丢在哪一步）

### 4.1 目标

把“任务成功率”拆成 “subgoal 成功率 × 到达率”，回答：

- 失败发生在抓取、运输、放置、插入、闭合、倾倒的哪一步？
- 哪些失败是 ID，哪些是 5 轴 OOD？
- 哪个技能/任务最值得加数据、加算力、加工具？

### 4.2 标签来源

| 来源 | 内容 | 成本 | 用途 |
|---|---|---|---|
| 官方 info.json | 子目标文本/权重/备注 | 零 | 图结构、权重 |
| 每题 5 条演示 | 成功轨迹视频 | 零 | 子目标完成帧弱定位 |
| 调试槽 | 1 任务真机、不计分 | 中 | 校准谓词/真实失败模式 |
| L2L 自采 | 实验室 G1/Dex1 | 高（需合规） | 补尾部技能 |
| 模型自标注 | 进度头/检测器 | 低 | 大规模弱标签 |

### 4.3 指标

```text
SR_task = #success / #trials
SR_sub(v) = #episodes where π_v true at end / #episodes
SR_skill(s) = mean_{v: Skill[v]=s} SR_sub(v)
SR_axis(a) = mean_{v: axis(v)=a} SR_sub(v)
StepScore_expected = Σ w_v · P(π_v)
Gap = StepScore_expected − SR_task   # 近似“离成功只差一步”的失败比例
```

失败分类（沿用第 7 轮 P1–P7，细化）：

| 代码 | 含义 | 典型信号 |
|---|---|---|
| P1 | 感知/位姿错 | 目标检测漂移、透明/反光 |
| P2 | 不可达/IK/限位 | 关节限位、工作空间、自碰撞 |
| P3 | 抓取失败 | 夹爪空、滑落、夹偏 |
| P4 | 运输失败 | 碰撞、掉落、路径受阻 |
| P5 | 终端接触失败 | 未插入、未叠稳、拉链未合、倾倒不到位 |
| P6 | 恢复失败 | 干扰后重试错、重复失败 |
| P7 | 协议/时延 | 超时、端口、chunk 延迟 |

### 4.4 诊断矩阵

```text
rows: 32 tasks
cols: subgoals (s1..sk)
cell: SR_sub + n
overlay: axis tag (position/distractor/background/unseen/human)
color: red <40%, yellow 40–70%, green >70%
```

决策规则：

- `SR_skill(grasp/extract) < 50%` → 加 acquisition 数据 + RGS 可达性 + 抓取专家。
- `SR_skill(insert/stack/close/pour/fold) < 50%` 且 `q>50%` → 加 terminal 数据 + PGL/OPT/SVL + 终端专家。
- `SR_ID − SR_OOD > 10pp` → GECE 图编辑 + 一致性训练。
- `p99 时延 > 预算` → SCG。
- 所有技能都低 → 先查数据/接口/协议，不要急着换模型。

### 4.5 与 MetaFine 的关系

MetaFine 用 compositional task graph 做 per-stage 诊断和 fine-tuning；我们的差异：

1. 图来自**官方评分 schema**，不是从视频自动切分；权重/备注是官方先验。
2. 诊断结果直接驱动**技能级数据采样 + 算力分配**，不只做 fine-tuning。
3. 诊断与**闭环恢复**绑定：每个谓词都能触发 repair，不只是离线分析。

## 5. GECE：图编辑反事实数据引擎

### 5.1 5 轴 = 5 类图编辑

| 轴 | 图编辑 | 官方备注 | 可渲染性 | 目标技能 |
|---|---|---|---|---|
| 位置 | 平移对象/目标/容器 | `position_*` | 高（刚体） | place/insert/stack |
| 干扰物 | 加入路径/容器附近刚体 | （任务自带） | 高 | grasp/place/recovery |
| 背景 | 换桌布/光照/背景纹理 | （任务自带） | 高 | 全部（不变性） |
| 未见物体 | 同 affordance 替换 | `unseen_object_*` | 中（刚体） | grasp/place/insert |
| 人为干扰 | 移动/撤销/放回 | `human_*` | 低（需配对） | recovery/close/stack |

### 5.2 官方备注解析

```text
T27 原文：
"human_1_note": "把粉色碗向下移动"
  → move(pink_bowl, down) before/at s1
  → invalidate: at/on predicates involving pink_bowl
"human_4_note": "叠了第二个之后拿下第二个"
  → remove(second_bowl) after s2
  → invalidate: on(bowl_2,bowl_1), on(bowl_3,bowl_2)
  → recovery target: 从受影响节点重新堆叠
"unseen_object_3": "除了塑料类型"
  → 原文含义待核实；先按“材质/类型替换”做假设，不要擅自改成“换高度碗”
  → keep: predicate schema, weights, graph edges

T10 原文：
"human_1_note": "抓插头前进行移动"
  → move(plug) before s2
  → invalidate: clear(plug)/grasp preconditions
"human_4_note": "将插头拔起"
  → remove(plug, socket_1) after s3
  → invalidate: inserted(plug,socket_1)
```

备注编号（`human_1..4`、`unseen_object_3`）的准确含义未在页面说明；以 info.json 文本为准，编号只做索引。[S24]

**重要异常**：T27 的任务描述是红/绿/蓝三碗，但 `human_1_note` 写的是“粉色碗”；这说明官方备注可能存在模板复用、跨任务串写或翻译噪声。GECE 不能把备注当 ground truth：先做“对象/任务一致性”检查，不一致的备注只保留“干扰类型”的弱先验，不生成具体对象编辑。

### 5.3 未见物体替换

- 建 **affordance 资产库**：杯（带把/不带把/高/矮）、碗（深/浅/宽/窄）、瓶（盖/泵/喷嘴）、盒（翻盖/抽屉/滑盖）、插头（两脚/三脚/角度）、拉链（拉头大小/松紧）。
- 替换规则：保持**抓取 affordance**（把手/边缘/拉头）和**放置支撑面**，改变外观/尺寸/比例；不改变谓词。
- 渲染：刚体用 2.5D 合成/局部 inpainting + 深度排序；透明/布料不做全物理，只做位置/背景编辑。
- 验证：替换后重新跑谓词标注；抓取点用 keypoint 映射，不沿用原对象位姿。

### 5.4 图一致性训练

| 编辑 | 不变性/等变性 | 损失 |
|---|---|---|
| 背景/干扰物 | 进度/技能预测不变；动作相对不变 | 对比损失（同轨迹不同背景） |
| 位置平移 | 终端位姿 SE(3) 等变；动作相对位移等变 | 动作/位姿一致性 |
| 未见物体 | affordance keypoint 等变；抓取位姿映射 | keypoint/pose 监督 |
| 人为干扰 | 被破坏谓词失效；恢复动作重新满足 | recovery 交叉熵/flow |

```text
L_consistency =
  λ_bg · ||f_prog(obs) − f_prog(edit_bg(obs))||²
  + λ_pos · ||T(edit_pos(a)) − a||²
  + λ_obj · ||φ(edit_obj(o)) − A·φ(o)||²
```

### 5.5 数据预算与 QA

- 真实 32k；合成目标 8–12k（≤30%），硬上限 50%。
- 只对刚体任务做全部 5 轴；透明/布料/拉链只做位置/背景/干扰，不做全物理。
- 每 200 条抽 10 条人工检查：对象不悬空/不穿模、谓词标签一致、动作无碰撞。
- 合成数据只进训练，不进评测；模型卡记录比例/来源/生成脚本。

### 5.6 与 NRB 的差异

NRB 是“官方备注剧本 + 回放”；GECE 是“图编辑 + 反事实配对 + 一致性训练”。前者增加多样性，后者增加**结构监督**：背景不变、位置等变、对象 affordance 等变、干扰可恢复。

## 6. 终端接触工具链（PGL / OPT / SVL / GCR）

### 6.1 PGL：放置目标阶梯

- 从演示中提取终端锚点：对象关键点、容器边缘/内部、支撑面法向。
- 生成候选位姿阶梯：中心/左/右/前/后 + 高度偏移；用支撑多边形、间隙、对称性打分。
- 选 top-k（k=3–5），交给 SVL 逐个试；不要只给一个点。

### 6.2 OPT：少样本位姿迁移

- GCR 检索同技能/同对象角色/同关系的 demo 段。
- 对齐源/目标对象坐标系（keypoint/ICP/基础模型），把抓取/放置位姿变换过去。
- 只在刚体/近似刚体启用；透明/布料回退到 PGL+SVL。

### 6.3 SVL：落点闭环

```text
for candidate in PGL/OPT:
    execute small servo toward candidate
    if predicate and stable:
        done
    else:
        adjust ±1cm / ±5° (max 3)
```

- `stable`：短时位姿变化 < 阈值 + 支撑多边形包含质心投影。
- 失败回退：重新抓取 → 重新选锚点 → 换候选。

### 6.4 GCR：图约束检索

检索键：

```text
key = (skill, object_role, relation, affordance, task_family)
```

- 不是全局 CLIP 相似度；先按图键过滤，再按视觉/语言排序。
- top-k=5；检索段是“子目标轨迹段”，不是整条 demo。
- 与 ICR 的差异：ICR 是扁平检索，GCR 用 ETSG 的技能/角色/关系约束，减少负迁移。

### 6.5 失败恢复

| 失败 | 恢复 |
|---|---|
| 抓取空/滑落 | 重抓（换抓取点/角度）→ 若连续失败，换对象/换手 |
| 运输碰撞 | 抬升/绕行/缩短 chunk |
| 插入未中 | PGL/OPT 候选 + SVL 微调；检查插座位姿 |
| 堆叠不稳 | 重新选锚点/降低速度/加大接触面积 |
| 拉链未合 | 重新夹拉头/换手/分段拉 |
| 人为干扰 | 失效被破坏谓词 → 重新满足；保留其他进度 |

## 7. SCG：分数感知的算力/时延调度（可选）

### 7.1 动机

终局接触权重高、成功概率低；抓取闸门也是低概率。均匀推理把算力花在“已经会”的步骤上。SCG 把算力从高置信步骤挪到高价值/高不确定步骤。

### 7.2 决策变量

| 级别 | 主干深度 | 分辨率 | 去噪步数 | 检索 K | 伺服 |
|---|---|---|---:|---:|---|
| L0 | 50% | 224 | 2 | 0 | 否 |
| L1 | 75% | 320 | 4 | 2 | 否 |
| L2 | 100% | 480 | 10 | 4 | 是 |

### 7.3 目标函数

```text
maximize  Σ_i v_i · ΔP_i(c_i)
subject to Σ_i latency_i(c_i) ≤ B
           Σ_i energy_i(c_i) ≤ E
           c_i ∈ {L0,L1,L2}

v_i = (w_i/100) · (1 − P_i) · g_i
g_i = 1.5 if terminal gate, 1.2 if acquisition gate, else 1.0
```

在线用贪心/背包近似：先给所有 terminal/低置信步骤 L2，再按边际收益分配剩余预算。

### 7.4 成功预测器

- 离线：SLDH 的 `P_i` 按任务/技能/轴分桶；isotonic calibration。
- 在线：动作熵 + ensemble/多 chunk 方差 + 历史重试次数。
- 触发：`P_i < 0.5` 或 `terminal` → L2；`P_i > 0.9` 且非闸门 → L0。

### 7.5 伪代码

```python
def allocate(steps, budget):
    for s in steps:
        s.level = L2 if (s.terminal or s.P < 0.5) else L1
    while latency(steps) > budget:
        cand = [s for s in steps if s.level > L0 and not s.terminal]
        if not cand:
            break
        s = min(cand, key=lambda x: x.v * x.dP(x.level, x.level-1) / x.dLatency(...))
        s.level -= 1
    return steps
```

### 7.6 何时关闭

- profiling 显示 p99 远低于预算、N 端口不紧张 → 关闭，固定 L2。
- SCG 导致成功率下降 >1pp → 关闭。
- 只在“算力/时延是约束”时启用；不要为了“能耗”而牺牲成功率。

### 7.7 物理能量稳定性（可选）

- 对堆叠/倾倒，用势能 `E_p = m g h`、支撑多边形、质心投影做 `stable` 检查。
- 只作为 SVL 的一个特征，不做控制器；质量/摩擦未知时用相对比较。

## 8. RGS：ROS 2 几何监督（离线/进程内，可选）

### 8.1 为什么不是在线接口

官方评测链是 WebSocket + msgpack，策略服务器在外部；ROS 2 不在链路上。在线引入 ROS 会增加节点发现、序列化、TF 延迟和不确定性。RGS 只做：

- 离线/进程内 FK/IK/碰撞/平滑检查；
- 实验室数据采集/回放；
- 开发期 TF/相机外参验证。

ROS 2 supervisor 的工程参考见 [S38]；它只做“机器人自身几何可行”的过滤，不保证任务成功。

### 8.2 架构

```text
policy action chunk
      │
      ▼
RGS filter (in-process, Python/C++)
  ├─ URDF: G1 + Dex1
  ├─ Pinocchio/KDL: FK/IK, joint limits
  ├─ FCL: self-collision, table plane
  ├─ workspace: reachability
  └─ jerk/smoothness
      │
      ├─ pass → send
      └─ fail → project / reduce chunk / fallback
```

### 8.3 检查项

| 检查 | 阈值（起始） | 失败动作 |
|---|---|---|
| IK 残差 | <1cm / <5° | 投影到最近可行解 |
| 关节限位 | 官方 URDF | 截断/回退 |
| 自碰撞 | FCL | 回退上一安全动作 |
| 桌面碰撞 | 近似平面 | 抬升/绕行 |
| 工作空间 | 可达球/盒 | 拒绝并重规划 |
| jerk | 经验阈值 | 平滑/降速 |

### 8.4 L2L 数据

- ROS 2 bag → LeRobot v3：对齐 4 路相机/关节/夹爪/语言；30fps；episode 边界。
- 只采“官方任务 + 刚体 + 可复位”场景；透明/布料/拉链不做大规模。
- 合规默认 OFF；邮件确认后再开。

### 8.5 限制

- 相机外参不一定可得；外参错会让 base 系目标全错。优先 wrist-relative / EE-relative。
- 对象位姿/透明物/布料不在 URDF 内；RGS 只保证“机器人自身几何可行”，不保证“任务成功”。
- 在线 ROS 不进入评测路径；只做离线/进程内。
