# 第 13 轮 · SERVICE-CONTRACT：先把基线做成测量仪，再把 94 个评分点做成 94 个服务契约

> 检索/复核日期：**2026-10-31（UTC）**。赛事身份不变：宇树 **UniBot 世界挑战赛**（unibot.unitree.com），G1 + Dex1，32 项桌面任务，通才单模型赛道，选手自部署 + 官方远程真机 API。本轮是灵感循环第 3 轮（任务卡标为第 1 轮，按状态文件延续编号），三个词是「服务设计」「用户测试」「基线复现」。本轮不推倒第 12 轮 CHUNK-SERVO，而是把它从「最后 3 厘米的控制层」推进到「跨评分点的服务层」。

## 0. 先给结论

1. **榜单前提要修正。** 截至 2026-10-31，官网首页、Leaderboard、Runs 三处都显示「即将发布 / Coming Soon」；第 12 轮记录的 MolmoAct2 29.7%、WALL-OSS-0.5 28.5% 等数字无法在官网复核，`leaderboard_data.json` 也返回 EdgeOne 拦截页。**因此本轮不把「榜首不到 30%」当作当前事实，也不围绕榜单做任务排序。** 这不是说 29.7% 一定假；而是说它现在不可复现，不能作为策略输入。当前唯一可信的公开信号是任务卡、参赛手册、提交模板、HF 数据和官方 WLA 基座。
2. **真正的公开信号在任务卡里。** 32 个任务共 **94 个评分点**，每个点 20–50 分；**25/32 个任务的最后一步值 40–50 分**；**7 个任务有 4–5 个评分点**。这比一个不可复核的榜单更适合做「用户测试」和「服务契约」。
3. **人为干扰不是边角。** 每个任务 10 次里 2 次是人为干扰，全局权重 **20%**；官方任务卡的 `human_4` 备注里，至少 7 个任务是「在你完成后把状态改回去」（拉拉链后又拉开、叠好毛巾又翻开、盖上盒盖又打开、叠好碗又拿走第二个、食物放回传送带起点等）。这正好是**服务契约**要解决的问题。
4. **接口事实要修正。** 腕部相机不是「没有内参」：HF 元数据里 `camera_params.wrist_*.color.camera_matrix` 有完整 fx/fy/cx/cy 和畸变；`action.pivot` 的实际顺序更可能是 `[vx, vy, yaw_rate, roll, pitch, yaw, height]`；Dex1 夹爪是 **5.5 开 → 0 合**，不是 0–1；提交模板 v2（2026-08-21）用 `obs_delta_indices` + `image_resize`，旧文档的 `data_keys`/`obs_chunk_size` 已过期。这些都会直接决定基线能不能跑通。
5. **本轮押注。** **SERVICE-CONTRACT**——把 94 个评分点变成 94 个可验证的服务契约，用 33k 成功演示的 before/after 状态做确定性校验；一旦检测到「步骤被撤销 / 目标被移走 / 进度回退」，用同一个 VLA 重规划 + CHUNK-SERVO 重做该里程碑，而不是从头再来。前置是 **BASELINE-LADDER**：先把官方 WLA 基线做成可复现的测量仪，否则无法知道任何改动是否真的涨点。

一句话：**先把「官方基线」做成测量仪，再把「评分点」做成服务契约；模型只用一个，增益来自跨步骤的契约守护和人为干扰恢复。**

## 1. 本轮核实/修正（只列会改变方案的）

### 1.1 榜单：从「29.7% 上限」降级为「无公开可信榜单」

2026-10-28 的第 12 轮记录了一个 8 模型榜单（MolmoAct2 29.7%、WALL-OSS-0.5 28.5%、DreamZero 27.9%、Spirit-v1.5 25.9%、DM0 23.5%、π0.5 22.8%、GigaBrain-0 22.6%、GR00T N1.5 20.5%）。本轮 2026-10-31 复核：

- 官网首页和 `/leaderboard.html` 的表格为空，显示「即将发布 / Coming Soon」；
- `/runs.html` 同样为空；
- `https://unibot.unitree.com/leaderboard_data.json` 返回 Tencent EdgeOne 的安全拦截页（带 request ID），不是 JSON。

**结论**：29.7% 只能作为「上一轮抓到的、当时未复核的快照」，不能作为当前 SOTA、任务难度表或失败分布。**本轮所有策略不依赖榜单名次。** 头部模型家族（MolmoAct2 / WALL-OSS / DreamZero / π0.5 / GigaBrain / GR00T）仍可作为技术路线参考，但不引用其具体分数。详见产物区 §1.1。

这反过来强化了「基线复现」的价值：**当外部榜单不可信时，唯一能校准队伍水平的是自己复现的官方基线。** 这也是本轮把 BASELINE-LADDER 放在主投位置的原因。

### 1.2 官方评分点：94 个、25/32 最后一针 40–50 分

官方挑战赛任务页（`challenges.html`）为每个任务加载 `tasks_v2/<slug>/info.json`。本轮通过 `r.jina.ai` 逐个抓取 32 个任务卡（检索日期 2026-10-31），得到：

| 项 | 数值 |
|---|---:|
| 任务数 | 32 |
| 评分点总数 | **94** |
| 难度 | Easy 12 / Medium 12 / Hard 8 |
| 每任务评分点数 | 2 步 11 个、3 步 14 个、4 步 5 个、5 步 2 个 |
| 最后一步 40–50 分的任务 | **25/32** |
| 4–5 步任务 | **7 个**（ToolboxStorage、OrganizeTools、FoldTowel、OrganizeStationery、PackBag、SpellRobot、StoreEarphones） |

任务卡还把每个评分点写成可读的「检查项」，例如：

- T01 HangCup：`抓杯把 50 分 → 挂到杯架标记位置 50 分`；
- T09 ToolboxStorage：`收两把工具 25 → 收完剩余工具 25 → 合盖 25 → 上锁 25`；
- T16 FoldTowel：`铺平 20 → 上下对折 20 → 左折 20 → 右折 20 → 折叠收起 20`；
- T19 ZipUp：`铺平 50 → 拉上拉链 50`；
- T26 PlugInEthernet：`抓网线 30 → 扶住网口 30 → 插入 40`。

**对方案的含义**：官方已经替我们定义了「用户旅程的检查点」。这些检查点不是模型内部的隐变量，而是**可观测、可验证、可计分的服务里程碑**。CHUNK-SERVO 解决「一个里程碑内最后 3 厘米」；SERVICE-CONTRACT 解决「里程碑完成后是否仍然成立」。

### 1.3 人为干扰：20% 权重，且大量是「撤销已完成步骤」

参赛手册（2026-10-31 复核）明确：每任务 10 次独立运行，5 类泛化各 2 次——位置、干扰物、桌面背景、未见物品、人为干扰。人为干扰轴 = **2/10 = 20%** 的 trial 权重。

官方任务卡的 `generalization` 字段还给出了 `human_1_note` 和 `human_4_note` 的具体干预。逐条读完后，可以分成四类：

| 类型 | 例子 | 数量（至少） | 对策略的含义 |
|---|---|---:|---|
| **完成后撤销/回退** | T10 插头被拔起、T16 毛巾被翻开、T17 笔盒合上后手动打开、T19 拉链拉上后拉开、T24 食物放回传送带起点、T27 叠好第二个碗后拿走、T29 外壳盖移开 | **7** | 必须做 postcondition 检查 + 重做 |
| **抓取后移动目标** | T08 抓书后挪架子、T11 抓电池后动绿盒、T12 中途拿走锁、T25 放第一个杯后挪底座、T26 移动网口 | **5** | 必须重定位目标 + 相对目标伺服 |
| **抓取前/中移动物体** | T01–T07、T13、T15、T18、T20–T23、T28、T30 等 | **十余个** | 位置泛化 + 快速重感知 |
| **力/位姿扰动** | T05 手握网口、T14 拧开盖后拧回去、T30 钉子移动 | 3–4 | 力/位姿监测 + 保守重试 |

这不是「避开人」的问题，而是「**世界在你完成后还会变**」的问题。传统开环 chunk 在 episode 级别没有「契约」概念：它不知道上一步是否仍然成立，也不知道什么时候该重做。SERVICE-CONTRACT 正是为这个结构设计的。

### 1.4 接口/数据修正：腕部有内参、pivot 顺序、夹爪范围、模板 v2

**(a) 腕部相机有内参。** 第 12 轮写「腕部相机没有内参矩阵」，本轮抽查 HangCup、ZipUp、PlugInEthernet、ToolboxStorage、FoldTowel 五个数据集的 `meta/info.json`，`camera_params.wrist_left/right.color` 均包含 `camera_matrix`、`dist_coeffs`、`width/height`、`model`。例如 HangCup：

```text
wrist_left.color.camera_matrix = [436.4058, 0, 323.9217; 0, 435.9215, 242.9332; 0, 0, 1]
wrist_left.color.dist_coeffs   = [-0.05146, 0.05475, -3.56e-05, 1.67e-04, -0.01769]
wrist_right.color.camera_matrix= [435.x, 0, 321.x; 0, 435.x, 242.x; 0, 0, 1]
```

**含义**：G0 从「腕部必须从零标定」降级为「跨数据集一致性检查 + 每机器人一次轻量校验」。这直接降低了 CHUNK-SERVO 的工程风险，也让腕部 IBVS 更可行。

**(b) pivot 顺序。** 官方提交 README 只写 `action.pivot [7]` 是「Lower-body / pivot target」，没有逐维定义。HF 数据集 README 写 `pivot` 7 维 = `vx, vy, angle_z, pivot_3, pivot_4, pivot_5, height`；一个独立派生数据集卡进一步写为 `pivot_vx, pivot_vy, pivot_vyaw, pivot_roll, pivot_pitch, pivot_yaw, pivot_height`。本轮读取 HangCup 实际 parquet（130,565 帧）：

```text
action.pivot ≈ [0, 0, 0, 0, 0.15, 0, 0.72–0.74]
action.base_command ≈ [0, 0, 0, 0.72–0.74]
action.waist_action_joint ≈ [-0.01, -0.004, 0.18]
```

这与 `[vx, vy, yaw_rate, roll, pitch, yaw, height]` 一致：索引 4 是固定的 pitch 0.15，索引 6 是高度 0.74。第 12 轮假设的 `[vx, vy, wz, yaw, pitch, roll, height]` 顺序需要修正。**但这仍是 B 级证据：真实 API 的 pivot 语义必须在单任务通道用零 pivot / 小角度 pivot 验证。**

**(c) 夹爪范围。** HF 数据集的 Dex1 约定是 **5.5 开 → 0 合**；HangCup 实际 `action.left_gripper` 范围 0.0096–4.5，`action.right_gripper` 0.0–4.5。第 12 轮写的「按 0–1 方向校验」是错的。**默认按 5.5–0 处理，并在 API adapter 里加 clamp；单任务通道再确认。**

**(d) 模板 v2。** GitHub 提交模板只有两个 commit：2026-06-26 首版，2026-08-21 v2（`version 2, support observation-based frame-skipping stacking, image scaling at the test end, and modifies the serialization method before image transmission`）。当前 `README.md` 的 metadata 是：

```python
{
  "control_space": "joint" | "ee",
  "obs_delta_indices": {key: [offsets]},
  "image_resize": {key: [height, width]},
  "action_chunk_size": int,
  "token": str,
}
```

网上仍能搜到旧版 `data_keys` / `obs_chunk_size` 的摘要；**用旧 schema 会在握手阶段被拒**。这是「基线复现」的第一个坑。

### 1.5 官方基线：WLA 6B / 30 步 / 24GB 微调，但「是否覆盖 32 任务」未知

官方 UnifoLM-WLA-1.0 的事实本轮复核不变：6B 参数、约 2,500 小时真机数据、64 个任务、统一 54 维动作 / 60 维状态、默认 `chunk_size=30`、`target_fps=30`、4 步去噪、冻结 VLM 只训 DiT action head + robot-state projector、默认单卡 24GB。挑战赛 API 是 2×6 EE + 2×1 gripper + 7 pivot = 21 维；WLA 的 54 维需要 adapter。

**关键未知**：WLA 的 64 个任务是否覆盖挑战赛 32 个任务？`pivot` 与挑战赛是否同义？EE 帧是否差一个 TCP 偏移？这些都不能假设，必须在 BASELINE-LADDER 的 R0/R1/R2 里逐项验证。

## 2. 诊断：为什么「服务层」是当前边际收益最高的地方

### 2.1 三个 1 秒之外，还有三个「服务断点」

第 12 轮已经论证了三个 1 秒：规划 1 秒（30 步 chunk）、推理/网络 0.1–0.3 秒、恢复 1 秒（下一个 chunk 才能纠正）。本轮再加三个服务断点：

1. **握手断点**：metadata 字段错、token 错、端口数不对、`obs_delta_indices` 不合法 → 直接连不上，0 分。
2. **reset 断点**：N 个端口共享状态、历史没清、plan cache 串台 → 一个端口的 episode 污染另一个，分数不可信。
3. **延迟断点**：GPU 队列堆积、图像解码慢、模型服务崩溃 → `get_action` 超时或返回非法动作；README 明确说评测端会记录时延、波动和动作统计规律，并可能随成绩公布。**服务不稳定不是「工程细节」，是成绩可信度的一部分。**

这三个断点不需要新模型，只需要「服务设计」。它们不直接涨成功率，但能避免「模型明明会做，却因为服务挂了拿 0 分」的灾难。

### 2.2 320 trials 的结构决定了「契约」比「更大的模型」更划算

- 人为干扰 20%：如果契约恢复把 human 轴从 `p_h` 提到 `p_h + Δh`，全局约 `+0.2 Δh`。`Δh = 15pp → +3.0pp`；`Δh = 25pp → +5.0pp`。
- 长程任务 7 个（4–5 步）：如果每个任务因「一步被撤销后重做」多成功 1/10，全局 `+7/32×10pp ≈ +2.2pp`。
- 两项不独立（human trial 也在长程任务里），保守合计 **+3–6pp**；乐观 +7–8pp。这是设计目标，不是承诺。
- 反过来，从零训一个更大的 VLA/World Model 需要 8+ GPU 周，且没有证据能解决「步骤被撤销」这种服务层问题。

### 2.3 模型层已被官方 WLA 覆盖，控制层已有 CHUNK-SERVO，服务层还是空白

| 层 | 已有工作 | 本轮定位 |
|---|---|---|
| 模型层 | 官方 WLA-1.0 6B、π0.5、GR00T、MolmoAct2、WALL-OSS、DreamZero | 不训新模型；最多 action-head 微调 |
| 控制层 | 第 12 轮 CHUNK-SERVO：30 步规划 + 5 步伺服 + 相对目标 | 保留，作为「重做里程碑」的执行器 |
| 服务层 | **空白**：没有人把 94 个评分点做成契约，也没有人系统处理 human_4 的「完成后撤销」 | **本轮主投** |
| 评测层 | 榜单不可复核；单任务通道不计分 | **BASELINE-LADDER + USER-PANEL** |

**结论**：当前边际收益最高的不是「再大 2B 参数」，而是「让已有的 6B 模型不在第 8 步被人类改回去」。这也正好落在三个灵感词上：服务设计（契约/蓝图）、用户测试（里程碑/旅程）、基线复现（测量仪）。

## 4. 主投 I1：SERVICE-CONTRACT

### 4.1 核心想法

把官方 94 个评分点变成 94 个「服务契约」：

```text
契约 k = (task_id, step_id, score, description,
          pre_ref, post_ref, predicate, revert_signature,
          redo_cost_s, priority)
```

- `pre_ref` / `post_ref`：从成功演示里挖出的「执行前 / 执行后」参考（头双目 + 腕部图 + EE 位姿 + 夹爪开度 + 目标相对位姿）。
- `predicate`：一个**确定性**的成立条件，例如「连接器进入网口 ROI 的参考图相似度 > τ」「拉链头到达参考位置 ±2cm」「盒子盖与盒体的相对角 < θ」「目标物体在容器 ROI 内」。
- `revert_signature`：回退特征，例如「post 相似度下降、pre 相似度上升」「拉链头反向移动」「物体离开目标 ROI」。
- `redo_cost_s`：重做该步的估计时间；用于 180s 预算。
- `priority`：`score` × `human_4 是否撤销` × `任务是否长程`。

在线：

```text
MONITOR → 检测到契约违反 → HOLD → 重定位目标 → 同一 VLA 重规划 → CHUNK-SERVO 重做 → VERIFY → MONITOR
```

**关键**：不是「从头重跑 episode」，也不是「第二个学习模型」。它只是**在正确的时刻，用同一个 VLA 重做正确的那一步**。

### 4.2 为什么这不是「第二个模型」

- 契约验证只用：图像相似度（SSIM / NCC / ORB inlier）、颜色/轮廓、深度/视差、EE 位姿、夹爪开度、关节状态、演示检索。**没有学习权重。**
- 重做用的是**同一个 VLA checkpoint**；CHUNK-SERVO 是确定性控制器；目标来自演示检索。符合第 12 轮的 C2/C3 合规模式。
- 离线可以用 VLM/人工标注来切分演示阶段；**离线标注不进线上推理**（C1）。线上只有确定性检查。

### 4.3 为什么它能打中「human_4 撤销」

以 T19 ZipUp 为例：

```text
pre_ref  = 拉链拉开、 pouch 铺平 的腕部图/头图
post_ref = 拉链闭合、拉链头在末端 的腕部图/头图
predicate = 拉链头 ROI 与 post_ref 的相似度 > τ_post，且拉链闭合线连续
revert_signature = 相似度从 >τ_post 掉到 <τ_pre + δ，或拉链头反向移动 >2cm
```

人类在 `human_4` 里把拉链拉开后，契约检测器看到 `post → pre` 的回退，触发重做。VLA 不需要重新理解整个任务，只需要「把拉链再拉上」。CHUNK-SERVO 负责最后 3 厘米的对齐。

T16 FoldTowel、T17 OrganizeStationery、T24 ConveyorSorting、T27 StackBowls、T29 PackPhone 同理。**这 7 个任务是第一批契约候选。**

### 4.4 预期收益（算术，不是承诺）

```math
\Delta S = 0.2\,\Delta p_h + \frac{1}{32}\sum_t \Delta p_t
```

- `Δp_h = 15pp` → `+3.0pp`；`Δp_h = 25pp` → `+5.0pp`。
- 7 个长程任务各 `+10pp` → `+2.2pp`。
- 两项有重叠，保守合计 **+3–6pp**；乐观 +7–8pp。
- 如果只有 12 个任务上线契约，收益按比例缩水；所以先用 USER-PANEL 选出 `q_t × Δ_t / cost_t` 最高的 5–8 个任务。

### 4.5 最小可落地版本（2 周）

1. 只做 5 个任务：T19 ZipUp、T27 StackBowls、T17 OrganizeStationery、T24 ConveyorSorting、T01 HangCup。
2. 每个任务只做 1–2 个契约：最后一步 + human_4 撤销的那一步。
3. 离线用留出演示做「合成回退」：把 post 帧替换成 pre 帧，测检测器；要求 recall ≥80%、false positive ≤10%。
4. 在线先 shadow mode：只记录「本应触发」，不干预；用单任务通道或多任务干跑收集 20–50 个 episode。
5. shadow 精度 ≥70% 后，开启 bounded redo：最多 2 次，每次只在剩余时间 > redo_cost + 20s 时触发。

### 5.2 R0 的具体单元测试（用真实数据）

用 HangCup `data/chunk-000/file-000.parquet` 第一帧（2026-10-31 读取）：

```text
action.pivot                = [0.0, 0.0, -0.0, 0.0, 0.15, 0.0, 0.74]
action.left_gripper         = 4.5
action.right_gripper        = 4.4786
action.left_ee_pose_gripper_base  = [0.30670, 0.27965, 0.07822, 0.03364, 0.34773, -0.18857]
action.right_ee_pose_gripper_base = [0.25793, -0.27789, 0.10858, 0.00440, 0.28605, 0.37044]
action.base_command         = [0.0, 0.0, -0.0, 0.74]
```

测试：

1. `pivot[0:3] == base_command[0:3]`；`pivot[6] == base_command[3]`；`pivot[3:6]` 与 roll/pitch/yaw 的符号/顺序用多个 episode 验证。
2. `gripper` 在 `[0, 5.5]`；开=5.5，合=0；不要 clamp 到 0–1。
3. EE action 是 base 系绝对目标；`action - observation` 的均值接近 0、最大差可到 0.4 rad（正常，因为 action 是下一目标）。
4. `obs_delta_indices` 用 `[-4,-2,0]` 这类合法偏移；`observation.language` 必须 `[0]`。
5. `image_resize` 的 key 必须同时在 `obs_delta_indices` 里。
6. N=3 端口同时启动，`reset()` 后状态隔离；一个端口崩溃不影响另一个。

### 5.3 为什么先做基线而不是先做契约

- 没有 R1/R2，就不知道「契约恢复 +3pp」是相对哪个基线；也无法判断 VLA 本身是不是已经 0 成功。
- 榜单不可复核，R2 是唯一的外部校准。
- R0 能提前发现 pivot/夹爪/模板 v2 的坑；这些坑会让所有后续实验归零。

## 6. 支撑 I3：SLA-CHUNK（服务设计）

### 6.1 延迟预算

```math
T_{\text{budget}} = H_c / f_c,\qquad
T_{\text{response}} = t_{\text{decode}} + t_{\text{preprocess}} + t_{\text{queue}} + t_{\text{model}} + t_{\text{adapter}} + t_{\text{serialize}}
```

- `H_c = 8`、`f_c = 30Hz` → 267ms；内部 SLO：p99 ≤ 200ms。
- `H_c = 5` → 167ms；p99 ≤ 120ms。
- `H_c = 30` → 1000ms；延迟不是问题，但开环是问题；只在 baseline 用。
- 如果实测 `f_c = 10Hz`，`H_c=5` 就是 500ms；必须降到 3 或只做 PBVS。

### 6.2 Plan-ahead 双缓冲

```text
episode start: 同步取 plan_0
执行 chunk k 的同时: 异步请求 plan_{k+1}
get_action:
  if plan_{k+1} ready: 用新 plan；旧 plan 丢弃
  elif plan_k 还有剩余: 用剩余 + servo
  else: 安全 hold / 上一组合法 chunk
```

### 6.3 降级阶梯

1. 新 plan 就绪 → 用新 plan。
2. 新 plan 未就绪、旧 plan 有剩余 → 用旧 plan + servo。
3. 无 plan → 安全 hold（保持位姿/零速度）。
4. 模型异常/NaN → 上一组合法 chunk；记录；不崩溃。

### 6.4 动作平滑

- 新旧 chunk 重叠 2 步，线性混合；每步关节/EE 增量限幅。
- 避免「chunk 边界跳变」被评测端视为异常动作规律。
- 契约重做时，先 `HOLD` 再 `REPLAN`，不要突然反向。

### 7.1 8 任务面板

| 失败族 | 任务 | 为什么选 |
|---|---|---|
| 插入/接触 | T26 PlugInEthernet、T10 PlugCharger | 最后一步 40 分；对齐容差小 |

### 7.2 协议

1. **Triage**：每任务 5 对 A/B（servo/contract off vs on），只做方向性筛选；报告配对差值和 95% CI，不声称显著性。
2. **Confirm**：对 triage 中 `Δ ≥ 10pp` 的 2–3 个任务，做 10–20 对；用 McNemar / bootstrap。
3. **失败阶段编码**：按官方 94 个评分点标注「第一个失败点」；不是只看 success。
4. **Shadow mode**：契约检测器先只记录不干预；用 `human_4` 备注设计合成回退，测 precision/recall。
5. **盲评**：视频标注时不告诉评审条件；减少确认偏差。

### 7.3 统计诚实

- 5 对只能看方向；双侧 McNemar 在 5 对下最极端 5:0 也只有 p=0.0625，不能声称显著。
- 320 trials 的 `SE ≈ 2.4pp`；`+3pp` 接近噪声。**必须用配对/重复/多任务合并，不能拿单次全量跑的一个小数当结论。**
- 报告：成功率、步骤分、time-to-success、恢复次数、p99 延迟、非法动作数。

#### 1.5.2 pivot 顺序

官方提交 README 只写 `action.pivot [7]` 是「Lower-body / pivot target」，没有逐维定义。HF 数据集 README 写 `pivot` 7 维 = `vx, vy, angle_z, pivot_3, pivot_4, pivot_5, height`；独立派生数据集卡（B）写为 `pivot_vx, pivot_vy, pivot_vyaw, pivot_roll, pivot_pitch, pivot_yaw, pivot_height`。

## 3. 问题形式化

### 3.1 评分与人为干扰轴

```math
S = \frac{1}{32}\sum_{t=1}^{32} p_t,\qquad
p_t = \frac{1}{10}\sum_{j=1}^{10} y_{t,j},\quad y_{t,j}\in\{0,1\}.
```

人为干扰轴权重：

```math
\Delta S_{\mathrm{human}} = \frac{2}{10}\,\Delta p_h = 0.2\,\Delta p_h.
```

| `Δp_h` | 全局增益 |
|---:|---:|
| 10pp | +2.0pp |
| 15pp | +3.0pp |
| 20pp | +4.0pp |
| 25pp | +5.0pp |
| 30pp | +6.0pp |

长程任务若各多成功 1/10：

```math
\Delta S_{\mathrm{long}} = \frac{n_{\mathrm{long}}}{32}\times 10\mathrm{pp}.
```

`n_long = 7` → +2.2pp。两项有重叠，保守合计 +3–6pp；乐观 +7–8pp。**这是设计目标，不是承诺。**

### 3.2 服务契约

对任务 `t`、评分点 `k`：

```math
C_{t,k} = \left(\mathrm{pre}_{t,k},\ \mathrm{post}_{t,k},\ \phi_{t,k},\ \rho_{t,k},\ c_{t,k},\ \pi_{t,k}\right)
```

- `pre/post`：成功演示的执行前/后参考（图像 ROI + EE 位姿 + 夹爪 + 目标相对位姿）；
- `phi`：确定性谓词，`phi(s_t) ∈ {0,1}`；
- `rho`：回退特征；
- `c`：重做成本（秒）；
- `pi`：优先级（分值 × human_4 撤销 × 长程）。

### 3.3 进度分与回退检测

对图像 ROI 定义相似度 `sim(·,·)`（SSIM/NCC/ORB inlier 的组合）：

```math
s_t = \mathrm{sim}(I_t, I_{\mathrm{post}}) - \mathrm{sim}(I_t, I_{\mathrm{pre}}).
```

- 契约成立：`s_t > τ_post` 且稳定 `W` 帧；
- 回退：`s_t` 从 `>τ_post` 掉到 `<τ_pre + δ`，或 `s_t` 在 `W` 帧内下降超过 `Δ`；
- 目标移动：`T_base_target` 变化超过阈值，但 `phi` 仍可能成立；此时重定位，不重做；
- 变形/透明：降低图像权重，加入夹爪滞止、深度、关节电流代理；置信度低不触发。

### 3.4 重做决策

```math
\mathrm{redo} =
\begin{cases}
1, & \mathrm{score} \ge 40 \ \land\ t_{\mathrm{remain}} > c_{\mathrm{redo}} + 20s \ \land\ n_{\mathrm{retry}} < 2,\\
0, & \text{otherwise}.
\end{cases}
```

- 只重做高分/高优先级契约；
- 最多 2 次；
- 重做前先 `HOLD`，避免碰撞；
- 连续两次失败 → `DEGRADE`（继续 VLA）或 `ABORT`，不无限重试。

### 3.5 延迟预算

```math
T_{\mathrm{budget}} = H_c / f_c,\qquad
T_{\mathrm{response}} = t_{\mathrm{decode}} + t_{\mathrm{preprocess}} + t_{\mathrm{queue}} + t_{\mathrm{model}} + t_{\mathrm{adapter}} + t_{\mathrm{serialize}}.
```

| `H_c` | `f_c=30Hz` | `f_c=10Hz` | 评价 |
|---:|---:|---:|---|
| 3 | 100ms | 300ms | 动态任务；请求密 |
| 5 | 167ms | 500ms | CHUNK-SERVO 默认 |
| 8 | 267ms | 800ms | 服务友好 |
| 30 | 1000ms | 3000ms | 只用于 baseline |

内部 SLO：`p99 T_response ≤ 0.7 T_budget`；`H_c=8` → ≤187ms；`H_c=5` → ≤117ms。如果实测 `f_c=10Hz`，`H_c=5` 的 500ms 预算必须改为 `H_c=3` 或只做 PBVS。

### 4.3 契约库构建管线

```text
for task in 32:
    rubric = load tasks_v2/<slug>/info.json
    demos = load HF episodes (success only)
    boundaries = segment(demos, rubric.n_steps)
        # gripper open/close events + EE motion + phase classifier (offline)
    for k, step in enumerate(rubric.score_steps):
        pre, post = select_keyframes(demos, boundaries[k])
        C = build_contract(
            task, k, step.score, step.text,
            pre_ref=ref(pre), post_ref=ref(post),
            predicate=define_predicate(task, k),
            revert_signature=define_revert(task, k),
            redo_cost=estimate_redo(demos, boundaries[k]),
            priority=step.score * human4_undo(task) * long_horizon(task),
        )
        validate_offline(C)
        human_review(C)
        contracts.add(C)
```

**阶段切分**：

- 2 步任务：抓取/放置两段，最容易；
- 3 步任务：抓取/中间/最终，用夹爪事件 + EE 位移；
- 4–5 步任务：先用离线 VLM/人工标注 50 个 episode，训练一个“阶段边界”启发式（不是线上模型），再推广；
- 先做 12 个任务，不一次铺 32 个。

**关键帧选择**：

- `pre`：动作开始前 1–3 帧，目标在视野内；
- `post`：动作完成后 1–3 帧，夹爪已释放/已闭合，目标稳定；
- 对“插入/拉链/合盖”取“接触后 + 稳定”帧；
- 对“抓取”取“夹爪闭合后 + 物体随动”帧。

### 4.4 在线状态机

```text
INIT
  └─ first obs → MONITOR
MONITOR
  ├─ contract satisfied → MONITOR
  ├─ progress drop → VIOLATED
  └─ target moved → RELOCALIZE → MONITOR (no redo)
VIOLATED
  └─ HOLD → RELOCALIZE → REPLAN (same VLA) → REDO (CHUNK-SERVO) → VERIFY
VERIFY
  ├─ satisfied → MONITOR
  ├─ retry < 2 and time ok → REDO
  └─ else → DEGRADE (VLA open-loop) or ABORT
```

### 4.5 伪代码

```python
class ContractVerifier:
    def __init__(self, contracts, cfg):
        self.contracts = contracts          # 94 items, per task
        self.cfg = cfg
        self.state = {}                     # contract_id -> {satisfied, last_s, t_satisfied}
        self.retry = {}                     # contract_id -> int

    def update(self, task_id, obs, ee, gripper, t):
        fired = []
        for c in self.contracts[task_id]:
            s = progress_score(obs, c.pre_ref, c.post_ref)
            st = self.state.setdefault(c.id, {"satisfied": False, "last_s": s, "t": t})
            if c.predicate(obs, ee, gripper, c):
                if not st["satisfied"]:
                    st["satisfied"] = True
                    st["t_satisfied"] = t
                st["last_s"] = s
                continue
            if st["satisfied"] and self._reverted(s, st, c):
                if self._should_redo(c, t):
                    fired.append(c)
                st["satisfied"] = False
            st["last_s"] = s
        return fired

    def _reverted(self, s, st, c):
        return (s < c.tau_pre + c.delta) or (st["last_s"] - s > c.drop)

    def _should_redo(self, c, t):
        return (c.score >= 40
                and self.retry.get(c.id, 0) < 2
                and self.remaining_time(t) > c.redo_cost + 20)

class ServiceContractPolicy:
    def get_action(self, obs):
        self.tick += 1
        fired = self.verifier.update(
            self.task_id, obs, obs["ee"], obs["gripper"], self.tick)
        if fired:
            c = max(fired, key=lambda x: x.priority)
            self.mode = "RECOVER"
            self.recover_target = c
            self.retry[c.id] = self.retry.get(c.id, 0) + 1
            self.plan = None              # force replan
            self.hold_until = self.tick + 3
        if self.mode == "RECOVER":
            return self._recover_action(obs)
        return self._normal_action(obs)
```

**注意**：`progress_score` 用 ROI，不用全图；`predicate` 先做几何/相似度，不做语义分类；`_recover_action` 先 `HOLD`，再请求同一 VLA 重规划，再用 CHUNK-SERVO 执行；不加载第二个 checkpoint。

### 5.4 离线指标

| 指标 | 定义 | 用途 |
|---|---|---|
| 每模块 MAE/MSE | 左/右 EE xyz、rotvec、gripper、waist、torso、legs | 判断 adapter/normalization 是否正确 |
| 夹爪准确率 | 开/合二分类与真值一致率 | 夹爪通道是否可用 |

## 6. USER-PANEL

### 6.1 8 任务面板

| 失败族 | 任务 | 为什么选 |
|---|---|---|
| 插入/接触 | T26 PlugInEthernet、T10 PlugCharger | 最后一步 40 分；对齐容差小 |
| 挂/叠 | T01 HangCup、T27 StackBowls | 2–3 步；human_4 会撤销 |
| 变形/拉链 | T16 FoldTowel、T19 ZipUp | 5 步/2 步；human_4 明确回退 |
| 长程/多步 | T09 ToolboxStorage 或 T31 OrganizePencilCase | 4–5 步；一步失败就 0 |
| 动态 | T24 ConveyorSorting | 传送带；human_4 放回起点 |

### 6.2 协议

1. **Triage**：每任务 5 对 A/B（contract off vs on），只做方向性筛选；报告配对差值和 95% CI，不声称显著性。
2. **Confirm**：对 triage 中 `Δ ≥ 10pp` 的 2–3 个任务，做 10–20 对；用 McNemar / bootstrap。
3. **失败阶段编码**：按官方 94 个评分点标注「第一个失败点」；不是只看 success。
4. **Shadow mode**：契约检测器先只记录不干预；用 `human_4` 备注设计合成回退，测 precision/recall。
5. **盲评**：视频标注时不告诉评审条件；减少确认偏差。

### 6.3 统计诚实

精确 McNemar（双侧）在 5 对下最极端 5:0 也只有 `p=0.0625`；10 对需要 9:1 才 `p=0.0215`；20 对需要 15:5 才 `p=0.0414`。因此：

- 5 对 = triage，只能看方向；
- 10–20 对 = confirm；
- 320 trials 的 `SE ≈ 2.4pp`；`+3pp` 接近噪声；必须配对/重复/多任务合并；
- 报告成功率、步骤分、time-to-success、恢复次数、p99 延迟、非法动作数。

## 7. SLA-CHUNK

### 7.1 延迟预算表

| 场景 | `H_c` | `f_c` | `T_budget` | 内部 p99 SLO | 评价 |
|---|---:|---:|---:|---:|---|
| 官方 WLA 默认 | 30 | 30Hz | 1000ms | 300ms | 只用于 baseline |
| CHUNK-SERVO 默认 | 5 | 30Hz | 167ms | 117ms | 接触精度优先 |
| 服务友好 | 8 | 30Hz | 267ms | 187ms | 推荐起点 |
| 低控制频率 | 5 | 10Hz | 500ms | 350ms | 改 3 或只 PBVS |

### 7.2 Plan-ahead 双缓冲伪代码

```python
def get_action(self, obs):
    self._tick(obs)
    self._maybe_request_plan(obs)
    if self.plan is None:
        self.plan = self.vla.predict(obs)   # cold start only
    a = self.plan[self.idx:self.idx + self.H_c]
    self.idx += self.H_c
    if self.idx >= len(self.plan):
        self.idx = 0
        self.plan = None
    return self.adapter.to_api(a, obs, self.token)

def _maybe_request_plan(self, obs):
    if self.future is not None and not self.future.done():
        return
    if self.future is not None:
        self.plan = self.future.result()
        self.idx = 0
        self.future = None
    if self.plan is None or self.plan_age >= self.plan_ttl:
        self.future = self.executor.submit(self.vla.predict, copy_obs(obs))
```

### 7.3 降级阶梯

1. 新 plan 就绪 → 用新 plan。
2. 新 plan 未就绪、旧 plan 有剩余 → 用旧 plan + servo。
3. 无 plan → 安全 hold（保持位姿/零速度）。
4. 模型异常/NaN → 上一组合法 chunk；记录；不崩溃。

### 7.4 动作平滑

- 新旧 chunk 重叠 2 步，线性混合；
- 每步关节/EE 增量限幅；
- 契约重做时先 `HOLD` 再 `REPLAN`，不突然反向；
- 避免 chunk 边界跳变被评测端视为异常动作规律。

### 7.5 压测矩阵

| 维度 | 取值 | 指标 |
|---|---|---|
| N 端口 | 1, 3, 8 | p50/p99/p999、超时、内存 |
| 网络延迟 | 0/50/100/150ms | 超时、降级次数 |
| 请求频率 | 10/30Hz | 队列深度、丢弃 |
| 故障注入 | 模型重启、单端口崩溃、NaN | 恢复时间、影响范围 |
| 图像尺寸 | 128/240/480 | 解码/传输/精度 |

## 8. 实验门 G0–G9

| 门 | 问题 | 通过标准 | 失败动作 |
|---|---|---|---|
| **G0** | 接口是否一致？ | token/shape/metadata/端口/reset 全过；round-trip <1e-5 | 修 adapter；不上真机 |
| **G1** | pivot/夹爪/EE 语义是否正确？ | 单元测试 + 单任务小角度/零 pivot 验证 | 改配置；只验证双臂 |
| **G2** | WLA 离线是否复现？ | 优于 copy-last/zero；夹爪准确率 >70% | 查 schema/归一化/相机映射 |
| **G3** | 单任务真机是否有信号？ | 至少 1/3 任务 >0；p99 <200ms；无非法动作 | 回退 R1；不烧正式评测 |
| **G4** | 契约离线是否可信？ | 合成回退 recall ≥80%、FPR ≤10%、检测 ≤15 帧 | 降阈值/缩任务/只记录 |
| **G5** | 契约 shadow 是否可用？ | precision ≥70%；至少 20–50 episode | 不开干预；继续调阈值 |
| **G6** | 契约恢复是否涨点？ | 3/5 任务 +10pp；正常 trial 不回归 >5pp | 只保留 shadow；不提交 |
| **G7** | 服务是否稳定？ | N=3/8 端口 p99 <200ms；零超时；内存稳定 | 加 chunk/降分辨率/关契约 |
| **G8** | 32 任务干跑是否稳定？ | 无端口串台；reset 干净；动作合法率 100% | 回退基线 |
| **G9** | 消融是否支持因果？ | contract on/off、shadow/active、H_c 3/5/8 | 保留有效部分；砍无效部分 |

## 9. 风险与合规

| 风险 | 影响 | 缓解 |
|---|---|---|
| 榜单不可复核 | 无法知道相对水平 | R2 单任务真机；不引用榜单分数 |
| 单任务通道不含 human trial | 契约恢复无法在线验证 | 邮件确认；离线合成回退 + shadow；正式评测只开保守阈值 |
| 契约误报 | 无谓重做，浪费 180s | 保守阈值；shadow 精度 ≥70% 再开；最多 2 次；剩余时间门 |
| 变形/透明不可验 | 毛巾/拉链/瓶盖误判 | 先排除或只记录不干预；轮廓/深度/夹爪滞止兜底 |
| 单模型解释 | 被判定第二个模型 | 契约验证无学习权重；重做用同一 checkpoint；C1/C2/C3 说明 |
| pivot/夹爪语义不符 | 动作被拒/机器人不动 | R0 单元测试；单任务零 pivot/小角度；adapter 开关 |
| 延迟/队列 | 超时、动作不合法 | SLA-CHUNK 双缓冲 + 降级；N 端口压测；p99 门 |
| 评测噪声 | +1–2pp 假阳性 | 配对 A/B；bootstrap；重复；不拿 5 对当显著 |
| 数据泄漏 | 离线指标虚高 | 按 episode/session 划分；相邻帧不跨 split |
| WLA 不覆盖 32 任务 | 基线很低 | R1 先测；必要时 action-head 微调；不假设即插即用 |
| 契约重做碰撞 | 安全风险 | 先 HOLD；限速/限幅；最大重试；编辑检测即停 |
| 端口串台 | 分数不可信 | 每端口独立实例；状态哈希；reset 风暴测试 |
| 模板版本混淆 | 握手被拒 | 用当前 README v2；R0 校验；不抄旧摘要 |
