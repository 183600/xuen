# 第 6 轮 · FLEET-GPR：把“评测舰队”当作第 6 泛化轴

> 检索/复核日期：2026-10-24。赛事身份不变：宇树科技 **UniBot 世界挑战赛**（unibot.unitree.com），G1 + Dex1，32 项桌面任务，通才模型赛道，单模型完成全部任务，选手自部署、官方远程 API 调用。[S1][S4] 本轮三个灵感词是「云边协同」「多机评测」「视觉编码器」。我先把它们各自还原成 UniBot 的真实约束，再合成一个判断：**真正没被官方写进五轴、却会系统性影响分数的，是“部署分布”——N 机并发、跨工位硬件差异、远程推理延迟。把它当作第 6 轴，比在已有五轴上继续抠 1pp 更划算。**

## 0. 本轮先核实：四个新事实

### 0.1 榜单仍是占位，不能拿它做任何排名判断

`leaderboard.html` 依旧“即将发布 / Coming Soon”；`leaderboard_data.json` 仍是 8 个模型、榜首 MolmoAct2 29.7%、WALL-OSS 28.5%、DreamZero 27.9%。[S2][S3] 与上一轮完全相同。它只能当“难度先验”，不能反推谁强谁弱，也不能证明“榜首输在某个轴”。上一轮的这个克制必须继续保持。

### 0.2 提交接口 v2 已经改过传输与观测

`unibot_submission` 只有两个 commit：2026-06-26 首版；2026-08-21 “version 2, support observation-based frame-skipping stacking, image scaling at the test end, and modifies the serialization method before image transmission”。[S5] 这说明官方已经在做**观测跳帧堆叠、评测端图像缩放、图像传输序列化优化**。所以“压缩传输”不是我们的差异化空间；差异化在**推理调度、状态隔离、跨机适应**。

### 0.3 多机评测的规则比上一轮记录得更硬

README 明确：评测在 **N 台测试机器人**上以随机顺序运行，N 由官方另行公布；每台机器人对应一个固定端口；提交必须暴露 **N 个连续端口**，从 8765 开始（8765…8765+N−1）；**端口数必须精确等于 N**；每个端口必须独立可靠完成本机器人的完整交互。[S5] 官方给两种实现：每端口一个独立进程（各加载一份模型，最稳但 N 份显存），或共享一个模型 + 服务端请求分发（省显存，但要处理**并发**与**状态隔离**）。[S5]

这条规则的分量被低估了：它不是“部署细节”，而是**评分的前置条件**。N 未知、端口必须精确、N 路可能同时调用、每端口 reset 与历史必须隔离——任何一项做错，不是掉几个点，而是直接拿不到有效评测。

### 0.4 手册 2.3 之后仍未读到，N 仍未公布

飞书手册中英文版都只能抓到约 2.2 节（约 4.3KB），2.3 之后被登录墙/懒加载截断。[S4] 因此“外部数据/仿真是否允许”“步骤分公式”“失败判定”“人工干预协议”仍是未核实项。N 也没有公开值，只能按 N∈{1,3,8} 做弹性设计。所有涉及这些的结论都标“未核实”。

## 1. 三个灵感词，各自还原成 UniBot 的真实问题

### 1.1 云边协同：UniBot 里没有“边缘模型”的位置，但有“延迟弹性”的硬需求

第一反应是 CloudEdgeVLA 那条路：云端大 VLA 出慢特征，边缘小头出快动作。CloudEdgeVLA 在 40 步均匀延迟窗口下还能保留 63.8–78.0% 成功率，而单路径基线最多 3.0%。[S6] VLA-ULAP 更直接：GR00T N1.7 在 A6000 上 289.3ms/40.46J，Jetson Orin Nano 上的超轻量动作预测只要 20.7ms/0.122J。[S7] 数字很诱人。

但 UniBot 的规则写的是“所有任务须基于同一模型完成，不得混合使用多个模型一起进行测试”。[S4] 云 VLA + 边缘头，哪怕端到端训练，也有被判定为“两个模型”的风险。**所以云边协同不能按“两个模型”做，只能按“一个 checkpoint 的两种时间尺度/两种服务位置”做。**

合规的落法有三层：

1. **服务拓扑的云边**：模型放在云端 GPU，机器人侧只做观测转发与动作执行；端口代理可以放在离评测机更近的边缘节点。这是官方已经规定的形态，不是创新，但可以做“端口代理 + 健康检查 + 自动重连”。
2. **单模型的双时间尺度**：VLM/Goal Compiler 低频跑（每 K 步或事件触发），Action Expert 高频跑；两者共享同一个 checkpoint。这是 GPR-VLA 本来的结构，只需要把调度显式化。
3. **延迟弹性推理**：用 RTC（real-time chunking）把“执行当前 chunk”和“推理下一个 chunk”重叠，冻结已确定执行的前缀、对剩余部分做 inpainting；RTC 对 flow-based VLA 开箱即用、无需重训，能扛 >300ms 延迟。[S8] 再叠加异构 chunk 调度：不同端口的 chunk 消费速率不同，按消费速率组 batch，而不是按到达顺序。[S9]

一句话：**云边协同在 UniBot 里不是“模型拆分”，是“延迟预算下的单模型调度”。**

### 1.2 多机评测：它引入了一个官方没写的“第 6 轴”

官方五轴是位置、干扰物、背景、未见物品、人为干扰。[S4] 但 N 台机器人同时评测，至少多出三类差异：

- **本体差异**：关节零点、减速器背隙、Dex1 手指摩擦/间隙、臂长公差；
- **工位差异**：相机安装外参、桌面高度、光照/色温、背景残留；
- **系统差异**：不同端口的链路延迟、并发批大小、GPU 争用。

这些差异不会出现在任务说明里，但会真实改变成功率。Self-Adaptive VLA 给了正面证据：在 actuation bias、joint encoder offsets 这类硬件偏移下，用策略自己的 rollout 做 context、通过 AdaLN 调制，能恢复 base policy 80% 以上的性能；换新工位也比 base 更稳。[S10] 这说明“跨机/跨工位”不是噪声，而是可建模、可适应的分布。

更关键的是：**这类差异在训练集里几乎不存在**。33k 条数据来自少数几台采集机器人、少数几个工位；评测却是 N 台不同的机器、不同工位。训练分布和评测分布之间，除了官方五轴，还横着一条“embodiment/calibration shift”。谁把这条轴吃掉，谁就拿到别人拿不到的分。

### 1.3 视觉编码器：不是“换个更强的”，而是“按轴分配视觉带宽”

WLA 的 VLM backbone 是通过 `qwen_vl_interface` 冻结的，默认微调只训练 action expert（DiT）和 robot-state projector。[S11] 这意味着视觉编码器不是随便能换的：换编码器就要重对齐 VLM，成本高、风险大。

但 2026 年的证据很一致：**视觉表征的选择直接决定 OOD**。

- DeepVision-VLA 把 DINOv3 作为 vision expert，用 VL-MoT 把多层视觉特征注入 VLA 深层，再加 Action-Guided Visual Pruning；仿真 +9.0%、真机 +7.5%。在同一设置下把 DINOv3 换成 SigLIP，成功率从 88% 掉到 77%。[S12]
- “What Matters for World Modeling in VLA” 的系统实验说：DINOv3 和 SigLIP 这类 2D 语义表示，在四种集成范式、两种 backbone 上都能稳定提升 ID 和 OOD 平均；LIBERO-Plus +4.4 pts。[S13]
- VLA-JEPA 用 SigLIP-2 做视觉编码器，配合潜在世界模型，在 LIBERO、LIBERO-Plus、SimplerEnv 和真机上都有泛化/鲁棒增益。[S14]
- FastVLA 证明视觉 token 可以按任务条件、按时间步自适应压缩，真机端到端延迟降 20%，成功率基本不变。[S15] SAPrune 则按阶段剪枝。[S16]

这三条线合起来指向一个判断：**视觉编码器的创新不在“替换”，在“路由 + 压缩 + 蒸馏”**。背景轴需要低频/全局信息，未见物品轴需要高频/局部信息，干扰物轴需要物体级边界信息；单一分辨率、单一编码器很难同时满足。与其换编码器，不如做一个**视觉带宽分配器（VBA）**：全局低频路径 + 目标局部高频路径 + 腕部接触路径，按任务阶段和不确定性分配 token 预算。

## 2. 本轮主判断：第 6 轴 = 部署分布，收益可能比第五轴更大

### 2.1 把“部署分布”写进评分算术

官方总分是五轴平均：

```text
S = (s_p + s_d + s_b + s_u + s_h) / 5
```

如果 N 台机器人中有比例 q 的机器存在未校准的硬件/工位偏移，且模型在这些机器上掉 Δ 个点，那么实际分数近似：

```text
S_eff ≈ S − q · Δ
```

这不是官方公式，是我用来做预算的近似。举例：q=1/3、Δ=10pp，则 S_eff 掉约 3.3pp；q=1/2、Δ=10pp，掉 5pp。**这跟“某一轴 +15pp”是同一量级。** 而且这部分掉分是“静默”的：你不会在任务清单里看到它，只会在某些端口上系统性失败。

延迟也是同理。设 chunk 执行时间 T_exec、推理+网络延迟 T_infer、chunk 长度 H。若 T_infer > T_exec，chunk 之间会出现空档；空档期间机器人要么停，要么执行过期动作。RTC 能把空档变成“前缀冻结 + 剩余 inpainting”，但它有上限。若并发导致 T_infer 翻倍，再好的策略也会抖。**所以服务层的 p99 延迟，是成功率的乘数，不是背景指标。**

### 2.2 为什么这一轴现在做最划算

- **竞争者少**：大多数队伍会把精力放在模型/数据，部署只做“能跑通”。官方又明确说 N 未知、端口必须精确，这本身就是一个筛子。
- **可快速验证**：不需要真机，不需要新数据；本地起 N 个端口 + 注入延迟就能测。
- **与已有方案正交**：PMSF/HAA 不改变 GPR-VLA 的建模，只改变训练条件和推理栈；可以独立上线、独立回滚。
- **收益确定**：即使模型不变，RTC + 异构调度也能减少 chunk 边界抖动和空档；Self-Adaptive VLA 类的适应能回收硬件偏移损失。

### 2.3 但不要把它做成“纯工程”

纯工程的天花板很低：调度再好，模型本身不会因此更泛化。所以本轮把“部署分布”反过来注入训练：

- 训练时随机注入**延迟 d、批大小 b、分辨率 r、相机外参扰动 e、关节零点扰动**，作为条件向量 c；
- 模型学习“在什么系统条件下该保守/该激进”，输出动作 chunk + 置信度 + horizon；
- 推理时从服务层读取真实 c，条件化生成。

这叫 **系统条件化（System-Aware Conditioning, SAC）**。它把“部署噪声”从测试时的意外，变成训练时的分布。这是本轮最有研究味的一步，也是与“只加一个 RTC”拉开差距的地方。

## 3. FLEET-GPR：在 TS-GPR 上加一层“部署即泛化”

上一轮的 TS-GPR 是：

```text
语言 l → Goal Compiler → z*
4 视图 + proprio → Part Encoder → b
r = z* − b → Action Expert → chunk/h/d
Belief Tracker（可逆）
```

本轮不推倒，只加四个件：

```text
┌─────────────────────── Offline / Fleet ───────────────────────┐
│  FLEET-BENCH: N-port sim + delay injection + hardware shift   │
│  HAA-offline: camera extrinsics / joint zero / table height   │
│  VBA-offline: DINOv3 expert + token-budget distillation       │
└──────────────────────────────┬────────────────────────────────┘
                               │ conditions c = (d, b, r, e, port)
                               ▼
语言 l → Goal Compiler → z* ─┐
4 视图 + proprio → VBA → b ──┼→ r = z* − b → Action Expert → chunk/h/d
                               │
                    Belief Tracker（可逆）
                               │
┌─────────────────────── Online / Serving ──────────────────────┐
│  PMSF: N ports, shared backbone, per-port state isolation     │
│  Heterogeneous chunk scheduling + RTC inpainting              │
│  HAA-online: reset self-calibration + AdaLN context token     │
│  Degrade: fewer views / lower res / shorter chunk under SLO   │
└───────────────────────────────────────────────────────────────┘
```

四个件：

1. **PMSF（Port-Multiplexed Serving Fabric）**：单 backbone 多端口；每端口独立 episode 状态（history、KV、Belief Tracker、reset 代际）；异构 chunk 调度；RTC 续接；端口编排器（N 未知）；SLO 降级。
2. **HAA（Hidden-Axis Adaptation）**：离线硬件扰动增强 + 在线 reset 自校准 + AdaLN context token（把 Self-Adaptive VLA 的思路做进 action expert，不引入第二个模型）。
3. **VBA（Visual Bandwidth Allocator）**：DINOv3 vision expert 注入 action expert 侧（不动冻结的 VLM）；任务条件 token 压缩；多教师蒸馏作为“零额外推理成本”的备选。
4. **FLEET-BENCH**：N=1/3/8 端口并发 + 延迟注入（p50/p99）+ 硬件扰动；测 p99 延迟、chunk 断流率、跨端口成功率方差。

## 4. 三个件的关键设计取舍

### 4.1 PMSF：为什么“共享 backbone + 状态隔离”是必答题

如果 N=8，每端口一份 6B 模型，bf16 权重约 12GB，8 份就是 96GB，还没算 KV/激活；单卡 80GB 放不下，多卡成本高。共享一份 backbone 是唯一经济的做法。但共享会带来两个坑：

- **并发**：N 路同时 `get_action`，朴素实现会串行排队，p99 爆炸；
- **状态串扰**：A 端口的 history/Belief Tracker 被 B 端口读到，`reset` 没清干净，直接错乱。

所以 PMSF 的核心不是“跑起来”，是“**每端口一个逻辑会话 + 一个共享推理后端 + 一个按 chunk 消费速率调度的批处理队列**”。Armory 在 10 台真实机器人舰队上证明：同构时朴素调度还行，异构（不同机器人以不同速率消费 chunk）时朴素调度会失配；按异构消费速率调度，真机吞吐最多 +18%。[S9] 这直接对应 UniBot 的 N 端口场景。

### 4.2 RTC：为什么它是“单模型合规”的关键

RTC 把异步 chunk 执行写成 inpainting：下一个 chunk 生成时，冻结“由于推理延迟已经确定会执行”的前缀，对剩余部分做条件生成，保证与上一 chunk 衔接。它对 diffusion/flow-based VLA 开箱即用，不需要重训，能扛 >300ms 延迟。[S8] WLA 的 action expert 是 MMDiT（flow matching），天然适配。[S11]

更重要的是，RTC 不引入第二个模型，不改变 checkpoint，只是推理算法。**这是云边协同在 UniBot 里最安全的落点。**

### 4.3 HAA：离线增强是主，在线适应是备

在线适应有风险：评测期间无标签，TENT/AdaBN 可能把模型带偏；Self-Adaptive VLA 的 context token 需要额外的 context encoder，如果打包不好会被视为第二个模型。

所以 HAA 的顺序是：

1. **离线优先**：训练时对相机外参、关节零点、桌面高度、光照色温做扰动增强；让模型见过“跨机差异”。这是零推理成本、零合规风险的。
2. **在线自校准（轻）**：reset 后 3–5 步，用机器人自身运动 + 视觉估计手眼偏移；只调整动作输出侧的补偿，不改网络权重。
3. **AdaLN context token（可选）**：把 Self-Adaptive VLA 的 context encoder 做进 action expert，作为同一个 checkpoint 的一个分支；默认关闭，只有在离线增强不够时才开。
4. **监控**：跨端口成功率方差、每端口 reset 后的前 10 步失败率；方差突增就触发降级/告警。

### 4.4 VBA：为什么先做“注入 action expert”而不是“换 VLM 编码器”

WLA 的 VLM 是冻结的，换视觉编码器要重对齐，成本高。DeepVision-VLA 的做法是把 DINOv3 作为 vision expert，通过 VL-MoT 注入 VLA 深层；它证明了视觉信息在深层会被稀释，需要显式注入。[S12] 但那是全量训练。

我们的轻量版：

- **只注入 action expert**：DINOv3 的 dense token 通过 cross-attention 进入 DiT 的中间层，不碰冻结 VLM；
- **只对腕部 + 目标 crop**：不做 4 视图全量 DINOv3，控制延迟；
- **token 预算固定**：每视图 K 个 token，按阶段分配；
- **蒸馏备选**：如果注入后延迟不达标，用 DINOv3 做教师，把 dense 能力蒸进现有编码器的 adapter，推理时去掉 DINOv3。

这条线的目标不是“刷 ImageNet”，是**背景轴和未见物品轴**：背景轴要抑制纹理、保留布局；未见物品轴要保留形状/材质细节。VBA 的带宽分配正好对应这两个需求。

## 6. 收益估算：先修“静默轴”，再修“显式轴”

用近似预算（不是官方公式）：

| 动作 | 假设 | 预期总分增益 |
|---|---|---:|
| RTC + 异构调度，消除 chunk 空档 | 10% 的失败来自断流/抖动 | +1.5–3pp |
| 端口编排 + 状态隔离，避免无效 run | 1–2 个端口出问题 | 避免 −3–10pp 灾难 |
| HAA 离线增强，跨机偏移 | q=1/3、Δ=8pp | +2.7pp |
| HAA 在线自校准 | 再回收一半 | +1.3pp |
| VBA（DINOv3 注入） | 背景/未见物品各 +5pp | +2pp |
| token 压缩，p99 延迟下降 | 断流率减半 | +0.5–1pp |

这些不能直接相加（有重叠），但量级说明：**部署层的组合收益，可能和“把某一轴从 20% 提到 40%”相当，而且确定性更高。**

## 7. 本轮最关键的三个不确定性

1. **N 到底是多少**：N=1 则 PMSF 的价值大降；N=8 则是必答题。设计必须能随 N 弹性伸缩。
2. **跨机差异到底有多大**：如果官方每台机器人标定得很好，HAA 的收益就小。需要 FLEET-BENCH + 真实多机校准来验证。
3. **视觉编码器改动是否值得**：VBA 的成本最高、周期最长；如果轴诊断显示背景/未见物品不是最弱轴，就应该把预算转到 HAA/PMSF。

## 8. 一句话押注

**把“N 机并发 + 跨工位差异 + 远程延迟”当作官方五轴之外的第 6 泛化轴：用 PMSF 保证 N 端口不崩、用 RTC 消除 chunk 空档、用 HAA 吃掉跨机偏移，再用 VBA 把视觉带宽按轴分配；先修静默轴，再修显式轴。**

### 2.3 预算近似

设官方五轴成功率为 `s_p, s_d, s_b, s_u, s_h`，部署轴造成的额外损失为 `L_deploy`：

```text
S_eff ≈ (s_p + s_d + s_b + s_u + s_h) / 5 − L_deploy
```

`L_deploy` 的三个来源：

```text
L_deploy = q_hw · Δ_hw + q_station · Δ_station + P(timeout | latency) · 1
```

- `q_hw`：存在硬件偏移的机器人比例；`Δ_hw`：这些机器上的成功率损失；
- `q_station`：工位差异导致的比例；`Δ_station`：对应损失；
- 超时项：延迟导致的整 episode 失败，权重是 1（直接记 0）。

**量级**：q=1/3、Δ=8pp → 2.7pp；q=1/2、Δ=8pp → 4pp。与“某一轴 +15pp（总分 +3pp）”同量级。

### 2.4 延迟预算推导（估算，不是实测）

单请求：

```text
T_req = T_prefill + T_denoise + T_net
T_exec = H / f
```

- 6B bf16 权重约 12GB；H100/A100 80GB 可放 1 份 + KV/激活；
- 4 视图 480×640，patch 28 → 每图约 17×23≈391 token，4 图约 1.5k token；若 `image_resize` 到 240×320，则每图约 8×11≈88 token，4 图约 350 token；
- 假设 prefill 1.5k token 约 60–120ms（H100，batch=1）；
- 假设 action expert 30 步 chunk、10 步去噪，约 120–250ms；
- 网络往返（跨区域）约 30–80ms；
- 合计 `T_req ≈ 210–450ms`；
- `H=8 @30fps` → `T_exec ≈ 267ms`；`H=16` → 533ms；`H=30` → 1,000ms。

**SLO 条件**：

```text
T_req ≤ T_exec + T_freeze
```

`T_freeze` 是 RTC 允许冻结的前缀时长（已确定执行、不会因新 chunk 改变）。若 `T_req` 超过右侧，就会出现 chunk 空档。

**并发放大**：N 路共享一个 backbone 时，批处理能提吞吐，但会抬高单请求延迟。若 batch=8 的吞吐是 batch=1 的 2.5×，则单请求延迟约变为 3.2×；原本 300ms 会变成约 960ms，远超 `T_exec`。这时必须：

1. 用 RTC 把重叠窗口拉长；
2. 用 token 压缩/降分辨率把 `T_req` 压下去；
3. 用异构调度让“快端口”先走、慢端口攒批；
4. 在 SLO 破裂前主动降级（减视图、短 chunk）。

> 以上数字是工程估算，必须在 FLEET-BENCH 里用真实模型/真实网络标定；不能写进提交材料当实测。

## 4. PMSF：多端口服务织物

### 4.1 端口编排器（N 未知）

```python
# supervisor.py (pseudo)
N = int(os.environ.get("UNIBOT_N", "0"))  # 0 = unknown

def spawn(port):
    subprocess.Popen(["python", "run_server.py", str(port)], env=...)

if N > 0:
    for i in range(N):
        spawn(8765 + i)
else:
    # 保守默认：先起 3 个；探测到新连接时热扩展
    for i in range(3):
        spawn(8765 + i)
    watch_new_connections(up_to=16, on_new=lambda i: spawn(8765 + i))
```

要点：

- **精确端口数**：官方要求“端口数必须精确等于 N”。热扩展有风险（多暴露端口可能被检查拒绝），所以生产环境优先用 `UNIBOT_N` 显式配置；热扩展只用于本地/演练。
- **健康检查**：每个端口独立 `/health`（TCP + 一次握手 + 一次零动作 chunk 校验 token）。
- **看门狗**：端口进程崩溃自动重启；重启后 `reset()` 代际 +1，清空该端口所有状态。
- **回滚**：新版本先起在 8765+N 的临时端口做 dry run，再切换；切换失败回滚旧进程。

### 4.2 每端口会话隔离

```python
class PortSession:
    def __init__(self, port, model):
        self.port = port
        self.model = model          # shared backbone
        self.history = {}           # per-port obs stack
        self.kv_cache = None        # per-port KV (if used)
        self.belief = BeliefTracker()  # per-port reversible state
        self.reset_gen = 0
        self.last_obs_ts = None
        self.pending_chunk = None

    def reset(self):
        self.reset_gen += 1
        self.history.clear()
        self.kv_cache = None
        self.belief.reset()
        self.pending_chunk = None

    def get_action(self, obs, ts):
        # 1) validate reset generation
        # 2) update history with obs_delta_indices
        # 3) estimate delay d = now - ts
        # 4) build condition c
        # 5) submit to scheduler; await chunk
        ...
```

**状态隔离的验收**：

- 并发 A/B 两端口，A 的 `reset()` 不影响 B 的 history/Belief；
- 交错调用 A/B 100 次，输出与单独调用逐位一致（确定性算子下）；
- 端口代际递增后，旧请求的响应必须丢弃（防止 reset 后旧 chunk 被写入）。

### 4.3 异构 chunk 调度

设端口 i 的 chunk 长度 `H_i`、执行帧率 `f_i`、上次请求完成时间 `t_i`。预测下一次需要请求的时间：

```text
deadline_i = t_i + H_i / f_i − T_req_est
slack_i = deadline_i − now
```

调度规则：

```python
def schedule(queue, max_batch, max_wait_ms):
    # 1) 先收紧急请求（slack < 0）
    urgent = [q for q in queue if q.slack < 0]
    # 2) 再按 slack 升序，凑 batch；batch 内按端口分组，保持 padding 最小
    queue.sort(key=lambda q: q.slack)
    batch = []
    while queue and len(batch) < max_batch:
        q = queue.pop(0)
        if batch and q.arrival - batch[0].arrival > max_wait_ms:
            queue.insert(0, q); break
        batch.append(q)
    return batch
```

与 Armory 的差异：

- Armory 解决“不同机器人消费 chunk 速率不同”导致的批处理失配；我们在此基础上加 **RTC 前缀冻结**，让“已经确定执行”的动作不参与重算；
- 加 **SLO 感知降级**：当 `slack` 连续为负，自动把该端口的 `image_resize` 降到 240×320、视图从 4 减到 3（去 head_stereo_right）、chunk 从 16 降到 8；
- 加 **端口优先级**：剩余时间少的 episode 优先（避免 180s 超时）。

> 注意：`image_resize` 是 metadata 固定的，服务端降级只能在收到图像后自己做 resize/drop，不能改 evaluator 的发送分辨率。收益是减少 VLM token，不是减少网络带宽。

### 4.4 RTC 续接

RTC 的核心：在执行当前 chunk 的同时生成下一个 chunk；把“因推理延迟已经确定会执行”的前缀冻结，剩余部分作为 inpainting 目标。[S8]

```python
def rtc_generate(model, obs, prev_chunk, executed_steps, delay_steps):
    # prev_chunk: [H, A]
    # executed_steps: 已经执行的步数
    # delay_steps: 由于延迟，接下来还会执行的步数
    freeze = prev_chunk[executed_steps : executed_steps + delay_steps]
    # 条件 flow matching: 冻结 freeze 对应的位置，生成其余
    new_chunk = model.sample(obs, freeze=freeze, freeze_mask=...)
    return new_chunk
```

工程细节：

- 冻结长度 `delay_steps` 必须由服务层的时间戳估计，不能用固定值；
- 若 `delay_steps >= H`，说明这一 chunk 已全部执行完，退化为普通同步生成；
- RTC 的 VJP/反传会增加推理成本；在 N 路并发下要计入 `T_req`，不能假设免费；[S8][S21]
- 若 RTC 成本过高，退化为 **A2C2 风格的轻量校正头**（每步运行，修正 base chunk）；但校正头是额外模块，合规上要打包进 checkpoint 或明确为推理算法。[S20]

### 4.5 SLO 降级阶梯

| 级别 | 触发 | 动作 | 风险 |
|---|---|---|---|
| L0 | 正常 | 4 视图、原生分辨率、chunk 16 | 无 |
| L1 | p99 > 0.7 × T_exec | 服务端 resize 到 320×240；chunk 12 | 精细任务掉点 |
| L2 | p99 > T_exec | 去 head_stereo_right；chunk 8；RTC 冻结加长 | 遮挡/深度信息变弱 |
| L3 | 连续 3 次 starvation | 只保留腕部 + head_left；chunk 4；降频推理 | 成功率明显下降，但避免超时 |
| L4 | 端口异常/崩溃 | 重启进程；该 episode 标记失败；不影响其他端口 | 单点失败 |

降级必须**每端口独立**，不能全局一刀切；并且要记录降级事件，便于赛后复盘。

## 5. HAA：隐藏轴适应

### 5.1 离线：硬件扰动增强

对每条真实 episode 的观测/动作做“物理一致”的扰动：

| 扰动 | 范围（起始） | 实现 | 监督 |
|---|---|---|---|
| 相机外参 | 平移 ±2cm、旋转 ±3° | 重投影/渲染；或用 homography 近似 | 动作不变 + 特征一致 |
| 关节零点 | ±0.02 rad | 在状态/动作空间加偏置 | 动作等变 |
| 桌面高度 | ±2cm | 调整基座/末端目标 | 动作等变 |
| 光照/色温 | ±20% 亮度、±500K | 颜色抖动/伽马 | 动作不变 |
| 手指摩擦/间隙 | 仿真参数扰动 | 仅仿真；真机用重放 | 接触/抓取标签 |

训练目标：

```text
L_haa = λ_inv ||f(o) − f(T_hw(o))||²
      + λ_eq  ||π(o) − T_hw(π(T_hw(o)))||²
      + λ_cal ||ĉ − c||²
```

其中 `T_hw` 是已知的硬件扰动变换，`ĉ` 是可选的校准头输出。

### 5.2 在线：reset 自校准

目标：在不改权重的前提下，估计当前工位的相机外参/末端偏置，并补偿动作。

```python
def self_calibrate(policy, robot, steps=5):
    # 1) 执行一个已知的小幅运动（例如末端画一个小方块）
    traj = robot.execute_probe()
    # 2) 用视觉观测 + 已知正运动学估计手眼偏移
    offset = estimate_hand_eye(traj.obs, traj.joint, traj.ee)
    # 3) 把 offset 写入 action 输出侧的补偿器
    policy.set_ee_offset(offset)
    return offset
```

风险：

- 评测是否允许“自检动作”？手册未读，未核实；如果不允许，改为**被动校准**：用前 3–5 步的自然运动 + 视觉估计，不额外加动作。
- 校准误差大时可能比不校准更差；设置置信度门槛，低置信度不补偿。

### 5.3 AdaLN context token（可选，P2）

借鉴 Self-Adaptive VLA：用策略自己的 rollout（多视图、proprio、动作）压缩成一个 context token，通过 AdaLN 调制策略；context token 可以 ensemble，逐步自校正。[S10]

合规做法：

- context encoder 作为 action expert 的一个分支，和 action expert 一起打包进**同一个 checkpoint**；
- 推理时只加载一个模型文件；
- 若审计要求更严，关闭该分支，只用离线增强 + 输出侧补偿。

### 5.4 监控指标

| 指标 | 定义 | 阈值（起始） |
|---|---|---|
| 跨端口成功率方差 | 各端口成功率的样本方差 | >0.03 触发排查 |
| reset 后前 10 步失败率 | 每个 episode 前 10 步失败比例 | >20% 触发告警 |
| 校准置信度均值 | 自校准输出的平均置信度 | <0.6 关闭补偿 |
| 降级触发率 | L1–L3 事件占比 | >10% 说明服务容量不足 |

## 6. VBA：视觉带宽分配器

### 6.1 动机

- 背景轴：需要抑制纹理、保留布局（低频/全局）；
- 未见物品轴：需要形状/材质/部件细节（高频/局部）；
- 干扰物轴：需要物体级边界（中频/实例）；
- 腕部接触：需要全分辨率近景。

单一编码器/单一分辨率难以同时满足；4 视图 × 480×640 的 token 量又直接决定延迟。

### 6.2 三条路径

```text
head_left/right (global) ──► downsample 224×224 ──► VLM visual tokens (低频/布局)
target/hand crop (local)  ──► DINOv3 dense tokens ──► action expert cross-attn (高频/部件)
wrist_left/right (contact) ─► full res ──► action expert (接触/抓取)
```

- **全局路径**：沿用 WLA 的 Qwen-VL 编码器；低分辨率，保布局和语言对齐。
- **局部路径**：用 Goal Compiler 的谓词 + Part Encoder 的 bbox 选目标区域；DINOv3 只编码 crop，token 数受控。
- **腕部路径**：全分辨率，但只送 action expert，不送 VLM（减少 VLM token）。

### 6.3 Token 预算

设每步总 token 预算 `K_total`：

```text
K_total = K_global + K_local + K_wrist
K_global ≈ 128–256
K_local  ≈ 64–128
K_wrist  ≈ 128–256
```

按任务阶段调整：

| 阶段 | 全局 | 局部 | 腕部 |
|---|---:|---:|---:|
| 接近/预抓取 | 中 | 高 | 高 |
| 抓取/接触 | 低 | 中 | 很高 |
| 搬运/放置 | 高 | 中 | 中 |
| 恢复/重规划 | 很高 | 高 | 中 |

### 6.4 与 WLA 的兼容

WLA 的 VLM 冻结，不能直接改视觉编码器；所以 VBA 的局部路径**只注入 action expert**：

```python
# action expert 的 cross-attention 增加一路 DINOv3 token
dit_block = MMDiTBlock(
    self_attn,
    cross_attn_vlm,      # 原有：VLM hidden states
    cross_attn_dino,     # 新增：DINOv3 dense tokens（局部 crop）
    cross_attn_wrist,    # 新增：腕部 token
)
```

训练时只训新增的 cross-attn 投影 + action expert 的 LoRA；VLM 保持冻结。这样成本可控，且不破坏语言对齐。

### 6.5 蒸馏备选（零额外推理成本）

如果 DINOv3 旁路导致延迟不达标：

1. 训练时用 DINOv3 + SigLIP2 + C-RADIOv3 作为多教师；
2. 学生是 WLA 现有视觉编码器 + 轻量 adapter；
3. 损失：特征对齐（cosine）+ 关系蒸馏（patch 间相似度）+ 动作 flow；
4. 推理时去掉教师，只保留学生；零额外成本。

蒸馏的风险是“容量不够”，可能只能回收一部分增益；所以先用小规模消融验证，再决定是否全量。

### 6.6 与 token 压缩的关系

FastVLA 证明任务条件、时间自适应的 token 压缩可以在真机上降 20% 延迟且基本不掉点。[S15] SAPrune 按阶段剪枝。[S16] 我们不需要重新发明压缩算法，只需要：

- 把 FastVLA/SAPrune 的“任务条件重要性”接到 Goal Compiler 的谓词上；
- 把压缩率作为 SLO 降级的一个旋钮；
- 监控“压缩后成功率”与“压缩率”的曲线，找每任务的拐点。

## 7. FLEET-BENCH：本地舰队评测台

### 7.1 目标

在不依赖真机的前提下，测三件事：

1. **服务韧性**：N 端口并发下的 p50/p99 延迟、chunk 断流率、超时率；
2. **跨机鲁棒**：注入相机外参/关节零点/桌面高度扰动后的成功率；
3. **策略回归**：模型改动是否在“舰队条件”下仍然有效。

### 7.2 协议

| 项 | 设置 |
|---|---|
| N | 1 / 3 / 8（可配置） |
| 端口 | 8765…8765+N−1，独立会话 |
| 任务 | 先 6 个代表任务：T02/T04/T10/T16/T20/T27 |
| 轴 | 5 轴 × 2 次 |
| 延迟注入 | p50 ∈ {20, 50, 100}ms；p99 ∈ {200, 500, 1000}ms；抖动 ±30% |
| 硬件扰动 | 外参 ±2cm/±3°；关节零点 ±0.02rad；桌面 ±2cm |
| 负载 | 同时注入 1–3 个“慢端口”（chunk 消费速率 ×0.5） |
| 指标 | 成功率、步骤分、p50/p99、starvation rate、timeout rate、跨端口方差 |
| 种子 | 每配置 ≥2 个种子；配对比较 |
| 校准 | 真机 60 trials（T02/T04/T10/T16/T20/T27 × 5 轴 × 2） |

### 7.3 指标定义

```text
starvation_rate = (# chunk 空档 > 50ms) / (# chunk 切换)
timeout_rate    = (# episode > 180s) / (# episodes)
cross_port_var  = Var(success_rate_port_1..N)
slo_violation   = P(T_req > T_exec + T_freeze)
```

### 7.4 使用门槛

- 服务指标（延迟/断流）直接用于工程决策；
- 成功率指标只有在“与真机相关 >0.7 且 MAE <10pp”时才用于模型选择；
- 否则只做失败挖掘，不写进提交材料。

| W5 | HAA 在线 + VBA 试点 | 被动校准；DINOv3 局部路径；E5/E6 | 在线净收益 >0；VBA 延迟可接受 |
| W6 | 全量整合 + 消融 | E7；A1–A8；SAP 预算 | 6 任务平均 +3pp；消融支持假设 |
| W7 | 32 任务课程 + 真机 60 trials | 全量训练；TCLB/FLEET-BENCH 320；soak | 总分 +3pp；相关 >0.7 |
| W8 | 冻结/提交 | 单 checkpoint；Docker；模型卡；dry run | 单模型审计通过；N 端口演练通过 |

**里程碑**：

- M1（W2）：端口编排 + 会话隔离可信 → 否则先修工程，不训模型。
- M2（W4）：RTC/调度带来可测收益 → 否则砍掉，回到同步基线。
- M3（W6）：6 任务 +3pp → 否则停止扩 32 任务，保 6 任务质量。
- M4（W8）：提交包完整、可复现、合规。

## 11. 风险、合规与开关

### 11.1 风险表

| 风险 | 概率 | 影响 | 缓解 | 停止条件 |
|---|---|---|---|---|
| N 未知/端口数不匹配 | 高 | 高 | supervisor + `UNIBOT_N` + 演练 | 官方检查拒绝 → 改独立进程 |
| 单模型审计（PMSF/HAA/VBA） | 中 | 高 | 全部打包进一个 checkpoint；推理算法显式声明 | 审计不通过 → 关闭在线分支 |
| RTC 增加推理成本 | 中 | 中 | 只在 L1+ 启用；监控 p99 | p99 超 SLO → 退回同步 |
| 在线适应带偏 | 中 | 高 | 置信度门槛；默认关闭；A/B | 真实掉 >2pp → 关闭 |
| VBA 延迟增加 | 高 | 中 | 只对 crop/腕部；token 预算；蒸馏备选 | 延迟超 20% → 蒸馏或砍掉 |
| DINOv3 许可不清 | 中 | 高 | 逐个核；只用离线教师 | 许可不清 → 不用 |
| 跨机扰动不真实 | 中 | 中 | 用真机/仿真标定；小范围 | 负迁移 → 缩小范围 |
| FLEET-BENCH 与真机不相关 | 中 | 中 | 60 trials 校准；只做相对比较 | 相关 <0.7 → 不做模型选择 |
| 状态串扰 | 中 | 高 | 代际 + 隔离测试 + 故障注入 | 复现串扰 → 回滚 |
| 网络抖动 | 高 | 中 | 重试/超时/幂等；多区域部署 | p99 超预算 → 降级 |
| 时间不够 | 中 | 高 | 先 6 任务；先 PMSF；VBA 可砍 | W6 未达 M3 → 缩范围 |

## 14. 开放问题

1. **N 的具体值**？N=1 则 PMSF 价值大降；N≥8 则是必答题。设计需弹性。
2. **“单模型”是否允许推理期在线适应/额外 context encoder**？当前默认打包进一个 checkpoint；需官方书面确认。
3. **评测是否允许 reset 后的自检动作**？若不允许，HAA 在线只能用被动校准。
4. **外部数据/仿真是否允许**？手册 2.3+ 未读；默认 `labels_only`。
5. **步骤分公式**？若步骤分对“完成阶段”很敏感，降级策略需要重算。
6. **网络拓扑**：评测机与选手服务的物理距离/带宽/SLA？决定 RTC 的冻结长度。
7. **N 台机器人的硬件/工位差异有多大**？需要真实多机校准或官方说明。
8. **是否允许在评测期间记录观测**？若允许，可做在线诊断；若不允许，只能本地复现。
9. **DINOv3 许可**？需逐个核权重/代码/资产。
10. **真实榜单**：仍占位；发布后重跑第 6 轴假设。
