# 第 13 轮（灵感循环重启第 1 轮）· TRI-RATE：把 chunk 执行窗口变成决策时间，用「option 图 + 投机计划 + 5 步边界伺服」补长程、边界与最后 3 厘米

> 检索/复核日期：**2026-10-28（UTC）**。赛事身份不变：宇树 **UniBot 世界挑战赛**（unibot.unitree.com），G1 + Dex1，32 项桌面任务，通才单模型赛道，选手自部署 + 官方远程真机 API。本轮三个灵感词是「**决策规划**」「**边缘计算**」「**开源硬件**」。本轮不推倒第 12 轮 CHUNK-SERVO，而是在它之上加两层：慢频 option 决策 + 边界投机，形成「**option 级决策 + chunk 边界投机 + 5 步边界伺服**」的三频闭环。

## 0. 先给结论：真正的共享瓶颈不止最后 3 厘米，还有 chunk 边界

第 12 轮的判断仍然成立：30 步 chunk 在接触段是开环的，最后 3 厘米需要视觉伺服。但本轮把问题再往前推了一层：

1. **长程开环**：Toolbox Storage 平均 37.6 秒，30 步 chunk 约 1 秒，意味着 30–40 个 chunk。任务没有显式的“现在做到哪一步、什么时候停、失败了回到哪一步”，误差会跨 chunk 复合。
2. **边界开环**：挑战赛是同步 request-response。evaluator 调用 `get_action` 后执行整个 chunk，期间没有新观测；下一次调用时，世界已经变了。**推理越慢，提交的 chunk 越旧。** PACT-VLA 证明“用提交前的观测挑候选”能显著涨点，但它需要推理期间的新观测，挑战赛 API 不提供。
3. **接触开环**：chunk 内没有反馈，插入、挂杯、拉拉链、拧瓶盖发生在最后 0.3 秒，CHUNK-SERVO 仍然必要。

所以本轮的押注是 **TRI-RATE**：

> **R0 慢频（0.2–1Hz）**：从 33k 成功演示里学一个确定性的 option/primitive 图，决定“做什么、做到哪、何时停、失败回到哪”。
> **R1 边界层（每个 chunk 边界；H=5 时 6Hz）**：在 chunk 执行窗口里，用**同一个 WLA checkpoint** 后台预生成 K 条候选计划；下一个边界用新观测 + 演示检索残差在 10ms 内选一条。
> **R2 执行层（动作 30Hz；H=5 时反馈 6Hz）**：每 5 步边界做一次 IBVS/PBVS，生成下一个 5 步修正块；块内仍开环，但反馈周期从 1s 降到 167ms。
> **HIL-CAL**：用 SO-101/UMI/RealSense 等开源硬件搭一个物理标定/压测台，只标定手眼、TCP、伺服阈值和评分器，不训练第二个模型。
> **EDGE-BUDGET**：把网络、预处理、动作生成、后处理拆开测，按实测延迟选 chunk 长度 H 和候选数 K，而不是拍脑袋用 30。

一句话：**把“等模型算完”改成“模型在机器人执行时就算下一批”，把“chunk 边界”从开环变成一次小规模决策。**

## 1. 本轮新核实/修正的事实（只列会改变方案的）

### 1.1 规则与 API：同步调用、chunk 内无观测、延迟会被记录

官方手册和提交模板（2026-10-28 复核）确认：

- 32 个任务，每个任务 10 次独立运行；5 类泛化各 2 次：位置、干扰物、桌面背景、未见物品、人为干扰。
- 所有任务必须用**同一模型**，不得混合多个模型；单次真机执行上限 180 秒；排名先看 32 任务总平均成功率，再平均步骤分，再更早提交。
- 评测跨 N 台机器人；从 **8765** 起暴露 N 个连续端口；每端口独立，`reset()` 状态必须隔离；不同端口可能同时被调用。
- API 只有四路 RGB（头左/头右/左腕/右腕，480×640）、双臂关节 7、EE 6（xyz+rpy，base 系）、夹爪 1、下身体 15、语言；**无 depth、camera_info、force/torque、tactile**。
- `action_chunk_size` 是每次 `get_action` 返回的 leading time-axis 长度；index 0 先执行，其余按顺序执行，直到 evaluator 再次调用；**chunk 内没有新观测，也没有打断机制**。
- README 明确：评测端逐调用记录**延迟、延迟波动、动作统计规律**，作为结果可信度的一部分；建议保持每步推理延迟稳定、动作格式正常。
- 另有**不计分的单任务测试通道**，可单独测某任务的成功率/步骤分。

**关键推论**：`get_action` 是一个“返回一批动作就下班”的同步接口。返回后到下一次调用之间，evaluator 在机器人上执行 chunk，而策略服务器可以继续算——这就是 EXEC-SPEC 的时间窗口。

### 1.3 官方 WLA：30 步、4 步去噪、延迟日志、`pivot` 语义都已有公开实现

- **UnifoLM-WLA-1.0**：6B，约 2,500 h 真机数据、64 任务；统一 54D action / 60D state；默认 `chunk_size=30`、`target_fps=30`、4 步扩散；冻结 VLM，只训 DiT action head + robot-state projector，单张 **24GB** GPU 可微调。模型服务器把内部相对 EE 的 xyz+rotvec 组合成绝对 EE 轨迹返回（`action.left_ee_rpy/right_ee_rpy`）；适配层要保留相对 delta。
- 模型服务器（`action_server_wbc_msgpack_unitree.py`）已经打印 `preprocess/predict/encode` 延迟，并输出整个预测 chunk（未归一化、绝对动作）；`action_horizon` 默认 30。
- `pivot` 语义已在代码中明确：**`[vx, vy, vw, yaw, pitch, roll, height]`**；waist `[yaw, roll, pitch]` 会 remap 到 pivot 的 `yaw, pitch, roll` 顺序。第 12 轮把 `pivot` 当未知风险，本轮可以降级为“实现时按代码对齐并实测”。
- 模型服务器输入是头左 + 左右腕三路图；挑战赛 API 还给头右，可用于双目深度/伺服，不一定要塞进 VLA。

**战略结论不变**：不要从零训 6B/14B；用官方 WLA 基座做 action-head 微调，把省下的算力投到执行层、投机层和单任务评测。

### 1.4 榜单仍是“预览”，不是可复现的 SOTA

官网榜单显示 MolmoAct2 29.7%、WALL-OSS-0.5 28.5%、DreamZero 27.9%、Spirit-v1.5 25.9%、DM0 23.5%、π0.5 22.8%、GigaBrain-0 22.6%、GR00T N1.5 20.5%。但：

### 1.5 外部证据：分层、停止决策、投机选择、边缘延迟都指向同一件事

- **SparkVLA**（arXiv:2608.16172）：stop-aware 分层 VLA，把“停止/继续执行多长”与动作前缀统一排序；RoboCerebra 47.12%，比分层基线 +30.57pp。说明“何时停/切”本身是独立决策，不应藏在一个固定 30 步 chunk 里。
- **H-VLA**（arXiv:2609.22895）：key-action 推理 + motion planning + 统一相机动作空间；Agilex 在位置/场景 OOD 上分别 +47/+16pp。说明“下一个关键动作/子目标”比直接回归整段更稳。
- **PACT-VLA**（arXiv:2610.28019）：训练无关，用提交前观测对候选 chunk 做 FlowRes 选择；比 RTC +15.0pp，真实机器人 60%→82%。但它需要 pre-commit 观测，挑战赛同步 API 拿不到——**这正是 EXEC-SPEC 要改造的地方**。
- **VLA-HWBench**（arXiv:2610.34717，2026-10-26）：18 个 VLA 在 Jetson AGX Thor / AMD Ryzen AI Max+ 395 上测七阶段延迟；**action-generation strategy 比模型大小更能解释延迟**，配置间差异 82×/157×，参数量最多解释 15% 方差；4-bit kernel fusion 对 π0.5/GR00T N1.7 快 2.6–2.9×。
- **Guild**（2026-07-02）：π0.5 在 Jetson Thor 上经 Shallow-π + SnapFlow + TensorRT + 量化达到 **43Hz**，比 base 快 11×；延迟 260ms→127ms→56ms→45ms。说明“动作生成策略 + 部署优化”可以单独拿一个数量级。
- **Jetson Thor**：128GB 统一内存、2070 FP4 TFLOPS；GR00T 1.7 eager ≈126ms/8Hz，`torch.compile` ≈105ms/9.5Hz。G1-EDU 自带 Jetson Orin NX 16GB，可选 Thor 背包；但挑战赛是远程 API，**“边缘”指选手的推理节点，不是 G1  onboard**。

## 2. 诊断：三个决策缺口，而不是一个感知缺口

```text
慢频（秒级）：现在该做哪个 option？完成了吗？失败回到哪？
     ↓
中频（100–200ms）：下一个 chunk 选哪条？新观测下还成立吗？
     ↓
执行层（动作 33ms；H=5 时反馈 167ms）：夹爪/目标偏了 2mm，往哪修？
```

1. **长程缺口**：固定 30 步 chunk 没有 option 语义。Toolbox Storage 37.6s、Store Racket 34.1s、Spell Robot 31.2s、Pack Phone 29.2s，都是 30+ 个 chunk；一个中间步骤失败，后面全错。
2. **边界缺口**：同步 API 下，下一次 `get_action` 才能看到新世界；如果推理 200ms、执行 1s，提交的动作已经基于 1.2s 前的观测。PACT 的“提交前观测”在挑战赛不存在，必须用“执行窗口内预生成 + 边界新观测选择”替代。
3. **接触缺口**：chunk 内没有反馈；视觉伺服是唯一能在 167ms（H=5）级别修最后 3 厘米的确定性手段；只有 H=1 才是 33ms 闭环。
4. **接口误读**：`action_chunk_size` 不是“模型能力”，是“控制周期”。固定值意味着 H 必须在提交前选好；但候选数 K 可以在运行时变。

## 3. TRI-RATE：三频 + 一个物理标定台

### 3.1 总架构

```text
                    ┌─────────────────────────────────────────────┐
                    │ R0 OPT-GRAPH（0.2–1Hz，CPU）                 │
                    │ 33k 演示 → phase/option 图 → 前置/效果/终止   │
                    │ 输出：当前 option g_t、目标关键帧、回退点     │
                    └───────────────┬─────────────────────────────┘
                                    │ g_t（语言/阶段/目标）
                                    ▼
┌──────────────┐   观测 o_t   ┌─────────────────────────────────────┐
│ evaluator    │ ───────────► │ R1 EXEC-SPEC（3–10Hz，GPU+CPU）      │
│ get_action   │              │ 返回当前 chunk；后台预生成 K 条候选   │
│ 执行 H 步    │ ◄─────────── │ 下一边界用 o_{t+H} 打分选一条         │
└──────┬───────┘   a_{t:t+H}  └───────────────┬─────────────────────┘
       │ H 步执行窗口                          │ 选中 chunk
       │（无新观测，但服务器可算）              ▼
       │                              ┌─────────────────────────────┐
       │                              │ R2 CHUNK-SERVO（动作 30Hz；反馈 6Hz @H=5）│
       │                              │ 5 步 IBVS/PBVS + 接触缩幅     │
       │                              └─────────────────────────────┘
       │
       └──────────────► 下一次 get_action：带 o_{t+H} 回来，完成选择
```

### 3.2 R0 OPT-GRAPH：把 33k 演示变成可执行的“任务语法”

- **离线分段**：用夹爪开合、EE 速度/高度、接触代理、物体位姿变化，把每条演示切成 `approach → grasp → lift → transport → align → insert/hang/zip → release → retreat` 等 phase。
- **聚类成 option**：对 phase 的起点/终点相对位姿、夹爪状态、目标类别聚类；每个 option 存：前置条件、效果、成功检测器、关键帧、相对轨迹、典型时长。
- **建图**：统计 option 转移 `P(o_{i+1} | o_i, task)`；剪掉低频/失败转移；得到每个任务的 DAG/自动机。
- **运行时**：用当前 `s_t`（目标位姿、夹爪、接触、phase 分类）选择 option；VLA 仍用任务语言 + 当前图像执行；option 提供**阶段提示、目标关键帧、终止条件、回退点**。
- **频率**：option **切换**约 0.2–1Hz；**终止/成功检测**每个 chunk 边界都跑，否则长程任务会错过切换点。
- **合规**：option 图是数据检索 + 确定性自动机，不是第二个学习策略；若用分类器，优先用同一 WLA checkpoint 的特征，或纯几何检测器。

**预期收益**：长程任务不再“一条 30 步 chunk 走到底”，而是“每次只对当前 option 负责”；失败可回到上一个 option，而不是整任务重来。

### 3.3 R1 EXEC-SPEC：把执行窗口变成候选计划的决策时间

这是本轮主押注。核心不是“再训一个模型”，而是**改调用时序**：

1. 第 t 次 `get_action`：立即返回已选好的 `a_{t:t+H}`；同时把 `(o_t, g_t)` 丢给后台 worker。
2. 机器人执行 H 步（例如 5 步 ≈167ms，或 10 步 ≈333ms）；worker 用**同一个 WLA checkpoint** 生成 K 条候选 chunk（不同噪声种子/不同 option 提示/不同图像增强），缓存候选动作、预测相对轨迹、生成耗时。WLA 服务器返回的是组合到当前 EE 的绝对轨迹，但内部是相对 delta；候选要保存 anchor + 相对 delta，边界可重锚到当前 EE。
3. 第 t+H 次 `get_action`：evaluator 带回 `o_{t+H}`；用 10ms 级确定性评分选一条：
   - **演示检索残差**：候选相对轨迹 vs 当前 option 的 top-M 演示轨迹（DTW/Frechet）；
   - **新观测目标残差**：从 `o_{t+H}` 更新目标位姿，算候选终点相对目标的误差；
   - **边界平滑**：与上一 chunk 的动作跳变；
   - **接触/滑移**：接触段法向运动惩罚；
   - **候选一致性**：K 条候选的 medoid 距离，低一致则降权/重规划。
4. 返回选中的 `a_{t+H:t+2H}`；若没有候选就绪/新观测显示场景大变/**option 在边界改变**，回退到新鲜规划；若新鲜规划也超时，返回保持/零动作并由 R2 伺服兜底。

**为什么这不是 PACT 照搬**：PACT 在推理过程中看 pre-commit 观测；EXEC-SPEC 在**上一次观测**下预生成候选，在**下一次观测**下选择。它把“推理延迟”藏进“执行窗口”，把“新观测”用在“选择”而不是“生成”。这正好匹配同步 API。

**为什么这不是第二个模型**：候选全部来自同一个 WLA checkpoint；评分器是几何/检索/控制律，无学习权重；option 图是数据自动机。单模型合规。

### 3.4 R2 CHUNK-SERVO：保留第 12 轮的 5 步边界闭环

- 每 5 步边界做一次 IBVS/PBVS 混合（块内开环）：头双目给深度/目标 3D，腕部彩色给局部 2D；目标来自演示检索的“目标-夹爪相对位姿 + 目标图”。
- 接触段法向缩幅、切向慢积分；检测滑移/编辑/人为干扰时停、重定位、重规划。
- 与 R1 的关系：R1 选“哪条计划”，R2 在计划内“怎么修”。两者不互斥；最差回退是只开 R2。
- **接口前提**：真正的闭环频率是 `f_c/H`，不是 30Hz；H=5 时 6Hz，H=3 时 10Hz，H=1 才是 30Hz。对 evaluator 返回的 `action_chunk_size` 必须设成 5–10；WLA 内部仍可规划 30 步，但生成成本按 30 步算。若把 30 步一次性交给 evaluator，R2 只能在返回前做一次前馈，不能做 chunk 内闭环。

### 3.5 HIL-CAL：开源硬件只做“标定 + 压测 + 少量补数”

| 用途 | 硬件 | 产出 |
|---|---|---|
| 腕部手眼/TCP | SO-101 + RealSense D435 + 3D 打印夹爪 | 外参、TCP 偏移、重投影误差 |
| 伺服增益/阈值 | SO-101 + 任务板 + ArUco | 收敛/超调/稳定域、接触缩幅系数 |
| 泛化压测 | 3D 打印背景/干扰物/新物体 + 人为移动 | 失败模式、评分器阈值 |
| 少量补数 | UMI/遥操作 + LeRobot 格式 | 200–500 条成对演示（仅缺口） |

**不做什么**：不从零训策略；不把 SO-101 数据当 G1 数据；不做第二个在线模型；不默认大规模采数。

### 3.6 EDGE-BUDGET：先测再选 H/K，不拍脑袋用 30

- 把一次 `get_action` 拆成：`T_net`（RTT/传输）、`T_pre`（JPEG/缩放/拼图）、`T_vlm`、`T_dit`、`T_post`、`T_queue`。
- 优先优化最大的两项：同区域部署/持久连接、文本/视觉前缀缓存、图像缩放、FP8/INT8、TensorRT/CUDA graphs、few-step action generation、CPU 预处理下放。
- 用实测 `T_g`（一次生成）和 `f_c`（控制频率）选 H：`H* = clamp(ceil((T_g - τ)·f_c), 3, 10)`；用 `K_max = floor((τ + H/f_c)/T_g)` 决定候选数。
- 保留 bf16 回退；量化/TensorRT 必须过单任务 A/B，不能只看吞吐。

## 4. 为什么是现在

- 官方 WLA 基座 + 24GB 微调：不用从零训。
- 33k 成功演示：不只是 imitation 数据，也是 option 图、目标关键帧、相对轨迹的检索库。
- 腕部彩色内参已在数据里；手眼/TCP 可用演示多视图 + 开源硬件补。
- `pivot` 语义、模型服务器延迟日志、`action_horizon` 都已公开；工程不确定性比第 12 轮低。
- PACT/SparkVLA/H-VLA/VLA-HWBench/Guild 分别证明了“候选选择、停止决策、关键动作、动作生成策略、边缘优化”有效；但还没有人把它们组合成“单模型 + 同步 API + 竞赛 chunk”的方案。

- **PACT-RAW**：需要 pre-commit 观测，同步 API 不提供；只保留“候选选择”思想，折进 EXEC-SPEC。

## 1. 事实核对

### 1.1 比赛规则（A）

| 项 | 核实结果 | 对方案的含义 |
|---|---|---|
| 赛事 | 宇树 UniBot 世界挑战赛；G1 + Dex1；桌面操作 | 硬件/相机/动作空间固定 |

### 1.2 提交 API 与服务端行为（A）

**观测**：

- 四路 RGB：`cam_left_high`、`cam_right_high`、`cam_left_wrist`、`cam_right_wrist`，480×640。
- 状态：左/右臂关节各 7；EE 各 6（xyz + rpy，base 系）；夹爪各 1；下身体 15；语言 `str`。
- 无 depth、camera_info、force/torque、tactile。

**动作**：

- `control_space` 只能是 `joint` 或 `ee`，二选一。
- `action_chunk_size` 固定，≥1；返回的 leading time-axis 长度必须等于它；index 0 先执行，其余按顺序执行，直到 evaluator 再次调用 `get_action`。
- `meta.token` 每次返回都要带；`metadata` 里的 `token` 在握手时校验。
- `obs_delta_indices` 决定观测键和堆叠帧数；`image_resize` 可缩放；这些是策略元数据的一部分。

**服务端行为（本轮读代码确认）**：

- `PolicyService` 在每个连接上串行处理请求：`async for frame` → `route(request)` → `await send(...)`。
- `get_action` 路由是同步调用；如果直接在 `get_action` 里跑 6B，事件循环会被阻塞。
- 因此 EXEC-SPEC 必须把生成放到**后台线程/进程**：`get_action` 只做“取缓存 + 10ms 打分 + 返回”，生成在两次调用之间跑。
- 多端口共享模型时，README 明确要求处理并发和状态隔离；`reset()` 必须按端口隔离。

**延迟条款（A）**：README 明确“评测端逐调用记录延迟、延迟波动、动作统计规律”，并建议保持每步推理延迟稳定、动作格式正常。**不要用不规则的长阻塞/短阻塞来“骗”时间**；EXEC-SPEC 的目标是稳定地把生成移出关键路径，而不是制造抖动。

## 2. 问题形式化

### 2.1 时间模型

设：

- `f_c`：控制频率（官方 WLA 默认 30Hz）。
- `H`：`action_chunk_size`（每次返回的动作步数）。
- `T_g`：一次完整生成时间（预处理 + VLM + 动作专家 + 后处理）。
- `τ`：一次请求的通信/排队/返回开销（RTT + JPEG + 服务端处理）。
- `T_s`：边界候选选择时间（CPU，目标 <10–20ms）。
- `W = H / f_c`：一个 chunk 的执行窗口。
- `f_c/H`：策略真正看到新观测/做一次伺服修正的频率（H=5 时 6Hz，不是 30Hz）。

**同步基线**：观测 `o_t` → 生成 `T_g` → 传输 `τ` → 返回 `a_{t:t+H}` → 执行 `W` → 下一次观测。观测到首个动作的延迟约 `T_g + τ`；chunk 内容在提交时已经比“当前世界”旧 `T_g + τ`。

**EXEC-SPEC**：第 t 次调用立即返回已缓存的 `a_{t:t+H}`；后台从 `t` 开始为下一次边界生成 K 条候选；执行 `W` 后，第 t+H 次调用带回 `o_{t+H}`，用 `T_s` 选一条。观测到首个动作的延迟约 `T_s + τ`；候选内容基于 `o_t`，但选择基于 `o_{t+H}`。

**关键条件**：`W + τ ≥ T_g` 才能至少生成 1 条候选；`W + τ ≥ K·T_g` 才能生成 K 条。若 `W + τ < T_g`，EXEC-SPEC 不能隐藏生成，退化为 CHUNK-SERVO。

### 2.2 三个决策缺口

| 缺口 | 时间尺度 | 现有方案 | TRI-RATE |
|---|---|---|---|
| 长程：做什么/做到哪/何时停 | 秒–十秒 | 固定 30 步 chunk，无显式终止 | R0 option 图 + 成功检测器 + 回退点 |
| 边界：下一条选哪条 | 100–200ms | 同步重新生成，慢且旧 | R1 后台候选 + 新观测选择 |
| 接触：偏了 2mm 怎么修 | 167ms（H=5） | chunk 内开环 | R2 每 5 步边界 IBVS/PBVS + 接触缩幅 |

### 2.3 投机窗口公式

```text
W = H / f_c
K_max = floor((τ + W) / T_g)          # 假设请求到达即启动后台 worker，且当前 chunk 已缓存
K_conservative = floor(W / T_g)       # 保守：worker 在返回后才启动
H* = clamp(ceil((T_g - τ) * f_c), 3, 10)
```

解释：

- `H*` 是“让执行窗口至少覆盖一次生成”的最小 H；下限 3 步（100ms）是为了保留伺服/反应，上限 10 步（333ms）是为了不让 chunk 太旧。
- `K_max` 是执行窗口内能生成多少条候选；在 `K_max ≥ 1` 时，K=1 就能把“生成”移出关键路径，K=2–3 才有“选择”空间。
- 如果 `T_g` 很大（如 400ms），`H*` 撞上限 10，K 仍可能是 0；此时必须先做 EDGE-BUDGET（量化/TensorRT/少步生成/同区域部署），否则 EXEC-SPEC 不成立。

### 2.4 候选评分目标

对候选 `c`，定义：

```text
S(c) = w_r * R_demo(c, g_t)
     + w_o * R_obs(c, o_{t+H}, g_t)
     + w_s * Smooth(c, a_{prev})
     + w_c * Contact(c)
     + w_a * Agreement(c)
     - w_u * Uncertainty(c)
```

- `R_demo`：候选的相对 EE 轨迹（由绝对轨迹反解）与当前 option 的 top-M 演示轨迹的 DTW/Frechet 距离；在生成时即可算。
- `R_obs`：从 `o_{t+H}` 更新目标位姿，算候选终点相对目标的误差；在边界算。
- `Smooth`：与上一 chunk 最后几步的动作跳变/加速度。
- `Contact`：接触段沿法向的运动惩罚；用 GEO-RESIDUAL 的滑移/接触代理。
- `Agreement`：K 条候选的 medoid 距离；低一致时降权或触发重规划。
- `Uncertainty`：去噪方差/多候选分歧；高不确定时不要硬选。

**选择规则**：`c* = argmax S(c)`；若 `max S < θ` 或 `R_obs` 显示场景大变（目标移动/遮挡/人为干扰），丢弃候选，走“新鲜规划 + CHUNK-SERVO”回退。

### 2.5 单模型合规

| 组件 | 是否学习模型 | 合规论证 |
|---|---|---|
| R0 option 图 | 否（数据检索 + 自动机） | 不是策略；无在线梯度/权重 |
| R1 候选生成 | 是，同一个 WLA checkpoint | 不加载第二个模型；不同噪声种子/提示 |
| R1 评分器 | 否（几何/检索/控制律） | 无学习权重；CPU |
| R2 伺服 | 否（IBVS/PBVS/控制律） | 无学习权重 |
| HIL-CAL | 否（标定/压测） | 不在线上决策路径 |
| 可选 phase 分类器 | 可能 | 优先用同一 checkpoint 特征或纯几何；否则不上线 |

**禁止**：在线加载第二个策略、残差网络、独立视觉编码器做决策；用不同任务切换不同 checkpoint；用未来观测（评测端不会给，也不允许作弊）。

## 3. 系统设计

### 3.1 总架构

```text
                         ┌──────────────────────────────────────────────┐
                         │ R0 OPT-GRAPH（0.2–1Hz，CPU）                  │
                         │ 33k 演示 → phase/option 图                    │
                         │ 前置/效果/终止/回退；关键帧 + 相对轨迹         │
                         └───────────────────┬──────────────────────────┘
                                             │ g_t（option/阶段/目标）
                                             ▼
┌────────────────┐      o_t        ┌──────────────────────────────────────┐
│ evaluator      │ ──────────────► │ R1 EXEC-SPEC（3–10Hz，GPU+CPU）       │
│ get_action     │                 │ 立即返回缓存 chunk                    │
│ 执行 H 步      │ ◄────────────── │ 后台：同一 WLA 生成 K 条候选           │
│ （无新观测）    │   a_{t:t+H}     │ 边界：o_{t+H} + 10ms 打分选一条        │
└───────┬────────┘                 └───────────────────┬──────────────────┘
        │ H 步执行窗口                                  │ 选中 chunk
        │（服务器可继续算）                             ▼
        │                                  ┌──────────────────────────────┐
        │                                  │ R2 CHUNK-SERVO（动作 30Hz；反馈 6Hz @H=5）│
        │                                  │ 5 步 IBVS/PBVS + 接触缩幅      │
        │                                  └──────────────────────────────┘
        │
        └──────────────► 下一次 get_action：带 o_{t+H} 回来，完成选择
```

### 3.2 R0 OPT-GRAPH

**离线管线**：

1. **分段**：用夹爪开合、EE 速度/高度、物体位姿变化、接触代理，把每条演示切成 phase。
2. **聚类**：对 phase 的起点/终点相对位姿、夹爪状态、目标类别聚类；每个 cluster 是一个 option。
3. **统计**：每个 option 的典型时长、成功率、前置条件、效果、下一步分布。
4. **建图**：每个任务得到 DAG/自动机；剪掉低频/失败转移；保留回退边。
5. **资产**：每个 option 存关键帧、相对 EE 轨迹、目标图、成功检测器、语言提示。

**运行时**：

- 输入 `s_t`：目标位姿、夹爪状态、接触代理、phase 分类、当前 option。
- 选择下一个 option：`argmin cost(s_t, o) + λ * demo_distance(s_t, o)`；确定性。
- 终止：成功检测器/超时/失败检测；成功则前进，失败则回退/重试。
- 频率：option **切换**约 0.2–1Hz；**终止/成功检测**每个 chunk 边界都跑（否则长程任务会错过切换点）。
- 输出 `g_t`：当前 option 的语言提示、目标关键帧、相对轨迹、期望时长。

**为什么不是第二个模型**：option 图是离线统计 + 运行时查表/自动机；成功检测器优先用几何/夹爪/物体位姿变化；如果要用分类器，优先用同一 WLA checkpoint 的特征，且只做 phase 分类，不做动作。

### 3.3 R1 EXEC-SPEC

**线程/进程模型**：

- 每个端口一个 `PolicyService` 连接；每个端口一个 `EpisodeState`（观测历史、上一 chunk、候选缓存、option 状态）。
- 一个共享的 `InferenceBackend`（WLA 模型服务器）处理生成请求；每端口一个轻量 `SpecWorker` 线程/协程。
- `get_action` 只做：解码观测 → 更新状态 → 取当前候选/回退 → 打分 → 返回；生成请求丢给 `InferenceBackend`。
- `reset()` 清空该端口的候选缓存、option 状态、观测历史；不影响其他端口。

**候选生成**：

- 输入：`o_t`、`g_t`、上一 chunk、任务语言。
- 多样性：不同噪声种子（flow/diffusion 天然）、不同 option 提示、不同图像裁剪/缩放；**不换模型**。
- 输出：K 条 `H` 步动作 + 预测相对轨迹 + 生成耗时 + 去噪方差。
- 预算：K=1 先上线；K=2–3 只在 `K_max ≥ 2` 且 GPU 有余量时开。

**边界选择**：

- 输入：`o_{t+H}`、K 条候选、上一 chunk、option 状态。
- 先算 `R_obs`（目标位姿/视觉一致性）和 `Smooth`；再算 `R_demo`（可预计算）和 `Agreement`。
- 若 `max S < θ`、场景大变或**option 在边界改变**：丢弃候选，走新鲜规划；若新鲜规划也超时，返回保持/零动作并由 R2 伺服兜底。
- 输出：选中的 `H` 步；缓存其后续/预测轨迹；启动下一轮候选生成。

**关键工程细节**：

- **当前 chunk 必须已缓存**：第一次调用冷启动可以同步生成；之后每次返回缓存，保证 `get_action` 快。
- **GPU 优先级**：当前边界的“新鲜规划”优先于后台候选；后台候选可被抢占/取消。
- **候选过期**：候选带 `o_t` 时间戳/场景描述子；边界用 `o_{t+H}` 检查；过期就丢。
- **动作格式**：候选必须与挑战赛 API 的 dtype/shape/`action_chunk_size` 完全一致；不要让后台线程写共享 buffer 时被读到半成品。

### 3.4 R2 CHUNK-SERVO

保留第 12 轮的边界闭环，但把“闭环频率”说清楚：

- **反馈频率是 `f_c/H`，不是 30Hz**。H=5 时 6Hz，H=3 时 10Hz，H=1 才是 30Hz；动作本身仍是 30Hz。
- 每个 chunk 边界做一次 IBVS/PBVS：头双目给深度/目标 3D，腕部彩色给局部 2D；目标来自演示检索的“目标-夹爪相对位姿 + 目标图”。
- 块内仍是开环：策略返回的 H 步在 evaluator 上顺序执行，期间没有新观测；所以“5 步伺服”是“每 5 步重算一次”，不是“每 33ms 闭环”。
- 接触段法向缩幅、切向慢积分；检测滑移/编辑/人为干扰时停、重定位、重规划。
- 与 R1 的关系：R1 选“哪条计划”，R2 在计划内“怎么修”。两者不互斥；最差回退是只开 R2。

**接口前提**：把 `action_chunk_size` 设为 **5–10**，让 evaluator 每 5–10 步回调一次；这是 R2 生效的前提。WLA 内部仍可规划 30 步（`action_horizon=30`），但生成成本按 30 步算；除非微调短 horizon 的 action head，否则不能把 `T_g` 当成 5 步的成本。若把 30 步一次性交给 evaluator，R2 只能在返回前做一次前馈，**不能**做 chunk 内闭环。

### 3.5 HIL-CAL

**目标**：

1. 标定腕部手眼 `T_ee_cam` 和 TCP 偏移；用官方演示多视图 + SO-101/RealSense 物理台交叉验证。
2. 标定伺服增益/阈值/接触缩幅；用 SO-101 + 任务板做可重复扰动。
3. 标定 option 检测器/评分器阈值；用 3D 打印背景/干扰物/新物体。
4. 只在数据审计发现缺口时，补 200–500 条成对演示；不默认大规模采数。

**流程**：

```text
官方演示（头双目 + 腕部 + EE 位姿）
  → 多视图束调整/手眼标定 → T_ee_cam 初值
  → SO-101 + RealSense 物理台 → 验证/修正
  → 伺服/评分阈值 → 单任务通道 A/B
  → 缺口补数（可选）→ 同一 WLA 微调（可选）
```

**不做什么**：不从零训策略；不把 SO-101 的动态当 G1；不做第二个在线模型；不假设仿真成功率能预测真机。

### 3.6 状态机

```text
IDLE
  → PERCEIVE（更新目标/夹爪/接触/phase）
  → SELECT_OPTION（R0）
  → SPECULATE（R1 后台；当前 chunk 已缓存）
  → EXECUTE（evaluator 执行 H 步）
  → BOUNDARY_SELECT（R1；o_{t+H}）
      ├─ 候选通过 → EXECUTE（下一 chunk）
      ├─ 候选不通过 → FRESH_PLAN → EXECUTE
      └─ 场景大变/人为干扰 → RECOVER → PERCEIVE
  → TERMINATE（option 成功/任务成功/超时/失败）
```

### 3.7 端口/并发拓扑

- **推荐**：每端口独立进程 + 独立 `PolicyService`；共享一个 `InferenceBackend`（模型服务器）通过本地队列/HTTP/WebSocket 调用。
- **状态隔离**：每端口 `EpisodeState` 独立；`reset()` 只清本端口；候选缓存带 `episode_id`。
- **并发**：后台候选生成不能阻塞当前 `get_action`；GPU 队列按“边界新鲜规划 > 当前 chunk 生成 > 后台候选”优先级。
- **故障隔离**：一个端口的 worker 崩溃不能拖垮其他端口；`get_action` 必须始终能在超时内返回（回退到零动作/上一 chunk 尾部/新鲜规划）。
- **不要**：N 个端口各自加载 N 份 6B（除非 GPU 足够）；共享模型但不做状态隔离（会串 episode）。

### 4.2 I1 EXEC-SPEC（主押注）

**动机**：同步 API 下，`get_action` 返回后 evaluator 执行整个 chunk，期间没有新观测；下一次调用时世界已变。PACT 证明候选选择能 +15pp，但它需要 pre-commit 观测；挑战赛不提供。EXEC-SPEC 把候选生成放到执行窗口，把新观测用在选择上。

**差异**：

- vs CHUNK-SERVO：CHUNK-SERVO 只在 chunk 边界修；EXEC-SPEC 在边界选整条计划。
- vs PACT：PACT 在推理中看 pre-commit 观测；EXEC-SPEC 用“上一观测预生成 + 下一观测选择”适配同步 API。
- vs RTC：RTC 是异步执行/前缀引导；EXEC-SPEC 是服务端候选库 + 确定性评分，不需要改 evaluator。
- vs 模型集成：不加载第二个模型；候选全部来自同一 checkpoint。

**可行性**：

- 官方 `PolicyService` 每个连接串行、`get_action` 同步；后台线程/进程可以在执行窗口跑生成。
- WLA 模型服务器已有 `predict` 接口和延迟日志；可以包一层本地队列。
- 在 `K_max ≥ 1` 时，K=1 就能隐藏生成；K=2–3 需要 `K_max ≥ 2`。
- 风险是 GPU 争用/候选过期/评分器误判；都有回退。

**资源**：

- 1×24GB GPU（WLA 推理）；1×48/80GB 或 2×24GB 可选（K>1/多端口）。
- 16–32 CPU 核：评分/检索/伺服。
- 33k 演示的关键帧/相对轨迹索引：<100GB（只存关键帧/轨迹）。
- 1 人 2–3 周做离线回放 + 单任务 A/B。

**步骤**：

1. G0：测 `T_pre/T_vlm/T_dit/T_post/τ`，确认 `W + τ ≥ T_g`。
2. 实现 `PolicyService` 包装：缓存 chunk + 后台 worker + 线程安全队列。
3. 实现候选生成（K=1/2/3，不同噪声种子/提示）。
4. 实现评分器（demo residual / obs target residual / smooth / contact / agreement）。
5. 离线回放：用演示边界做 1,000 次选择，测选择准确率/AUROC/延迟。
6. 单任务 A/B：PlugInEthernet、HangCup、ZipUp、StackBowls、ToolboxStorage。
7. 接入 CHUNK-SERVO；全量干跑；消融。

**风险**：

| 风险 | 影响 | 缓解 |
|---|---|---|
| 候选过期 | 选到旧计划 | 场景描述子/目标位姿检查；过期丢弃；回退新鲜规划 |
| GPU 争用 | 边界延迟抖动 | 优先级队列；K=1；后台可取消；监控 p99 |
| 评分器误判 | 选错候选 | 多信号加权；低置信回退；离线校准阈值 |
| API 固定 H | 窗口不够 | 选 H*；EDGE-BUDGET；K=1；短 chunk |
| 线程安全 | 半成品动作 | 双缓冲/不可变候选；`get_action` 只读快照 |
| 合规解释 | 被当第二模型 | 全部候选同 checkpoint；评分器无学习权重；文档说明 |

### 4.3 I2 OPT-GRAPH（支撑）

**动机**：37.6s 任务 = 30–40 个 chunk；固定 chunk 没有“做到哪/何时停/失败回到哪”。SparkVLA/H-VLA 证明停止决策/关键动作有效。

### 4.4 I3 EDGE-BUDGET（必做工程）

**动机**：延迟是 first-order；VLA-HWBench 显示动作生成策略比模型大小更能解释延迟；Guild 把 π0.5 做到 43Hz。挑战赛远程 API 的 RTT/推理延迟直接决定 chunk 新旧。

**差异**：

- 不是“换更大模型”，而是把七阶段拆开测，优化最大的两项。
- 不是“无脑 30 步”，而是用 `H*` 公式选 H。
- 不是“只做量化”，而是网络/预处理/动作生成/后处理/队列一起看。

**可行性**：官方服务器已有 `preprocess/predict/encode` 日志；TensorRT/FP8/少步生成都有公开路径；1 人 2–3 周。

**资源**：24GB GPU（起步）；48/80GB 或 Thor（可选）；profiling 工具；同区域部署。

**步骤**：

1. 加 `T_net/T_queue/T_pre/T_vlm/T_dit/T_post` 计时；跑 100 次。
2. 优化 top 2：同区域/持久连接/压缩、图像缩放、文本缓存、TensorRT/FP8、少步生成。

4. 单任务 A/B：量化/TensorRT vs bf16；不过就回退。
5. 监控 p50/p99/内存/端口隔离。

**风险**：量化掉点、TensorRT 复杂度、网络抖动、过拟合一个 RTT。缓解：bf16 回退、A/B、留安全余量、按 p99 不按均值。

## 5. 关键推导

### 5.1 `H*` 表（`f_c=30Hz, τ=50ms`）

| `T_g` (ms) | `W+τ` (ms) | `H*` | 说明 |
|---:|---:|---:|---|
| 80 | 130 | 3 | 下限 3；生成很快 |
| 120 | 170 | 3 | 3 步足够 |
| 160 | 210 | 4 | 4 步 |
| 200 | 250 | 5 | 5 步 |
| 250 | 300 | 6 | 6 步 |
| 300 | 350 | 8 | 8 步 |
| 400 | 450 | 10 | 撞上限 |
| 500 | 550 | 10 | 撞上限；先优化延迟 |

### 5.2 `K_max` 表

`K_max = floor((τ + H/f_c)/T_g)`，`τ=50ms`：

| `T_g` \ `H` | 3 | 5 | 8 | 10 |
|---:|---:|---:|---:|---:|
| 80 | 1 | 2 | 3 | 4 |
| 120 | 1 | 1 | 2 | 3 |
| 160 | 0 | 1 | 1 | 2 |
| 200 | 0 | 1 | 1 | 1 |
| 250 | 0 | 0 | 1 | 1 |
| 300 | 0 | 0 | 1 | 1 |
| 400 | 0 | 0 | 0 | 0 |
| 500 | 0 | 0 | 0 | 0 |

**读法**：

- `T_g=200ms, H=5`：K=1，只能隐藏生成，不能多候选；这是最稳的起点。
- `T_g=120ms, H=5`：K=1；H=10 才能 K=3，但 chunk 太旧。
- `T_g=300ms, H=8`：K=1；H=5 时 K=0，不能投机。
- `T_g≥400ms`：先做 EDGE-BUDGET，不要硬上 EXEC-SPEC。

### 5.3 有效反应时间

- 新鲜规划：观测到首个动作 ≈ `T_g + τ`；动作内容基于当前观测。
- EXEC-SPEC：观测到首个动作 ≈ `T_s + τ`；动作内容基于上一观测，但选择基于当前观测。
- 有效改善：`T_g - T_s`（例如 200ms - 10ms = 190ms），但只在候选被接受时成立；候选被拒绝时回退新鲜规划，延迟回到 `T_g + τ`。
- 因此必须监控**候选接受率**；接受率低说明候选库/评分器/场景变化建模有问题。

### 5.4 评分器校准

- 离线回放：用演示的真实下一帧作为 `o_{t+H}`；候选的 ground-truth 是演示动作/下一段轨迹。
- 选择准确率：`argmax S(c)` 是否落在 top-1 最低动作误差候选。
- AUROC：`S(c)` 是否能区分“场景变了/没变”。
- 阈值 `θ`：在验证集上按“拒绝率 ≤20%”选，保证回退不会太频繁。
- 权重：先手调/网格搜索；不要过拟合 5 个单任务；用 32 任务离线回放做泛化。

### 5.5 回退策略

| 情况 | 回退 |
|---|---|
| 无候选就绪 | 返回保持/零动作 + R2 伺服；若时间够则新鲜规划 |
| 候选全低分 | 新鲜规划；若超时，返回保持/零动作 + R2 伺服 |
| 场景大变/目标移动 | 丢弃候选；重新感知/option 选择；新鲜规划 |
| option 在边界改变 | 丢弃旧 option 的候选；按新 option 新鲜规划/重生成 |
| 人为干扰 | 停/回撤；等稳定；重定位；重规划 |
| 评分器异常/NaN | 选 medoid；仍异常则新鲜规划 |
| GPU 过载 | K=1；降低分辨率；bf16；跳过后台候选 |
| 端口状态污染 | `reset()` 清状态；候选带 `episode_id`；拒绝跨 episode |

## 6. 伪代码

### 6.1 `PolicyService` 包装

```python
class TriRatePolicy:
    def __init__(self, cfg):
        self.cfg = cfg
        self.state = EpisodeState(cfg)
        self.backend = InferenceBackend(cfg)   # shared WLA server
        self.worker = SpecWorker(self.backend, cfg)
        self.current = None                    # immutable chunk snapshot
        self.candidates = []                   # immutable candidate list

    def reset(self):
        self.state.reset()
        self.worker.cancel_all()
        self.current = None
        self.candidates = []

    def get_action(self, obs):
        self.state.update(obs)
        selected = self.boundary_select(obs, self.candidates)
        if selected is None:
            # cold start / no candidate / stale: fresh plan with timeout
            try:
                selected = self.backend.generate(
                    obs, self.state.option, k=1,
                    timeout=self.cfg.fresh_timeout,
                )[0]
            except Timeout:
                selected = self.safe_hold(obs)
        self.current = selected
        # start/continue background generation for next boundary
        self.worker.submit(obs, self.state.option, self.state)
        return selected.actions
```

**注意**：`boundary_select` 只在有 `o_{t+H}` 时用新观测；第一次调用没有候选，走新鲜规划；**不要重放上一 chunk**（那会重复动作）。`safe_hold` 返回与 `action_chunk_size` 同形状的保持/零动作，且必须夹爪保持/限速。后台 worker 的提交要幂等，避免重复生成。

### 6.2 后台 worker

```python
class SpecWorker:
    def submit(self, obs, option, state):
        if self.inflight and not self.cfg.preempt:
            return
        self.queue.put(CandidateRequest(
            obs=obs.copy(), option=option, state=state.snapshot(),
            k=self.cfg.k, seeds=range(self.cfg.k),
            deadline=now() + self.cfg.window_s,
        ))

    def run(self):
        while True:
            req = self.queue.get()
            if req.cancelled:
                continue
            try:
                cands = self.backend.generate(
                    req.obs, req.option, k=req.k, seeds=req.seeds,
                    timeout=req.deadline - now(),
                )
                for c in cands:
                    c.demo_residual = self.scorer.demo_residual(c, req.option)
                    c.smooth = self.scorer.smooth(c, self.last_chunk)
                    c.agreement = self.scorer.agreement(c, cands)
                self.publish(cands, req.episode_id)
            except Timeout:
                self.publish([], req.episode_id)
```

### 6.3 边界选择

```python
def boundary_select(self, obs, candidates):
    if not candidates:
        return None
    # 1) cheap obs gate: has the scene changed?
    scene_score = self.scorer.scene_consistency(obs, self.state.last_obs)
    if scene_score < self.cfg.scene_threshold:
        self.worker.cancel_all()
        return None  # force fresh plan / recover
    # 2) score
    scored = []
    for c in candidates:
        s = (self.cfg.w_r * c.demo_residual
             + self.cfg.w_o * self.scorer.obs_residual(c, obs, self.state.option)
             + self.cfg.w_s * c.smooth
             + self.cfg.w_c * self.scorer.contact_penalty(c, self.state)
             + self.cfg.w_a * c.agreement
             - self.cfg.w_u * c.uncertainty)
        scored.append((s, c))
    scored.sort(key=lambda x: x[0], reverse=True)
    best_s, best = scored[0]
    if best_s < self.cfg.accept_threshold:
        return None
    return best
```

### 6.4 option 规划

```python
def select_option(self, state):
    # deterministic retrieval + automaton
    candidates = self.graph.next_options(state.task, state.current_option)
    scored = []
    for o in candidates:
        cost = self.graph.transition_cost(state, o)
        cost += self.cfg.lambda_demo * self.graph.demo_distance(state, o)
        scored.append((cost, o))
    return min(scored)[1]

def option_done(self, state):
    return self.graph.detector(state.current_option).success(state)
```

### 6.5 伺服（保留第 12 轮）

```python
def servo_step(self, obs, target, contact):
    err = self.perception.target_error(obs, target)   # 2D/3D
    if contact:
        err = self.contact.project_tangent(err)
        gain = self.cfg.gain_contact
    else:
        gain = self.cfg.gain_free
    return self.controller.clip(gain * err)
```

### 6.6 WLA 54D → 挑战赛动作适配

- 官方 WLA 内部是 54D 相对动作（EE xyz+rotvec + gripper + waist + torso + base + legs）；模型服务器用 `_compose_ee_to_xyz_rpy(anchor, delta)` 把它组合成**绝对 EE 轨迹**返回（`action.left_ee_rpy/right_ee_rpy`）。挑战赛 API 需要 `joint` 或 `ee` 的动作，`action_chunk_size` 固定。
- **候选重锚**：保存候选的 anchor + 相对 delta；边界若机器人偏离预测，可把相对 delta 重锚到当前 EE，而不是直接复用旧绝对轨迹。偏差超过阈值则丢弃/伺服。
- 必须在 `example_env.py`/单任务通道验证：
  - EE 动作是相对还是绝对、在哪个坐标系；
  - `pivot` 的 7 维顺序与 waist remap；
  - gripper 的归一化/开合方向；
  - dtype/shape/时间轴；
  - 是否需要 `base_command`/`lower_body`。
- 适配层只做确定性坐标/裁剪/限幅，不做学习。

**方法**：

- 用 ground-truth 演示动作/下一段轨迹算动作误差；用评分器选候选；算：
  - top-1 选择准确率；
  - 候选 oracle 上界；
  - 评分器 AUROC（场景变/不变）；
  - 边界选择延迟；
  - 候选接受率。
- 注入扰动：目标移动、遮挡、背景替换、人为遮挡；测拒绝/回退。

## 10. 风险与合规

### 10.1 单模型合规

| 模式 | 做法 | 风险 | 建议 |
|---|---|---|---|
| C1 离线标注 | option/phase 只离线生成；线上只有 VLA | 最低 | 保守可选 |
| C2 确定性控制器 | 伺服/评分器无学习权重；VLA 是唯一模型 | 低；需说明 | **主推** |
| C3 同 checkpoint 特征 | 目标描述子/phase 分类用同一 WLA encoder | 低–中；需说明 | 需要时用 |
| C4 第二个模型 | 独立策略/残差/编码器 | 高；可能违规 | **禁止** |

**提交材料**：写清楚“唯一学习模型是 WLA；option 图是演示检索/自动机；评分器是几何/控制律；伺服无学习权重；所有候选来自同一 checkpoint”。
