# 第 3 轮迭代（灵感循环 v3：「多机评测」×「Gazebo」）——把评价单元从「单机 episode」换成「机队格点」，把 Gazebo 从「离线裁判」升级为「数字孪生机队」

> 承接 v2（UIP-01′~15）。本轮不推倒重来，而是更换**评价单元**：官方把评测定义为 **N 台真机、随机顺序、端口数与 N 精确相等**，官网愿景第一条即「多机评测集群」。于是核心对象从「单 episode 期望分」变为「机队级格点分 + 并发延迟稳定性」；Gazebo 的用法也从「单实例离线计分神谕」升级为「N 实例数字孪生机队 / 数字风洞」。本轮还顺手修正了 v2 的一个**接口级误读**：`action_chunk_size` 不能在运行时自适应变长，它正是「反应性 vs 机队负载」的唯一全局旋钮。

## 0. 直觉解释与严谨定义

### 0.1 直觉（先给画面）

想象评测机房并排放着 N 台 G1。每台机器人连到你提交服务的一个固定端口：`8765, 8766, …, 8765+N−1`。评测按**随机顺序**把 32 个桌面任务派给这些机器人；每个端口必须独立完成自己那台机器人的整段交互。你的模型如果只有一份，N 个端口会同时敲门；只要有一个端口慢、`reset()` 把邻座状态清掉、或少开/多开一个端口，整场评测的有效性或可信度就会崩。你在家能做的最有价值的事，不是再训一个更强的单机策略，而是**用 N 个 Gazebo 副本把这间机房先演练一遍**：既算步骤分，也算「并发时每个端口的延迟抖动」。

### 0.2 严谨定义（把画面变成可计算对象）

- **评测格点** `c=(i,t,r)`：第 `i` 台机器人、任务 `t`、第 `r` 次重复；顺序 `π` 随机。
- **步骤分**：任务 `t` 的计分点为 `p_{t,1..K_t}`（`Σ p = 100`）；若完成前缀 `m` 步，则 `s_t = Σ_{k≤m} p_{t,k} / 100`；成功率 `y_t = 1[m=K_t]`。
- **榜单代理**：`M = (mean_c y_c, mean_c s_c)`；精确权重未公开，按双口径处理（Pareto）。
- **机队尾部风险**：`W = min_t mean_i s_{i,t}`（最弱任务）或 `CVaR_α({s_c})`（最差 `α` 分位均值）。
- **跨端口干扰**：`I = (q95(ℓ | N 端口并发) − q95(ℓ | 单端口)) / q95(ℓ | 单端口)`；**抖动** `J = q95(ℓ)/q50(ℓ)`。
- **端口谓词**：`P_N = (监听端口数 == N) ∧ (所有端口 metadata/token/权重哈希一致) ∧ (∀i, reset_i 不串扰)`。
- **块长**：`T_a = metadata.action_chunk_size`，按接口**每次必须返回恰好 `T_a` 步**；它同时决定重观测周期（扰动发现延迟 ≤ `T_a` 个控制步）与机队请求率 `λ ≈ N/(T_a·Δt)`。

## 2. 由新事实反推：v2 哪些判断被推翻/升级

1. **推翻：UIP-13 的「运行时自适应块长」不合法。** README §3 明确每次返回的每个动作数组形状为 `(T_a, …)`，`T_a` 是 metadata 里的定值；评测端**整块执行完**才再次调用。因此不能「声明最大 k、实际返回 ≤k」，也不能按任务阶段在运行期改 k。**验证/重做的周期 = T_a**，不是独立的 `k`。v2 的 ACS 需要改写为 **T_a-FLEET：离线选一个全局 T_a，并用机队风洞测出「反应性 vs 并发」的 Pareto 前沿**。
2. **升级：UIP-08′ 从「工程优化」变成「保命约束」。** 端口数精确匹配、每端口状态隔离、共享后端并发，这三件事任一失败都可能让整场评测无效或可信度受损。拆成 **UIP-17（服务架构）+ UIP-19（起飞前自检）**。
3. **升级：UIP-11 GSO → 11′ 机队神谕；UIP-12 DRF → 12′ 机队数据工厂。** 单实例 Gazebo 只能离线打分；N 实例 Gazebo 才能同时测「分数 + 并发延迟 + 端口隔离」，并复现随机顺序。
4. **新增：UIP-18 机队实例鲁棒（FLEET-R）。** N 台真机不是同一台机器的 N 次复制：相机标定、关节零位、夹爪摩擦、桌面高度、光照都会不同。公开数据大概率只覆盖少数实例；这是一个 v2 五轴之外的新泛化轴（**机器人实例轴**）。
5. **新增：UIP-20 调试槽校准阶梯（CAL-LADDER）。** 平台提供不计分单任务调试槽——这正好补上 v2 一直缺的「真机锚点」，而且比计分槽便宜。用少量调试槽校准 Gazebo 神谕，再用计分槽冲榜。

## 3. 两个灵感词的解读

1. **多机评测**：不是「单机评测 × N」的算术放大，而是**统计单元与约束结构**的改变：格点变多、顺序随机、端口数硬约束、并发延迟进入可信度、评测时段稀缺。它把优化目标从 `E[s]` 推向「均值 + 尾部风险 + 延迟稳定性」。
2. **Gazebo**：不只是一台离线裁判，而是**可并行的数字孪生机队**。N 个 headless Gazebo 副本可以分布到 M 台机器，分别绑定一个端口，跑真实 `PolicyService`。物理/接触保真度仍是代理，但**服务链路、端口并发、状态隔离、延迟测量是真的**——这使 DTF 成为「服务风洞」而非「物理真值」。

## 4. 瓶颈假设（v3）

- **H1（保命）**：在机队评测里，**部署正确性 > 模型能力**。端口数、状态隔离、事件循环阻塞这三类错误，会在模型还没上场前就毁掉整场评测。
- **H2（拉分）**：扰动恢复仍是最被规则写明、数据最空白、且与 `T_a` 强耦合的得分点：`T_a` 越大，人为撤回的发现越晚，重做越晚。小 `T_a` 提分，但提负载。
- **H3（耦合）**：`T_a` 是「反应性 ↔ 机队负载」的唯一全局旋钮。存在一个机队最优 `T_a*`，由 DTF 的 `score(T_a)` 与 `I(T_a), J(T_a)` 共同决定；v2 的「按阶段自适应」不可实现。
- **H4（尾部）**：榜单是平均值，但机队格点让**最弱任务/最弱实例**的方差放大；按均值选 checkpoint 可能选到「平均高、尾部脆」的策略。
- **H5（校准）**：Gazebo 机队只可信到「结构/顺序/延迟」；分数必须用调试槽做逐任务校准，否则会「在仿真里刷分」。

## 5. 本轮最大风险（一句话）

**把「多机评测」误当成「单机复制 N 份」**——真正的风险不是模型不够强，而是端口精确匹配、共享状态串扰、事件循环阻塞会在开赛前就把整场评测打废；同时，Gazebo 机队若不做真机调试槽校准，很容易刷出一个与真机机队无关的高分。

**→ 本轮最值得押注：UIP-16 DTF（数字孪生机队）× UIP-20 CAL-LADDER（调试槽校准）× UIP-13″（T_a-FLEET）组成的「先算后测」闭环**——用可并行的 Gazebo 机队预演端口/并发/分数，用稀缺的真机调试槽校准，再把唯一的全局 `T_a` 调到机队 Pareto 前沿；其中 UIP-09′ 的扰动恢复仍是最大单点得分缺口。

## 1. 目标函数与接口纠错（本轮先钉死度量）

### 1.1 机队格点与榜单代理

- 格点 `c=(i,t,r)`：机器人 `i∈[N]`、任务 `t∈[32]`、重复 `r`。
- 步骤分 `s_t = (Σ_{k≤m} p_{t,k}) / 100`，`m` 为已完成前缀计分步；`y_t = 1[m=K_t]`。
- 榜单代理 `M = (mean_c y_c, mean_c s_c)`（精确权重未公开，按双口径）。
- 尾部风险 `W = min_t mean_i s_{i,t}`；`CVaR_α(S) = E[s | s ≤ VaR_α(S)]`。

### 1.2 机队服务度量

- 单端口延迟序列 `ℓ_i(t)`；跨端口干扰 `I = (q95(ℓ|N 并发) − q95(ℓ|单端口)) / q95(ℓ|单端口)`；抖动 `J = q95(ℓ)/q50(ℓ)`。
- 目标：`I ≤ I*`、`J ≤ J*`、`q95(ℓ) ≤ L*`，同时不牺牲 `mean_c s_c`。

### 1.3 接口纠错（推翻 v2 的运行时自适应块长）

README §3：`action_chunk_size = T_a` 是 metadata 定值，**每次返回的每个动作数组形状必须是 `(T_a, …)`**；评测端整块执行完才再次调用。由此：

1. **不能返回少于 `T_a` 步**；「声明最大 k、实际返回 ≤k」不合法。
2. **运行期不能按任务阶段改 `T_a`**；`T_a` 是提交级全局超参。
3. **验证/重做周期 = `T_a`**：两次 `get_action` 之间是开环，`human_*` 的反向撤回最多要等 `T_a` 个控制步才被发现。
4. **机队请求率 `λ ≈ N/(T_a·Δt)`**：`T_a` 越大，往返越少、并发压力越小，但扰动发现越慢；`T_a` 越小则相反。**这就是 v3 的中心权衡。**

> 因此 v2 的 UIP-13「自适应块长」改写为 UIP-13″；UIP-01′ 的「每 k 步核验」也改写为「每 `T_a` 步核验」。

### 1.4 head-of-line 上界（解释为什么共享后端会翻车）

若一个进程在 asyncio 事件循环里同步执行 forward，单次耗时 `τ`，N 个端口同时到达时，FIFO 下第 N 个请求的等待上界 `(N−1)τ`，故 `q95(ℓ) ≈ Nτ`。这解释了为什么「共享一份模型」在参考实现上会天然产生 `I≈N−1` 量级的跨端口干扰；必须把 forward 移出事件循环并做批处理/公平调度。

## 2. 元旗舰：UIP-16 · DTF（Digital Twin Fleet，数字孪生机队）

### 2.1 机制

- **N 个 headless Gazebo 副本**，每个副本绑定一个端口 `8765+i`，各自加载对应任务的桌面场景与机器人实例参数；评测模拟器 `E` 像真实评测端一样连到端口，调用真实 `PolicyService`。
- **M 台机器**横向扩展：每台跑 `ceil(N/M)` 个副本；所有端口外部可达。
- **两种服务模式都要测**：
  - `replicated`（Approach 1）：每端口独立进程、独立模型副本；测显存/启动/隔离。
  - `shared`（Approach 2）：N 个端口 → 一个共享骨干后端；测并发、批处理、状态隔离、跨端口干扰。
- **随机顺序**：每台机器人采样一个 32 任务的随机排列 `π_i`，按排列顺序跑完；重复 `R` 次以估计方差。
- **实例随机化**：每个副本采样相机外参/内参扰动、关节零位、夹爪摩擦、桌面高度、光照（服务 UIP-18）。

### 2.2 与 v2 GSO 的差异

| 维度 | v2 GSO（单实例） | v3 DTF（机队） |
|---|---|---|
| 实例数 | 1 | N（可跨 M 台机器） |
| 评价对象 | 离线回放/单 rollout 分数 | 分数 + 并发延迟 + 端口隔离 + 随机顺序 |
| 服务链路 | 不经过真实端口 | 经过真实 `PolicyService`/端口/网络 |
| 延迟测量 | 无（或离线） | **真实**（服务链路是真的；只有物理是仿真） |
| 主要用途 | 计分代理 | 机队级「服务风洞 + 计分代理」 |

### 2.3 关键论点

**DTF 的分数是代理，但延迟/并发/隔离不是代理。** 因为 DTF 复用了真实的 websocket 服务、真实的 N 端口并发、真实的模型进程/共享后端；Gazebo 只替换了物理与相机。因此 DTF 可以在预约真机前就把「端口数错、共享 reset 串扰、事件循环阻塞、批处理抖动」这些**非物理失败**提前暴露。

### 2.4 伪代码

```python
async def run_dtf(policy_factory, n, tasks, repeats, mode):
    ports = [8765 + i for i in range(n)]
    perms = [random_permutation(tasks) for _ in range(n)]
    results = []

    async def robot(i):
        for t in perms[i]:
            for r in range(repeats):
                env = GazeboReplica(task=t, instance_seed=hash((i, t, r)))
                pol = policy_factory(port=ports[i], mode=mode)   # 每端口一个会话
                results.append(await run_episode(env, pol, record_latency=True))

    await asyncio.gather(*(robot(i) for i in range(n)))          # N 台并发
    return aggregate(results)   # mean_y, mean_s, W, CVaR, I, J, P_N

async def run_episode(env, pol, record_latency):
    obs = env.reset()
    await pol.reset()
    while not env.done():
        t0 = now()
        act = await pol.get_action(obs)      # 必须恰好 T_a 步
        lat = now() - t0
        assert len(act["action.left_arm"]) == pol.metadata["action_chunk_size"]
        obs, done, info = env.step(act)      # 整块执行
        yield Record(task=env.task, score=info.step_score, latency=lat)
```

> 注：`run_episode` 里 `yield` 仅示意记录；实际实现用回调/队列收集，避免阻塞事件循环。

## 3. 保命旗舰：UIP-17 · FLEET-SERV（机队服务架构）

### 3.1 从参考实现读出的三条硬约束

1. **事件循环不可跑 forward**：`PolicyService._on_connection` 在 `async for` 里直接调用同步 `get_action`；共享后端必须把推理移到线程池/独立进程，否则 N 端口串行。
2. **不能共享同一个 stateful policy 对象**：`policy_reset` 是 `self._policy.reset()`；若 N 个端口共用同一对象，A 的 `reset()` 会清掉 B 的 episode 状态。正确做法是**共享权重，分离会话**。
3. **每端口状态必须独立**：history、KV cache、子目标 `g`、`redo` 计数、验证器缓存都按端口/会话隔离；`reset()` 只清自己的。

### 3.2 架构

```text
evaluator ──ws──> [port 8765 endpoint] ──> PortSession(0) ─┐
evaluator ──ws──> [port 8766 endpoint] ──> PortSession(1) ─┼─> InferenceBatcher ─> SharedBackbone (GPU)
   ...                                                     │
evaluator ──ws──> [port 8765+N-1]      ──> PortSession(N-1)┘
```

- **每个端口一个轻量 endpoint**：只做 msgpack/JPEG 编解码、会话绑定、deadline 标记。
- **一个共享骨干**：只保存模型权重，不保存 episode 状态（满足「单模型」合规）。
- **每个端口一个 `PortSession`**：保存该机器人/该 episode 的历史与状态；`reset()` 只清自己。
- **中央 `InferenceBatcher`**：把 N 个端口的请求按 `window_ms` 或 `max_batch` 聚批；在独立线程/进程跑 forward；按最早 deadline 排序。
- **backpressure**：队列超限时先丢「投机预计算/重复验证」等可选工作，绝不丢真实 `get_action`。

### 3.3 伪代码（关键是 async endpoint + off-loop 推理）

```python
class PortSession:                     # 每端口一个，状态隔离
    def __init__(self, port, backbone, T_a):
        self.port, self.backbone, self.T_a = port, backbone, T_a
        self.reset()
    def reset(self):
        self.hist, self.g, self.redo, self.kv = [], 0, 0, None
    def get_action(self, obs):         # 在工作线程里执行，不占事件循环
        req = Req(port=self.port, obs=obs, hist=self.hist,
                  g=self.g, redo=self.redo, T_a=self.T_a,
                  deadline=now() + LAT_BUDGET)
        out = INFER.submit(req)        # 阻塞的是工作线程
        self.hist.append(obs); self.g, self.redo = out.g, out.redo
        return out.actions             # 恰好 T_a 步

class InferenceBatcher:
    def __init__(self, backbone, max_batch=8, window_ms=8):
        self.backbone, self.max_batch, self.window_ms = backbone, max_batch, window_ms
        self.q = deque()
    def submit(self, req):
        fut = Future()
        with self.lock:
            self.q.append((req, fut))
        return fut.result()            # 工作线程等待；事件循环不被阻塞
    def run(self):
        while True:
            batch = self.collect(self.window_ms, self.max_batch)
            batch.sort(key=lambda x: x[0].deadline)      # 最早 deadline 优先
            with torch.no_grad():
                outs = self.backbone([r for r, _ in batch])
            for (req, fut), out in zip(batch, outs):
                fut.set_result(out)

# 注意：共享模式不能原样用参考 PolicyService 的同步 route；
# 需要 async handler 把推理丢到线程池/独立进程。
async def handle(ws, session):
    async for frame in ws:
        req = thaw(frame)
        if req["type"] == "policy_reset":
            session.reset()                            # 只清本端口
        else:
            out = await asyncio.get_running_loop().run_in_executor(
                None, session.get_action, req["obs"])
            await ws.send(freeze(out))
```

### 3.4 设计不变量

- `INV-1`：事件循环线程内**永不**执行 `backbone.forward`。
- `INV-2`：`PortSession.reset(i)` 不改变任何 `PortSession(j≠i)` 的状态。
- `INV-3`：所有端口共享**同一份不可变权重**与同一 `token`/`metadata`。
- `INV-4`：每个响应恰好 `T_a` 步，形状/dtype 严格符合 §3。
- `INV-5`：`q95(ℓ) ≤ L*` 且 `I ≤ I*`；否则先降可选工作，不降真实响应。

## 4. 保命：UIP-19 · PRE-FLIGHT（起飞前自检）

### 4.1 为什么必须做

规则是「端口数必须精确等于 N」且「每端口独立完成整段交互」。N 由主办方另行公布，不能硬编码 3；少开/多开/端口复用/某个端口加载了旧权重，都会在开赛前埋雷。

### 4.2 清单

```python
def preflight(n, token, weight_hash_expected):
    ports = list(range(8765, 8765 + n))
    assert count_listeners(ports) == n                    # 精确 N，不多不少
    metas = [handshake(p) for p in ports]
    assert all(m == metas[0] for m in metas)              # metadata 一致
    assert all(m["token"] == token for m in metas)        # token 一致
    assert all(model_hash(p) == weight_hash_expected for p in ports)
    assert all(externally_reachable(p) for p in ports)    # NAT/防火墙
    # 状态隔离哨兵
    set_sentinel(ports[0], S); reset(ports[1])
    assert get_sentinel(ports[0]) == S                    # 邻座 reset 不串扰
    # 形状/ dtype 冒烟
    for p in ports:
        act = get_action(p, smoke_obs(p))
        assert valid_shape(act, T_a) and valid_dtype(act)
    # 并发延迟探针
    lats = concurrent_probe(ports, rounds=20)
    assert q95(lats) <= L_max and jitter(lats) <= J_max
    return Manifest(n=n, ports=ports, token=token,
                    weight_hash=weight_hash_expected, metadata=metas[0])
```

### 4.3 故障注入表（用于 E301）

| 故障 | 现象 | 自检能否发现 |
|---|---|---|
| 少开一个端口 | 监听数 < N | ✅ 端口计数 |
| 多开一个端口 | 监听数 > N | ✅ 端口计数 |
| 端口复用/旧进程 | 旧权重/token | ✅ 权重哈希 + token |
| 共享 policy 对象 | 邻座 reset 清状态 | ✅ 哨兵测试 |
| 同步 forward 堵事件循环 | 并发 q95 暴涨 | ✅ 并发探针 |
| 某端口不可外达 | 外部握手失败 | ✅ 外达探针 |
| 返回步数 ≠ T_a | 形状校验失败 | ✅ 冒烟 |

### 4.4 启动脚本

- `launch_fleet.py --n N --mode {replicated,shared}`：由 N 自动推导端口区间，生成 `fleet_manifest.json`；`--check` 只跑 preflight 不启动。
- 保留 `/healthz`（参考实现已有）供外部探活。

## 5. 拉分：UIP-18 · FLEET-R（机队实例鲁棒 + 尾部稳健）

### 5.1 机制

- **实例随机化轴**（Gazebo 每副本独立采样）：相机外参/内参、关节零位、夹爪摩擦/回差、连杆质量/质心、桌面高度、光照色温、控制延迟抖动。
- **训练**：把实例参数作为域随机化变量；验证集按**留出实例**划分（不是留出 episode）。
- **选型**：不只最大化均值，而是解约束优化

```text
max_θ   mean_c s_c(θ)
s.t.    min_t mean_i s_{i,t}(θ) ≥ τ_task      # 最弱任务
        min_i mean_t s_{i,t}(θ) ≥ τ_robot     # 最弱实例
```

或用拉格朗日 `max mean_c s_c − λ·CVaR_α(−s)`。

### 5.2 为什么这是新轴

v2 的泛化轴是「未见物品 / 人为干扰 / 位置 / 干扰物 / 背景」。**机器人实例轴**是机队评测新增的：N 台真机的标定、磨损、装配差异，会让同一策略在不同端口上表现不同。公开数据大概率来自少数实例，这一轴没有覆盖。

### 5.3 风险

过度随机化会拉低均值；用「留出实例验证 + 小范围随机化」控制，先保均值再压尾部。

## 6. 校准：UIP-20 · CAL-LADDER（调试槽校准阶梯）

### 6.1 机制

平台提供**不计分单任务调试**槽。把它当作稀缺的真机锚点：

1. **离线**：用 DTF/GSO-F 给候选 checkpoint 打逐任务代理分 `s_GSO,t`。
2. **选任务**：按 `priority_t = w_t · σ_t · |∂rank/∂s_t|` 选少量任务；`σ_t` 用多 checkpoint/多实例种子的分歧估计。
3. **真机调试**：每个选中任务跑 `k_d` 个 episode，得 `s_real,t`。
4. **校准**：逐任务拟合 `f_t: s_GSO,t → s_real,t`（isotonic/仿射，样本少时用层次收缩）。
5. **选型**：用校准后的机队分 `S_cal = mean_t f_t(s_GSO,t)` 选 checkpoint，再约计分多任务槽冲榜。

### 6.2 伪代码

```python
def calibrate_and_select(candidates, tasks, debug_budget):
    gso = {c: {t: score_gso(c, t) for t in tasks} for c in candidates}
    chosen = active_select(gso, budget=debug_budget)      # 任务子集
    real = {t: run_debug_slot(chosen_task=t) for t in chosen}
    f = {t: fit_isotonic(gso_history[t], real_history[t]) for t in chosen}
    def s_cal(c):
        vals = [f[t](gso[c][t]) if t in f else gso[c][t] for t in tasks]
        return mean(vals), cvar_alpha(vals)
    return max(candidates, key=lambda c: s_cal(c)[0])
```

### 6.3 边界

- 调试槽**不计分**，不能当榜单代理；只用于校准与发现硬故障。
- 单任务调试可能只用 1 台/少量机器人（手册未明说），因此它校准的是「任务难度 + 策略行为」，不是机队方差；机队方差仍靠 DTF/FLEET-R 估计。

## 7. 其余升级项（与 v2 的差异）

### UIP-01″ · RHPV-D/F（滚动验证-重做，机队版）

- **修正**：验证周期 = `T_a`，不是独立 `k`；`get_action` 必须返回恰好 `T_a` 步。
- **机制**：每个 chunk 边界用验证器判 `{done, ongoing, fail, regressed}`；`regressed`（反向撤回）→ 重做同一子目标；`redo` 计数与历史按端口隔离。
- **机队差异**：每端口独立状态；`reset()` 只清自己；重做预算由 UIP-15′ 按端口 deadline 约束。

```python
class RHPVD_F:
    def __init__(self, backbone, verifier, T_a, token, max_redo=2):
        self.backbone, self.verifier, self.T_a = backbone, verifier, T_a
        self.token, self.max_redo = token, max_redo
        self.reset()
    def reset(self):
        self.g, self.redo, self.hist = 0, 0, []
    def get_action(self, obs):
        st, conf = self.verifier(obs, self.g)
        if conf >= CONF_THR:
            if st == "done": self.g += 1; self.redo = 0
            elif st == "regressed" and self.redo < self.max_redo:
                self.redo += 1                     # 重做同一子目标
            elif st == "fail" and self.redo < self.max_redo:
                self.redo += 1
        chunk = self.backbone(obs, subgoal=self.g) # shape (T_a, ...)
        assert len(chunk) == self.T_a
        self.hist.append(obs)
        return to_action_dict(chunk, self.token)
```

### UIP-02″ · SSG-F（机队步骤分安全网）

- 按 §8 的 32 任务计分表有序推进：保前置、搏末步。
- **新增**：按任务边际分配验证/重做算力——高价值末步（40/50 分）与高不确定任务优先；低风险任务快速通过，节省机队时段。

### UIP-09′ · DCR-R（扰动撤回检测-重做）

- 保留 v2 核心：检测「已完成进度被撤回」并重做。
- **机队强化**：干扰时机/速度/轨迹在 DTF 中按机器人实例随机化；每端口独立 `regressed` 状态。

### UIP-11′ · GSO-F（机队计分神谕）

- 单实例几何谓词 → N 副本并行；同一谓词库跨实例复用。
- 输出逐任务 `s_GSO`、跨实例方差、失败模式；作为 UIP-18/20 的输入。

### UIP-12′ · DRF-F（机队扰动-恢复数据工厂）

- 在 DTF 的每个副本里按 `human_*` 文本复现反向撤回（拧回、翻开、拉开、拿走、挪底座），并生成 `(干扰前 → 撤回 → 恢复)` 三元组。
- **新增**：实例参数随机化，使恢复策略对机器人差异也鲁棒。

### UIP-13″ · T_a-FLEET（块长机队调度）

- **离线**选全局 `T_a`：用 DTF 扫 `T_a ∈ {1,2,4,8,16}`，得到 `score(T_a)` 与 `I(T_a), J(T_a)`；选满足延迟预算且分数最高的点。
- **块内安全轮廓**：chunk 后段设计为减速/保持/回撤安全动作，降低下一块延迟期间的越界风险。
- **投机预计算**：评测端执行当前块时，后台按预测观测预生成下一块；真实观测到达后只做一致性校验/小修正。
- **灰区（待手册确认）**：是否允许不同端口声明不同 `T_a`。若允许，可做「端口组合对冲」；若不允许，严格全局一致。默认按不允许处理。

### UIP-14 · MSGR（模块化技能图路由）

- 单骨干 + 参数高效技能头；路由必须**无跨端口状态**，仅依赖 `observation.language` + 当前观测。
- 技能图与 UIP-01″ 的子目标状态机对齐。

### UIP-15′ · CSG-F（机队可信度安全阀）

- 每端口延迟预算 + 抖动上限 + 最大重做次数；全局公平调度（最早 deadline 优先）。
- 动作形态平滑，避免统计规律性异常。
- 队列过载时先丢投机/重复验证，不丢真实响应。

## 8. Gazebo 机队实现要点

1. **headless 多实例**：`gzserver`/`gz sim -s` 无 GUI；每实例独立 `GAZEBO_MASTER_URI`/端口/工作目录；CPU 绑核；按 `ceil(N/M)` 分布到 M 台机器。
2. **场景资产**：G1 29-DoF 固定底座 + Dex1 + 桌面资产；相机命名/分辨率对齐接口（`cam_left_high`、`cam_right_high`、`cam_left_wrist`、`cam_right_wrist`，480×640）。
3. **任务与计分谓词**：每任务 2–5 个几何谓词（抓持、接触、插入深度、堆叠关系、拉链位置等），与 §9 计分点对齐。
4. **干扰发生器**：脚本化运动学机械手，按 `human_*` 文本执行「反向撤回」；随机化时机/速度/轨迹。
5. **实例随机化**：相机外参/内参、关节零位、摩擦、桌面高度、光照；每副本固定种子，可复现。
6. **时间与延迟**：物理用仿真时钟；**服务延迟用墙钟**（这才是要测的真实量）。记录 `sim_time/wall_time` 作为保真度诊断。
7. **随机顺序**：每机器人一个任务排列；重复 `R` 次；报告排列间方差。

## 11. 合规与风险

- **端口红线**：端口数必须精确等于 N；多开/少开/不可外达都可能直接失败。N 未公布前，一律用参数化启动与 preflight。
- **状态隔离红线**：共享后端不得共享 episode 状态；`reset()` 必须按端口隔离。参考实现的 `policy_reset` 是共享对象的，不能直接照搬。
- **单模型合规**：所有端口共享同一条骨干与同一 token；技能头/适配器也须属于同一模型。外部 VLM 验证器仍有「非单模型」风险，优先几何/规则验证器。
- **接口红线**：每次恰好 `T_a` 步；形状/dtype/token/`meta.token` 严格符合 README §3；返回步数不足或动作异常都会伤可信度。
- **延迟可信度**：共享后端必须 off-loop + 批处理 + 公平调度；否则跨端口 head-of-line blocking 会让 `I/J` 爆表。
- **仿真过拟合**：DTF 的分数是代理；必须用调试槽校准（UIP-20），并保留计分槽做最终验证。
- **未核实项**：N 的具体值、每个时段的时限/每任务 episode 数、调试模式使用几台机器人、是否允许不同端口不同 `T_a`、5 轴中的位置/干扰物/背景——均待手册或主办方公布。

## 12. 本轮最大风险 & 押注

**一句话**：把「多机评测」误当成「单机复制 N 份」，会让端口数、共享状态、事件循环阻塞在开赛前就毁掉整场评测；而 Gazebo 机队若不做真机调试槽校准，只会刷出与真机机队无关的高分。

**→ 押注：UIP-16 DTF × UIP-20 CAL-LADDER × UIP-13″ T_a-FLEET 的「先算后测」闭环**——先用 N 副本 Gazebo 机队预演端口/并发/分数，用稀缺调试槽校准，再把唯一全局 `T_a` 调到机队 Pareto 前沿；`UIP-09′` 的反向撤回恢复仍是最大单点得分缺口。
