# 第 8 轮 · SURE-BT：成功率先行，恢复是主战场，行为树是落地形态

> 检索/复核日期：2026-10-27（UTC）。赛事身份确认不变：宇树 **UniBot 世界挑战赛**（unibot.unitree.com），G1 + Dex1，32 项桌面任务，通才单模型赛道，选手自部署 + 官方远程真机 API。本轮三个灵感词是「任务规划」「行为树」「场景落地」。我先核实规则与数据，再把三个词钉到本轮新增的硬事实上，最后合成主判断：**排名是字典序——总平均成功率第一，步骤分只在并列时用；每任务 10 次、5 类泛化各 2 次；人类干扰轴占 20%，且是唯一动态轴。上一轮把终局放置当作约 60% 步骤分的大头、并据此把预算压在放置上；这个纠正是本轮预算重排的起点——放置仍是成功闸门，但恢复的边际价值更高。真正的高杠杆不是“再多拿一点部分分”，而是“在扰动和接触误差下仍把整条任务做完”。行为树是把官方评分图编译成运行时、在固定 chunk 边界做验证与恢复的合适形态；但接口的 chunk 是开环执行的，BT 只能在 chunk 边界 tick——这是本轮最重要的工程约束，也是“场景落地”的真正含义。**

## 0. 本轮先核实：七个事实与一个纠正

### 0.1 排名是字典序，不是加权和

参赛手册（中文 [S2]、英文 [S3]）明确：

> 实时榜单按 32 个任务的 **总平均成功率** 进行排序；成功率相同时按 **总平均步骤分** 排序；若仍相同，则 **提交日期较早** 的模型排序靠前。

这句话改变了优化目标。上一轮（PILOT）把“终局放置≈60% 步骤分”当作主要预算依据；现在必须纠正：**步骤分不是奖金，只是并列时的第二关键字**。它仍然有价值——作为诊断“钱丢在哪一步”的 X 光——但不能作为主要优化目标。任何为了提高步骤分而牺牲整任务完成率的策略，在字典序下都是亏的。

### 0.2 每任务 10 次，5 类泛化各 2 次

手册 [S2][S3]：每个任务执行 10 次独立运行，5 类泛化（位置、干扰物、背景、未见物品、人为干扰）各出现 2 次。于是：

- 总评测 = 32×10 = **320 个 episode**；
- 单任务成功率分辨率 = 10%（0/10, 1/10, ...）；
- 单轴 = 32×2 = **64 个 episode**，占总分 20%；
- 单个任务对总分的最大贡献 = 1/32 = **3.125pp**。

这三个数字决定了资源分配：**一个任务值 3.125pp；一个轴值 20%；人类干扰轴只有 64 次观测，却和位置/背景/未见物品同权。**

### 0.3 180 秒、单模型、不得混用

手册 [S2][S3]：单次真机执行上限 180s，超时记失败；所有任务须基于同一模型完成，不得混合多个模型；模型类型不限（World Model、VLA 均可）；选手自部署，官方远程调用。

“单模型”是硬约束。它排除了“LLM 规划器 + VLA 执行器”的双模型堆栈，也排除了“每个任务一个专用模型”。因此本轮的规划器必须是**编译期的确定性代码**，运行时只允许一个学习 checkpoint；任何辅助头（谓词、风险、角色）都必须挂在同一 backbone 上。这一点直接决定了行为树的形态：**不是让 LLM 在线生成 BT，而是离线把官方评分图编译成 BT。**

### 0.4 数据规模与底座

HF collection [S5] 的 32 个数据集在 2026-10-14 全部更新；逐仓统计合计 **33,276 episodes / 18,282,246 frames / 30fps ≈ 169.28h**（[S5][S6][S11]）。四路相机（head stereo ×2 + wrist ×2）、双臂关节/EE 位姿、夹爪、下身、语言指令齐全。

更重要的一条：官方 **UnifoLM-WLA-1.0-Base** 于 2026-09-28 发布（6B、Apache-2.0、约 2,500h 真机数据、64 任务、支持二指夹爪与五指手；[S12]）。UniBot 数据集本身就在它的数据 collection 里。这意味着：**底座大概率已经见过这 32 个任务的正样本；我们再在同一批 33k 上做普通微调，边际收益有限。真正的 gap 是 OOD 执行可靠性（位置/背景/干扰/未见物品/人扰），不是任务知识。** 这为“运行时恢复层”而不是“再训一个更大的 VLA”提供了依据。

### 0.5 提交接口的 chunk 是开环执行的

提交模板 [S7]：

- `metadata.action_chunk_size` 是**一个固定整数**；
- `get_action` 返回形状 `(T_a, ...)` 的动作块；
- 评测端按 index 0..T_a-1 顺序执行，**执行完整个 chunk 才再次调用 `get_action`**；
- 动作空间 joint 或 ee 二选一；观测可选、可叠帧、可缩放；语言全程不变。

推导出的硬约束：**行为树只能在 chunk 边界 tick，不能在 chunk 内中断。** 若 T_a=8、控制 30Hz，则 BT 的决策周期是 267ms；若 T_a=16，则是 533ms。人类干扰可能发生在 chunk 中间，机器人要到下一个边界才知道。这个“反应盲区”是主流 VLA（MolmoAct2 明确说一批 10–30 步执行期间不重规划；[S13]）在人扰轴上失分的结构性原因。解决方案不是“让 BT 更快”，而是**让每个 chunk 都结束在一个安全、可验证、可恢复的端点**（见 §3.4）。

### 0.6 榜单仍是占位，不能拿 29.7% 当真实头部

`leaderboard_data.json` 仍写着 `generated_from: gen_leaderboard.py`；8 个模型 ×32 任务 = 256 条 `task_metrics`；`runs.html` 是 256/256；详情页写明“测试视频占位”；榜单页底部仍是“即将发布”（[S8][S9]）。所以：

- **29.7% 只能当难度先验，不能当真实排名证据；**
- 不能从占位数据推断“哪个轴最弱”或“哪队最强”；
- 可以分析这 8 个模型族（MolmoAct2、WALL-OSS-0.5、DreamZero、Spirit-v1.5、DM0、π0.5、GigaBrain-0、GR00T N1.5）的公开技术路线，把它们当作“头部可能长什么样”的假设。

### 0.7 规则/数据/接口本轮无变更；外部生态有一条新消息

GitHub 提交仍是 2026-08-21 的 v2（[S7]）；数据集最后更新 2026-10-14；手册新增的是评测协议细节，不是规则变更。2026-10-22 宇树发布的是另一个更大的“世界物理 AI 大赛”（八大赛道、年度奖金；[S34]），与 UniBot 不是同一赛事，不能混用。

## 1. 把上一轮的账重算一遍

### 1.1 任务和轴的权重

| 量 | 数值 | 含义 |
|---|---:|---|
| 总 episode | 320 | 32×10 |
| 单任务权重 | 3.125pp | 1/32 |
| 单轴权重 | 20% | 2/10 |
| 单轴 episode | 64 | 32×2 |
| 单任务分辨率 | 10% | 10 次 |

### 1.2 噪声与功效

在 p≈0.3 时：

| 样本 | 二项 SE | 95% CI 半宽 |
|---:|---:|---:|
| 320 | 2.56pp | ±5.0pp |
| 64 | 5.73pp | ±11.2pp |
| 10 | 14.5pp | ±28.4pp |

如果是配对比较（同一批 320 个条件跑两个版本），差值 SE ≈ sqrt(d/320)，d 为不一致率。d=0.10 → 1.77pp；d=0.15 → 2.17pp；d=0.20 → 2.50pp。**所以 +3pp 在配对设计下才勉强可测；+5pp 才是稳妥目标。** 单任务 +10% 的波动完全可能是噪声，不能据此判断方案好坏。单轴 64 次更粗，轴级差异 <11pp 不要当真。

### 1.3 单任务 3.125pp：组合策略比“全面小修”更划算

- 把一个任务从 0% 做到 100%：+3.125pp；
- 把 16 个任务各提高 10pp：+5pp；
- 把人类干扰轴从 10% 提到 40%：+6pp（0.2×30pp）。

这三条路径都可行，但成本不同。**“翻转任务”（flip tasks）通常比“所有任务都涨一点”便宜**：一个任务只差一个终局步骤时，修一个谓词/一个恢复算子就可能从 0 到 60%。这就是“几乎成功前沿”的价值。

### 1.4 步骤分的新用途：X 光，不是奖金

步骤分仍然有用，但用法变了：

- 它告诉我们 episode 死在第几步（step-drop diagnostics）；
- 它给出“几乎成功”的任务清单（S_{k-1} 高、S_k 低）；
- 它是并列时的第二关键字，所以不能完全放弃；
- 但它不是主要目标。**不要为了多拿 20 分步骤分，去冒一次不可逆失败的风险。**

## 2. 三个灵感词，钉到本轮事实上

### 2.1 任务规划：从“在线生成”改为“离线编译 + 组合分配”

UniBot 的任务规划有三层，且都不需要第二个模型：

1. **Episode 层**：官方 `score_steps` 是公开的线性步骤图；用 5 条英文复述匹配任务；把步骤图编译成 BT。对于多物体任务（T02/T04/T06/T11/T13/T15/T20/T21/T22/T25/T27），从 33k 演示里挖**偏序**（哪些步骤可以换序），而不是硬编码官方顺序。
2. **角色层**：约 14–16 个任务需要双手协作（T05/T09/T10/T12/T14/T16/T17/T18/T19/T23/T26/T28/T31/T32）。从演示里挖“支撑手/操作手”的角色分配，编译成 BT 的 `Parallel(Support, Act)` 子树。
3. **组合层（meta）**：32 个任务等权，但可修复性不同。用“几乎成功前沿”估每个任务的 flip potential，把有限的工程/调试槽分配给最可能翻盘的任务。这是“任务规划”在比赛层面的真正含义。

**为什么不用 LLM 规划器？** 单模型规则 + 延迟 + 可复现性。LLM 规划器的输出不稳定，且很难证明它不算“第二个模型”。离线编译的 BT 是确定性的、可审计的、零推理延迟。

### 2.2 行为树：不是“把计划画成树”，而是“在 chunk 边界做决策的运行时”

行为树的真正价值在 UniBot 里是三条：

- **反应性**：条件节点可以在每个 chunk 边界重新评估，失败就走 fallback；
- **模块性**：每个步骤是一个子树，恢复算子可以复用；
- **可验证**：每个步骤有明确的 postcondition，成功/失败可审计。

但标准 BT 假设可以随时 tick；UniBot 的接口是 chunk 开环。所以本轮的 BT 是 **Chunk-Synchronous BT（CS-BT）**：

- tick 周期 = `action_chunk_size / 30` 秒；
- 每个 chunk 的最后一个动作必须是“安全端点”（保持/回撤/预放置姿态），不能在高速运动中结束；
- BT 在边界读取观测，更新步骤信念，决定 `continue / verify / recover / replan`；
- 恢复不能依赖 chunk 内中断，只能依赖“端点安全 + 下一块纠正”。

这把“行为树”从抽象的规划表示，变成了**接口约束下的运行时协议**。这是本轮最具体的创新点之一。

### 2.3 场景落地：不是“泛化口号”，而是“32×10 矩阵 + 人扰剧本 + 分块部署”

“场景落地”在本轮有三层含义：

1. **评测落地**：官方 10 次 = 5 轴×2。我们要在本地复刻这个分层矩阵（SMB-320），而不是随机扰动。位置/背景/干扰物/未见物品是静态分布移，人扰是动态分布移；两者要用不同的验收标准。
2. **干扰落地**：官方 `generalization` 字段给出了逐任务的人扰备注（human_1_note / human_4_note），绝大多数是“把某物平移一次”或“完成某步后撤销它”。这不是模糊的“鲁棒性”，而是**可场景化的剧本**：目标位移、夹具位移、步骤回退、动态遮挡四类。把它们变成恢复算子库和训练对。
3. **部署落地**：选手自部署、远程 API、固定 chunk、token 双校验、可能的多端口并发。BT 状态必须 per-connection/per-episode 隔离；恢复逻辑不能是全局单例；p99 延迟必须小于 chunk 时长。很多“模型很强”的队伍会死在这些工程细节上。

## 3. 失败模型：成功率先行后，什么最致命？

在“全步骤完成才算成功”的字典序下，失败分两类：

- **可恢复失败**：抓空、滑落、放偏、拉链卡住、目标被移动——还能重抓/重放/重拉；
- **不可逆失败**：倒药洒了、插头弯了、碗摔了、水洒了、锁死/卡死——本 episode 基本结束。

人扰备注里，约 2/3 是“目标/夹具平移”，1/3 是“完成后再撤销”。这两类分别对应：

| 失败模式 | 触发 | BT 响应 |
|---|---|---|
| F1 目标在抓取前被移动 | human_1 平移 | 重新定位→更新锚点→重抓 |
| F2 已完成步骤被撤销 | human_4 undo | 谓词回退→重做该步→继续 |
| F3 夹具/容器被移动 | 平移架子/底座/网口 | 更新容器系→重算放置位姿 |
| F4 人手进入工作区/遮挡 | 动态人扰 | 暂停/回撤→等清空→重观测 |
| F5 支撑手漂移 | 双手任务 | 支撑手稳定器→暂停操作手→重抓 |
| F6 接触-rich 插入/闭合失败 | 插头/网线/拉链/锁 | 柔顺搜索→小步retry→重抓 |
| F7 chunk 内开环漂移 | 固定 chunk | 安全端点→边界验证→下一块纠正 |
| F8 谓词误判提前推进 | 视觉噪声 | 迟滞+几何校验→回退 |
| F9 超时 | 重试过多 | 预算守卫→放弃恢复→保步骤分 |

**核心假设（可证伪）**：人扰轴的 baseline 成功率显著低于其他四轴；恢复层带来的增益主要落在人扰轴（20% 权重），并外溢到非人扰轴的执行失败。若调试槽显示人扰轴并不更差，则恢复优先级下调。

证据链：

- MolmoAct2 公开承认“一批 10–30 步执行期间不重规划，遇到意外不能调整”（[S13]）——这正是 F7；
- Wall-OSS-0.5 的零样本任务进度在毛巾折叠 10%、餐桌摆放 9%、充电器插入 9%（[S14]）——接触-rich/可变形/插入是硬骨头；
- π0.5 在 SO-101 真机基准上的恢复率只有 30.77%，执行不稳定是主要失败源（[S21]）；
- HELM 用“记忆+验证器+回滚”在 LIBERO-LONG 上 +23.1pp（[S18]）；ANCHOR 的分层恢复把真机成功率从 53.3% 提到 71.7%，扰动恢复率 71.4%（[S19]）；FLARE 用 Retry/Reset 范式（[S17]）；AgentChord 用“预期恢复分支”在双臂长程任务上提升成功率与效率（[S16]）。
- 这些工作共同说明：**恢复不是附属功能，而是长程成功率的独立乘数。**

## 4. SURE-BT 的轮廓

```text
官方 info.json（32×score_steps + 5 复述 + 人扰备注）
        │
        ▼  离线编译（确定性，无第二个模型）
┌──────────────────────────────────────────────┐
│ 步骤图 → 偏序（演示挖掘）→ 双手角色图          │
│ 每步：谓词模板 / 不可逆标签 / 恢复算子 / 权重  │
│ 输出：32 棵 BT（JSON/XML）                     │
└──────────────────────────────────────────────┘
        │
        ▼  运行时（每个 chunk 边界 tick）
┌──────────────────────────────────────────────┐
│ 观测 → 谓词头（同 checkpoint）→ 步骤信念 b_t   │
│ BT Selector：continue / verify / recover /     │
│              replan / abort                    │
│ 角色仲裁：support hand ↔ act hand              │
│ 护理级别：fast / normal / careful              │
│ 动作块：末步=安全端点；下一块按恢复结果生成     │
└──────────────────────────────────────────────┘
        │
        ▼
单卡/多卡策略服务（per-connection 状态隔离）
```

一句话：**把官方评分图编译成“分块同步的行为树”，用人类干扰剧本训练恢复算子，用双手角色图稳住支撑手，用几乎成功前沿分配工程预算。**

## 6. 风险与合规（先立后破）

- **单模型边界**：BT 是确定性代码；谓词/风险/角色头必须挂在同一 checkpoint。不要用第二个 VLM/LLM 做在线诊断。若用 SAM/FoundationPose 等现成感知模型，先披露并询问组委会；默认不用。
- **谓词噪声**：谓词 F1 <0.85 时，BT 会误推进或过度重试。回退方案：固定相位时长 + 粗粒度成功检测（夹爪开合、EE 位移、接触），只对终局/不可逆步骤做细验证。
- **人扰剧本不等于测试剧本**：官方备注是训练先验，不是测试泄漏。训练时同时覆盖随机平移/撤销/遮挡，避免过拟合备注。
- **chunk 延迟**：T_a=8 时 p99 必须 <267ms；否则机器人会在块间停顿。优化：图像缩放、KV cache、量化、批量多连接；或 T_a=16 换稳定性。
- **调试槽稀缺**：每个大版本最多 1 槽；先离线 SMB-320 筛选，再上真机。
- **榜单占位**：不要用 29.7% 做模型选择；等真实榜单或自己跑调试槽。
- **外部数据**：默认 OFF；邮件确认后再开。
- **统计噪声**：320 次、p≈0.3，SE≈2.56pp；+3pp 不当真，+5pp 才下结论；用配对/分层 bootstrap。

## 2. 评分算术与目标函数

### 2.1 字典序目标

```text
maximize  S = (1/32) Σ_t (1/10) Σ_{r=1..10} 1[all steps completed in (t,r)]
subject to 每 episode ≤180s
tie-break: 步骤分（仅在 S 相同）
```

步骤分：

```text
P = (1/32) Σ_t (1/10) Σ_r Σ_i w_{t,i} 1[step i completed in (t,r)]
```

但排序只用 S；P 是第二关键字。**所以任何“提高 P 但降低 S”的策略都不划算。**

### 2.2 权重与噪声

| 量 | 值 |
|---|---:|
| 总 episode | 320 |
| 单任务权重 | 3.125pp |
| 单轴权重 | 20% |
| 单轴 episode | 64 |
| 单任务分辨率 | 10pp |
| SE(320, p=.3) | 2.56pp |
| SE(64, p=.3) | 5.73pp |
| SE(10, p=.3) | 14.5pp |
| 配对差值 SE(d=.15) | 2.17pp |

**决策规则**：+3pp 只当“可能有信号”；+5pp 才当“可下结论”；单任务 +10pp 不当真；轴级 <11pp 不当真。用配对种子/分层 bootstrap。

### 2.3 任务组合（portfolio）

- 每个任务满值 3.125pp；把 0% 翻到 100% 最贵，但“差一步”的任务翻到 50–80% 很便宜。
- 用几乎成功前沿估 `g_i`（可达成功率增益）和 `c_i`（工程/调试成本），解背包：`max Σ g_i s.t. Σ c_i ≤ C`。
- 经验优先级：先修“终局/不可逆一步”的任务，再修“双手支撑”的任务，最后修“从 0 开始”的难任务。

### 2.4 几乎成功前沿（Almost-Success Frontier）

对每个任务 t、步骤 k：

```text
S_{t,k} = P(step k completed | steps < k completed)
drop_{t,k} = S_{t,k-1} - S_{t,k}
flip_{t,k} ≈ S_{t,k-1} × (1 - S_{t,k}) × 3.125pp
```

`flip` 是“如果只修这一步，最多能拿回多少总分”的上界。优先修 `flip` 大、且该步可修（放置/恢复/谓词）的任务。这个指标把官方步骤分变成了**故障定位器**，而不是奖金。

### 2.5 护理级别分配（Care Allocation）

设步骤 i 的到达概率 `a_i`、通过后剩余成功概率 `q_i`、失败可恢复率 `r_i`。护理的边际价值近似：

```text
V_i ∝ a_i × q_i × (1 - r_i) × Δp_i / Δcost_i
```

直觉：

- 终点/不可逆步骤 `r_i≈0`，`q_i=1` → 护理价值最高；
- 可重试步骤 `r_i` 高 → 护理价值下降；
- 早期步骤 `a_i` 高，但 `q_i` 可能低；晚期步骤 `a_i` 低，但 `q_i` 高；乘积通常在中后段/终局达到峰值。

玩具例子（3 步，p=0.8，步骤 1/2 可重试一次，步骤 3 不可逆）：

| 策略 | 成功率 |
|---|---:|
| 无护理 | 0.512 |
| 护理步骤 1 | 0.766 |
| 护理步骤 2 | 0.766 |
| 护理步骤 3（终局） | 0.876 |

→ **把护理预算给终局/不可逆步骤**，而不是均匀慢放。实现为 BT 的 `CareLevel` 装饰器：fast（自由空间运输）、normal（一般抓放）、careful（插入/倾倒/闭合/堆叠终局）。

### 2.6 人扰轴的杠杆

人扰 = 20% 权重。若其他四轴 p=0.30、人扰 p=0.15：

```text
S = 0.8×0.30 + 0.2×0.15 = 0.27
```

把人扰提到 0.45：

```text
S = 0.8×0.30 + 0.2×0.45 = 0.33  (+6pp)
```

这比“所有任务各涨 2pp”（+2pp）更划算。且恢复能力会外溢到非人扰的执行失败，实际增益更高。**这就是本轮把恢复放在第一位的原因。**

## 3. 失败分类与恢复算子

### 3.1 官方人扰备注的四类剧本

从 32 个 `info.json` 的 `generalization` 字段归纳（[S4]）：

1. **目标位移**（最常见）：抓取前把目标/水果/积木/杯子等平移一次。
2. **夹具/容器位移**：移动盘子、架子、底座、网口、插排、盒子。
3. **步骤回退**：完成后再撤销（盖回瓶盖、拉开拉链、翻开毛巾、拿走第二个碗、拔起插头）。
4. **动态遮挡/追加**：手进入工作区、把网线另一头也插上、传送带物品临近。

### 3.2 恢复算子库（BT 子树）

| 算子 | 触发 | 动作 | 适用 |
|---|---|---|---|
| `Relocalize(obj)` | 目标位移/丢失 | 重新检测→更新 6D 位姿→重算接近 | F1/F3 |
| `Regrasp(obj)` | 抓空/滑落 | 开爪→回撤→重对准→闭爪→抬升验证 | F5/F6 |
| `Reanchor(container)` | 容器/夹具位移 | 更新容器系→重算放置位姿/锚点 | F3 |
| `Redo(step)` | 谓词回退 | 从当前状态重做该步（不重置整任务） | F2 |
| `Rewind(step)` | 多步回退 | 回退到受影响步骤，重做后续 | F2 |
| `WaitClear()` | 人手/遮挡 | 暂停/回撤→等场景清空→重观测 | F4 |
| `Nudge/Insert()` | 插入/闭合失败 | 柔顺小步搜索/微推/轻压 | F6 |
| `Abort()` | 不可逆/超时 | 停止恢复，保步骤分，避免更大损伤 | F9 |

这些算子不是“新模型”，是 BT 的确定性/参数化子树；执行仍由同一个 VLA 生成动作，BT 只改条件、角色、护理级别和目标。

### 3.3 32 任务的双手/不可逆分类（我们的分类，非官方）

| 类别 | 任务 | 数量 |
|---|---|---:|
| 显式双手（hold+act） | T05, T09, T10, T12, T14, T16, T17, T18, T19, T23, T26, T28, T31, T32 | 14 |
| 隐式双手（稳定/小件） | T03, T29 | 2 |
| 单臂为主 | 其余 16 | 16 |
| 不可逆/高风险步骤 | T05, T07, T09, T10, T12, T14, T16, T18, T19, T23, T26, T28, T31, T32 | 14 |
| 双手∩不可逆 | 13 | — |

**含义**：约一半任务需要双手协调，约四成有不可逆步骤。BT 的 `Parallel(Support, Act)` + 护理级别正好覆盖这两个交集。

### 3.4 人扰轴的可测假设

- H1：人扰轴成功率 < 其他四轴平均（若 true，恢复优先级最高）。
- H2：恢复算子对“目标位移/夹具位移”最有效（+20pp 级），对“步骤回退”次之（+10pp 级），对“动态遮挡”最难（+5pp 级）。
- H3：支撑手稳定器对 T10/T19/T31 的双手任务 +5–10pp。
- H4：安全端点/小 chunk 对 F7 有 +3–5pp，但会增加时延；净收益需 A/B。

## 4. SURE-BT 架构

### 4.1 总览

```text
┌────────────────────── Offline（编译/训练）──────────────────────┐
│ info.json ×32 → 步骤图 G_t → 偏序 P_t（演示挖掘）              │
│ 33k demos → 相位切分 → 角色标签（support/act）→ 角色图 R_t      │
│ 人扰备注 → 干扰分类 → 恢复算子库 O                                 │
│ 不可逆标签 → 护理表 C_t；谓词模板 → 谓词头训练                     │
│ 输出：32 棵 BT（JSON）+ 谓词/风险头权重（同一 checkpoint）         │
└──────────────────────────────────────────────────────────────────┘
                                 │
┌────────────────────── Runtime（每 chunk 边界 tick）──────────────┐
│ obs → 谓词头 p(step done) → 信念 b_t → BT Selector               │
│   ├─ continue：下一块正常执行                                     │
│   ├─ verify：安全端点 + 迟滞 + 几何校验                           │
│   ├─ recover：Relocalize/Regrasp/Reanchor/Redo/Rewind/Wait        │
│   └─ replan：偏序重排/角色交换/护理升级/Abort                      │
│ 角色仲裁：SupportHold ↔ Act；护理级别：fast/normal/careful        │
│ 动作块：末步=安全端点；下一块按恢复结果生成                        │
└──────────────────────────────────────────────────────────────────┘
                                 │
                                 ▼
                  PolicyService（N 端口/per-connection 状态隔离）
```

### 4.2 离线编译

**输入**：`info.json` 的 `score_steps`、`generalization`、5 条英文复述（HF `meta/tasks.parquet`）、33k 演示。

**步骤**：

1. **任务识别**：5 条复述 + 中文描述 → 任务 ID；规范化（小写/去标点）+ 嵌入兜底。覆盖 160 条。
2. **步骤图**：线性 `s0→...→sk`，带官方权重 `w_i`（只用于诊断/tie-break）。
3. **偏序挖掘**：对多物体任务，用演示中的物体运动/接触顺序统计，得到 `P_t`；若演示顺序一致，退化为线性。
4. **角色挖掘**：每段轨迹按“支撑手（低位移、持续接触/闭合）/操作手（大位移、开合）”分类；得到每步的角色标签和切换点。
5. **不可逆标签**：人工表 + 物理先验（倾倒/插入/闭合/锁/堆叠终局）；标 `r_i`（可恢复性）。
6. **谓词模板**：`grasped(obj)`, `in(obj, container)`, `on(obj, support)`, `inserted(plug, port)`, `closed(zipper/lid)`, `upright(bag)`, `stable(obj, window)`；用 TLE 标签训练谓词头。
7. **BT 生成**：`Sequence` + `Fallback` + `Parallel` + `CareLevel` + `Retry` + `TimeGuard`；输出 JSON/XML（可审计）。

**BT JSON 示例（T27）**：

```json
{
  "task": "T27",
  "steps": [
    {"id": 1, "score": 30, "predicate": "bowl1_at_center", "care": "normal",
     "recovery": ["relocalize", "regrasp"]},
    {"id": 2, "score": 30, "predicate": "bowl2_on_bowl1", "care": "careful",
     "recovery": ["reanchor", "redo"]},
    {"id": 3, "score": 40, "predicate": "bowl3_on_bowl2", "care": "careful",
     "recovery": ["relocalize", "nudge", "regrasp"]}
  ],
  "bt": "sequence(step1, step2, step3, verify_all)"
}
```

### 4.3 运行时：Chunk-Synchronous BT

**Tick 周期**：`L/30` 秒（L=`action_chunk_size`）。每个 tick：

```python
def tick(obs):
    b = update_belief(obs)                  # 谓词头 + 几何校验
    if surprise(b, obs):                    # 人扰/回退/滑落
        return recover(b, obs)
    if b.current_done and stable(b):
        advance()
        if done(): return verify_all()
    care = care_table[current_step]
    role = role_graph[current_step]
    anchor = anchor_provider(current_step, obs)
    chunk = policy.act(obs, step=current_step, role=role,
                       care=care, anchor=anchor, endpoint="safe")
    return chunk
```

**关键规则**：

- 谓词必须“连续 N 帧为真 + 几何/接触校验”才算完成；避免 F8。
- 每个 chunk 的末步是安全端点：保持/回撤/预放置；不在高速运动中结束。
- 恢复在 chunk 边界执行；若恢复需要精细动作，下一块用 `careful`。
- `TimeGuard` 监视剩余时间；低于阈值时降级为 `Abort`（保步骤分，不冒险）。
- 所有状态 per-episode；`reset()` 清空。

### 4.4 Chunk 合同（Chunk Contract）

| L | 块时长 | BT tick | 反应性 | 推理压力 | 建议 |
|---:|---:|---:|---|---|---|
| 4 | 133ms | 7.5Hz | 高 | 很高（p99<133ms 难） | 只在模型很快时 |
| 8 | 267ms | 3.75Hz | 中 | 中（p99<267ms 可行） | **默认** |
| 16 | 533ms | 1.9Hz | 低 | 低（p99<533ms 易） | 延迟不达标时 |

- 若推理 p99 > 块时长，机器人会在块间停顿；180s 可吸收少量，但不能频繁。
- 安全端点让“块内盲区”不至于造成不可逆失败；这是比“减小 chunk”更便宜的补救。
- 优化的优先级：图像缩放（240×320）→ KV cache/量化 → 多连接批处理 → 最后才增大 L。

### 4.5 双手角色图

**角色定义**：

- `Support(obj)`：稳定夹具/容器，保持位姿，不主动移动；
- `Act(obj, target)`：执行抓取/放置/插入/倾倒；
- `Handover`：角色交换（少数任务）；
- `Release`：任务完成后释放。

**挖掘**：从演示的每段轨迹计算两手的位移、夹爪开合、与物体的接触/相对位姿；低位移+持续接触=Support，大位移+开合=Act。得到每步的角色标签。

**运行时**：

- BT 用 `Parallel(SupportHold, Act)`；`SupportHold` 成功条件=支撑物相对位姿稳定（<ε）+ 夹爪闭合；
- 若支撑手漂移 >ε，暂停 Act，执行 `Regrasp(Support)`，再恢复；
- 角色不绑死左右手：`role_graph` 可交换，避免“左撇子/右撇子”过拟合。

**示例**：

- T10：左手 `Support(power strip)`，右手 `Act(plug → socket)`；插入时支撑手稳定器保持插排位姿。
- T19：左手 `Support(pouch)`，右手 `Act(zipper)`；拉链卡住时 `Nudge` + 支撑手微调。
- T31：左手 `Support(case)`，右手 `Act(zipper)`；合上后 `Verify(closed)`。
- T32：左手 `Support(cup)`，右手 `Act(syringe)`；推注时支撑手稳定。

### 4.6 风险头（可选）

- 在同一 backbone 上加一个二分类头：输入当前观测/历史/动作块，预测“本 chunk 后是否即将失败/需要恢复”。
- 标签：最终成功/失败 + 恢复事件；也可用“下一块是否发生谓词回退/滑落”作为细标签。
- 校准：温度缩放/分位数；阈值偏保守（高精度，低误报），避免频繁打断。
- 触发：风险 >τ → BT 选择 `verify` 或 `careful`，不直接 `Abort`。
- 证据：Foresight 用 action-conditioned world-model embedding 做失败检测（[S31]）；我们只用轻量头，不训练完整世界模型。

### 4.7 单模型合规矩阵

| 组件 | 类型 | 是否学习 | 合规说明 |
|---|---|---|---|
| WLA-1.0-Base | 唯一 checkpoint | 是 | 主体 |
| 谓词头 | 同 checkpoint 辅助头 | 是 | 共享 backbone |
| 风险头 | 同 checkpoint 辅助头 | 是 | 共享 backbone |

## 5. 任务规划的两个层级

### 5.1 Episode 层：偏序 + BT

- 官方步骤图给出“必须做什么”；演示偏序给出“可以先做什么”。
- 对多物体任务，按“可达性/遮挡/稳定性/角色占用”选顺序：
  - 先拿遮挡其他物体的；
  - 先放需要支撑手持有的容器；
  - 易碎/易洒的放最后；
  - 人扰后按新位置重排。
- 这比固定官方顺序更鲁棒，但不改变评分步骤的语义。

### 5.2 组合层：几乎成功前沿 + 调试槽分配

- 每次调试跑完，记录每任务每步的完成率；
- 计算 `drop` 和 `flip`；
- 优先修 `flip` 大且可修的任务；
- 用背包/贪心分配工程周和调试槽；
- 对“从 0 开始”的难任务，只在它能作为多个任务的共享技能锚点时投入（例如拉链、插入、倾倒）。

### 5.3 假设的优先级（待调试槽验证）

| 优先级 | 任务 | 理由 |

| P0 | T19 ZipUp, T31 OrganizePencilCase | 双手+闭合；人扰 undo 直接命中 |
| P0 | T27 StackBowls | 终局堆叠；放置门控的典型 |

## 8. 创新点清单（本轮迭代）

### I1 SURE-BT：评分图编译的分块同步行为树（押注｜新）
- 动机：排名成功率先行；官方 32 任务评分图公开；主流 VLA chunk 内开环，长程/人扰易断。

- 可行性：备注公开；64 条剧本；算子可参数化；可用同一 VLA 执行。
- 资源：1 人 ×2 周；数据合成/回放。

## 9. 风险、合规与开关

| 风险 | 概率 | 影响 | 缓解 | 停止条件 |
|---|---|---|---|---|
| 人扰假设不成立 | 中 | 高 | 调试槽先测人扰 vs 其他轴 | 人扰不更差 → 恢复降级 |
| 谓词噪声 | 高 | 高 | 迟滞+几何校验；F1<0.85 回退 | 误推进 >5% → 回退 |
| chunk 延迟 | 中 | 高 | 缩放/量化/L=16 | p99>块时长 → 增 L |
| 单模型审计 | 中 | 高 | 辅助头同 checkpoint；BT 代码；披露 | 审计不过 → 去风险头 |
| 双手角色冲突 | 中 | 中 | 角色可交换；稳定器可关 | 双手任务回归 → 关 |
| 备注过拟合 | 中 | 中 | 随机扰动混采 | 随机扰动下降 → 调权重 |
| 调试槽稀缺 | 中 | 中 | 离线 SMB 先筛 | 无槽 → 保守提交 |
| 外部数据违规 | 低 | 高 | 默认 OFF | 禁止 → 停 |
