# 第 13 轮 · COOL-SERVE：把 320 次真机评测当成一个有热预算的服务班次

> 检索/复核日期：**2026-10-31（UTC）**。赛事身份不变：宇树 **UniBot 世界挑战赛**（unibot.unitree.com），G1 + Dex1，32 项桌面任务，通才单模型赛道，选手自部署 + 官方远程真机 API。本轮是新灵感循环第 1 轮，三个词是「服务设计」「热管理」「UniBot」。本轮不推倒第 10 轮 FACT-VLA、第 11 轮 GEO-RESIDUAL、第 12 轮 CHUNK-SERVO，而是在它们之上补一层此前没人认真对待的东西：**真机评测不是 320 个独立 episode，而是一个会发热、会排队、会降级、会恢复的服务班次。**

## 0. 先给结论：缺的可能不是更聪明的策略，而是“服务退化”没有被建模

第 12 轮把问题定位为“最后 3 厘米的开环执行”，这是对的；但只解释了单次 episode 内的失败。还有一类失败不在 episode 内，而在 episode 之间：

1. **`reset()` 只重置任务状态，不重置机器人温度。** 32 任务 × 10 次、跨 N 台机器人连续评测；单个任务平均 6.2–37.6 秒，整场评测是小时级。热时间常数是分钟级，热状态会跨 episode 累积。
2. **`action_chunk_size` 握手时固定，不能按“当前热不热”动态改。** 它同时决定反馈新鲜度和 VLA 请求负载；选错不是“慢一点”，而是排队不稳定或接触段开环。
3. **API 没有温度、电流、力矩、触觉。** 不能等温度报警再处理；只能用关节状态、动作、跟踪残差和 URDF 逆动力学做**热代理观测**。
4. **单模型规则不允许再加一个学习型热预测器。** 但热账本、服务治理、chunk 定尺、休息位姿都是确定性控制/服务逻辑，不是第二个模型。

所以本轮的押注是 **COOL-SERVE**：

> 把评测当成一个 shift（班次）来运营：用**跨 episode 的热账本**记录每个端口的累计热债；用**逆动力学 + 跟踪残差**估计不可直接测量的热负载；用 **SLO/error budget** 管住延迟、超时和降级；用**热态 p99** 一次性选定固定的 API chunk 与内部 VLA plan horizon；用**休息位姿、微暂停、双臂负载均衡、接触段降速**把热负载从接触精度上挪开；用**服务蓝图**把 handshake/reset/observe/plan/execute/recover 的失败点写清楚。

一句话：**先把机器人当成一台会过热的服务器来运营，再谈策略能不能多涨 3 个百分点。**

三个可验证创新点：

1. **STL（Shift-level Thermal Ledger）**：跨 `reset()` 保留每端口热账本；若进程被重启，则用首帧观测与时间戳保守重建。
2. **TORQUE-SHADOW**：用 G1 URDF 逆动力学估计关节扭矩，用 `action_t` 与 `state_{t+1}` 的跟踪残差做负载代理；不声称是温度计。
3. **HOT-CHUNK + SERVICE-GOVERNOR**：把 API chunk 与内部 VLA horizon 分开定尺；用排队论和热态 p99 选固定值；用 SLO/error budget 做降级与恢复。

三个灵感词怎么落到方案里：

| 灵感词 | 落到哪里 | 不做什么 |
|---|---|---|
| **服务设计** | 把评测当 shift：SLO、error budget、服务蓝图、端口隔离、降级/恢复、可观测性 | 不把“服务治理”包装成第二个策略；不增加评测端不存在的接口 |
| **热管理** | 热账本、逆动力学热代理、休息位姿、微暂停、双臂均衡、接触段降速、热态 chunk 定尺 | 不假设能读温度；不训练第二个学习型热模型；不牺牲接触精度换低温 |
| **UniBot** | 32 任务 ×10、N 端口 8765+、180s、单模型、官方 WLA 基座、33k 演示、单任务不计分通道 | 不从零训 6B/14B；不逐任务训策略；不把历史榜单当当前事实 |

## 1. 本轮新核实/修正的事实（只列会改变方案的）

### 1.1 规则：这是一次跨机器人、跨 episode 的服务评测

官方参赛手册与提交模板（2026-10-31 复核）确认：

- 所有任务须基于**同一模型**完成；模型类型不限，但不得混合多个模型一起测试。
- 32 个任务，每任务 **10 次**独立运行；5 类泛化各 2 次：位置、干扰物、桌面背景、未见物品、人为干扰。
- 单次真机执行上限 **180 s**；排名先看 32 任务总平均成功率，再看总平均步骤分，再看更早提交。
- 评测跨 **N 台机器人**；提交须从 **8765** 起暴露 N 个连续端口；每端口独立交互，`reset()` 状态必须隔离。
- 另有**不计分的单任务测试通道**，可用于单任务成功率/步骤分/延迟/热行为验证。

**对方案的约束**：COOL-SERVE 必须是每端口独立、CPU 轻量、不抢 GPU 的服务层；热账本可以跨 episode，但不能跨端口串状态；任何“热适应”都不能变成第二个学习模型。

### 1.2 API：chunk 固定、没有热遥测，但腕部内参已经能拿到

提交模板 README（2026-10-31）确认：

- 观测：`cam_left_high`、`cam_right_high`、`cam_left_wrist`、`cam_right_wrist` 四路 RGB **480×640**；双臂关节 `[7]`、EE 位姿 `[6]`（xyz+rpy，base 系）、夹爪 `[1]`、下身体 `[15]`、语言 `str`。
- 动作：`control_space` 仅 `joint`/`ee`；`action_chunk_size` **握手时固定**，index 0 先执行，其余顺序执行，直到 evaluator 再次调用 `get_action`。
- `obs_delta_indices` 决定传哪些键和时间堆叠；`image_resize` 可缩放；`metadata.token` 每次 `get_action` 都要带。
- **没有 depth、camera_info、force/torque、tactile、temperature、current。**
- 评测端逐调用记录延迟、波动和动作统计规律，作为结果可信度的一部分。

**修正第 12 轮的一处事实**：HangCup 的 `meta/info.json`（2026-10-31 复核）中，腕部相机**已经有内参**：左腕 `fx≈436.406`、`fy≈435.922`、`cx≈323.922`、`cy≈242.933`；右腕 `fx≈435.115`、`fy≈434.499`、`cx≈319.025`、`cy≈240.993`，并有 inverse Brown-Conrady 畸变。第 12 轮“腕部无内参、必须先棋盘格标定”的判断应降级为“内参可用，但仍需验证安装外参与热漂移”。

### 1.4 热事实：G1 的“静置也会热”和“长时间连续运行”是公开可查的

- G1 ankle roll 在 SONIC 控制下 **5–10 分钟到 90°C**，即使 idle；stock controller 约 30–45°C（NVlabs/GR00T-WholeBodyControl issue #174，2026-06-02）。这说明“下身体静置支撑”本身就是背景热负载。
- G1 + Inspire 手会导致肩部电机过热、手臂失响应（unitree_sdk2_python issue #129）。桌面任务虽然不是全身运动，但**长时间前伸、悬停、夹持**会持续给肩/肘加载。
- Unitree A1 的热感知 locomotion 把连续运行时间从约 **7 分钟**提升到 **27 分钟**（arXiv 2603.01631）。这是“用执行策略换热预算”的直接先例。
- G1+ 官方宣称同扭矩发热降低约 **72%**（二手/宣传口径，B 级），Fraunhofer IPA 报告手臂水平伸展无负载 **1–2 分钟**可能过热关机（二手报道，B 级）。两者都只作为风险方向，不进入定量模型。
- 相机热漂移是已知问题：长时运行会出现 warm-up drift 与标定漂移（公开文献，B 级）。本轮只把“相机自标定”列为可选子项，不把它当主线。

### 1.5 榜单：当前不可复核，历史分数只能当先验

2026-10-31 访问 `leaderboard.html`、`runs.html` 均显示 **Coming Soon**；`leaderboard_data.json` 返回 EdgeOne 反爬 HTML，JSON 解析失败（`Expecting value: line 1 column 1 (char 0)`）。第 12 轮记录的 8 个模型与 29.7% 等数字，**只能作为历史先验**，不能作为当前 SOTA、任务难度表或失败分布。

模型家族路线仍然有参考价值：MolmoAct2 的 action reasoning、WALL-OSS-0.5 的 4B VLA、DreamZero 的 14B world-action model、GigaBrain-0 的世界模型数据、GR00T N1.5 的部署生态、π0.5 的开放世界泛化。它们的公开延迟（H100/RTX 5090/Jetson Thor，口径不同）只能做数量级参考：180ms–790ms 的 VLA 推理意味着**任何“每次 get_action 都跑 VLA”的方案都必须先过排队论**。

### 1.6 服务设计：SLO、error budget、服务蓝图不是“软话题”

- Google SRE 的 SLO/error budget 把“可靠性”变成可运营的预算：不是追求零失败，而是在预算内做风险决策。
- NN/g 的服务蓝图把前台接触点、后台流程、支撑系统、失败点和恢复动作放在同一张图里；这对“N 端口 + 共享模型 + 单任务测试通道”的评测非常贴合。
- NVIDIA GR00T 部署文档明确讨论 stop-and-go、异步推理、RTC（real-time chunking）和 30FPS 延迟预算；这说明“推理服务化”已经是机器人基础模型的部署前沿，而不是我们硬造的概念。

## 2. 诊断：三个“服务不匹配”

### 2.1 episode 独立假设 vs 班次热累积

评测方按 episode 计分，但机器人不按 episode 冷却。一次 10 次 trial 的连续任务，可能比一次 180 秒长任务更热；一个端口的第 10 次 trial 可能继承第 1–9 次的热债。如果策略假设“每次 reset 都是冷启动”，它会在后半段遇到：

- 跟踪残差变大 → 动作执行偏差 → 接触失败；
- 电机降额/保护 → 动作变慢 → 超时或步骤分下降；
- 相机 warm-up/热漂移 → 视觉伺服目标偏移。

这些不是模型语义问题，而是**服务退化**。

### 2.2 固定 chunk vs 变化的服务负载

`action_chunk_size` 固定，但服务负载随 N、控制频率、VLA 推理时间、图像分辨率、是否启用伺服而变化。chunk 选小：

- 反馈新鲜，但 `get_action` 调用频率高；若每次调用都触发 VLA，排队会爆炸；
- chunk 选大：VLA 负载低，但接触段开环时间长。

第 12 轮已经用双频（VLA 30 步 plan + 5 步 servo）解决了一部分；本轮要把它形式化：**API chunk 和 VLA plan horizon 是两个不同的量，不能混为一谈。**

### 2.3 只看成功率 vs 服务 SLO

比赛最终只看成功率/步骤分，但成功率是结果，不是可运营的过程指标。若没有延迟、超时、降级、热债、恢复时间这些 SLO，团队无法判断“这次失败是模型不行，还是服务层在发热/排队/超时”。服务设计的作用不是直接加分，而是**让失败可归因、让降级可控制、让恢复可演练**。

## 3. 方法：COOL-SERVE

### 3.1 总架构

```text
                 ┌────────────────────────────────────────────┐
                 │ Evaluator (N ports 8765..8765+N-1)         │
                 └───────────────┬────────────────────────────┘
                                 │ websocket: obs / action chunk
                                 ▼
                 ┌────────────────────────────────────────────┐
                 │ Per-port Service Plane (CPU)               │
                 │  ├─ STL thermal ledger (cross-episode)     │
                 │  ├─ TORQUE-SHADOW observer                 │
                 │  ├─ SLO governor / error budget            │
                 │  ├─ plan cache + servo (CHUNK-SERVO)       │
                 │  ├─ goal retrieval (DG-KEYFRAME)           │
                 │  └─ action adapter (WLA 54D → API 21D)     │
                 └───────────────┬────────────────────────────┘
                                 │ async, batched, stateless
                                 ▼
                 ┌────────────────────────────────────────────┐
                 │ Shared VLA server (GPU), one checkpoint     │
                 │ UnifoLM-WLA-1.0 / 微调 action head          │
                 └────────────────────────────────────────────┘
```

- **模型面**：仍然只有一个学习模型（WLA/VLA）。COOL-SERVE 不加载第二个策略、不训练第二个热预测网络。
- **服务面**：每端口一个进程/实例，独立 reset、独立热账本、独立 plan cache；共享 VLA server 只做无状态推理。
- **控制面**：CHUNK-SERVO 的双频执行保留；热管理只改变“何时休息、用哪只臂、接触段多快、chunk 定多大”，不改变 VLA 的语义输出。

### 3.2 STL：跨 episode 的热账本

每个端口维护：

```text
port_state = {
  heat_index x,            # 0..1 的相对热债，不是摄氏温度
  cumulative_exposure E,   # ∫ max(0, x - x_ref) dt
  last_update_t,
  episode_count,
  mode,                    # NORMAL / CONSERVE / HOLD / RECOVER
  calibration_quality,
}
```

- `reset()` 只清任务态（plan、goal、相位、编辑检测），**不清热账本**。
- 如果评测端重启进程、换端口或换机器人：用首帧时间戳、关节温度代理（见 3.3）和保守初值重建；无法重建时从 `CONSERVE` 模式起步。
- 账本按端口隔离，不跨端口共享；共享 VLA server 不知道热状态，保持无状态。

### 3.3 TORQUE-SHADOW：没有温度计时的热代理

对每条臂的 7 个关节，用 G1 URDF 做逆动力学：

```text
τ_hat = M(q) q̈ + C(q, q̇) q̇ + g(q) + τ_friction
```

`q` 来自观测，`q̇/q̈` 由有限差分/滤波得到。定义归一化热负载：

```text
b_t = clip(
  Σ_j w_j (|τ_hat_j| / τ_max_j)^2
+ Σ_j w_v (|q̇_j| / q̇_max_j)^2
+ w_s · 1[|q̇_j| < ε] · (|τ_hat_j| / τ_max_j)
+ w_r (r_t / r_scale)^2,
  0, 1)
```

其中 `r_t = ||a_t ⊖ state_{t+1}||` 是动作跟踪残差（关节空间或 EE 位姿空间），`w_*` 是可解释权重。然后用一阶热模型更新相对热债：

```text
x_{k+1} = clip(x_k + α b_k (1 - x_k) - β x_k, 0, 1)
```

- `α` 是加热系数，`β` 是冷却系数；初始值由公开热时间常数/单任务 endurance 拟合，**只用于相对排序，不声称是温度**。
- `x` 高不代表一定过热，只代表“当前动作组合在该机器人上更可能积累热债”；阈值必须用 endurance test 校准。
- 下身体静置支撑作为背景负载单独计一项；桌面任务主要看肩/肘/腕。

### 3.4 SERVICE-GOVERNOR：SLO 与 error budget

定义四类 SLO（每个端口/每场评测）：

| SLO | 指标 | 初始目标 | 作用 |
|---|---|---|---|
| 成功 SLO | 32 任务平均成功率 | 不低于基线 -1pp | 不允许热管理伤成功率 |
| 延迟 SLO | `get_action` p99 | ≤150ms（不含 VLA 冷启动） | 防止排队拖垮接触 |
| 超时 SLO | 单次 episode 超时率 | ≤1% | 防止热降额导致 180s 超时 |
| 热 SLO | `x > x_crit` 的时间占比 | ≤5% | 触发 CONSERVE/HOLD |

- **NORMAL**：正常 CHUNK-SERVO。
- **CONSERVE**：降低接触段速度、增加微暂停、优先用低热臂、缩短伺服图像分辨率；不改变 VLA 语义。
- **HOLD**：仅当 `x` 接近危险区且任务允许时，用低扭矩休息位姿等待 0.2–1s；接触中禁止急停。
- **RECOVER**：跟踪残差突变/相机标定漂移/超时前兆时，回退缓存 plan 或安全 hold，下一 episode 从保守模式起步。

Error budget 的用法：不是“允许失败”，而是**把风险预算花在能涨分的任务上**。例如高价值接触任务允许更高的伺服计算/更低的 chunk；低价值长任务优先 CONSERVE，避免把热债带到后面的任务。

### 3.5 HOT-CHUNK：把 API chunk 与 VLA horizon 分开

这是本轮最重要的工程修正。设：

- `f_c`：evaluator 控制频率（需实测，默认 30Hz）；
- `H_api`：提交 metadata 的 `action_chunk_size`；
- `H_vla`：内部 VLA plan horizon（可以是 30，不受 API 限制）；
- `N`：端口数；
- `E[S_vla]`、`p99_vla`：VLA 服务时间均值/p99；
- `E[S_servo]`、`p99_servo`：`get_action` 中伺服/缓存路径的均值/p99；
- `τ`：网络 + 图像 + 调度等效延迟；
- `T_max`：接触任务允许的最大反馈周期。

VLA 请求率（有 plan cache 时）：

```text
λ_vla = N · f_c / H_vla
ρ_vla = λ_vla · E[S_vla]
```

`get_action` 请求率（每 `H_api` 步一次）：

```text
λ_api = N · f_c / H_api
ρ_servo = λ_api · E[S_servo]
```

约束：

```text
H_api  ≤ floor((T_max - τ) · f_c)                 # 反馈新鲜度
H_api  ≥ ceil(p99_servo · f_c) + 1                # 伺服不被调用频率压垮
H_vla  ≥ ceil(N · f_c · E[S_vla] / ρ_max)         # VLA 容量
H_vla  ≥ ceil(p99_vla · f_c) + 1                  # plan 不欠载
```

例子（N=3，f_c=30，E[S_vla]=0.18s，p99_vla=0.25s，E[S_servo]=0.01s，p99_servo=0.01s，ρ_max=0.7，T_max=0.3s，τ=0.05s）：

- `H_vla ≥ ceil(3×30×0.18/0.7)=24`，且 `≥ceil(0.25×30)+1=9` → 取 30；
- `H_api ≤ floor((0.3-0.05)×30)=7`，且 `≥ceil(0.01×30)+1=2` → 取 5；
- 若**每次 get_action 都跑 VLA**（无 plan cache）：`λ=18/s`，`ρ=3.24`，不稳定；
- 有 plan cache：`λ_vla=3/s`，`ρ_vla=0.54`；`λ_api=18/s`，`ρ_servo=0.18`。

**结论**：`H_api=5` 只有在“VLA plan cache + 伺服路径”成立时才安全；`H_api=30` 稳定但接触段太旧；`H_vla=30` 是容量/新鲜度的折中，不是 API chunk。**COOL-SERVE 的 HOT-CHUNK 在提交前一次性选定，运行时绝不动态改 `action_chunk_size`。**

### 3.6 热感知执行：把热从接触精度上挪开

| 手段 | 做法 | 何时启用 | 风险 |
|---|---|---|---|
| 休息位姿 | 非接触段回到低扭矩、低前伸的 pose | `x` 高、任务允许 | 可能增加耗时 |
| 微暂停 | 100–300ms 低扭矩保持，等 VLA plan | plan 未就绪、非接触 | 不能用于接触/插入 |
| 双臂负载均衡 | 简单搬运改用低热臂 | 任务不限定手、A/B 通过 | 可能改变策略分布 |
| 接触段降速 | 降低接近/插入速度，减小扭矩峰值 | `x` 高、接触任务 | 可能超时/步骤分下降 |
| 相机自标定 | 用头双目 + 腕部内参检查重投影漂移 | 长班次/温漂疑点 | 计算开销；只做检测不做重训 |

原则：**任何热感知执行都必须先在单任务通道做 A/B，成功率先不回归，再谈热收益。** 热管理不是目的，服务稳定性才是。

## 6. 竞赛策略：先保服务，再谈涨点

| 动作空间 | `control_space` 仅 `"joint"` 或 `"ee"`，二者互斥 |
| 共享动作 | `action.left_gripper [1]`、`action.right_gripper [1]`、`action.pivot [7]` |
| EE 动作 | `action.left_ee_pose_gripper_base [6]`、`action.right_ee_pose_gripper_base [6]`（绝对目标位姿，xyz+rpy，base 系） |
| chunk | `action_chunk_size` ≥1，**握手时固定**；index 0 先执行，其余顺序执行，直到 evaluator 再次调用 `get_action` |
| token | 握手校验一次；每次 `get_action` 的 `meta.token` 都要匹配 |
| 缺失 | **没有 depth、camera_info、force/torque、tactile、temperature、current** |
| 监控 | 评测端逐调用记录延迟、波动、动作统计规律，作为结果可信度的一部分 |

**关键推论**：

- `action_chunk_size` 是控制参数，不是推理参数；chunk 内没有新观测，也没有打断机制。
- 如果每次 `get_action` 都同步跑 VLA，chunk 越小，请求率越高，排队越危险。
- 如果 VLA 走 plan cache、每 `H_api` 步只做一次伺服，则 API 请求率与 VLA 请求率可以解耦。
- 控制频率未在 README 中写死；本报告默认 30Hz，必须在单任务通道实测。

## 2. 问题形式化

### 2.1 评分与统计功效

总分：

```math
S = \frac{1}{32}\sum_{t=1}^{32} p_t,\qquad
p_t = \frac{1}{10}\sum_{j=1}^{10} y_{t,j},\quad y_{t,j}\in\{0,1\}.
```

320 trials 下，若 `p≈0.25`：

```math
\mathrm{SE}(S)\approx \sqrt{\frac{p(1-p)}{320}}\approx 0.0242.
```

即全局标准误约 **2.4pp**。单任务 10 次 trial 的标准误更大（`p=0.25` 时约 13.7pp），只能分辨很大的差异。热 endurance 用 20–30 次连续 episode 看方向，不宣称显著性；正式 A/B 用配对设计和 bootstrap 区间。

人为干扰轴：

```math
\Delta S_{\mathrm{human}} = \frac{2}{10}\,\Delta p_h = 0.2\,\Delta p_h.
```

热管理如果救回的是“后半段 trial 的执行失败”，它影响的是所有任务的 `p_t`，不是单独一个轴；这也是为什么它值得做，但必须先证明热漂移真实存在。

### 2.2 班次级热模型

把每个关节/每条臂看成集总热容：

```math
C_{\mathrm{th}}\frac{dT}{dt} = P(t) - \frac{T-T_{\mathrm{amb}}}{R_{\mathrm{th}}}.
```

令 `x = (T-T_amb)/(T_max-T_amb)`、`u = P/P_max`，并取 `T_max-T_amb = P_max R_th`，得到无量纲形式：

```math
\tau_{\mathrm{th}}\frac{dx}{dt} = u - x,\qquad \tau_{\mathrm{th}}=R_{\mathrm{th}}C_{\mathrm{th}}.
```

离散：

```math
x_{k+1}=a x_k + (1-a)u_k,\qquad a=e^{-\Delta t/\tau_{\mathrm{th}}}.
```

工程上用非对称更新，允许加热/冷却时间常数不同：

```math
x_{k+1}=\mathrm{clip}\left(x_k+\alpha b_k(1-x_k)-\beta x_k,\ 0,\ 1\right),
```

其中 `b_k` 是热负载代理（见 2.3），`α/β` 由 endurance 拟合。**`x` 是相对热债，不是摄氏温度；没有温度遥测时，只能做相对排序和保守阈值。**

### 2.3 TORQUE-SHADOW 热负载代理

对每条臂的 7 个关节，用 G1 URDF 做逆动力学：

```math
\hat{\tau} = M(q)\ddot{q}+C(q,\dot{q})\dot{q}+g(q)+\tau_{\mathrm{friction}}.
```

`q` 来自观测，`\dot q/\ddot q` 由有限差分 + 低通滤波得到。定义：

```math
b_k=\mathrm{clip}\Big(
\sum_j w_j\left(\frac{|\hat\tau_j|}{\tau_{\max,j}}\right)^2
+\sum_j w_v\left(\frac{|\dot q_j|}{\dot q_{\max,j}}\right)^2
+w_s\sum_j \mathbf 1[|\dot q_j|<\epsilon]\frac{|\hat\tau_j|}{\tau_{\max,j}}
+w_r\left(\frac{r_k}{r_{\mathrm{scale}}}\right)^2,\ 0,1\Big).
```

跟踪残差：

```math
r_k=\|a_k\ominus s_{k+1}\|,
```

- `joint` 模式：归一化关节误差；
- `ee` 模式：位置误差（米）+ 旋转误差（弧度，按 `r_scale` 归一化）。

解释：

- `|\hat\tau|^2` 近似铜损/热功率；
- `|\dot q|^2` 捕捉高速运动；
- 静止项 `1[|\dot q|<ε]·|\hat\tau|` 捕捉“悬停/前伸/夹持”的持续负载；
- `r_k` 捕捉接触、卡滞、负载突变——这些是逆动力学没建模的部分。

**HangCup 的启示**：左臂平均速度只有右臂的 43%，但整臂静止帧比例是右臂的 4.3 倍（25.8% vs 6.0%）。如果只看速度，会误判左臂“很轻松”；静止悬停的重力扭矩可能才是热源。TORQUE-SHADOW 必须同时看扭矩和静止占比。

### 2.4 排队论与 chunk 定尺

设：

- `f_c`：evaluator 控制频率；
- `H_api`：提交的 `action_chunk_size`；
- `H_vla`：内部 VLA plan horizon；
- `N`：端口数；
- `E[S_vla]`、`p99_vla`：VLA 服务时间均值/p99；
- `E[S_servo]`、`p99_servo`：`get_action` 中伺服/缓存路径的均值/p99；
- `τ`：网络 + 图像 + 调度等效延迟；
- `ρ_max`：目标最大利用率（如 0.7）；
- `T_max`：接触任务允许的最大反馈周期。

VLA 请求率（有 plan cache）：

```math
\lambda_{\mathrm{vla}}=\frac{N f_c}{H_{\mathrm{vla}}},\qquad
\rho_{\mathrm{vla}}=\lambda_{\mathrm{vla}}E[S_{\mathrm{vla}}].
```

API 请求率：

```math
\lambda_{\mathrm{api}}=\frac{N f_c}{H_{\mathrm{api}}},\qquad
\rho_{\mathrm{servo}}=\lambda_{\mathrm{api}}E[S_{\mathrm{servo}}].
```

反馈周期：

```math
T_{\mathrm{fb}}=\frac{H_{\mathrm{api}}}{f_c}+\tau.
```

约束：

```math
H_{\mathrm{api}}\le \left\lfloor (T_{\max}-\tau)f_c\right\rfloor,
```

```math
H_{\mathrm{api}}\ge \left\lceil p99_{\mathrm{servo}}f_c\right\rceil+1,
```

```math
H_{\mathrm{vla}}\ge \left\lceil \frac{N f_c E[S_{\mathrm{vla}}]}{\rho_{\max}}\right\rceil,
```

```math
H_{\mathrm{vla}}\ge \left\lceil p99_{\mathrm{vla}}f_c\right\rceil+1.
```

**算例**：`N=3`、`f_c=30`、`E[S_vla]=0.18s`、`p99_vla=0.25s`、`E[S_servo]=0.01s`、`p99_servo=0.01s`、`ρ_max=0.7`、`T_max=0.3s`、`τ=0.05s`：

| 方案 | `H_api` | `H_vla` | 是否 plan cache | `λ_api` | `ρ_api` | `λ_vla` | `ρ_vla` | `T_fb` | 结论 |
|---|---:|---:|:---:|---:|---:|---:|---:|---:|---|
| 官方默认 | 30 | 30 | 否 | 3/s | 0.54 | 3/s | 0.54 | 1.05s | 稳定但接触段太旧 |
| 小 chunk 无缓存 | 5 | 5 | 否 | 18/s | 3.24 | 18/s | 3.24 | 0.217s | 不稳定 |
| 双频 + 缓存 | 5 | 30 | 是 | 18/s | 0.18 | 3/s | 0.54 | 0.217s | 可行 |
| 保守双频 | 8 | 30 | 是 | 11.25/s | 0.11 | 3/s | 0.54 | 0.317s | 高 RTT 时可行 |

其中 `ρ_api` 在“无缓存”行用 `E[S_vla]` 计算，在“有缓存”行用 `E[S_servo]` 计算。

**结论**：

- `H_api=5` 不是天然安全；只有“plan cache + 伺服路径”成立时才安全。
- `H_api=30` 不是天然错误；它稳定，但接触段反馈太慢。
- `H_vla=30` 是容量与新鲜度的折中；它不等于 API chunk。
- HOT-CHUNK 在提交前一次性选定；运行时绝不动态改 `action_chunk_size`。

### 2.5 SLO 与 error budget

每个端口/每场评测定义：

| SLO | 指标 | 初始目标 | 触发动作 |
|---|---|---|---|
| 成功 SLO | 32 任务平均成功率 | 不低于基线 -1pp | 回滚热执行/降级 |
| 延迟 SLO | `get_action` p99 | ≤150ms（不含冷启动） | 降分辨率/用缓存 |
| 超时 SLO | 单次 episode 超时率 | ≤1% | CONSERVE/HOLD |
| 热 SLO | `x > x_crit` 时间占比 | ≤5% | CONSERVE/HOLD |
| 恢复 SLO | 故障后下一 episode 可用 | 100% | 保守初值/重启 |

Error budget：

```math
B = 1 - \mathrm{SLO}.
```

它不是“允许失败”，而是**把风险预算花在能涨分的任务上**：

- 高价值接触任务：允许更高伺服计算、更小 `H_api`；
- 低价值长任务：优先 CONSERVE，避免把热债带到后面的任务；
- 预算耗尽：关闭热执行，回退基线，保成功率。

### 2.6 服务状态与 `reset()` 语义

把状态分成两层：

```text
task_state = {plan, plan_idx, goal, phase, edit_score, retry_count}
service_state = {heat_index, exposure, episode_count, mode, calibration_quality}
```

- `reset()` 清 `task_state`，保留 `service_state`。
- 如果官方要求“reset 后完全无记忆”，则 `service_state` 只能从首帧观测/时间戳重建；不能假设进程常驻。
- 端口之间不共享 `service_state`；共享 VLA server 只保存无状态请求。
- 任何跨 episode 记忆都必须在提交材料中说明，避免被判“状态不隔离”。

## 3. 系统设计

### 3.1 进程/端口拓扑

```text
                 ┌────────────────────────────────────────────┐
                 │ Evaluator (N ports 8765..8765+N-1)         │
                 └───────────────┬────────────────────────────┘
                                 │ websocket: obs / action chunk
                                 ▼
                 ┌────────────────────────────────────────────┐
                 │ Per-port PolicyService (CPU)               │
                 │  ├─ STL thermal ledger                     │
                 │  ├─ TORQUE-SHADOW observer                 │
                 │  ├─ SLO governor / error budget            │
                 │  ├─ plan cache + servo (CHUNK-SERVO)       │
                 │  ├─ goal retrieval (DG-KEYFRAME)           │
                 │  └─ action adapter (WLA 54D → API 21D)     │
                 └───────────────┬────────────────────────────┘
                                 │ async, batched, stateless
                                 ▼
                 ┌────────────────────────────────────────────┐
                 │ Shared VLA server (GPU), one checkpoint     │
                 │ UnifoLM-WLA-1.0 / 微调 action head          │
                 └────────────────────────────────────────────┘
```

- 每端口一个 `PolicyService` 实例，独立 `reset()`、独立热账本、独立 plan cache。
- 伺服/检索/热观测是 CPU 线程，不阻塞 websocket；VLA 请求异步、可批处理。
- 共享 VLA server 用 session ID 区分端口；模型权重只有一份，不违反单模型。
- 观测适配器把挑战赛的 xyz+rpy 转成 WLA 需要的 rot6d；动作适配器把 WLA 的相对 EE 54D compose 成挑战赛的绝对 EE 21D。

### 3.2 STL：跨 episode 热账本

```python
class ShiftThermalLedger:
    def __init__(self, port_id, robot_id):
        self.port_id = port_id
        self.robot_id = robot_id
        self.x = 0.0
        self.exposure = 0.0
        self.episode_count = 0
        self.last_t = None
        self.mode = "CONSERVE"   # 新端口/未知机器人从保守模式起步

    def on_reset(self, first_obs):
        self.episode_count += 1
        if self.last_t is None:
            self.last_t = first_obs.timestamp
        # 只清任务态；热账本保留
        # 若进程重启/端口变化，用首帧观测重建（见 3.3）

    def update(self, obs, action, next_obs):
        b = estimate_heat_load(obs, action, next_obs)
        dt = max(0.0, obs.timestamp - self.last_t)
        self.last_t = obs.timestamp

        # 非对称一阶模型；x 是相对热债，不是温度
        self.x = clip(
            self.x + ALPHA * b * (1.0 - self.x) * dt
                     - BETA * self.x * dt,
            0.0, 1.0,
        )
        self.exposure += max(0.0, self.x - X_REF) * dt
        self.mode = governor_mode(self.x, self.exposure, self.episode_count)
```

关键点：

- `x` 不是温度；`ALPHA/BETA` 只用于相对排序。
- 时间戳 `dt` 必须来自评测端观测或本地单调时钟；不能用 episode 内帧数硬编码频率。
- 如果 `obs.timestamp` 不可用，用本地 `time.monotonic()`，并在日志中标注。
- 进程重启后，`x` 从保守初值（如 0.5）起步，不假设冷启动。

### 3.3 TORQUE-SHADOW：实现细节

```python
def estimate_heat_load(obs, action, next_obs):
    q = obs.arm_joint_pos            # 14
    dq = obs.arm_joint_vel           # 14（若无，差分）
    ddq = finite_difference(dq)      # 14，低通
    tau = rnea(g1_urdf, q, dq, ddq)  # 14，含重力/科氏/惯性

    b = 0.0
    for j in range(14):
        b += W_TAU[j] * (abs(tau[j]) / TAU_MAX[j]) ** 2
        b += W_VEL[j] * (abs(dq[j]) / DQ_MAX[j]) ** 2
        if abs(dq[j]) < EPS_STATIC:
            b += W_STATIC[j] * (abs(tau[j]) / TAU_MAX[j])
    b += W_RES * (tracking_residual(action, next_obs) / R_SCALE) ** 2
    return clip(b, 0.0, 1.0)
```

- `rnea` 用 Pinocchio/`unitree_ros` 的 G1 URDF；摩擦项先用库仑+粘滞近似，不追求精确。
- `TAU_MAX`/`DQ_MAX` 用电机铭牌或保守估计；权重按“肩 > 肘 > 腕”先验，但必须用 endurance 校准。
- `tracking_residual` 在 `joint` 模式用归一化关节误差；在 `ee` 模式用位置+旋转误差。
- **不要用 `x` 直接触发急停**；只用它切换 CONSERVE/HOLD，并记录日志。

### 3.4 SERVICE-GOVERNOR 状态机

```text
INIT ──first obs──▶ NORMAL
  ▲                   │
  │                   ├─ x > x_cons ──▶ CONSERVE
  │                   │                    │
  │                   │                    ├─ x < x_relax ──▶ NORMAL
  │                   │                    └─ x > x_hold ──▶ HOLD
  │                   │                                         │
  │                   │                                         └─ x < x_safe ──▶ CONSERVE
  │                   │
  │                   └─ residual spike / timeout risk ──▶ RECOVER
  │                                                              │
  └──────────────────────── success/reset ◀──────────────────────┘
```

- `NORMAL`：正常 CHUNK-SERVO；热账本只记录，不干预。
- `CONSERVE`：接触段降速 10–20%、优先低热臂、微暂停；不改变 VLA 语义。
- `HOLD`：仅非接触段；低扭矩休息位姿 0.2–1s；接触中禁止急停。
- `RECOVER`：残差突变/相机漂移/超时前兆；回退缓存 plan 或安全 hold；下一 episode 从 CONSERVE 起步。

阈值先验（需 G2 校准）：

```text
x_cons  = 0.55
x_relax = 0.40
x_hold  = 0.80
x_safe  = 0.60
```

### 3.5 HOT-CHUNK：提交前定尺

```python
def choose_chunks(N, f_c, p99_vla, p99_servo, e_vla, rho_max, T_max, tau):
    # 容量下界
    h_vla_cap = ceil(N * f_c * e_vla / rho_max)
    # plan 不欠载
    h_vla_lat = ceil(p99_vla * f_c) + 1
    h_vla = max(30, h_vla_cap, h_vla_lat)

    # 反馈新鲜度上界
    h_api_max = floor((T_max - tau) * f_c)
    # 伺服调用下界
    h_api_min = ceil(p99_servo * f_c) + 1
    if h_api_min > h_api_max:
        return None  # 可行域为空；需要降分辨率/加缓存/换模型
    h_api = clamp(5, h_api_min, h_api_max)
    return h_api, h_vla
```

- `H_api` 是 metadata 的 `action_chunk_size`；提交前固定。
- `H_vla` 是内部 plan horizon；可以等于 30，也可以 45；不受 API 限制。
- 如果可行域为空：优先加 plan cache/降图像分辨率/异步；不要运行时改 chunk。
- 单任务通道扫 `H_api ∈ {3,5,8}`；`H_vla ∈ {30,45}` 只在离线/仿真扫，避免影响正式评测。

### 3.6 热感知执行

| 手段 | 实现 | 启用条件 | 预期收益 | 风险 |
|---|---|---|---|---|
| 休息位姿 | 预定义低扭矩、低前伸 pose；非接触段插值过去 | `x>0.55`，任务允许 | 降低肩/肘静态扭矩 | 增加耗时 |
| 微暂停 | 100–300ms 保持，等 VLA plan | plan 未就绪、非接触 | 减少“举着等”的热债 | 接触中禁用 |
| 双臂均衡 | 简单搬运改用低热臂 | 任务不限定手；A/B 通过 | 分担负载 | 改变策略分布 |
| 接触降速 | 接近/插入速度 ×0.8–0.9 | `x>0.55`，接触任务 | 降低扭矩峰值 | 超时/步骤分 |
| 相机自检 | 每 N episode 检查头双目/腕部重投影 | 长班次 | 发现热漂移 | 误报；只检测不重训 |

**安全约束**：

- 接触中禁止切换到休息位姿/急停；只能在自由空间或任务允许的停顿点。
- 降速/微暂停必须保证 180s 内完成；否则回退 NORMAL。
- 双臂均衡不能改变任务成功定义（例如必须用右手拧瓶盖的任务）。
- 所有热执行默认关闭，逐项 A/B 打开；成功率先不回归。

### 3.7 服务蓝图

| 阶段 | 前台（evaluator 看到） | 后台 | 支撑 | 失败点 | 恢复 |
|---|---|---|---|---|---|
| Handshake | 端口/ token / metadata | 校验 `action_chunk_size`、`control_space` | 配置中心 | token 不匹配、端口冲突 | 拒绝启动/换端口 |
| Reset | 新 episode | 清任务态，保留 STL；重置 plan/相位 | 日志/时钟 | 热账本误清、跨端口串状态 | 从观测重建；端口隔离 |
| Observe | 四路 RGB + 本体 | 图像缩放、时间堆叠、标定检查 | 相机内参 | 掉帧、模糊、热漂移 | 降分辨率/回退 PBVS |
| Plan | 不直接可见 | VLA 异步请求、plan cache | GPU 队列 | 超时、batch 抖动 | 用旧 plan；CONSERVE |
| Execute | action chunk | 伺服、动作适配、限幅 | 控制频率 | NaN、形状错、pivot 语义错 | 安全 hold/上一组合法 chunk |
| Recover | 继续或失败 | 编辑检测、重定位、重规划 | 单任务通道 | 目标丢失、人挡视野 | 停→重定位→重规划 |
| Finish | 成功/超时 | 写热账本、SLO 日志 | 存储 | 账本丢失 | 保守初值 |

### 3.8 与 CHUNK-SERVO / DG-KEYFRAME / GEO-RESIDUAL 的接口

- **CHUNK-SERVO**：提供 `H_api=5` 的执行块、`H_vla=30` 的 plan cache、5 步伺服；COOL-SERVE 只决定 `H_api/H_vla` 的定尺和热模式。
- **DG-KEYFRAME**：提供相对目标检索；热模式不改变目标，只改变执行速度/臂选择。
- **GEO-RESIDUAL**：提供 `d_t`、`n_t`、`r_static`、`r_grasp`、`edit_score`；TORQUE-SHADOW 复用这些信号做残差项，避免重复计算。
- **FACT-VLA**：提供相位；热执行只在自由空间/非接触相位启用。

## 4. 关键伪代码

### 4.1 `reset()`

```python
def reset(self, first_obs=None):
    self.plan = None
    self.plan_idx = 0
    self.goal = None
    self.phase = "INIT"
    self.edit_score = 0.0
    self.retry_count = 0
    self.ledger.on_reset(first_obs)
    self.logger.info("reset", port=self.port_id,
                     heat=self.ledger.x, mode=self.ledger.mode)
```

### 4.2 `get_action()`

```python
def get_action(self, obs):
    self.ledger.update(self.last_obs, self.last_action, obs)
    self.last_obs = obs

    mode = self.ledger.mode
    self._maybe_request_plan(obs, mode)

    if self.plan is None:
        # 冷启动/plan 丢失：安全 hold，同时同步请求一次
        self.plan = self.vla.predict(obs)
        self.plan_idx = 0

    h_api = self.h_api
    a_ff = self.plan[self.plan_idx:self.plan_idx + h_api]
    a_cmd = self.servo.apply(a_ff, obs, self.goal, mode)
    a_cmd = self.adapter.to_api(a_cmd, obs, self.token)
    a_cmd = self.safety.limit(a_cmd, self.last_action, mode)

    self.plan_idx += h_api
    if self.plan_idx >= len(self.plan):
        self.plan = None
    self.last_action = a_cmd
    self.logger.log(obs, a_cmd, self.ledger, mode)
    return a_cmd
```

### 4.3 `_maybe_request_plan()`

```python
def _maybe_request_plan(self, obs, mode):
    if self._future is not None and not self._future.done():
        return
    if self._future is not None:
        self.plan = self._future.result()
        self.plan_idx = 0
        self._future = None
    if self.plan is None or self.plan_age >= self.plan_ttl:
        snapshot = copy_obs(obs)
        self._future = self.executor.submit(self.vla.predict, snapshot)
```

规则：

- VLA 永远不阻塞 `get_action`（除冷启动）；plan 过期就用旧 plan + 伺服。
- `CONSERVE/HOLD` 不改变 VLA 请求；只改变执行速度/休息位姿。
- `RECOVER` 可以丢弃旧 plan，请求新 plan；但必须保证返回合法动作。

### 4.4 安全 hold

```python
def safe_hold(self, obs, last_action):
    # 保持当前 EE/关节附近，限速回退；不进入接触
    target = self.rest_pose if self.in_free_space(obs) else last_action
    return self.adapter.to_api(target, obs, self.token)
```

- `rest_pose` 必须是低扭矩、低前伸、无碰撞的姿态。
- 接触中 `last_action` 保持，不切换到 rest pose。
- 任何异常返回上一组合法 chunk，绝不返回 NaN/错误形状。

### 5.1 数据与指标

从 Hugging Face 下载 HangCup 的 1,043 episodes（194,564 frames），在 `/tmp/opencode/hf` 做离线审计：

| 跟踪残差 p95 | 0.057 rad | 0.095 rad |
| 跟踪残差 p99 | 0.075 rad | 0.148 rad |

### 5.2 session 内热漂移检查

6 个 session 内，按 episode 顺序与跟踪残差中位数的 Spearman ρ：

| session | ρ | 方向 |
|---|---:|---|
| 1 | -0.55 | 后段残差下降 |
| 2 | -0.48 | 后段残差下降 |
| 3 | +0.06 | 基本无趋势 |
| 4 | +0.14 | 弱上升 |
| 5 | +0.57 | 后段残差上升 |
| 6 | +0.75 | 后段残差上升 |

### 5.3 解释

- **没有一致热漂移证据**：6 个 session 方向不一致，不能拿 HangCup 证明“越跑越热”。
- **左臂更“静”但可能更累**：左臂速度低、静止比例高；如果它长期悬停/支撑，静态重力扭矩可能比右臂的高速运动更热。这正是 TORQUE-SHADOW 要区分的。
- **短任务不够**：HangCup 平均 6.2s，热时间常数是分钟级；要验证热假设，必须用 ToolboxStorage（37.6s）、Store Racket（34.1s）等长任务做 20–30 次连续 endurance。
- **pilot 的价值**：建立了动作/状态/残差分析管线，证明数据可读、指标可算；不是热结论。

### 6.4 消融

1. STL on/off（跨 episode 热账本）。
2. Governor on/off（SLO 降级）。
3. HOT-CHUNK：`H_api=5` vs 8 vs 30；`H_vla=30` vs 45。
4. 热执行：休息位姿/微暂停/双臂/降速逐项开关。
5. TORQUE-SHADOW：只用速度 vs 速度+扭矩+残差。
6. 相机自检 on/off（仅长班次）。

- 正式评测：32×10；报告总平均成功率、步骤分、p99、超时、恢复次数。

- 热 endurance：20–30 次连续 episode；报告趋势和置信带，不宣称显著性。

## 9. 风险与合规

### 9.1 单模型合规的三种模式

| 模式 | 做法 | 风险 | 建议 |
|---|---|---|---|
| C1 离线标注 | 热参数/阈值离线拟合；线上只有 VLA 输出动作 | 最低 | 保守首选 |
| C2 确定性控制器 | 热账本/观测器/治理器是规则/控制律，无学习权重；VLA 是唯一学习模型 | 低；需说明 | 主推 |
| C3 同 checkpoint 特征 | 目标描述子用 VLA 同一 checkpoint 的 encoder，不加载第二个模型 | 低–中；需说明 | 需要强描述子时用 |

禁止：加载第二个学习策略/残差网络/独立视觉编码器做在线决策；训练热预测网络；用外部温度模型替代 VLA 决策。

### 9.2 风险表

| 风险 | 影响 | 缓解 |
|---|---|---|
| 热假设不成立 | STL/热执行白做 | G2 先验证；失败则只保留服务治理/HOT-CHUNK |
| 评测端每 episode 重启进程 | 热账本丢失 | 首帧观测重建；保守初值；不依赖绝对温度 |
| 热代理不准 | 错误降级 | 只做相对排序；阈值宽松；成功率先不回归 |
| 热执行伤成功率 | 直接丢分 | 单任务 A/B；接触中禁止急停；默认关闭逐项开 |
| HOT-CHUNK 可行域为空 | 排队或接触失败 | 加 plan cache、降分辨率、异步；回退 H_api=8/10 |
| 控制频率/N 未知 | 定尺错误 | 单任务通道实测；按 N 参数化；提交前干跑 |
| 单模型解释 | 被判第二个模型 | 热逻辑无学习权重；C1/C2；提交材料写清 |
| 端口串状态 | 评测污染 | 每端口独立 STL/plan；共享 server 无状态 |
| 安全 | 休息位姿/降速导致碰撞/超时 | 限速/限幅；接触段不切换；最大重试；超时前回退 |
| 评测噪声 | 把 1–2pp 当结论 | 配对 A/B、bootstrap、320 trials SE≈2.4pp |
| 数据泄漏 | 离线指标虚高 | 按 session/物体/背景分组；相邻帧不跨 split |
| 榜单不可复核 | 误判当前 SOTA | 只把历史分数当先验；不据其排任务难度 |
