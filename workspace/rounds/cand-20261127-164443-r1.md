## 1. 直觉与动机（两个灵感的碰撞）

**灵感 1（云边协同 → 赛制本身就是云边系统，但真正的瓶颈是「提交带宽」）**
直觉：大多数人把云边协同理解成「训练在云、推理在边」的算力分工。这场比赛的赛制（F22）恰好就是这样：选手自托管推理服务（边），云端/离线做训练与数据。但真正的云边接口不是网络带宽，而是**提交**：云到边只能通过一次「打包—提交—评测」的异步过程，反馈只有 32 个任务的成功率/步骤分（F21）和未来的视频（F25），延迟是预约排期（F26），噪声是每任务 10 次采样（F27）。所以云边协同的设计问题是：**哪些东西允许跨过这条低带宽、高延迟、带噪的边界？** 直觉答案：只允许「冻结的权重 + 可审计的配置 + 只读索引」跨过去；任何会持续改变行为的在线更新都必须留在云侧。核心反直觉点：**云边协同的价值不是省算力，而是把「学习」关进云端、把「不学习」留给边缘，从而把诚信红线变成一条可工程化的边界。**

**灵感 2（在线学习 → 比赛里有两种在线学习，一种违规，一种被严重低估）**
直觉：在线学习在这场比赛里是「带电的红线」——评测期对评测分布做适应，既违反手册的稳定在线推理/公平约束，也会触发 F24 的动作统计异常判定。但另一种合法的在线学习被忽略了：**两次提交之间的学习**。榜单是实时的（F20），单任务通道可重复预约（F26），详情页将给视频（F25）——这是一个延迟奖励、部分可观测、带宽受限的在线学习回路。反直觉点：**评测期最好的「在线学习」是「不学习」；真正的学习发生在两次提交之间，而且它的主要形式不是拟合，而是「在预注册假设库里做在线选择」。**

**碰撞与统一**：云边协同回答「学习放在哪」（云端提交间隔），在线学习回答「怎么用反馈」（延迟奖励下的选择与调度）。两者合并成一条设计律：**把学习的时间尺度与位置显式化，边缘只做 episode-local、reset 可清、可审计的适应；云端用提交反馈做在线模型选择与离线重训。** 本轮结论：**中期胜负手仍是数据引擎（第 2 轮），但数据引擎的「油门」是云边提交回路；谁先把这条回路工程化，谁就能把 29.7% 的天花板往上顶。**

## 2. 严谨定义（先直觉，后定义）

### 2.1 云与边：按时间尺度定义，不按物理位置
- **云（cloud）**：不受单 chunk 时延约束、可在提交间隔内做批处理与权重更新的计算。物理上可以是同一台机器。
- **边（edge）**：评测期承载 `PolicyService` 的推理端；受 T_a 决策周期、N 端口并发、180s/任务、F24 可信度约束。
- **判据**：一个操作属于云还是边，取决于它**是否发生在评测期、是否改变持久化参数**，而不取决于它在哪台机器上跑。→ 这样定义才能把「同机多进程」也纳入合规分析。

### 2.2 学习 vs 适应：按「是否改变未来 episode 的行为」定义
设策略在 episode e 结束时的持久状态为 S_e（权重、索引、阈值、缓存）。若 S_{e+1} ≠ S_e 且该差异会影响 e+1 的行为，称为**学习（learning）**；若只在 e 内变化、episode 结束即被 `reset()` 清除，称为**适应（adaptation）**。

| 时间尺度 | 位置 | 改持久参数? | 合规判断 | 例子 |
|---|---|---|---|---|
| τ0 训练期 | 云 | 是 | 允许 | 全参/LoRA 训练 |
| τ1 提交间隔 | 云 | 是 | 允许，但受「测试集泄漏」约束（§2.3） | 用榜单/视频选择假设后重训 |
| τ2 episode 间 | 边 | 否（reset 清空） | 允许 | 每集重新检索 |
| τ3 episode 内、chunk 间 | 边 | 否（episode-local） | 允许，但受「适应预算」约束（§2.4） | guard 触发、检索先验缓存 |
| τ4 评测期跨 episode 持久化 / 在线更新权重 | 边 | 是 | **禁止**（诚信红线；待书面确认） | 用评测流做 SGD / BN 统计更新 |

**结论**：本轮把「在线学习」严格定义为 τ4（禁止），把 τ3 称为「无学习在线适应」（允许但有预算），把 τ1 称为「跨提交在线学习」（合法主战场）。这一定义消除了「在线学习」一词的歧义，也直接给出合规审计的对象。

### 2.3 跨提交在线学习 = 在线选择 + 离线重训（不是在线拟合）
把可提交的改动限制在一个**预注册假设库** H = {h_1…h_K}（每个 h 是一次可复现的训练/配置变更：增广轴、孪生语料权重、guard 参数、检索阈值…）。每次提交只选择 h ∈ H，训练只在官方数据/自采数据上完成；榜单反馈只用于**选择**，不用于**拟合**。这样：
- 反馈容量 = O(log K) 比特/次，而不是整条评测流的梯度；
- 多重比较风险可计算（K 个假设、m 次提交的 family-wise error）；
- 可审计：每次提交都能回答「相对上一次只改了哪个预注册假设」。

核心反直觉点：**在测试集上做模型选择是不可避免的；把它限制成「有限假设库的选择」而不是「高容量拟合」，是把测试集过拟合从不可控变成可预算。**

### 2.4 适应预算（adaptation budget）
边缘每个 chunk 的适应动作 a_t 相对基线策略 π0 的偏移，需满足：
- 单 chunk 偏移 ≤ ε_chunk（动作 L2 或分布 KL）；
- 全 episode 累计偏移 ≤ ε_episode；
- 偏移方向必须可由当前观测解释（检索命中/guard 触发），且写入审计日志；
- 不得跨 episode 持久化。

直觉：F24 会看动作统计规律性；「适应」如果让动作看起来像异常，收益会被可信度判定吃掉。适应预算是把「性能增益」与「可信度风险」放在同一个约束里优化。

## 3. 对第 2 轮痛点的增量修订

- **P2（泛化缺口）**：F20 给出硬天花板 29.7%，第 1 与第 8 仅差 9.2 个百分点 → 泛化仍是主因；但「步骤分比成功率高 7–10 分」（F20）说明**大量 episode 是「做了一半」**，恢复/收尾（I5）可能是比继续扩增广更快见效的杠杆。

- **P7（先手）**：榜单仅 8 个模型（F20）→ 先手窗口比第 2 轮估计更真实。
- **新增 P9（反馈稀疏/延迟/有偏）**：只有聚合分数 + 未来视频；单任务通道采样分布与正赛不同（F26）→ 在线学习是延迟奖励、部分可观测、有偏反馈问题。

## 0. 创新点清单（每点：动机 / 与现有方案差异 / 技术可行性 / 所需资源 / 落地步骤 / 风险）

### I10 v1 冻结学习边界 FLB + 合规审计（新） ★★★★★

- **动机**：赛制是选手自托管推理 + 组委会远程调用（F22），评测期明确记录动作统计规律性与时延波动（F24）。第 1–2 轮的合规清单把「不在评测时段对评测分布做在线学习/适应」列为诚信红线，但一直停留在口号；没有可执行契约，就无法向组委会证明、也无法在工程上防止误越界。
- **与现有方案差异**：不是算法模块，而是一层**部署契约 + 运行时审计**。多数队伍靠「我们没写在线更新」自证；本点把「零持久化更新」变成 manifest、只读挂载、状态隔离、哈希审计四件套，可静态检查、可运行时验证、可红队测试。
- **组成**：
  1. **bundle**：`weights.safetensors` + `retrieval.faiss` + `calibration.yaml` + `guard.yaml` + `manifest.json` + `SHA256SUMS`；
  2. **manifest**：版本、git commit、训练数据 manifest 哈希、训练阶段、`eval_policy="frozen_weights"`、`adaptation_scope="episode_local"`、`persistent_writes_at_eval=false`、允许的 episode 状态键、审计 schema 版本；
  3. **edge loader**：bundle 只读挂载；`torch.inference_mode()`；不构造 optimizer、不调用 `.train()`、不更新 BN 统计；固定随机种子；每端口独立 `EpisodeState`，`reset()` 清空全部 episode-local 状态；
  4. **audit**：每 chunk 记录 `{episode_id, chunk_idx, retrieval_hit, guard_trigger, action_norm, chunk_latency_ms, prior_strength}`，哈希链追加；评测结束后校验 bundle 文件哈希未变、无写回；
  5. **合规证明**：静态扫描（无 `optimizer.step`/`save`/评测期网络出口）+ 运行时监控（文件 mtime/哈希、状态字典快照）+ 红队测试（故意注入一个「跨 episode 计数器」看审计能否抓到）。
- **技术可行性**：高。纯工程，1 人周；不需要额外 GPU。
- **所需资源**：1 人周；与 I6 共用部署机。
- **落地步骤**：①定 manifest schema；②写 edge loader；③接审计日志；④用 `run_client.py` 做端到端合规回归；⑤红队测试；⑥把「审计通过」设为每次提交的门禁。
- **风险**：合规条款未书面确认（缓解：把「允许的 episode-local 适应」写成确认项提交组委会）；云边同机导致物理边界模糊（缓解：以「是否改持久参数」而非「是否跨机器」判定）；审计日志本身被误读为异常（低风险，日志不改变动作）。

### I11 v1 跨提交在线数据飞轮 + 提交调度（新） ★★★★★

- **动机**：榜单已实时（F20），单任务通道可重复预约（F26），详情页将给逐任务视频（F25）；但反馈是**延迟、带噪、有偏、低带宽**的。第 2 轮的 I8 只做「离线代理→真机增益」的校准，没有把「提交」本身当成学习动作。
- **与现有方案差异**：多数队伍把提交当「交作业」；本点把提交当**在线决策**：在预注册假设库 H 里选择、用贝叶斯后验更新每任务成功率、用多重比较校正控制测试集过拟合、用提交调度处理「更早提交」的字典序平局（F21）。
- **组成**：
  1. **反馈采集**：榜单 32 维 `(p_i, s_i)`；详情页视频（阶段/物体诊断）；单任务通道结果（相对信号，不作无偏估计）；本地 `run_client` 的健康度指标。
  2. **失败诊断**：视频 → 阶段分类器（接近/抓取/搬运/放置/释放）+ 物体/位姿描述；**只用于诊断和假设匹配，不生成训练标签**（避免测试集泄漏）。
  3. **预注册假设库 H**：有限、可复现，每个 `h` = 一次训练/配置变更（增广轴、孪生权重、guard 参数、检索阈值、蒸馏温度…），附「预期影响任务、成本、先验成功率」。
  4. **在线选择**：每任务 `p_i ~ Beta(α_i, β_i)`、`s_i ~ Normal(μ_i, σ_i²)`；采集函数 = 期望字典序排名增益 / 成本；每轮最多选 `K_budget` 个假设；用 Bonferroni 或 Bayesian FDR 控制 family-wise error。
  5. **提交调度**：字典序目标 `(S, T, -submit_time)`；若「更早提交」指首次提交，则先交一个安全基线锁定时间戳；若指最近一次，则等最优；规则未知前采用保守策略并书面确认。
  6. **云端重训**：只在官方数据/自采数据上训练；产出冻结 bundle；过 L0/L1 门禁；单任务通道 canary；再提交。
- **技术可行性**：中-高。反馈采集与假设库是工程；调度器是统计；失败诊断可先用现成 VLM/视频模型。
- **所需资源**：数据工程 1 人 + 训练 1 人；训练 1×24GB 起步；视频诊断 1×GPU 日。
- **落地步骤**：①反馈 schema；②假设库 v0（先 6–8 个假设）；③调度器 v0（先规则后贝叶斯）；④跑通 1 个完整回路（诊断→选假设→重训→canary→提交）；⑤复盘多重比较与排名变化。
- **风险**：测试集泄漏/多重比较（缓解：预注册 + 校正 + 限制假设数）；反馈有偏（单任务通道与正赛分布不同）；视频尚为占位（缓解：先用本地失败集与单任务通道）；提交规则未知（列为待核实，不把猜测写进硬逻辑）。

### I9 v2 边缘检索类比迁移 + 适应预算 ★★★★

- **动机**：未见物品轴（同类不同外观）在 32 任务 × 2/10 次中全面出现；纯参数化泛化对新外观方差大。第 2 轮 I9 只做检索，没有回答「检索先验能改多少、会不会被可信度判定吃掉」。
- **本轮深化**：`reset()` 期一次检索（F23：每 episode 恰好一次）；嵌入库由云端构建、随 bundle 只读下发；检索结果作为**软先验**，受 §2.4 适应预算约束：单 chunk 偏移 ≤ ε_chunk、全 episode ≤ ε_episode，超预算回退 π0；置信门控（距离阈值）不命中则无先验。检索与审计日志联动，可解释每一次先验注入。
- **与现有方案差异**：纯通才策略靠训练分布平均化覆盖新物体；本点是「检索后类比 + 有预算的软注入」，零权重更新，PR2/PR6 合规。
- **技术可行性**：中-高。索引离线构建；reset 期检索 <1s；episode 内零额外每步开销（结果缓存）。
- **所需资源**：嵌入 1×GPU 日 + FAISS；1 人周工程。
- **落地步骤**：①物体库（首帧开放词汇检测裁剪）；②嵌入 + 索引；③可迁移参数化（gripper 开度、接近高度/朝向、技能模式）；④reset 检索 + 预算内软注入；⑤L0 未见轴消融 + 单任务 canary。
- **风险**：误检索伤原本会的任务（距离阈值 + 软偏置 + 预算回退）；VLM 嵌入对「同类不同外观」不敏感（DINOv2 patch 池化 + 几何描述词）；预算过紧无增益/过松触发可信度异常（L0 扫 ε）。

### I6 v2 云边部署 + 可信度守护 + 教师蒸馏 ★★★★

- **动机**：F22 自托管、F24 可信度、F23 N 端口与 T_a 固定。部署目标不是单纯低延迟，而是「低延迟 × 低方差 × 动作统计可信」；同时 PR2 要求单模型。
- **本轮深化**：
  1. **云边拓扑**：2×A100 80G 共享 backend + N 个轻量端口；每端口独立 `EpisodeState`；并发调度；p99 目标仍 <40ms，但决策周期按 `T_a / 15Hz` 计（T_a=8 → ≈533ms），不是单步 66ms。
  2. **可信度守护**：监控 action norm、jerk、chunk 边界跳变、每步时延方差；超阈值时回退 π0 或做平滑；指标随审计日志记录。
  3. **云端教师→边缘单模型蒸馏**：云端用多 seed/多增广教师集成（或 WMA-0 合成数据）训练，蒸馏到单个边缘学生；教师只在云端，边缘只跑学生，满足 PR2 与延迟。
- **与现有方案差异**：多数队伍直接部署大模型或多模型；本点用「云端重、边缘轻」的分工，把算力和合规都放到正确的一侧。
- **技术可行性**：高。官方单卡微调 + LoRA 已具备（F11）；蒸馏是标准流程。
- **所需资源**：云端 1×24GB 起步、8×A100 上限；边缘 2×A100 80G。
- **落地步骤**：①共享 backend + 端口隔离；②可信度监控；③教师集成训练；④蒸馏学生；⑤canary 对比；⑥压测 p99 与动作统计。
- **风险**：蒸馏丢稀有技能（缓解：按任务族分层蒸馏 + 保留 I5 恢复示教）；守护过保守（用 L0 扫阈值）；T_a 固定导致自适应 chunk 不可表达（改为前缀选择）。

### I8 v2.1 云边校准总线 ★★★★

- **动机**：第 2 轮 I8 的「离线代理→真机增益」注册表只回答「离线指标可不可信」；本轮加入「提交预测→榜单实际排名」的第二条校准轴，直接服务 I11 的提交调度。

```python
class FrozenPolicyService:
    def __init__(self, bundle_dir):
        assert bundle_hashes_ok(bundle_dir)
        self.weights = load_readonly(bundle_dir / "weights.safetensors")
        self.index   = load_readonly(bundle_dir / "retrieval.faiss")
        self.calib   = load_yaml(bundle_dir / "calibration.yaml")
        self.guard   = load_yaml(bundle_dir / "guard.yaml")
        self.state   = {}          # port_id -> EpisodeState（每端口隔离）
        self.audit   = HashChainLog(bundle_dir / "audit.log")

    @torch.inference_mode()
    def get_action(self, obs, port_id):
        st = self.state[port_id]
        chunk, meta = self.policy(obs, st, self.index, self.calib)
        chunk = self.guard.clamp(chunk, meta, self.audit)
        self.audit.append({**meta, "port_id": port_id, "chunk_idx": st.chunk_idx})
        st.chunk_idx += 1
        return chunk

    def reset(self, port_id):
        self.state[port_id] = EpisodeState()   # 唯一允许的 episode 间写入
```

**审计不变量**：评测期间 `weights`/`index`/`calib`/`guard` 的文件哈希不变；`EpisodeState` 只在同端口内读写，`reset()` 后所有 episode-local 字段归零；无 optimizer、无 `.train()`、无评测期网络出口。

### 1.3 提交调度：字典序 + 多重比较校正

```python
def should_submit(posterior, baseline, rule, time_left, n_tests, alpha=0.05):
    # 字典序：先成功率，再步骤分，再提交时间
    ucb_success = posterior.ucb_success(delta=alpha / max(1, n_tests))
    gain = ucb_success - baseline.success
    if rule == "earlier_first_submission" and not baseline.submitted:
        return True                     # 先锁时间戳（规则待确认）
    if time_left < RESERVE:
        return True
    return gain > TAU_SUCCESS
```

### 1.4 适应预算守护

```python
def apply_adaptation(a, a0, budget, meta, audit):
    d = l2(a, a0)
    if d > budget.eps_chunk:
        a = clamp_toward(a, a0, budget.eps_chunk)      # 单 chunk 上限
    budget.spent += l2(a, a0)
    if budget.spent > budget.eps_episode:
        a = a0                                         # 超总预算回退基线
        meta["fallback"] = True
    audit.append({"adapt_d": float(l2(a, a0)), **meta})
    return a
```

- [ ] **动作可信度（F24）**：适应预算约束；时延平滑；动作良构、无异常离群；每次提交前跑动作健康度回归。
- [ ] **端口与状态隔离（F23）**：N 个连续端口；每端口独立 `EpisodeState`；`reset()` 清空；并发不互相阻塞。
- [ ] **数据许可**：官方数据集（32 任务 + 110 语料 + DiverseManip，apache-2.0）许可内使用，共训注明来源。
- [ ] **混合推理边界（I3/I9）**：模块化推理路径的「单模型」边界书面确认；确认前不上计分通道，I3' 预案备好。
