# 第 13 轮（新灵感循环第 1 轮）· TWIN-PHM：把 MuJoCo 从「训练场」改成「在线医生」，用双足平衡健康指标在失败前维护

> 检索/复核日期：**2026-11-02（UTC）**。赛事身份：宇树 **UniBot 世界挑战赛**（unibot.unitree.com），G1 + Dex1，32 项桌面任务，通才单模型赛道，选手自部署 + 官方远程真机 API。本轮灵感词是「MuJoCo」「双足机器人」「预测性维护」。本轮不推倒第 12 轮 CHUNK-SERVO，而是在它外面加一层**物理健康监测 + 故障预测 + 维护动作**：**VLA 仍然是唯一学习模型；MuJoCo 不是训练场，而是运行时的医生；双足不是用来走路，而是用来读平衡健康；预测性维护不是修机器，而是在失败发生前改写动作。**

## 0. 先给结论：不要再加一个模型，要给现有模型加一个「健康层」

如果只看「32 任务、单模型、远程 API、榜首不到 30%」这几个事实，最自然的反应是再训一个更大的 VLA，或者再堆一个世界模型。但前 12 轮已经把「更大模型」这条路走到了官方 WLA 的边界：6B 基座、2500 小时真机、30 步 action horizon、单卡 24GB 可微调。继续从零训 6B/14B，边际收益很低。

我本轮真正想押注的是另一件事：

> **在 VLA 和评测器之间，插一个每端口独立、CPU 轻量、无学习权重的「物理健康层」。它用官方 G1 的 MuJoCo 模型做短时前向预测，估计当前动作计划的剩余寿命（RUL）和失败先兆；在失败发生前，用确定性的维护动作（投影到可行域、降速/缩 chunk、配重臂、回退重抓、重规划）把 episode 拉回来。**

一句话：**把「预测下一个动作」变成「预测这个动作还有多久会失败，并在失败前维护」。**

本轮最便宜、也最容易被忽略的一个发现是：演示数据里 `action.pivot` 几乎恒定为 `[0, 0, 0, 0, 0.15, 0, 0.74]`，而官方参考实现输出全零 pivot。**如果评测端不覆盖 pivot，那么「输出演示里的 pivot 先验」可能是一个几乎零成本的基线修复**；如果评测端覆盖，它也能帮我们读双足的平衡状态。这个发现把「双足机器人」这个灵感词从「走路/移动底盘」拉回到了「平衡与姿态通道」，也直接剪掉了「绕桌移动」这个高风险方向。

因此，前几轮引用的「MolmoAct2 29.7%、WALL-OSS-0.5 28.5%……」在**今天无法复核**。我不把它们当作 SOTA、难度表或失败分布；只把用户口述的「榜首不到 30%」当作方向性约束。**本轮不基于任何具体榜单数字做设计。**

### 1.2 数据：pivot 恒定，双足不是用来走路的

我下载了 HangCup 的 `data/chunk-000/file-000.parquet`（130,565 帧）并统计，又用 HF datasets-server 抽查了 StackBowls、ToolboxStorage、ZipUp 的首帧。结果高度一致：

```text
HangCup (130,565 frames):
  action.pivot      mean [0, 0, 0, 0, 0.15, 0, 0.7391]
                    std  [0, 0, 0, 0, 0.00, 0, 0.0022]
                    min  [-0, -0, -0, 0, 0.15, 0, 0.7213]
                    max  [0.0033, 0.0001, -0, 0, 0.15, 0, 0.7400]
  action.base_command mean [0, 0, 0, 0.7391], std [0,0,0,0.0022]
  action.lower_body   std 0.017–0.077 rad（腿）/ 0.007–0.016 rad（腰）
  分段验证：前 6 = left_leg，中 6 = right_leg，后 3 ≈ waist；
            obs.lower_body 与 action.lower_body 完全一致（maxabs = 0）

StackBowls / ToolboxStorage / ZipUp 首帧:
  action.pivot = [0, 0, -0, 0, 0.15, 0, 0.74]
  action.base_command = [0, 0, -0, 0.74]
```

含义非常明确：

1. **演示中底盘不平移、不旋转**；base_command 的 x/y/yaw 全为 0，只有高度约 0.74 m。
2. **双足/腰部有小幅运动**，但量级只有 0.01–0.08 rad，是平衡/姿态补偿，不是行走。
3. **pivot 的第 5 维恒为 0.15、第 7 维恒为 0.74**，很可能是某种固定偏置 + 身高；不同任务几乎一样。
4. 官方参考 `example_policy.py` 输出 `np.zeros((T, 7))` 的 pivot；如果评测端不覆盖，这可能让机器人失去演示中的身高/姿态先验。

所以「双足机器人」在本赛题里的正确用法不是「绕桌走」，而是：

- **把 `lower_body[15]` 当作平衡/姿态传感器**：偏离演示分布 → 机器人在挣扎 → 降速/回退；
- **把 CoM/ZMP/足底接触当作健康指标**：伸手过远、搬重物、单臂伸展时预警；
- **只做小幅维护**：配重臂、轻微 waist/height 调整；**不做底盘平移/旋转**（数据里没有，OOD，且安全风险高）。

这是一个由数据驱动的剪枝：**绕桌移动、底盘重定位、双足行走，全部不做。**

### 1.3 API/规则：单模型、无深度/力/触觉、30 步 chunk、N 端口隔离

- 参赛手册（中/英，`r.jina.ai` 抓取）确认：所有任务须基于**同一模型**，不得混合多个模型；模型类型不限；32 任务；每任务 10 次独立运行；5 类泛化各 2 次（位置、干扰物、背景、未见物品、人为干扰）；单次上限 **180 s**；排名先看 32 任务总平均成功率，再看总平均步骤分，再看更早提交。
- 提交 README 确认：观测是四路 RGB 480×640 + 双臂关节/EE/夹爪 + `lower_body[15]` + 语言；**没有 depth、camera_info、force/torque、tactile**；动作是 `joint` 或 `ee` 互斥，另有 `action.pivot[7]`；`action_chunk_size` 固定，chunk 内不重新看世界；`meta.token` 每次都要带。
- 部署确认：从 **8765** 起暴露 **N 个连续端口**，每端口独立 episode、独立 `reset()`、独立状态；不同端口可能并发调用。

对 TWIN-PHM 的约束：

- 必须是**每端口独立**的轻量进程/线程，不能抢 GPU；
- 不能是第二个学习策略；MuJoCo + 确定性控制律是 C2 合规范式；
- 只能改 EE/关节/gripper/pivot 这些允许的键；
- 必须在 180 s 内完成，且不能因为孪生计算把 p99 延迟推高。

### 1.4 官方基座与仿真：G1 29-DoF MuJoCo 模型是现成的

- 官方 `unifolm-wla` 的训练配置明确：`action_dim: 54`、`state_dim: 60`、`action_horizon: 30`、`num_inference_timesteps: 4`；VLM 冻结，只训 action head + state projector；默认单卡 24GB；Apache 2.0。
- 官方 `unitree_mujoco` 仓库自带 `unitree_robots/g1/g1_29dof.xml`、`scene_29dof.xml` 和完整 STL 网格；有 floating base、29 个关节、足底接触、关节限位/力矩范围。
- 这意味着：**我们不需要自己搭 G1 的物理模型**；只需要把 API 的 29 个关节映射到 MuJoCo qpos，把桌子/物体作为可选几何体加进去。

## 2. 诊断：<30% 的瓶颈是「失败前 0.5 秒」没人管

把一次失败拆开，通常不是「模型不认识杯子」，而是：

```text
t0:      VLA 看到图，输出 30 步 chunk（1 秒）
t0+0.1s: 评测器开始执行，chunk 内不再看世界
t0+0.3s: 夹爪碰到杯沿/网口/拉链，产生 2–5mm 侧向偏差
t0+0.5s: 偏差累积成卡住/滑移/顶桌
t0+1.1s: 下一个 chunk 才看到，已经进入不可恢复状态
```

现有 VLA 优化的是 `p(action | observation)`；它没有显式建模：

- `p(failure | state, planned_action)`：这个动作计划会不会在未来 0.5 秒内撞桌/滑落/失衡？
- `RUL(state, plan)`：当前计划还有多久会失败？
- `maintenance_action`：如果会失败，最小干预是什么？

这正是「预测性维护」的用武之地：不是等坏了再修，而是**在故障先兆出现时、在还能挽回的时间窗内维护**。

三类失败先兆，恰好都能用本体 + MuJoCo 抓到，且不需要力/触觉：

1. **运动学先兆**：关节接近限位、机械臂接近奇异、肘/腕/夹爪与桌沿/自身距离变小、目标不可达。
2. **平衡先兆**：CoM/ZMP 逼近支撑多边形边缘、足底接触力分布异常、腰部/腿部偏离演示分布。
3. **接触先兆**： commanded EE 运动与 observed EE 运动出现残差（说明碰到了东西）、夹爪开度变化率异常（说明滑移/空抓）、物体相对夹爪的视觉位移。

第 3 条是「无力的力估计」：MuJoCo 前向运动学预测「如果没碰到东西，EE 应该在哪」，观测 EE 却在别处，残差就是接触/滑移的证据。这比等夹爪把杯子推倒再反应早 0.2–0.5 秒。

## 3. 三个灵感词怎么落到方法里

| 灵感词 | 传统用法 | 本轮用法 | 明确不做 |
|---|---|---|---|
| **MuJoCo** | 训练策略、sim-to-real、域随机化 | **运行时的短时前向预测器 + 健康指标计算器 + 动作投影器**；离线只用来回放演示、标定阈值 | 不在 MuJoCo 里训 6B 策略；不假设 sim 成功率能预测真机 |
| **双足机器人** | 走路、移动底盘、全身控制 | **平衡/姿态健康通道**：CoM/ZMP、足底接触、腰部/腿部偏离；维护动作只做配重臂和小幅 waist/height | 不做底盘平移/旋转、不做绕桌移动、不做双足行走 |
| **预测性维护** | 设备振动/温度/剩余寿命 | **动作计划的 RUL + 失败先兆 + 维护动作菜单 + 故障日志**；把每个 episode 当成一台需要维护的设备 | 不做第二个学习失败头（除非同 checkpoint，C3）；不把「维护」做成逐任务策略 |

## 4. TWIN-PHM 总览

```text
                    ┌─────────────────────────────────────┐
                    │  Evaluator (N ports 8765..8765+N-1) │
                    └──────────────┬──────────────────────┘
                                   │ obs / action chunk
                                   ▼
        ┌──────────────────────────────────────────────────────┐
        │  Per-port PolicyService (CPU)                        │
        │                                                      │
        │  VLA plan cache ──► CHUNK-SERVO ──► action adapter   │
        │        │                  ▲                │         │
        │        ▼                  │                ▼         │
        │  ┌──────────────────────────────────────────────┐    │
        │  │ TWIN-PHM (MuJoCo, deterministic)             │    │
        │  │  sync qpos ─► health indicators ─► prognostics│    │
        │  │       │              │                 │      │    │
        │  │       │              ▼                 ▼      │    │
        │  │       │        maintenance menu ─► repair    │    │
        │  │       └──────────── failure log ◄────────────┘    │
        │  └──────────────────────────────────────────────┘    │
        └──────────────────────────┬───────────────────────────┘
                                   │ async, batched
                                   ▼
                    ┌─────────────────────────────────────┐
                    │  Shared VLA server (GPU)            │
                    │  UnifoLM-WLA-1.0, 30-step           │
                    └─────────────────────────────────────┘
```

核心原则：

- **VLA 是唯一学习模型**；TWIN-PHM 是「物理引擎 + 控制律 + 有限状态机」。
- **每端口一个 twin**；twin 只读该端口的 obs，状态隔离。
- **twin 在后台跑**；`get_action` 永远不因 twin 超时；twin 失败就回退纯 VLA。
- **先 robot-only，后 object-aware**：不依赖物体位姿也能做 70% 的检查；物体位姿只在可靠时启用。

### I1 · TWIN-GUARD：机器人本体物理护栏（不依赖物体位姿）

- **动机**：很多失败不是语义错，而是「手伸太远、肘撞桌、腕接近奇异、夹爪顶穿桌面」。这些用官方 G1 MuJoCo 模型 + 29 个关节角就能查，不需要物体位姿。
- **与现有方案的差异**：现有 VLA 不做显式运动学可行性检查；现有 sim-to-real 把 MuJoCo 当训练场。TWIN-GUARD 把 MuJoCo 当**运行时过滤器**。
- **技术可行性**：高。`g1_29dof.xml` 现成；`mj_forward` 算 FK/雅可比/碰撞距离；29 DoF 单步 <0.2 ms。qpos 映射：双臂 14 + `lower_body[15]` = 29；floating base 固定为演示先验（0.74 m），不做底盘运动。
- **所需资源**：官方 MuJoCo XML；CPU 1 核/端口；无需 GPU；需要一次关节名映射和桌子平面标定。
- **落地步骤**：① 映射 qpos；② 用成功演示回放，记录健康指标分布；③ 设定阈值；④ 在 `get_action` 后、返回前，对候选 chunk 做检查；⑤ 违规时投影/裁剪。
- **风险**：模型与真机有 1–2 cm 外参/连杆误差；用相对阈值和 5–10 mm 安全裕度缓解。

### I2 · PHM-PROGNOSIS：动作计划的剩余寿命 RUL

- **动机**：只看当前帧的健康指标会太晚；要在「还能挽回」的时间窗内介入。预测性维护的核心不是检测故障，而是预测**何时**故障。
- **与现有方案的差异**：Backtrack/FPC-VLA 用学习到的失败头；PREFAIL 用物体相对运动。本方案用**物理 roll-out + 健康指标穿越阈值的时间**，无需失败标签，且可解释。
- **技术可行性**：中高。把候选 chunk 转成关节/EE 目标，在 MuJoCo 里跑 H=10–30 步；对动作噪声、物体位姿、摩擦做 K=4–8 个扰动样本；取最早违规时间作为 RUL。计算量：K×H×0.2 ms ≈ 8–48 ms/次，可后台做。
- **所需资源**：CPU 2–4 核/端口；成功演示做阈值标定；可选物体位姿。
- **落地步骤**：① 定义健康指标向量 h(t)；② 标定每个指标的「正常分布」；③ 实现 roll-out；④ 用离线扰动数据校准 RUL 误差；⑤ 设定干预阈值。
- **风险**：没有真实失败数据，RUL 只能做相对排序；用「成功演示 + 人工扰动」校准，不宣称绝对概率。

### I3 · HEALTH-CHUNK：健康自适应 chunk

- **动机**：第 12 轮固定 5 步；但接触前可以长 chunk 省 RTT，接触期必须短 chunk 才能反应。chunk 长度应该是**健康状态的函数**，不是常数。
- **与现有方案的差异**：现有工作把 chunk 当推理/吞吐参数；这里把它当**维护调度参数**。
- **技术可行性**：高。metadata 的 `action_chunk_size` 在握手时固定，不能每步变；但可以在固定上限内返回**有效长度**（例如声明 15，但只填 3 步有效动作 + 保持），或声明 5 并在健康时复用 plan。需要先确认评测端是否允许「声明长度 > 实际有效步数」；若不行，只能选一个保守固定值，把自适应放在「plan 复用/重规划频率」上。
- **所需资源**：单任务通道实测控制频率与 chunk 语义；无需额外算力。
- **落地步骤**：① 在单任务通道测 chunk=3/5/10/30 的成功率与延迟；② 实现「健康时复用 plan、异常时立即重规划」；③ 若 API 允许，再做有效长度自适应。
- **风险**：API 语义不清；先做保守版，不猜。

### I4 · BALANCE-MAINT：双足平衡维护

- **动机**：数据证明底盘不动，但双足/腰部有小幅平衡运动。伸手过远或搬重物时，VLA 可能把 CoM 推出支撑多边形；现有策略没有显式平衡约束。
- **与现有方案的差异**：大多数人形操作把下半身冻结；这里把 `lower_body[15]` 当健康传感器，把非操作臂当配重，把 waist/height 当小维护量。
- **技术可行性**：中。CoM 可由 MuJoCo 质量分布 + qpos 算；支撑多边形由双脚几何近似；ZMP 需二阶差分，噪声大，用低通。配重臂只动非操作臂，安全。pivot 语义未知，先只读不写。
- **所需资源**：G1 质量/惯量（XML 自带）；足底尺寸；成功演示的 lower_body 分布。
- **落地步骤**：① 算 CoM/ZMP 指标；② 在演示上标定正常范围；③ 仅在指标越界时，命令非操作臂到配重姿态；④ pivot 只做「输出演示先验」的 A/B，不主动改高度。
- **风险**：CoM 估计对物体质量未知；配重臂可能干扰 VLA 的下一段计划；用小幅、短时、可回退的维护。

### I5 · DEMO-MAINT：演示数据的物理维护

- **动机**：33k 条演示不可能条条干净；标定漂移、遮挡、关节读数噪声会污染 BC。预测性维护也可以用在「数据资产」上。
- **与现有方案的差异**：常见做法是启发式过滤（长度/动作范围）；这里用 MuJoCo 回放算物理一致性残差，按残差加权/剔除。
- **技术可行性**：中高。只回放本体关节轨迹，不需要物体模型；算 FK/EE 残差、关节速度/加速度异常、足底穿透。离线一次，成本可控。
- **所需资源**：CPU 集群/单机多核；169 h 数据；无需 GPU。
- **落地步骤**：① 流式读取 parquet；② 回放 29 维 qpos；③ 计算残差与异常分；④ 输出每条 episode 的 health score；⑤ 在 BC 中降权/剔除 top 5–10%。
- **风险**：物理模型误差会把好数据误杀；只做降权，不做硬删除；在验证集上确认不伤性能。

### I6 · FAILURE-LOG：故障日志 / 同 checkpoint 辅助头（可选）

- **动机**：每次干预都应留下「哪个指标、什么时候、做了什么、结果如何」的日志；这是下一轮迭代的燃料。
- **与现有方案的差异**：现有 VLA 评测只看成功率；这里把失败过程结构化，形成可复用的维护知识。
- **技术可行性**：高（日志）；中（学习头）。学习头若要做，必须用**同一个 VLA checkpoint 的 encoder + 一个线性/小 MLP 头**，避免第二个模型；这是 C3 合规模式，需向官方说明。
- **所需资源**：日志存储；单任务通道的 outcome 标签；少量 GPU。
- **落地步骤**：① 记录 health/RUL/干预/结果；② 离线分析哪些指标真正预测失败；③ 若线性头显著优于阈值，再考虑 C3；否则只用阈值。
- **风险**：单模型解释；没有足够失败样本；先做日志，不急着学习。

## 6. 与第 10–12 轮：保留、升级、剪枝

**保留**：

- 第 10 轮 FACT-VLA 的相位化 BC、CAC 柔顺执行、EGP 证据门控；

**升级**：

- 从「固定 5 步」升级到「健康自适应 chunk/重规划」。

- 从「双足=冻结下半身」升级到「双足=平衡健康通道 + 小维护量」。

## 7. 竞赛策略：先修免费的 pivot，再投接触任务

### 7.1 先做 P0：PIVOT-PRIOR 基线修复

在单任务通道做 5 次 A/B：

- A：参考实现的 `pivot = zeros`；
- B：`pivot = [0,0,0,0,0.15,0,0.74]`（从演示统计）。

如果 B 的成功率/步骤分更高，说明评测端确实吃 policy 的 pivot；这是一个**零学习成本**的基线提升。如果无差异，说明评测端覆盖 pivot；后续只把 pivot 当只读/保守量。

### 7.2 任务分诊（先验，待单任务通道更新）

- **优先投 TWIN-PHM（接触/平衡密集）**：HangCup、ArrangeTestTubes、ZipUp、Unlock、DisconnectEthernet、PlugCharger、PlugInEthernet、StackBowls、StoreCups、PaperCupStacking、ToolboxStorage、SyringeWaterTransfer、PourOutMedicine、StoreEarphones、StorePaddle、OrganizePencilCase、PackPhone、PackBag。
- **中等**：ArrangePlates、ColorArrangement、FruitCollection、FruitSorting、OrganizeBookshelf、OrganizeStationery、OrganizeTools、PackDoll、PlacePhotoFrame、RemovePinnedNote、PickOutBatteries。
- **低（变形/语义/动态，主要靠 VLA）**：FoldTowel、SpellRobot、ConveyorSorting。

分诊规则：`priority_t = q_t × Δ_t / cost_t`，其中 `q_t` 是失败发生在「物理执行/接触/平衡」的比例（先验 → 单任务通道更新），`Δ_t` 是 TWIN-PHM 条件增益，`cost_t` 是标定/调试成本。先做 `q_t` 最高、`cost_t` 最低的 3–5 个任务。

### 7.3 320 trials 的算术

- 设基线 `p≈0.25`；如果 TWIN-PHM 在 15 个接触任务上把「本来会失败」的 20% 救回来，全局约 `15/32 × 0.25 × 0.20 ≈ +2.3 pp`。
- 如果在 25 个任务上减少 10% 的物理失败，全局约 `25/32 × 0.25 × 0.10 ≈ +2.0 pp`。
- 两项叠加的保守区间 **+3–5 pp**；乐观 +6–8 pp。**这是设计目标，不是承诺**；必须用配对 A/B 和 bootstrap 置信区间证明。
- 人为干扰轴占 20%（2/10）；如果回退/重抓把 human 轴提高 10pp，全局约 +2 pp。

## 8. 实验门 G0–G8

| 门 | 问题 | 通过标准 | 失败动作 |
|---|---|---|---|
| G0 | pivot 先验是否有效？ | 单任务 B vs A 成功/步骤分有正向趋势；不改坏 | 只读 pivot，不写 |
| G1 | twin 回放是否一致？ | 成功演示的 EE 重投影/关节残差 ≤5 mm/2° | 只做 robot-only 粗检查 |

| G4 | 误干预率是否可接受？ | 正常 episode 误干预 ≤5%；不伤成功率 | 提高阈值/只在高风险段启用 |
| G5 | 单任务是否涨点？ | ≥3/5 任务 +10pp；FoldTowel 不回归 | 不提交 twin 版本 |

| G7 | 延迟是否可接受？ | p99 ≤150 ms；timeout 不升 | 后台化/降 roll-out |
| G8 | 全量干跑是否稳定？ | N 端口隔离、reset 干净、内存不涨 | 回退基线 |

所有门先在离线回放和单任务不计分通道上过；没有过门，不烧正式 320 trials。

# 第 13 轮产物 · TWIN-PHM 技术报告

> 检索/复核日期：**2026-11-02（UTC）**。对象：宇树 **UniBot 世界挑战赛**（G1 + Dex1，32 项桌面任务，通才单模型赛道，选手自部署 + 官方远程真机 API）。本报告是第 13 轮想法区「TWIN-PHM」的工程化产物；不替换第 10 轮 FACT-VLA、第 11 轮 GEO-RESIDUAL、第 12 轮 CHUNK-SERVO，而是在它们外面加一层**运行时的物理健康监测与预测性维护**。

## 0. 结论与边界

### 0.1 一句话结论

官方 WLA 的 30 步 action chunk 是吞吐优势，也是接触/平衡失败的结构性弱点；在 VLA 与评测器之间加一个**每端口独立、CPU 轻量、无学习权重**的 MuJoCo 健康层，用机器人本体状态做短时前向预测，估计动作计划的剩余寿命（RUL），并在失败前用确定性维护动作（投影、降速、缩 chunk、配重臂、回退重抓）介入，可以在不新增学习模型、不移动底盘的前提下，把「失败后恢复」变成「失败前维护」。

### 0.2 证据等级

| 等级 | 含义 | 本报告中的例子 |
|---|---|---|
| A | 官方文档、提交模板、数据集元数据、官方仓库直接核实 | 规则、API、`action_horizon=30`、`pivot` 常数、G1 MuJoCo XML |
| B | 我们在公开数据/网页上做的分析，可复现 | HangCup parquet 统计、HF datasets-server 抽样、leaderboard 状态 |
| C | 设计假设，需 G0–G8 验证 | RUL 可校准、健康指标 AUROC≥0.8、维护动作 +10pp |

### 0.3 本轮不做什么

- 不从零训 VLA/World Model；官方 WLA 6B 基座已开源。
- 不做底盘平移/旋转/绕桌移动；演示数据中 base 不动。
- 不做第二个学习策略/残差网络/独立失败头（除非同 checkpoint 的 C3 模式）。
- 不做完整 6D 物体位姿网络；先 robot-only，object-aware 只在可靠时启用。
- 不做完整 sim-to-real 策略训练；MuJoCo 只做运行时检查和离线回放。
- 不做 30Hz 广域网伺服；chunk 仍然受 RTT 约束。
- 不引用未复核的榜单具体分数；今日官网排行榜为 Coming Soon。

### 1.3 API（A）

提交 README（2026-11-02 复核）给出：

| 项 | 规格 |
|---|---|
| 观测图像 | `cam_left_high`、`cam_right_high`、`cam_left_wrist`、`cam_right_wrist` 四路 RGB **480×640** |

| 缺失 | **没有 depth、camera_info、force/torque、tactile** |
| 监控 | 评测端逐调用记录延迟、波动、动作统计规律 |

## 2. 问题形式化

### 2.1 评分与不确定性

总分：

```math
S = \frac{1}{32}\sum_{t=1}^{32} p_t,\qquad
p_t = \frac{1}{10}\sum_{j=1}^{10} y_{t,j},\quad y_{t,j}\in\{0,1\}.
```

320 trials 下，若 `p≈0.25`：

```math
\mathrm{SE}(S)\approx \sqrt{\frac{p(1-p)}{320}}\approx 0.0242.
```

配对 A/B 的方差取决于任务内相关；报告必须给配对差值的 bootstrap 95% CI，而不是只报两个平均值。

人为干扰轴：

```math
\Delta S_{\mathrm{human}} = \frac{2}{10}\,\Delta p_h = 0.2\,\Delta p_h.
```

### 2.2 失败过程的时间模型

设：

- `f_c`：评测端控制频率（假设 30 Hz，待实测）；
- `H_c`：提交的 `action_chunk_size`；
- `τ`：网络 RTT + 推理 + 图像传输的等效延迟；
- `T_fb = H_c/f_c + τ`：从世界变化到策略看到变化的反馈周期；
- `T_int`：从失败先兆出现到不可恢复的时间（干预窗口）。

| 场景 | `H_c` | `f_c` | `τ` | `T_fb` | 评价 |
|---|---:|---:|---:|---:|---|
| 官方 WLA 默认 | 30 | 30 | 50ms | **1050ms** | 接触段基本开环 |
| 本方案保守 | 5 | 30 | 50ms | **217ms** | 可做 1–2 次接触修正 |
| 本方案高延迟 | 5 | 30 | 150ms | **317ms** | 增益降档 |
| 低控制频率 | 5 | 10 | 50ms | **550ms** | 改 `H_c=3` 或只做 PBVS |

预测性维护要有效，必须满足 `T_fb < T_int`。对于插入/挂/叠/拉链，`T_int` 可能在 0.2–0.8 s；所以 `H_c=5` + 低 RTT 是必要的，`H_c=30` 基本来不及。

### 2.3 健康状态与 RUL 定义

在时刻 `t`，给定状态 `s_t` 和候选动作计划 `a_{t:t+H}`，定义健康指标向量：

```math
h(s_t) = [h_{kin}, h_{bal}, h_{con}, h_{pol}] \in [0,1]^m,
```

其中 1 表示健康，0 表示越过安全阈值。定义计划在第 `k` 条扰动样本下的首次违规时间：

```math
\tau^{(k)}_{\mathrm{fail}} =
\min\left\{ t' \in [t, t+H] : \exists i,\ h_i(s^{(k)}_{t'}) < \theta_i \right\}.
```

剩余寿命与失败概率：

```math
\widehat{\mathrm{RUL}} = \min_k \tau^{(k)}_{\mathrm{fail}},\qquad
\hat p_{\mathrm{fail}} = \frac{1}{K}\sum_{k=1}^{K}\mathbb{1}\left[\tau^{(k)}_{\mathrm{fail}} \le H\right].
```

干预条件：

```math
\text{intervene} \iff \hat p_{\mathrm{fail}} > \theta_f \ \lor\ \widehat{\mathrm{RUL}} < H_c.
```

注意：`RUL` 是**相对**指标，不是绝对物理寿命；它的价值是排序「哪个计划更危险、还能撑多久」，而不是预测精确秒数。

### 2.4 维护动作的约束

维护动作 `m` 必须满足：

1. 只改 API 允许的键（EE/关节/gripper/pivot）；
2. 每 chunk 的修正量有界：`||Δx|| ≤ 1 cm`、`||Δθ|| ≤ 0.05 rad`；
3. 不改变底盘平移/旋转；pivot 高度只在演示先验 ±2 cm 内；
4. 连续干预不超过 `K_int` 个 chunk；超过则回退/重规划；
5. 任何异常 → 返回上一组合法动作或安全保持；绝不返回 NaN/错误形状。

## 3. TWIN-PHM 系统设计

### 3.1 进程/端口拓扑

```text
                    ┌─────────────────────────────────────┐
                    │  Evaluator (N ports 8765..8765+N-1) │
                    └──────────────┬──────────────────────┘
                                   │ websocket: obs / action chunk
                                   ▼
        ┌──────────────────────────────────────────────────────┐
        │  Per-port PolicyService (CPU)                        │
        │  ├─ plan cache / CHUNK-SERVO                         │
        │  ├─ TWIN-PHM (MuJoCo + deterministic rules)          │
        │  ├─ maintenance menu / failure log                   │
        │  └─ action adapter (WLA 54D → API 21D)               │
        └──────────────────────────┬───────────────────────────┘
                                   │ async, batched
                                   ▼
                    ┌─────────────────────────────────────┐
                    │  Shared VLA server (GPU)            │
                    │  UnifoLM-WLA-1.0, 30-step           │
                    └─────────────────────────────────────┘
```

- 每个端口一个 `PolicyService` 实例，独立 `reset()`、独立 twin、独立 plan cache、独立日志。
- twin 在后台线程跑；`get_action` 只读最近一次健康结果；超时就用上一结果或纯 VLA。
- 共享 VLA server 用 session ID 区分端口；权重只有一份，不违反单模型。

### 3.2 状态同步

qpos 映射（G1 29-DoF）：

| qpos 段 | 来源 | 维度 |
|---|---|---:|
| 左腿 | `lower_body[0:6]` | 6 |
| 右腿 | `lower_body[6:12]` | 6 |
| 腰 | `lower_body[12:15]` | 3 |
| 左臂 | `left_arm[0:7]` | 7 |
| 右臂 | `right_arm[0:7]` | 7 |
| 合计 | | **29** |

floating base：API 不提供 base 位姿。两种处理：① 若机器人站在地面，用双腿关节角 + 双脚着地假设做 floating-base 估计（足底接触点约束 + 腿 IK），再算 CoM/ZMP；② 若平台把机器人固定在支架上，则关闭平衡检查，只保留运动学/接触检查。默认先用固定先验 `z≈0.74`、姿态单位四元数，用相对裕度、保守阈值缓解误差。若 `pivot` 第 7 维含义被验证为高度，则用它更新 `z`。

桌子平面：从头部双目点云 RANSAC 拟合，或假设任务固定桌面高度；拟合失败则关闭桌面检查。

物体位姿：可选。刚体任务用头双目 + 简单几何（box/cylinder）拟合；透明/反光/变形任务不启用 object-aware 检查。物体位姿置信度低于阈值时，只做 robot-only 检查。

### 3.3 两档 twin：K-mode / D-mode

**K-mode（运动学，默认）**：

- `mj_forward` 算 FK、雅可比、关节限位、自碰/桌碰距离、可操作度；
- 对候选 EE 目标做阻尼最小二乘 IK，检查可达性/限位；
- 不做物体动力学，不做接触力；
- 单次检查 <1 ms；适合每 chunk 都跑。

**D-mode（动力学，按需）**：

- `mj_step` 跑短时 roll-out，算 CoM/ZMP、足底接触、关节力矩裕度；
- 只在 K-mode 发现风险、或接近接触/搬运重物时启用；
- K=4–8 个扰动样本 × H=10–20 步；单次 10–40 ms，后台跑。

伪代码：

```python
def twin_check(obs, plan, mode="K"):
    qpos = map_obs_to_qpos(obs)
    set_mujoco_state(qpos, base_prior)
    hj = mj_forward(model, data)
    h = compute_kin_health(model, data, plan)   # K-mode
    if mode == "D" or h.min() < 0.5:
        h = min(h, compute_dyn_health(model, data, plan))
    return h
```

### 3.4 `get_action` 伪代码

```python
class TwinPHMPolicy:
    def get_action(self, obs):
        self._tick(obs)
        self._maybe_request_plan(obs)

        if self.plan is None:
            self.plan = self.vla.predict(obs)  # cold start only
            self.plan_idx = 0

        # 1) 取候选 chunk（CHUNK-SERVO 前馈 + 视觉伺服）
        a_ff = self.plan[self.plan_idx : self.plan_idx + self.H_c]
        if self.mode == "SERVO" and self.goal is not None:
            a_ff = compose_relative(a_ff, self.servo.compute(obs, self.goal))

        # 2) TWIN-PHM 检查（不阻塞；用最近一次结果）
        health = self.twin.latest_health(obs)
        if health is not None and health.should_intervene:
            a_cmd = self.maintenance.apply(a_ff, obs, health)
            self.log(health, a_cmd)
        else:
            a_cmd = a_ff

        # 3) 安全适配 + 返回
        self.plan_idx += len(a_cmd)
        if self.plan_idx >= len(self.plan):
            self.plan = None
        return self.adapter.to_api(a_cmd, obs, self.token)
```

## 4. 健康指标

### 4.1 运动学指标

**关节限位裕度**：

```math
m_q = \min_i \min\left(
\frac{q_i - q_i^{\min}}{\epsilon_q},
\frac{q_i^{\max} - q_i}{\epsilon_q}
\right),
```

`ε_q` 取 0.1 rad；`m_q<1` 表示接近限位。

**可操作度**：

```math
\mu = \sqrt{\det\left(J(q)J(q)^\top\right)},
```

对每条 7-DoF 臂单独算；用成功演示同任务/同相位的中位数归一化：

```math
h_{\mathrm{manip}} = \mathrm{clip}\left(\frac{\mu}{\mu_{\mathrm{ref}}},\ 0,\ 1\right).
```

**自碰/桌碰距离**：用 MuJoCo `mj_geomDistance` 或碰撞对的最小距离 `d_self`、`d_table`；归一化：

```math
h_{\mathrm{col}} = \mathrm{clip}\left(\frac{\min(d_{\mathrm{self}}, d_{\mathrm{table}})}{d_{\mathrm{safe}}},\ 0,\ 1\right),
```

`d_safe` 取 2 cm。

**可达性**：对候选 EE 目标做阻尼最小二乘 IK：

```math
\Delta q = J^\top (JJ^\top + \lambda I)^{-1} e,
```

若迭代 20 次后 `||e|| > 5 mm` 或关节越限，`h_reach=0`。

### 4.2 平衡指标

CoM：

```math
c = \frac{\sum_i m_i c_i}{\sum_i m_i}.
```

支撑多边形 `P`：双脚四个角点（或足底接触点凸包）。CoM 裕度：

```math
d_{\mathrm{com}} = \mathrm{dist}\left(c_{xy}, \partial P\right),
\qquad
h_{\mathrm{com}} = \mathrm{clip}\left(\frac{d_{\mathrm{com}}}{d_{\mathrm{com,safe}}},0,1\right).
```

ZMP：

```math
p_{\mathrm{zmp}} = c_{xy} - \frac{z_c}{g}\ddot{c}_{xy},
```

`c_{xy}` 用低通/卡尔曼平滑；`z_c` 为 CoM 高度。ZMP 裕度同理。若 `d_zmp < 1 cm`，`h_bal` 降档。

足底接触：MuJoCo `mj_contactForce` 或足底 geom 的接触法向力；左右脚法向力比异常（如一脚几乎为 0）→ 降档。

### 4.3 接触/抓取指标

**EE 残差**（无力的接触检测）：

```math
r_{ee} = \|x_{ee}^{\mathrm{obs}} - x_{ee}^{\mathrm{pred}}\|,
```

`x_{ee}^{\mathrm{pred}}` 是 twin 在「无碰撞」假设下按 commanded action 前向积分的 EE 位置。`r_ee` 突然增大 → 碰到东西/被阻挡。

**夹爪异常**：

```math
r_g = |g^{\mathrm{obs}} - g^{\mathrm{pred}}| + \lambda |\dot g^{\mathrm{obs}} - \dot g^{\mathrm{pred}}|.
```

夹爪闭合过快/过慢 → 空抓/滑移/物体太小。

**摩擦锥裕度**（object-aware，可选）：

```math
m_f = \mu_s f_n - \|f_t\|,
\qquad
h_{\mathrm{grasp}} = \mathrm{clip}\left(\frac{m_f}{m_{f,\mathrm{safe}}},0,1\right).
```

只在物体位姿/质量可靠时启用；否则用 `r_ee`/`r_g` 代理。

**物体-夹爪相对位移**：

```math
r_{\mathrm{slip}} = \|T_{\mathrm{ee}}^{-1} x_{\mathrm{obj}}(t) - T_{\mathrm{ee}}^{-1} x_{\mathrm{obj}}(t-1)\|,
```

超过阈值 → 滑移。

### 4.4 策略健康

- **动作不确定性**：若 VLA 返回多个去噪样本，算 chunk 方差；若只返回一个，用连续 chunk 的不一致度。
- **视觉新颖性**：目标区域特征与演示库的距离；过高 → OOD。
- **延迟裕度**：最近 p99 延迟 / 预算；过高 → 降速/缩 chunk。

这些指标不直接触发维护，只用于**降低干预置信度**或**选择保守动作**。

### 4.5 归一化与阈值

对每个任务/相位，用成功演示的健康指标分布标定：

```math
\theta_i = \mathrm{Percentile}_{5}\left(h_i^{\mathrm{success}}\right),
```

即成功演示中 5% 分位数作为安全阈值；低于阈值即「异常」。为降低误报，使用滞回：

```text
进入异常：h_i < θ_i 连续 K=3 帧
退出异常：h_i > 1.2 θ_i 连续 K=5 帧
```

## 5. 预测与维护

### 5.1 Roll-out

对候选 chunk 的每个 EE 目标，用 K-mode IK 转成关节目标；在 MuJoCo 中按 `dt=1/30` 推进：

```python
for k in range(K):
    data.qpos = qpos_now + noise[k]
    for t in range(H):
        q_target = ik(model, data, ee_target[t])
        data.ctrl = q_target
        mj_step(model, data)
        h[k, t] = compute_health(model, data)
```

扰动来源：

- 关节角噪声 `N(0, 0.005 rad)`；
- 物体位姿噪声 `N(0, 5 mm/2°)`（仅 object-aware）；
- 摩擦系数 `U(0.6, 1.2)`；
- 控制延迟 `0–2` 步；
- 桌面高度 `±1 cm`。

### 5.2 RUL / 失败概率

按 §2.3 计算 `RUL` 和 `p_fail`。实践细节：

- `H` 取 `max(2H_c, 10)`；接触段 `H=20`，自由段 `H=10`。
- `K` 取 4–8；CPU 紧张时 `K=4`、`H=10`。
- 若 `p_fail > 0.5` 或 `RUL < H_c`，进入维护。
- 若 `RUL` 在 `[H_c, 2H_c]`，降速/缩短 chunk，不立即回退。
- 若连续 3 次 `p_fail > 0.7`，判定不可恢复，回退/重规划。

### 5.3 维护动作菜单

| 动作 | 触发 | 做法 | 安全限制 |
|---|---|---|---|
| **M1 投影** | 碰撞/越限/不可达 | 把 EE 目标投影到可行域；IK 重解 | ≤1 cm/0.05 rad |
| **M2 降速** | RUL 中等/接近接触 | 缩放 EE 速度/延长轨迹 | 0.3–1.0× |
| **M3 缩 chunk** | 接触/高不确定 | 返回更短有效 chunk，尽快重观测 | 受 API 语义限制 |
| **M4 配重臂** | CoM/ZMP 裕度低 | 非操作臂移到配重姿态 | 不碰桌/不挡相机 |
| **M5 姿态** | 够不到/平衡差 | 小幅 waist/height 调整 | 只在 pivot 语义验证后 |
| **M6 回退** | 已进入坏状态 | 沿最近 EE 轨迹回退到安全点 | 限速/限幅 |
| **M7 重抓** | 滑移/空抓 | 张开→后退→重新闭合 | 最多 2 次 |
| **M8 重规划** | 目标不可见/持续失败 | 请求 VLA 用新观测重规划 | 超时回退 |

优先级：M1/M2/M3（最小侵入）→ M4/M5 → M6/M7 → M8 → 放弃。

### 5.4 干预优先级与安全限幅

```python
def apply(self, a, obs, health):
    cause = health.argmin()  # 最不健康的指标
    if cause in ("collision", "reach", "limit"):
        return project(a, obs, max_dx=0.01, max_dth=0.05)
    if cause == "balance":
        return counterweight_or_slow(a, obs, max_waist=0.05)
    if cause == "grasp":
        return regrasp_or_slow(a, obs, max_retries=2)
    if cause == "unrecoverable":
        return backtrack_or_replan(a, obs)
    return a
```

- 每 chunk 最多一个维护动作；不要叠加。
- 连续干预 `K_int=1`，之后必须让 VLA 至少执行一个原始 chunk，避免「维护层变成第二个策略」。
- 任何维护动作都记录到 failure log。

### 5.5 误报控制

- 只在 `h.min() < 0.5` 且 `p_fail > 0.5` 时干预；正常 episode 的误干预目标 ≤5%。
- 用滞回 + 连续帧确认。
- 在单任务通道先测「twin 只观察不干预」的误报率，再开干预。
- 若某任务误报高，关闭该任务的 twin 干预，只保留日志。

## 6. 双足 / pivot 的具体用法

### 6.1 数据证据

见 §1.5：`action.pivot` 恒定 `[0,0,0,0,0.15,0,0.74]`；`base_command` 的 x/y/yaw 为 0；`lower_body` 小幅波动。结论：

- **不做底盘移动**；
- **双足是平衡/姿态通道**；
- **pivot 先验值得 A/B**。

### 6.2 CoM/ZMP

用 MuJoCo 的质量/惯量算 CoM；用双脚几何近似支撑多边形；ZMP 用 CoM 二阶差分。健康指标：

```math
h_{\mathrm{bal}} = \min\left(h_{\mathrm{com}}, h_{\mathrm{zmp}}, h_{\mathrm{foot}}\right).
```

只在 `h_bal < 0.5` 时触发配重/降速。

### 6.3 配重臂

当右臂在操作时，左臂可以移到远离桌面的配重姿态，把 CoM 拉回支撑中心。做法：

- 离线用 MuJoCo 算「操作臂在当前 EE 目标下，非操作臂在若干候选姿态下的 CoM 裕度」；
- 选一个不碰桌、不挡相机、关节裕度足够的姿态；
- 只在小范围调整（≤0.3 rad），且不改变 VLA 的操作臂计划。

这不是「第二个策略」，而是**姿态优化**。

### 6.4 pivot 先验与 A/B

P0 实验：

| 组 | pivot 输出 |
|---|---|
| A | `zeros(7)`（参考实现） |
| B | `[0,0,0,0,0.15,0,0.74]`（演示统计） |

每任务 5 次，比较成功率/步骤分/耗时。若 B 更好，保留；若无差异，pivot 被评测端覆盖，改为只读。**不要在没有 A/B 的情况下主动改 pivot 高度**。

## 7. 演示数据维护

### 7.1 回放管线

```text
for each episode:
    for t in frames:
        qpos = concat(left_arm[t], right_arm[t], lower_body[t])
        set_mujoco_state(qpos, base_prior)
        mj_forward()
        ee_pred = site_xpos("left_gripper"), site_xpos("right_gripper")
        r_ee[t] = ||ee_pred - ee_obs[t]||
        r_vel[t] = ||qvel_pred - qvel_fd||
        r_limit[t] = min joint limit margin
        r_foot[t] = foot penetration
    score = aggregate(r_ee, r_vel, r_limit, r_foot)
```

### 7.2 异常分

```math
s_{\mathrm{ep}} = \mathrm{mean}_t \left(
w_1 \tilde r_{ee} + w_2 \tilde r_{vel} + w_3 \tilde r_{limit} + w_4 \tilde r_{foot}
\right),
```

`~` 表示按任务归一化。取 top 5–10% 为「可疑」，在 BC 中降权（不是硬删除）。

### 7.3 训练中的降权

```python
weight = 1.0 if score < p90 else 0.5 if score < p97 else 0.1
```

在验证集上确认降权不伤性能；若伤，回退。

## 9. 竞赛策略

### 9.1 任务分诊

按「物理失败杠杆」分三档（先验）：

- **高（18）**：HangCup、ArrangeTestTubes、ZipUp、Unlock、DisconnectEthernet、PlugCharger、PlugInEthernet、StackBowls、StoreCups、PaperCupStacking、ToolboxStorage、SyringeWaterTransfer、PourOutMedicine、StoreEarphones、StorePaddle、OrganizePencilCase、PackPhone、PackBag。
- **中（11）**：ArrangePlates、ColorArrangement、FruitCollection、FruitSorting、OrganizeBookshelf、OrganizeStationery、OrganizeTools、PackDoll、PlacePhotoFrame、RemovePinnedNote、PickOutBatteries。
- **低（3）**：FoldTowel、SpellRobot、ConveyorSorting。

优先级：

```text
priority_t = q_t * Δ_t / cost_t
```

- `q_t`：失败发生在物理执行/接触/平衡的比例（先验 → 单任务通道更新）；
- `Δ_t`：TWIN-PHM 条件增益（A/B）；
- `cost_t`：标定/调试成本。

先做高挡中 `q_t` 最高、`cost_t` 最低的 3–5 个任务；不要一次铺 18 个。

### 9.2 预算与收益

| 方案 | 成本（估算） | 预期收益 | 建议 |
|---|---|---|---|
| PIVOT-PRIOR A/B | 2–3 人天 | 0 到 +1–2pp（未知） | 先做；零学习成本 |
| TWIN-GUARD（robot-only） | 2–3 人周 + CPU | 高挡 +5–10pp → 全局 +2–4pp | 主投 |
| PHM-PROGNOSIS | 2 人周 | 让干预更早，+1–2pp | 主投 |
| BALANCE-MAINT | 1–2 人周 | 小幅；主要是防摔/防撞 | 可选 |
| DEMO-MAINT | 1 人周 + CPU | 数据质量；间接 | 可做 |
| 学习失败头（C3） | 2–3 GPU 周 + 合规沟通 | 不确定；风险高 | 暂不做 |

收益算术（设计目标，不是承诺）：

- 高挡 18 任务各 +5pp → `18/32×5 ≈ +2.8pp`；各 +10pp → +5.6pp。
- 若只在高挡 10 个任务生效 +10pp → `10/32×10 ≈ +3.1pp`。
- human 轴 +10pp → +2pp。
- 保守合计 +3–5pp；乐观 +6–8pp。

### 9.3 提交节奏

1. **W0**：官方 WLA + API adapter + chunk 30 基线；单任务通道跑 1 个任务，确认接口/pivot/token。
2. **W1**：PIVOT-PRIOR A/B；twin 只观察，测误报。
3. **W2–W4**：TWIN-GUARD + PHM-PROGNOSIS；离线/仿真/单任务。
4. **W5**：chunk/阈值扫描；全量干跑。
5. **W6**：最终提交；保留回滚开关。

若只允许一次提交：跳过安全基线提交，W5 后再交；不要用正式 320 trials 做未验证的 A/B。

## 11. 风险与合规

### 11.1 单模型合规

| 模式 | 做法 | 风险 | 建议 |
|---|---|---|---|
| C1 离线标注 | twin 只离线生成标签；线上只有 VLA | 最低 | 保守 |
