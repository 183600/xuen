# 第 1 轮（承接历史第 12 轮）· CONSISTENCY-FIRST：先修数据一致性，再把 30 步开环压成 deadline 驱动的 5–8 步闭环

> 检索/复核日期：**2026-10-31（UTC）**。赛事身份不变：宇树 **UniBot 世界挑战赛**（unibot.unitree.com），G1 + Dex1，32 项桌面任务，通才单模型赛道，选手自部署 + 官方远程真机 API。本轮是新一轮灵感循环的第 1 轮，三个词是「嵌入式系统」「数据质量」「最小可行产品」。
>
> 与第 12 轮 CHUNK-SERVO 的关系：**不推倒，降级**。CHUNK-SERVO 的「30 步规划 + 5 步执行 + 相对目标」保留为 P1 控制层；但完整数字孪生、9–10 周计划、腕部无内参的前提被剪掉。本轮主投改为 **DATA-CANON + EDGE-DEADLINE + MVP-0**：先把数据一致性和执行时限做成可测的系统变量，再决定要不要投视觉伺服。

## 0. 先给结论：不是模型不够大，是数据和反馈不够“同分布、够快”

这轮我先做了三件事：重新抓赛事规则/API/榜单，逐个核对 32 个公开数据集，再把头部模型公开路线与官方 WLA 基座对齐。结论可以压成三句：

1. **榜单不是 SOTA，是预览。** 榜首 MolmoAct2 29.7%，8 个模型全在 20.5–29.7% 之间；但 `leaderboard_data.json` 的 `generated_from` 是 `gen_leaderboard.py`，8×32 个 `step_score ~ success_rate` 回归 **R² > 0.999999**，跨模型任务成功率平均相关只有 **0.098**，成功率还不是 10 次 trial 的整数倍，详情页 32 个视频全是占位。把它当难度信号可以，当架构结论不行。
2. **官方 WLA 已经把“大模型”这件事做完了。** UnifoLM-WLA-1.0 是 6B、约 2,500h、64 任务，Base 权重 2026-09-28 已开源；默认 30 步 chunk、4 步扩散、冻结 VLM 只训 action head，单张 24GB 可微调。再从零训 6B/14B/World Model，边际收益很低。
3. **真正剩下的两个变量是数据一致性和执行时限。** 33k 演示不是“脏数据”，而是“干净但异质”：32 个任务只有 **10 种头部相机 profile**，每个任务只用其中 **1 种**；8 个 robot、150 个 session，平均每任务只覆盖 **2.94/8** 个 robot，14 个任务 ≤2 个 robot，9 个任务 >90% 由单 robot 贡献；语言是 **5 条同义句用 `@` 拼成一个字符串**；动作目标比状态超前 **2–3 帧**。与此同时，API 的 30 步 chunk 在 30Hz 下就是 **1 秒开环**，6B 推理约 100ms，RTT 未知——接触任务恰恰死在最后 3 厘米。

所以本轮的判断是：

> **Consistency before capacity, deadline before dexterity.**
> 先把 33k 演示修成“相机-任务解耦、robot/session 平衡、动作-语言对齐”的可复现数据管线；再用 deadline-aware 的 5–8 步 chunk 把 30 步开环压到 200–300ms 反馈；MVP-0 不过门，不投视觉伺服。

这不是“更宏大的方案”，而是把上一轮 CHUNK-SERVO 的假设逐条做压力测试后，留下的更小、更硬、更可证伪的版本。

## 1. 三个灵感词怎么落到方案里

| 灵感词 | 直接落点 | 具体做法 | 明确不做什么 |
|---|---|---|---|
| **嵌入式系统** | `EDGE-DEADLINE` | 用 p99 延迟选固定 `H_c`；VLA 后台预计算 30 步 plan，前台每 5–8 步返回一次；per-port 隔离、watchdog、动作 hold、优先级批处理 | 不把 6B 塞进 MCU；不声称“边缘端跑大模型”；不做 30Hz 广域网闭环 |
| **数据质量** | `DATA-CANON` | 用每个数据集的相机内参做虚拟相机规范化 + FOV 随机化；task×robot×session 平衡采样；动作-状态对齐；语言按 `@` 拆开 | 不做去重/去噪（审计未发现大量重复/坏帧）；不重新采 33k 数据；不把“更多数据”当默认答案 |
| **最小可行产品** | `MVP-0` | 72 小时：官方 WLA + API adapter + 3 个任务 + 单任务不计分通道，先测通接口、控制频率、RTT、reset | 不一上来跑 32×10；不先搭完整数字孪生；不先训新模型 |

## 2. 为什么不是“更大的模型”

### 2.1 榜单是预览，不能反推架构

| 排名 | 模型 | 平均成功率 | 步骤分 |
|---|---|---:|---:|
| 1 | MolmoAct2 | **29.7%** | 39.0 |
| 2 | WALL-OSS-0.5 | 28.5% | 38.9 |
| 3 | DreamZero | 27.9% | 37.9 |
| 4 | Spirit-v1.5 | 25.9% | 34.4 |
| 5 | DM0 | 23.5% | 31.7 |
| 6 | π0.5 | 22.8% | 30.6 |
| 7 | GigaBrain-0 | 22.6% | 29.5 |
| 8 | GR00T N1.5 | 20.5% | 28.1 |

三条取证比分数本身更重要：

- `leaderboard_data.json` 的 `generated_from = "gen_leaderboard.py"`；`generalist` 有 8 个，`specialist` 为空。
- 8 个模型 ×32 任务的 `step ~ success` 回归 R² > 0.999999，最大残差 <0.006；这不是实测步骤分，是脚本生成的线性缩放。
- 8 个模型的 32 维任务成功率两两相关，平均 off-diagonal corr ≈ **0.098**；如果任务难度真实，不同模型的任务级成功率应该正相关。再加上成功率出现 27.29%、27.85% 等非 10% 整数倍，以及详情页 32 个任务视频全是占位，基本可以判定：**这是预览/合成榜单，不是可复现的 SOTA 表**。

**对策略的含义**：不从榜单任务排名里挑“难任务”或“易任务”；只从公开模型家族的技术路线、官方数据/规则、以及我们自己能测的单任务通道里找信号。

### 2.2 官方 WLA 已经把基座做完了

| 项 | 事实 |
|---|---|
| 模型 | UnifoLM-WLA-1.0，**6B** |
| 数据 | 约 **2,500h** 真机，**64** 任务 |
| 动作/状态 | 54 维 action / 60 维 state |
| 默认 chunk | **30 步 @30Hz**，约 1 秒 |
| 扩散步数 | 4 |
| 微调 | 冻结 VLM，只训 DiT action head + robot-state projector；单张 **24GB** GPU |
| 权重 | Base 于 **2026-09-28** 开源，Apache-2.0 |
| 推理 | 官方材料约 **100ms**；30 步 chunk 约 1s 开环 |

这意味着：**不要从零训通用 VLA/World Model**。把官方 WLA 拿来，先验证它能不能吃挑战赛的观测/动作；能，就只微调 action head；不能，就做 adapter/小规模继续预训练。省下的算力应该投到数据一致性和执行层，而不是再造一个 6B。

### 2.3 API 把“更大模型”变成“更慢反馈”

- 观测只有四路 RGB 480×640；**没有 depth、camera_info、force/torque、tactile**。
- 动作是 `ee` 绝对目标位姿 + gripper + `pivot[7]`；`action_chunk_size` 固定，chunk 内没有新观测、没有打断机制。
- 30 步 chunk @30Hz = **1 秒开环**；6B 推理约 100ms，远程 websocket + JPEG 还会加 RTT。
- MolmoAct2 公开材料称 base action call **180ms**、adaptive depth **790ms**（H100），而且一次规划 10–30 步、batch 内不反应；WALL-OSS-0.5 是 4B，公开的 60.5% 是 average task progress，不是 success。

**越大的模型，越倾向长 chunk；越长的 chunk，越不反应。** 在这个 API 下，“更大”首先买到的是更慢的反馈，而不是更高的接触精度。接触任务需要的是“现在偏了 2mm 就往回修”，不是“想象未来 1 秒”。

### 2.4 数据异质性是更便宜的杠杆

我们逐数据集读了 32 个 `meta/info.json` 和 32 个 episodes 元数据，关键结果：

- **10 种头部相机 profile**：`fx` 约 **186.0–296.1**，`cy` 约 **225.0–347.0**，`Tz` 约 **-18.9–+3.1mm**；每个任务只用 **1 种** profile，任务内部没有相机多样性。
- **8 个 robot、150 个 session**：robot 8520 占 **11,709/33,276 ≈ 35%**；平均每任务 **2.94/8** 个 robot；14 个任务 ≤2 个 robot；9 个任务 >90% 由单 robot 贡献。
- **语言标签**：每个任务的 `tasks` 是“一个字符串的 list”，字符串由 **5 条同义指令用 `@` 拼接**，长度 166–451 字符；评测给的是单条指令。
- **动作对齐**：3 个任务审计显示，`action.*_ee_pose_gripper_base` 比 `observation.state.*` 超前 **2–3 帧（67–100ms）**；最佳 lag 下仍有 1.1–1.6cm 残差。
- **反向结果**：轨迹本身很干净——`recomputed_ee_valid ≈ 1.0`，零运动帧 ≈0.0002，gripper action-state corr ≈0.997，无 NaN，最大关节步长 <0.44rad；3 个任务的近重复检查显示 <1cm 的 pair 为 **0%**，没有大规模重复。

所以“数据质量”不是去噪、去重、再采 33k；而是**打破 task-camera、task-robot 的伪相关，修语言/动作的标签错位**。这比再训一个大模型便宜得多，也更可能直接改善多机器人评测。

## 3. 我是怎么从三个词推到这 8 个点的

先把失败拆成五类：

1. **接口未知**：控制频率、RTT、reset、图像顺序、`pivot` 语义都没实测；不先做 MVP，后面全是空中楼阁。
2. **任务-相机 OOD**：每个任务只有一种头部相机 profile；评测换机器人/换相机，模型可能把“任务”和“相机”一起记。
3. **任务-机器人 OOD**：14 个任务 ≤2 个 robot，9 个任务 >90% 单 robot；评测是多机器人。
4. **开环延迟**：30 步 chunk = 1s；6B 推理 + RTT；接触段没有反馈。
5. **标签错位**：5 条指令用 `@` 拼成一个长字符串；动作目标比状态超前 2–3 帧。

再把干预按“证据强度 × 边际收益 / 成本”排序：

- 接口未知 → **MVP-0**（必做，否则无法测）。
- 任务-相机 OOD → **CAM-CANON**（证据最强：每任务 1 个 profile）。
- 任务-机器人 OOD → **SESSION-BALANCE**（证据强：平均 2.94/8）。
- 开环延迟 → **EDGE-DEADLINE**（API 结构决定，必须做）。
- 标签错位 → **LANG-SPLIT**、**ACTION-ALIGN**（便宜，先做 A/B）。
- 最后 3 厘米 → **CHUNK-SERVO-LITE**（证据中等、实现最重，降为 P1）。
- 评测相机完全未知 → **SELF-CALIB**（长线，P2）。

排序的硬约束是**单模型规则**：任何“再加一个学习模型”的方案先扣分；数据管线、确定性控制器、同一个 checkpoint 的辅助头优先。

## 5. 逐点展开

### I-01 MVP-0：72 小时先证明“接口是通的”

- **动机**：所有方案都假设 `action_chunk_size`、控制频率、RTT、reset、图像顺序、`pivot` 语义已知；实际上这些都没在公开文档里写死。没有 MVP，后面的数据/控制优化可能全是错位的。
- **与现有方案差异**：头部队伍通常先训模型、再适配；我们反过来，先用官方 WLA Base 做“接口 + 延迟 + 失败模式”的基线，再决定训什么。
- **技术可行性**：官方 WLA 有 Base 权重和模型服务器；提交模板有 `example_policy.py`/`web_policy.py`；挑战赛 API 是 Python `PolicyService`，可直接包一层 adapter。先返回 `ee` 动作，`pivot` 全零，chunk 8。
- **所需资源**：1 张 24GB GPU；1 名工程师 72h；3 个任务（HangCup、PlugInEthernet、FoldTowel）；单任务不计分通道；不需要新数据。
- **落地步骤**：
  1. D1：跑通 echo policy + `get_action` 形状/token/端口；记录 `f_c`、图像顺序、reset 行为。
  2. D2：接 WLA server，做 54D→21D adapter；`pivot=0`；chunk=8。
  3. D3：3 任务 ×5 次，记录成功/步骤分/耗时/p50/p95/p99/崩溃。
  4. D4：写 MVP-0 报告：哪些假设被证实/证伪；决定是否继续。
- **风险/门**：WLA 与挑战赛观测/动作不兼容；`pivot` 语义不明；GPU 被占；网络抖动。**门 G0**：3 任务 ×5 次无崩溃、动作形状合法、p99 <300ms；否则先修接口，不训模型。

### I-02 CAM-CANON：把“任务-相机”伪相关拆开

- **动机**：32 个任务只有 10 种头部相机 profile，且**每个任务只用 1 种**；`fx` 跨度 186–296，`cy` 跨度 225–347。评测是多机器人，API 又不给 `camera_info`。模型完全可能把“任务外观”和“某个相机视角”一起记住；换相机就掉点。
- **与现有方案差异**：第 12 轮假设“腕部无内参、需要标定”；复核发现腕部内参其实存在（左 9 种、右 7 种，fx 432.9–437.5），真正的大头是**头部相机跨任务不一致**。不再把标定当主创新，而是做**训练期虚拟相机规范化 + FOV 随机化**；推理期用标称相机，必要时再接 I-08。
- **技术可行性**：用每个数据集的 `camera_matrix/dist_coeffs` 把图像裁切/重采样到固定角视场（virtual pinhole）；对主点偏移做平移；训练时在 10 个 profile + 连续 FOV 范围里随机化。只做 2D warp/crop，不需要深度。先跑 camera-ID probe：冻结特征预测相机 profile，若准确率很高，说明 shortcut 存在。
- **所需资源**：33k episodes / 18.3M frames 的原始视频（on-the-fly 处理，不落盘全量）；1 张 GPU；无新标注；1 名工程师 1–2 周。
- **落地步骤**：
  1. 解析 32 个 `info.json`，建立 task→profile 表；确认每个任务只有 1 个 profile。
  2. 训练 camera-ID probe（冻结 WLA/VLM 特征 + 线性分类）；若 >90%，shortcut 成立。
  3. 实现 canonicalizer：固定虚拟 `fx/cx/cy`，按内参裁切/缩放；训练时随机 FOV/主点。
  4. 固定 seed 微调 WLA action head：baseline vs canon vs canon+aug。
  5. 留出 2–3 个 camera profile 做 OOD 验证；再上单任务通道。
- **风险/门**：评测相机超出训练范围；裁切丢上下文；主点估计误差；过增强伤精度。**门 G1**：camera-ID probe 高 + 留出 profile 上 canon 版成功率 ≥ baseline；否则降级为“只做 FOV 随机化”或放弃。

### I-03 SESSION-BALANCE：别让 8520 和单 robot 任务定义“通才”

- **动机**：8 个 robot、150 个 session；8520 占 35%；平均每任务只覆盖 2.94/8 个 robot；14 个任务 ≤2 个 robot；9 个任务 >90% 单 robot（FoldTowel 95.3%、ToolboxStorage 95.3%、StoreCups 95.1%…）。评测跨 N 台机器人，模型很可能把“任务”与“某个 robot 的运动学/视角”绑定。
- **与现有方案差异**：标准训练按 episode 均匀采样，等于让 8520 和少数 robot 主导梯度；我们改成 **task×robot×session 平衡采样**，并做 **robot-held-out** 验证。不采新数据，只改采样和验证协议。
- **技术可行性**：元数据里 `task_id` 带 robot/date，可直接构造 sampler；PyTorch `WeightedRandomSampler` 即可；推理不受影响。
- **所需资源**：CPU；无额外 GPU；1 名工程师 3–5 天。
- **落地步骤**：
  1. 统计每个任务的 robot/session 分布；标记 ≤2 robot 和 >90% 单 robot 的任务。
  2. 构造三种 split：random、robot-held-out、session-held-out。
  3. 训练 baseline vs balanced；看 held-out robot 的成功率/动作误差。
  4. 对缺失 robot 的任务，用同任务其他 robot 的样本做上采样，但不重复到过拟合。
- **风险/门**：平衡会牺牲主 robot 的拟合；有些任务根本没有多 robot 数据，无法凭空造多样性；评测若只用同一 robot，平衡可能不涨。**门 G2**：robot-held-out 上平衡版 ≥ baseline，且主 robot 不回归 >3pp；否则按任务调权重。

### I-04 ACTION-ALIGN：动作是“未来目标”，不是“当前状态”

- **动机**：3 个任务审计显示，`action.*_ee_pose_gripper_base` 相对 `observation.state.*` 的最佳 lag 是 **2–3 帧**；lag 0 的平均位置误差 1.3–2.0cm，最佳 lag 仍 1.1–1.6cm。naive 的 `(obs_t, action_t)` 配对会让模型学“用当前状态解释未来目标”，在接触段产生系统性超前/滞后。
- **与现有方案差异**：多数 BC 管线默认 action 是 next-step；我们显式估计 lead，按 `action_{t+lead}` 对齐，或训练“预测未来目标”的 delta。不是新模型，只是数据对齐 A/B。
- **技术可行性**：cross-correlation 估计 lag；按任务/机器人分别估计；构造 aligned dataset；微调 action head。成本低，但 lead 可能随任务/速度变化，不能假设全局常数。
- **所需资源**：CPU 做 lag 统计；1 张 GPU 做 A/B；无新数据；3–5 天。
- **落地步骤**：
  1. 对 32 个任务全量估计 lag（不只 3 个）；看分布是否稳定。
  2. 生成 `aligned` 版本：`obs_t → action_{t+lead}`；保留原版做对照。
  3. 微调 WLA action head；离线看动作平滑度/轨迹误差；单任务看成功率。
  4. 若 lead 不稳定，改用“预测未来 2–3 帧的 relative target”而不是硬 shift。
- **风险/门**：lead 可能来自控制/测量延迟，不是标签错误；硬 shift 可能破坏因果；全量 lag 可能因任务而异。**门 G3**：aligned 版在 ≥3 个接触任务上不回归，且有 1–2 个任务 +5pp；否则只保留“relative target”不改标签。

### I-05 LANG-SPLIT：5 条指令拼成 1 条长字符串，不是“多语言泛化”

- **动机**：每个任务的 `tasks` 是“一个字符串的 list”，字符串由 **5 条同义指令用 `@` 拼接**，长度 166–451 字符；评测给的是单条指令。naive tokenizer 会看到 `@` 分隔的长文本，和评测分布不一致；模型可能学会“忽略前半段/找关键词”，也可能被分隔符干扰。
- **与现有方案差异**：不做“语言增强”大工程；只做标签拆分：每条 paraphrase 单独采样，留一条做 held-out 语言验证；同时映射到官方任务名。
- **技术可行性**：纯文本处理；1 小时可完成；不需要 GPU。
- **所需资源**：CPU；32 个任务的元数据；无新数据。
- **落地步骤**：
  1. 解析 `tasks`，按 `@` 拆成 5 条；确认 32/32 都是 5 条。
  2. 训练时每条随机采样；验证时分别测“同义句”和“官方单句”。
  3. 留出 1 条 paraphrase 做语言 held-out；看是否比整串训练更好。
- **风险/门**：评测若也给整串（需确认），拆分可能不匹配；同义句可能语义噪声。**门 G4**：官方单句上 split 版 ≥ 整串版；否则保留整串作为 fallback。

### I-06 EDGE-DEADLINE：chunk size 是控制参数，不是推理参数

- **动机**：30 步 chunk @30Hz = 1s 开环；6B 推理约 100ms；MolmoAct2 180/790ms；接触任务需要 <200–300ms 的反馈。API 的 `action_chunk_size` 固定，所以必须在提交前选一个 `H_c`，让“执行时间 ≥ p99 推理+RTT”，同时尽量短。
- **与现有方案差异**：不是再训一个更快模型；而是做**deadline-aware 执行层**：固定 `H_c` 由 p99 决定；VLA 后台预计算下一个 30 步 plan；前台每 `H_c` 步返回一次；plan 未就绪就复用旧 plan/安全 hold；per-port 隔离 + watchdog。把“模型延迟”变成“可调度的系统参数”。
- **技术可行性**：API 允许 `H_c=1..30`（固定）；WLA server 可异步；per-port 进程/线程；CPU 做图像解码/动作拼接。工程量大头在稳定性和 p99，不在算法。
- **所需资源**：1 张 GPU；每端口 1 个 CPU 进程；1–2 名工程师 2–3 周；单任务通道。
- **落地步骤**：
  1. 在 MVP-0 测 `f_c`、RTT、推理 p50/p95/p99；算 `H_c >= ceil(τ_p99 × f_c)`；若 τ=100ms、f_c=30Hz，则 `H_c≥3`；τ=200ms 则 `H_c≥6`。
  2. 扫 `H_c ∈ {3,5,8,10,30}`；每个值测成功率、p99、超时、动作平滑度。
  3. 实现后台 plan + 前台 chunk；plan 过期/未完成时的 fallback：旧 plan 剩余段 → 安全 hold。
  4. N 端口并发压测：GPU 批处理、优先级、内存、reset 隔离。
  5. 选“p99 达标 + 成功率不回归”的最小 `H_c`。
- **风险/门**：`H_c` 太短导致 VLA 调用过频/GPU 打满；太长回到开环；RTT 抖动；官方是否允许固定 chunk 之外的动态行为（先按固定做）。**门 G5**：p99 ≤300ms、超时/崩溃不升、3 任务成功率 ≥ baseline；否则加 `H_c` 或回退 30。

### I-07 CHUNK-SERVO-LITE：第 12 轮的遗产，但只做“轻版”

- **动机**：最后 3 厘米的接触/插入/挂/拉链是 32 任务的主战场；纯开环 chunk 无法修正。视觉伺服是合理的控制层补丁。
- **与现有方案差异**：保留“30 步规划 + 5 步执行 + 演示检索相对目标”；**剪掉**完整数字孪生、6D 物体位姿网络、9–10 周计划、30Hz 广域网伺服。只选 2–3 个刚体接触任务（HangCup、PlugInEthernet、ZipUp/StackBowls），用腕部内参（已确认存在）+ 头部双目做经典 IBVS/PBVS；不做透明/变形任务。
- **技术可行性**：WLA 给 30 步 plan；5 步执行；目标位姿/目标图从成功演示检索；经典视觉伺服不需要学习权重；单模型合规。难点是遮挡、透明、标定和目标位姿估计。
- **所需资源**：2–3 个任务；1 张 GPU；1 名工程师 4–6 周；单任务通道；不需要全量仿真。
- **落地步骤**：
  1. 在 I-02/I-03/I-06 过门后，选 2–3 个任务；先做“无伺服”的 5 步执行基线。
  2. 建目标库：每个任务 1–2 个关键帧，存相对位姿 + 腕部目标图 + 质量分。
  3. 先做 PBVS（头双目/EE 相对目标），再做 IBVS（腕部 2D）；只在接触段启用，限幅 1cm/0.05rad。
  4. A/B：servo off/on；每任务 5–10 次；看成功率、步骤分、p99。
- **风险/门**：目标估计不稳；透明/反光；标定误差；规则解释；收益不抵工程。**门 G6**：2/3 任务 +10pp，且非接触任务不回归；否则砍掉，只保留 5 步执行。

### I-08 SELF-CALIB：如果 FOV 随机化还不够，就让机器人自己标定

- **动机**：评测 API 不给 `camera_info`；10 种头部 profile 说明相机几何确实会变。如果 I-02 的 FOV 随机化在留出相机上仍掉点，就需要在线估计相机参数。
- **与现有方案差异**：不训练第二个模型；用机器人自身运动 + 已知关节角/URDF + 头部双目，在 `reset()` 后做一次经典 PnP/自标定；或者在同一 checkpoint 加一个相机参数辅助头（单模型）。
- **技术可行性**：难。头部相机是否稳定看到自己的手臂/夹爪需实测；关键点检测可能需要轻量模型（有单模型风险）；透明/遮挡会失败。可行路径是“已知末端执行器标记 + 关节角 → 3D 点 → 2D 检测 → PnP”。
- **所需资源**：1–2 名工程师 4–8 周；标定姿态数据；GPU；高风险。
- **落地步骤**：
  1. 在 MVP-0 录 20 帧 reset 姿态，检查手臂/夹爪是否在头部视野。
  2. 用颜色/几何标记或已知夹爪轮廓做 2D 关键点；用 URDF 算 3D；PnP 求 K/R/t。
  3. 验证重投影误差；只在高置信时启用 canonical warp；否则回退标称相机。
- **风险/门**：手臂遮挡、关键点检测、规则解释、时间不够。**门 G7**：重投影 ≤5px 且留出相机成功率 ≥ I-02；否则放弃，保持 P2。

## 8. 6 周最小可行路线（含 go/no-go）

| 阶段 | 时间 | 做什么 | 通过标准 | 失败动作 |
|---|---|---|---|---|
| **MVP-0** | 72h | WLA + API + 3 任务 + chunk 8 | 无崩溃、动作合法、p99 <300ms | 先修接口，不训模型 |
| **数据审计** | 第 1 周 | camera/robot/session/language/action 全量统计；camera-ID probe | 确认 task-profile 与 robot 覆盖假设 | 若 probe 低，CAM-CANON 降级 |
| **数据修复** | 第 2 周 | CAM-CANON + SESSION-BALANCE + LANG-SPLIT + ACTION-ALIGN 的 A/B | 留出相机/robot 不回归，≥1 项 +3pp | 只保留有效项 |
| **EDGE-DEADLINE** | 第 3–4 周 | 测 RTT/f_c；扫 H_c；后台 plan + watchdog；N 端口压测 | p99 ≤300ms、3 任务不回归 | 回退 H_c=30 或加 GPU |
| **CHUNK-SERVO-LITE** | 第 5–6 周 | 2–3 个任务 PBVS/IBVS A/B | 2/3 任务 +10pp | 砍掉，只保留 5 步执行 |
| **全量干跑** | 第 6 周末 | N 端口、reset、内存、超时、32 任务干跑 | 稳定、可复现、无泄漏 | 回退安全基线 |

**预算原则**：320 trials 是最终评测，不是开发集；开发主要用单任务通道。`p≈0.25` 时 320 trials 的全局标准误约 **2.4pp**，所以不要把 +1–2pp 当结论；至少看配对 A/B 的 bootstrap 区间。本报告里所有“+3pp/+10pp”都是待验证假设（C 级），不是承诺。

## 9. 这轮最值得押注的是什么

如果只能押一个组合，我押：

> **DATA-CANON + EDGE-DEADLINE + MVP-0**：
> 先用 72 小时证明官方 WLA 能在挑战赛 API 上跑通；再用 CAM-CANON/SESSION-BALANCE 把“任务-相机/任务-机器人”伪相关拆开；再用 deadline-aware 5–8 步 chunk 把 1 秒开环压到 200–300ms；CHUNK-SERVO-LITE 只在数据/执行门都过了之后，选 2–3 个接触任务做。

这不是最炫的方案，但它有三个优点：

1. **可证伪**：camera-ID probe、robot-held-out、p99、单任务 A/B 都能提前告诉你对不对。
2. **合规**：数据管线不改模型数量；deadline 层是调度；轻量伺服是确定性控制器；没有第二个学习模型。
3. **边际收益高**：数据修复影响 32 个任务和多机器人评测；deadline 影响所有接触任务；两者都不依赖“再训一个更大的模型”。

## 10. 一句话押注

**先把 33k 演示修成相机-任务解耦、robot/session 平衡、动作-语言对齐的可复现数据管线，再用 deadline-aware 的 5–8 步 chunk 把 30 步开环压到 200–300ms 反馈；MVP-0 不过门，不投视觉伺服。**

# 第 1 轮产物 · CONSISTENCY-FIRST 技术报告

> 检索/复核日期：**2026-10-31（UTC）**。对象：宇树 **UniBot 世界挑战赛**（G1 + Dex1，32 项桌面任务，通才单模型赛道，选手自部署 + 官方远程真机 API）。本报告是想法区「CONSISTENCY-FIRST」的工程化产物；它承接第 12 轮 CHUNK-SERVO，但把主投从“视觉伺服”改成“数据一致性 + deadline 执行 + MVP-0”，CHUNK-SERVO 降为 P1 条件项。

## 0. 结论与边界

### 0.1 一句话结论

公开 WLA 6B 已经把“大模型基座”这件事做完了；这个挑战赛剩下的主要矛盾，是 **33k 演示的 task-camera / task-robot 异质性**与 **30 步开环 chunk 的反馈延迟**。先用 MVP-0 测通接口，再用 CAM-CANON/SESSION-BALANCE/ACTION-ALIGN/LANG-SPLIT 修数据一致性，最后用 deadline-aware 5–8 步 chunk 把反馈压到 200–300ms；视觉伺服只在前述门都通过后，选 2–3 个接触任务做轻量版。

### 0.2 证据等级

| 等级 | 含义 | 本报告中的例子 |
|---|---|---|
| **A** | 官方文档、提交模板、数据集元数据、排行榜 JSON 直接核实 | 规则、API、33,276 eps、10 个头部相机 profile、WLA 30 步 chunk |
| **B** | 我们在公开数据/网页上做的分析，可复现 | 32 任务/robot/session 分布、camera-ID probe、action lag、近重复负结果、榜单回归 |
| **C** | 设计假设，需单任务通道/真机验证 | CAM-CANON 涨点、5–8 步优于 30 步、轻量伺服 +10pp |

### 0.3 本轮不做什么

- 不从零训 VLA/World Model；官方 WLA Base 已开源。
- 不做完整数字孪生/9–10 周 sim-to-real；先用真实 API 测。
- 不做第二个学习模型/残差策略；优先数据管线、调度器、确定性控制器、同 checkpoint 辅助头。
- 不做 6D 物体位姿网络、力/触觉闭环、30Hz 广域网伺服。
- 不把预览榜单的任务排名当实测难度；只当先验。
- 不做去重/去噪/再采 33k；审计未发现大量重复/坏帧。

### 0.4 两条重要修正

1. **腕部相机不是“没有内参”**。32 个数据集的 `wrist_left/right.color.camera_matrix` 都存在；左腕 9 种、右腕 7 种，`fx` 约 432.9–437.5。第 12 轮把“腕部无内参”当主问题是错的。
2. **头部相机是 10 种 profile，不是 11 种**。按 `camera_matrix_left/right + T + dist_coeffs + R` 的完整元组统计，32 个任务只有 10 种；每个任务只用其中 1 种。此前“11 种”是计数口径差异，以本报告的 10 为准。

## 1. 事实核对

### 1.1 比赛规则（A）

官方参赛手册（飞书 docx；2026-10-31 通过 `r.jina.ai` 复核中文/英文两版）：

| 项 | 规则 |
|---|---|
| 模型 | 所有任务须基于**同一模型**完成，不得混合多个模型一起测试；模型类型不限（World Model、VLA 均可） |
| 任务 | **32 项**桌面任务 |
| 次数 | 每任务 **10 次**独立运行 |
| 泛化 | 5 类各 2 次：位置、干扰物、桌面背景、未见物品、人为干扰 |
| 时限 | 单次真机执行上限 **180 s** |
| 排名 | 先比 32 任务总平均成功率；相同看总平均步骤分；再相同看更早提交 |
| 部署 | 评测跨 **N 台机器人**；提交须从 **8765** 起暴露 N 个连续端口；每端口独立交互，`reset()` 状态必须隔离 |
| 测试通道 | 另有**不计分的单任务测试通道**，可用于单任务成功率/步骤分验证 |

**约束**：任何“第二个学习模型”都要先考虑规则风险；任何“多端口共享状态”都要先考虑 `reset()` 隔离。

### 1.2 提交 API（A）

当前 `unibot_submission` main README（commit `edd0a1c9`，2026-08-21）与 `example/example_policy.py`、`policy/web_policy.py` 核实：

| 项 | 规格 |
|---|---|
| 观测图像 | `cam_left_high`、`cam_right_high`、`cam_left_wrist`、`cam_right_wrist` 四路 RGB **480×640** |
| 本体 | 双臂关节 `[7]`、EE 位姿 `[6]`（xyz+rpy，base 系）、夹爪 `[1]`、下身体 `[15]`、语言 `str` |

| EE 动作 | `action.left_ee_pose_gripper_base [6]`、`action.right_ee_pose_gripper_base [6]`（**绝对目标位姿**，xyz+rpy，base 系） |
| chunk | `action_chunk_size` 固定；index 0 先执行，其余顺序执行，直到 evaluator 再次调用 `get_action` |
| 元数据 | `control_space`、`obs_delta_indices`、`image_resize`、`action_chunk_size`、`token` |
| token | 握手校验一次；每次 `get_action` 的 `meta.token` 都要匹配 |
| 缺失 | **没有 depth、camera_info、force/torque、tactile** |
| 监控 | 评测端逐调用记录延迟、波动、动作统计规律，作为结果可信度的一部分 |

**注意**：GitHub 搜索快照可能显示旧字段 `data_keys`/`obs_chunk_size`；以 main raw README 的 `obs_delta_indices`/`image_resize` 为准。旧快照不要用于写 adapter。

**关键推论**：

- `action_chunk_size=30`、控制频率 30Hz 时，一次 `get_action` 之后有 **1 秒开环执行**；chunk 内没有新观测、没有打断机制。
- 视觉伺服要生效，必须把 `H_c` 降到 3–8，或把 VLA 规划与执行拆成双频；`H_c` 是提交前要扫的超参数。
- 控制频率未在 README 中写死；本报告默认 30Hz，必须在 MVP-0 实测。

传输层细节（`policy/web_policy.py`）：websocket + msgpack；图像 JPEG quality 95；每个连接同步 `route()`，推理期间阻塞事件循环。这意味着“边缘服务”优化有明确空间，但也意味着不要把 GPU 推理放在 websocket 回调里同步做。

### 1.6 语言 / 动作 / 轨迹审计（B）

**语言**：

- 32/32 任务的 `tasks` 列都是“一个字符串的 list”。
- 字符串由 **5 条同义指令用 `@` 拼接**；长度 **166–451 字符**。
- 评测给的是单条指令；naive 训练会把整串（含 `@`）当成一条长指令。
- 例：HangCup 的首条是 “Hang the cup on the marked spot on the cup rack.”，整串 255 字符、5 条。

取证分析（B）：

1. `generated_from = "gen_leaderboard.py"`；`generalist` 8 个，`specialist` 空。
2. 8 个模型 ×32 任务，`step_score ~ success_rate` 回归 **R² > 0.999999**，最大残差 <0.006；每个模型斜率不同，形式是 `step ≈ k_model × success`。

1. **task-camera 伪相关**：每个任务只有一种头部相机 profile，模型没有机会在同一任务上学习相机不变性；评测换相机就是 OOD。

4. **动作超前**：action 目标比 state 超前 2–3 帧；最佳 lag 仍有 1.1–1.6cm 残差；需要 A/B，不是无脑 shift。
5. **轨迹干净**：无 NaN、EE 有效、零运动少、gripper 一致；近重复 <1cm pair 为 0%。**不要浪费时间做去重/去噪**。
6. **相机内参不是“缺失”**：腕部内外参都有；真正变化大的是头部相机（fx 186–296）。
7. **榜单不可反推**：预览/合成；只当“大家都不高”的难度信号。

### 2.4 这些发现如何映射到创新点

| 发现 | 创新点 | 为什么便宜/可证伪 |
|---|---|---|
| 每任务固定 1 个 camera profile | **CAM-CANON** | camera-ID probe 可直接验证 shortcut 是否存在 |
| robot 覆盖低 | **SESSION-BALANCE** | 只改 sampler，不采数据；robot-held-out 可直接验证 |
| 语言 `@` 拼接 | **LANG-SPLIT** | 纯文本，1 小时；官方单句验证 |
| action 超前 2–3 帧 | **ACTION-ALIGN** | lag 统计 + A/B；不新模型 |
| 30 步开环 | **EDGE-DEADLINE** | 测 p99/f_c；扫 H_c；单任务验证 |
| 最后 3 厘米 | **CHUNK-SERVO-LITE** | 只选 2–3 任务；过门才做 |
| 评测相机未知 | **SELF-CALIB** | P2；FOV 随机化不够时再上 |
| 接口未知 | **MVP-0** | 72h；不做就无法测任何东西 |

## 3. 问题形式化

### 3.1 评分与不确定性

总分：

```math
S = \frac{1}{32}\sum_{t=1}^{32} p_t,\qquad
p_t = \frac{1}{10}\sum_{j=1}^{10} y_{t,j},\quad y_{t,j}\in\{0,1\}.
```

320 trials 下，若 `p≈0.25`，全局标准误：

```math
\mathrm{SE}(S)\approx \sqrt{\frac{p(1-p)}{320}}\approx 0.0242.
```

所以：

- 不要把 +1–2pp 当结论；至少看配对 A/B 的 bootstrap 区间。
- 人为干扰轴占 `2/10=20%`；human 轴 +10pp → 全局 +2pp（`0.2 × 10pp`）。
- 若 10 个接触任务各 +15pp，全局约 `10/32 × 15 ≈ +4.7pp`；这是本报告的量级假设（C），不是承诺。

### 3.2 接口时间模型

设：

- `f_c`：evaluator 控制频率（假设 30Hz，待测）；
- `H_c`：提交的 `action_chunk_size`；
- `τ`：网络 RTT + 推理 + 图像传输的等效延迟；
- `T_fb`：从“世界变化”到“策略看到变化”的反馈周期。

则：

```math
T_{\mathrm{fb}} \approx \frac{H_c}{f_c} + \tau.
```

为了避免“chunk 执行完了、下一 chunk 还没来”造成停顿，需要：

```math
\frac{H_c}{f_c} \gtrsim \tau
\quad\Longrightarrow\quad
H_c \gtrsim \tau f_c.
```

| 场景 | `H_c` | `f_c` | `τ` | `T_fb` | 评价 |
|---|---:|---:|---:|---:|---|
| 官方 WLA 默认 | 30 | 30 | 50ms | **1050ms** | 接触段基本开环 |
| 保守 | 5 | 30 | 50ms | **217ms** | 可做 1–2 次接触修正 |
| 低 RTT | 5 | 30 | 20ms | **187ms** | 需低 RTT |
| 高 RTT | 5 | 30 | 150ms | **317ms** | 增益降档/加 chunk |
| 低控制频率 | 5 | 10 | 50ms | **550ms** | 改 `H_c=3` 或只做 PBVS |
| 极低延迟 | 3 | 30 | 20ms | **120ms** | 动态任务可用 |

**结论**：`H_c` 必须由实测 `τ_p99` 和 `f_c` 选；不能把 30 步默认值直接搬到远程 API。若 `τ_p99=100ms`、`f_c=30Hz`，则 `H_c≥3`；若 `τ_p99=200ms`，则 `H_c≥6`。`H_c` 太小会把 GPU 打满，太大回到开环。

### 3.3 相机不可辨识性

图像观测可写成：

```math
I = \pi(K, T_{\text{base}\to\text{cam}}, X_{\text{scene}}),
```

其中 `K` 是相机内参，`T` 是外参，`X` 是场景。挑战赛 API 只给 `I`，不给 `K/T`；训练集有 10 种 `K`，每个任务只有 1 种。模型要学的是：

```math
a = f(I, q, l)
```

其中 `q` 是本体状态，`l` 是语言。如果训练中 `l`（任务）与 `K` 高度相关，模型可能学到：

```math
a = f(I \mid K(l), q, l),
```

即“先认出任务，再用该任务的相机先验解释图像”。评测换相机时，`K` 变，模型没有 `camera_info`，就会出现系统性偏差。

**可行干预**：

1. **训练期规范化**：把所有训练图像 warp 到虚拟相机 `K0`；这样 `I` 的像素几何一致，模型不必记 `K`。
2. **FOV/主点随机化**：让模型见过比 10 种更宽的相机分布，逼近评测的未知 `K`。
3. **辅助头**：同一 checkpoint 加一个 `K` 预测头，用预测的 `K` 做 warp；但不是第二个模型。
4. **在线自标定**：用机器人自身运动 + 已知关节角做 PnP；高成本，P2。

### 3.4 动作超前

设 `s_t` 是测量状态，`a_t` 是动作目标。审计显示：

```math
a_t \approx s_{t+\ell},\qquad \ell\approx 2\text{–}3.
```

如果训练用 `(s_t, a_t)`，模型学的是“从当前状态预测 2–3 帧后的目标”；这不一定错，但和“下一步动作”的语义不同。两种处理：

- **对齐**：训练 `s_t → a_{t+\ell}`；让标签与“未来目标”一致。
- **保留 + 相对目标**：训练 `s_t → (a_t - s_t)`；让模型学“目标相对当前状态的位移”，避免绝对位置漂移。

本报告建议先做 lag 全量统计，再用 A/B 决定；不假设 shift 一定涨点。

### 3.5 单模型合规

挑战赛要求“同一模型”。本报告的合规边界：

- 数据管线（canonicalization/balance/align/language）不增加模型。
- `EDGE-DEADLINE` 是调度/服务层，不增加学习参数。
- `CHUNK-SERVO-LITE` 是确定性控制器（IBVS/PBVS），不训练权重。
- `SELF-CALIB` 若是经典 PnP，不增加模型；若加辅助头，必须同一个 checkpoint，且推理时只走一个模型。
- 任何“第二个学习模型/残差策略”先视为不合规，除非官方明确允许。

## 4. 系统设计

### 4.1 MVP-0 架构

```text
┌──────────────────────────────────────────────┐
│ Evaluator (N ports 8765..8765+N-1)           │
└───────────────┬──────────────────────────────┘
                │ websocket: obs / action chunk
                ▼
┌──────────────────────────────────────────────┐
│ Per-port PolicyService (CPU)                  │
│  ├─ obs adapter (rpy→rot6d, image resize)     │
│  ├─ action adapter (WLA 54D→API 21D)          │
│  ├─ deadline scheduler / watchdog             │
│  └─ plan cache (30-step VLA plan)             │
└───────────────┬──────────────────────────────┘
                │ async, batched
                ▼
┌──────────────────────────────────────────────┐
│ Shared WLA server (GPU, 6B)                   │
│  UnifoLM-WLA-1.0 Base, chunk 30               │
└──────────────────────────────────────────────┘
```

MVP-0 的最小配置：

- 3 个任务：HangCup（短、挂）、PlugInEthernet（插入）、FoldTowel（长、变形，防回归）。
- `control_space="ee"`；`pivot` 全零；`action_chunk_size=8`。
- 每端口独立进程/状态；共享 GPU 模型；单任务不计分通道。
- 记录：`f_c`、RTT、推理 p50/p95/p99、reset 行为、图像顺序、动作形状、崩溃。

### 4.2 数据管线

```text
for each dataset d:
    K_d, dist_d = read_camera(d)
    for each episode e in d:
        # 1) camera canonicalization (training only)
        I_t = warp_to_virtual_camera(I_t, K_d, dist_d, K0)
        # optional: randomize K around K0 within observed range
        # 2) language split
        instr = sample_one_of(split(e.tasks, "@"))
        # 3) action alignment
        target = action[e.t + lead(e)]  or  action[e.t] - state[e.t]
        # 4) balanced sampling
        weight = 1 / (count(task, robot, session))
        yield (I_t, state_t, instr, target, weight)
```

**CAM-CANON 细节**：

- 目标虚拟相机 `K0`：取训练集 `fx` 中位数附近，例如 `fx0=250`、`cx0=320`、`cy0=240`（480×640）。
- 对每个源 `K_d`，计算目标视场对应的源像素窗口，裁切/缩放；主点偏移用平移补偿；畸变用 `undistort`。
- 训练时对 `fx0`、`cx0/cy0` 做小范围随机化；不要随机到超出源图有效区域。
- 推理时用 `K0`；若已知评测相机 `K`（未来 API 可能提供），直接用它 warp 到 `K0`。
- 不要用深度做透视变换；平面单应/裁切足够，避免引入深度误差。

**SESSION-BALANCE 细节**：

- 采样权重 `w ∝ 1 / n(task, robot, session)`；再按任务归一化，避免长尾任务被过度采样。
- 训练 split 按 robot/session 分组，验证 split 留出 robot；不要按帧随机 split（会泄漏）。
- 对 ≤2 robot 的任务，不能凭空造 robot；只能让模型在已有 robot 上更均衡，并用 camera/FOV 随机化补多样性。

**ACTION-ALIGN 细节**：

- 对每个任务估计 lag `ℓ_t`；若分布集中（如 2–3），用任务级 `ℓ`；若分散，用相对目标而不是硬 shift。
- 训练目标可以是 `a_{t+ℓ}`（绝对目标）或 `a_t - s_t`（相对位移）；二者都试，选单任务不回归的。
- 不要改变推理接口：仍然返回绝对目标位姿。

**LANG-SPLIT 细节**：

- `tasks[0].split("@")` 得到 5 条；训练随机采样 1 条；验证分别测同义句和官方单句。
- 留出 1 条 paraphrase 做语言 held-out；如果官方评测用固定单句，优先优化官方句。
- 保留整串作为 fallback，防止评测实际给整串。

### 4.3 EDGE-DEADLINE

```python
class DeadlinePolicy:
    def __init__(self, H_c, f_c, p99_tau):
        self.H_c = H_c
        self.f_c = f_c
        self.plan = None
        self.future = None
        self.safe_hold = None

    def get_action(self, obs):
        # 1) ensure a plan; never block the websocket for long
        if self.plan is None:
            self.plan = self._predict_with_timeout(obs)  # cold start
        elif self.future is None or self.future.done():
            self._maybe_adopt_future()

        # 2) take H_c steps; if plan exhausted, hold/replan
        if self.plan is None or self.plan_idx >= len(self.plan):
            return self._safe_hold(obs)

        chunk = self.plan[self.plan_idx : self.plan_idx + self.H_c]
        self.plan_idx += self.H_c

        # 3) prefetch next 30-step plan while executing this chunk
        if self.future is None:
            self.future = self.executor.submit(self._predict, copy_obs(obs))

        return self.adapter.to_api(chunk, obs, self.token)
```

关键规则：

- `H_c` 固定；由 `τ_p99` 和 `f_c` 选，不在线变（除非官方允许）。
- 后台 plan 必须在 `H_c/f_c` 内完成；否则用旧 plan 的剩余段，再不行安全 hold。
- 每端口独立 `plan_idx/plan/future`；`reset()` 清空。
- `get_action` 永远返回合法形状；NaN/超时 → hold/上一组合法 chunk。
- 多端口：优先级队列按 `deadline` 排序；小 batch 合并同批请求；不要为了吞吐牺牲 p99。

**安全 hold**：保持当前 EE 位姿、gripper 不变、`pivot=0`；不要发零位/突然大幅动作。

### 4.4 动作适配（WLA 54D → 挑战赛 21D）

```text
WLA 54D:
  left_ee_rel[6], left_gripper[1], left_hand[6],
  right_ee_rel[6], right_gripper[1], right_hand[6],
  waist[3], torso[3], base_vxvy[2], base_wz[1],
  base_pose_rel[6], height[1], left_leg[6], right_leg[6]

挑战赛 ee 21D:
  left_ee_abs[6], right_ee_abs[6],
  left_gripper[1], right_gripper[1], pivot[7]
```

映射：

1. `left_ee_abs = compose(T_base_ee_left_current, exp(left_ee_rel))`；转 xyz+rpy。
2. `right_ee_abs` 同理。
3. gripper 直通（按挑战赛的 0–1 方向校验）。
4. `pivot = [vx, vy, wz, yaw, pitch, roll, height]`，从 WLA base/waist 组合；具体符号/顺序必须用 `example_env.py` 和单任务通道验证。
5. 腿部/灵巧手在挑战赛 `ee` 模式下不直接下发；若 `pivot` 需要下身体，按官方 WLA server 的 `action.pivot` 语义映射。

**关键细节**：WLA 的每个未来动作是“相对 plan-time 当前 EE”的位姿（compose 后才是 base 系绝对目标），不是累积增量；adapter 必须先把整个 30 步 compose 成 base 系绝对目标，再按 `H_c` 切片。否则第 6–30 步会以错误锚点解释，产生系统性偏移。

**帧/TCP 风险**：WLA 的 EE 帧与挑战赛的 `*_ee_pose_gripper_base` 帧可能差一个 TCP/夹爪长度偏移；必须用 `example_env.py` 的观测和真实数据做一次手眼/工具坐标校准（平移 ≤1cm、旋转 ≤2°）。这是 G0 的第一验证项。

**`pivot` 风险**：README 只写 “Lower-body / pivot target”，没有逐维定义。先返回全零 pivot（保持下身体不动），只验证双臂；不要猜符号。

### 4.5 CHUNK-SERVO-LITE（P1 条件项）

只有在 I-02/I-03/I-06 过门后，才做 2–3 个任务：

```text
VLA:   每 30 步产出一个 30 步 plan；后台线程；不阻塞 get_action
Servo: 每 5 步用最新腕部/头部图修正一次；返回 5 步 chunk
API:   metadata.action_chunk_size = 5；evaluator 执行 5 步后再次调用
```

- **目标**：从成功演示检索 `T_target_ee*`（受器→夹爪相对位姿）和腕部目标图；在线用头双目/PnP 估计 `T_base_target(t)`，期望 `T_base_ee^d = T_base_target · T_target_ee*`。
- **控制**：远距离 PBVS，近距离 IBVS；误差 `e = log(T_ee^{-1} T_ee^d)`；每块限幅 1cm/0.05rad；接触段法向缩幅。
- **控制律**：

```math
e = \log\!\left(T_{ee}^{-1}T_{ee}^{d}\right),\qquad
\Delta = \mathrm{clip}\!\left(K_p e + K_d \dot e,\ \pm\delta_p,\ \pm\delta_r\right),\qquad
a_{cmd} = a_{ff}\circ\exp(\Delta).
```

  其中 `a_ff` 是 VLA 的 5 步前馈，`Δ` 是伺服修正；每块限幅 1cm/0.05rad，接触段法向缩幅、切向保留。

- **回退**：目标位姿不可靠 → 只用腕部 IBVS；腕部遮挡 → 只用头双目 PBVS；都不行 → VLA 开环。
- **不做**：完整数字孪生、6D 物体位姿网络、透明/变形任务、30Hz 广域网伺服。
- **门 G6**：2/3 任务 +10pp，且非接触任务不回归；否则砍掉，只保留 5 步执行。

## 5. 实验设计与门

### 5.1 离线探针

| 探针 | 目的 | 通过/失败含义 |
|---|---|---|
| **camera-ID probe** | 冻结特征预测 10 种相机 profile | 高准确率 → task-camera shortcut 存在；低 → CAM-CANON 降级 |
| **robot-ID probe** | 冻结特征预测 8 个 robot | 高 → robot/场景 shortcut；低 → 覆盖问题可能不严重 |
| **task-ID probe** | 语言/图像预测任务 | 作为 sanity check；太高不一定是坏事 |
| **action-lag 全量** | 32 任务估计 lag 分布 | 集中 → 可 shift；分散 → 用相对目标 |
| **language split** | 5 条 paraphrase 的语义一致性 | 一致 → split 安全；不一致 → 保留整串 |
| **near-dup** | 轨迹/图像近重复 | 已完成 3 任务负结果；全量可选 |

### 5.2 微调 A/B

- **Baseline**：官方 WLA Base + 官方数据处理 + 30 步 chunk。
- **+CAM-CANON**：虚拟相机 + FOV 随机化。
- **+SESSION-BALANCE**：task×robot×session 平衡采样。
- **+ACTION-ALIGN**：lag 对齐/相对目标。
- **+LANG-SPLIT**：按条采样 + 留一。
- **全组合**：逐项加，记录 held-out camera/robot 与单任务成功率。
- 训练预算：先小步数（如 1–2k steps）看趋势，再全量；不要一开始 8 卡大跑。

### 5.3 单任务通道

- 任务：HangCup（挂）、PlugInEthernet（插入）、ZipUp 或 StackBowls（接触/叠）、FoldTowel（长/变形，防回归）。
- 每个任务 5–10 次；A/B 同初始条件；记录成功、步骤分、耗时、p99、崩溃。
- 先测 baseline，再测数据修复，再测 `H_c`，最后才测 servo。
- 单任务通道不计分，但它是唯一敢做 A/B 的地方；不要拿正式 320 trials 做开发。

### 5.4 全量干跑

- N 端口并发；每端口独立 `reset()`；检查内存不涨、状态不串、超时不崩。
- 32 任务 ×1 次干跑；记录每任务耗时/失败阶段；不追求成功率。
- 确认提交包大小、依赖、token、端口范围、启动时间。

### 5.5 门 G0–G7

| 门 | 问题 | 通过标准 | 失败动作 |
|---|---|---|---|
| **G0** | 接口是否通？ | 3 任务 ×5 次无崩溃；动作形状合法；p99 <300ms | 先修 adapter/接口，不训模型 |
| **G1** | task-camera shortcut 是否存在？ | camera-ID probe 高；留出 profile 上 CAM-CANON ≥ baseline | 降级为 FOV 随机化或放弃 |
| **G2** | robot 覆盖是否影响？ | robot-held-out 上平衡版 ≥ baseline；主 robot 不回归 >3pp | 按任务调权重/放弃 |
| **G3** | 动作超前是否可修？ | ≥3 个接触任务不回归，1–2 个 +5pp | 只保留相对目标，不硬 shift |
| **G4** | 语言拆分是否有效？ | 官方单句 ≥ 整串；同义句不崩 | 保留整串 fallback |
| **G5** | deadline 是否达标？ | p99 ≤300ms；超时/崩溃不升；3 任务不回归 | 加 `H_c`/加 GPU/回退 30 |
| **G6** | 轻量伺服是否涨点？ | 2/3 任务 +10pp；非接触不回归 | 砍掉 servo，只保留 5 步执行 |
| **G7** | 全量是否稳定？ | N 端口/reset/内存/超时全过 | 回退安全基线 |

### 5.6 指标

- 主指标：32 任务平均成功率；步骤分；单任务成功率。
- 系统指标：`f_c`、RTT p50/p95/p99、推理 p50/p95/p99、超时率、崩溃率、内存。
- 动作指标：关节步长/EE 步长、零运动比例、gripper 一致性、重规划次数。
- 数据指标：camera-ID/robot-ID probe、held-out camera/robot 成功率、语言 held-out。
- 统计：配对 bootstrap；报告均值 + 95% CI；不要只报点估计。

### 5.7 统计现实

- 320 trials 的全局 SE ≈2.4pp；单任务 10 次 trial 的 SE 很大（p=0.5 时约 15.8pp）。
- 单任务 +1 次成功不足以证明 +10pp；至少 5–10 次配对，最好跨多个任务。
- 评测有 5 类泛化，每类 2 次；不要把“位置泛化”与“人为干扰”混在一起报。

## 6. 竞赛策略

### 6.1 320 trials 是投资组合

- 总分是 32 个任务平均；单任务权重相同。
- 优先投“失败发生在最后 3 厘米/接触段”的任务；数据修复影响所有任务，deadline 影响所有长任务。
- 用单任务通道测 `q_t`（失败在最后 3cm 的比例）× `Δ`（修复增益）/ `cost_t` 排序；每 3–5 个任务更新一次。
- 不要把预算全押在 1–2 个任务；32 个任务平均，分散更稳。

### 6.2 任务分档（先验，待单任务通道）

- **A 档：接触/插入/挂/叠/拉链/锁**（先验约 19 个）：HangCup、DisconnectEthernet、ToolboxStorage、PlugCharger、Unlock、ArrangeTestTubes、PourOutMedicine、OrganizeStationery、PackBag、ZipUp、PaperCupStacking、StorePaddle、StoreCups、PlugInEthernet、StackBowls、StoreEarphones、PackPhone、OrganizePencilCase、SyringeWaterTransfer。
- **B 档：VLA/语义/变形**（约 13 个）：FruitCollection、PackDoll、FruitSorting、ColorArrangement、PlacePhotoFrame、OrganizeBookshelf、PickOutBatteries、OrganizeTools、FoldTowel、ArrangePlates、SpellRobot、ConveyorSorting、RemovePinnedNote。
- **C 档：低投入/观察**：单任务通道里 `p_t` 接近 0 且失败在早期感知/抓取的任务；不投伺服，保留 VLA 基线。

这张表是语义先验，不是榜单排名；不要从预览榜单反推。

### 6.3 提交节奏

- 若允许多次提交（需邮件确认）：先交**安全基线**（官方 WLA + `H_c=30` + 官方 API adapter），锁定“更早提交”的 tie-break；再交 `EDGE-DEADLINE` 版本；最后交数据修复版本。
- 若只允许一次：先用单任务通道把 `H_c` 和数据修复打磨到稳定，再交最终版。
- 不要把 320 trials 浪费在“从零训 6B”“完整世界模型”“32 任务各训策略”上。

### 6.4 预算

| 项 | 估计 |
|---|---|
| GPU | 1×24GB（WLA 微调/推理）；全量微调可 1–2 卡 |
| CPU | 每端口 1 进程；N 端口 |
| 存储 | 33k episodes 视频 + 索引；按需流式读取 |
| 人力 | 1–2 人；6 周 |
| 评测 | 单任务通道做开发；正式 320 trials 只跑最终候选 |

## 8. 风险与合规

| 风险 | 影响 | 缓解 |
|---|---|---|
| WLA 与挑战赛观测/动作不兼容 | MVP 跑不通 | adapter 先行；`pivot=0`；单任务通道逐项验证 |
| 评测相机超出 10 种 profile | CAM-CANON 失效 | FOV 随机化；SELF-CALIB 兜底；训练时留出 profile |
| 任务内 robot 太少 | SESSION-BALANCE 无法造多样性 | 按任务调权重；camera/FOV 增强；held-out 现实评估 |
| 动作 lag 不稳定 | ACTION-ALIGN 不涨 | 先全量统计；改用相对目标；不硬 shift |
| 语言评测格式未知 | LANG-SPLIT 不匹配 | 保留整串 fallback；单任务通道确认 |
| `H_c` 太短导致 GPU 打满 | p99 超标/超时 | 用 p99 选；后台 plan；优先级批处理；回退 30 |
| `pivot` 语义不明 | 下身体乱动/碰撞 | 先全零；只验证双臂；读 `example_env.py` |
| 单模型解释 | 被判第二个模型 | 数据/调度/确定性控制器；同一 checkpoint；材料写清楚 |
| 过拟合单任务通道 | 正式评测不涨 | 多任务、held-out camera/robot、配对 bootstrap |
| 数据泄漏 | 离线指标虚高 | 按 session/robot/camera 分组 split；相邻帧不跨 split |
| 安全 | 回撤/重抓碰撞 | 限速/限幅/最大重试；watchdog；hold |
