# 第 3 轮迭代（灵感循环 v3：「场景驱动创新」×「评测指标」）—— 从"预测分数"到"预测排名"：场景合约代数 × 排名保真评测

> 承接 v2（UIP-01′~15）。v2 把 `human_*` 读成"反向撤回"这条规则事实，并用 Gazebo 造数据、给单步打分。本轮换一个更根本的提问：**我们到底在优化什么？** 比赛不是一个"绝对分数"的回归问题，而是**在未知场景分布、未知评分合成方式、N 个机器人、有限 episode 下的排名问题**。两个灵感词正好击中它的两端：「场景驱动创新」回答**测试场景从哪来**（场景合约 + 扰动代数），「评测指标」回答**怎样用最少代价把排名测准**（配对场景 / 分层分配 / cluster 设计 / Pareto 口径）。
>
> 本轮有两个反直觉的合成实验结论：① 在同等 episode 预算下，配对场景采样把"两两排序正确率"从 0.904 提到 0.962，达到同样精度约省 **4×** episode；② **策略侧的结果方差并不改变期望排名**（等均值时胜率恒为 0.50），所以不要为了"稳"牺牲均值——真正该降的是**评测器方差**，不是策略方差。

## 0. 本轮核实的事实（检索日期 2026-11-12）

沿用 v2 已核实的 32 任务计分点（2 步 50/50 ×11、3 步 30/30/40 ×14、4 步 25×4 ×5、5 步 20×5 ×2；末步恒 ≥ 前序步）与"`human_*` = 把已完成进度撤回"。本轮新增两条来自官方 submission 仓库 README 的事实：

| 事实 | 内容 | 来源 |
|---|---|---|
| 评测 = N 机器人 / 随机顺序 / 每机器人固定端口 | "Evaluation runs across **N test robots in randomized order** ... the evaluator connects to one fixed port per robot ... must expose exactly **N consecutive ports**" | unibot_submission README §5（2026-11-12） |
| 可信度是另一套口径，不是分数 | 逐步延迟及其波动、返回动作的统计规律性会被记录，并可能随成绩一并展示 | 同上 §6（2026-11-12） |

这两条把"评测"从一句口号变成**可设计的对象**：N 端口 = N 个 cluster；随机顺序 = cluster-randomized；可信度 = 硬约束而非优化目标。v2 只把延迟当工程问题，本轮把它当**评测设计**问题。

## 1. 两个灵感词的解读

### 1.1 场景驱动创新：先给直觉

不要把 32 个任务当成 32 个静态数据集。每个任务其实是一个**场景生成器**：官方 `info.json` 只列了它的几条 `generalization` 实例（未见物品、人为撤回……），真正的评测是**从这个生成器里再抽样**。所以创新不该是"为这 32 个场景各训一个策略"，而应是"**把场景的生成语法写下来**，在语法的闭包里做设计、造数据、做评测"。场景驱动 = 先问"测试场景能被哪些操作变换出来"，再问"策略在变换下是否保持"。

### 1.2 场景驱动创新：再给严谨定义

对任务 `i` 定义**场景合约**：

```
C_i = ( O_i, G_i, {φ_{i,k}, w_{i,k}}_{k=1..K_i}, U_i, D_i )
```

- `O_i`：物体/资产集合与初始位姿分布；`G_i`：成功谓词；
- `φ_{i,k}, w_{i,k}`：第 k 个计分步的谓词与分值（来自 `scoring_points`，`Σ_k w_{i,k}=100`）；
- `U_i = {u_obj, u_pos, u_dis, u_bg, u_human}`：五类扰动算子（未见物品 / 位置 / 干扰物 / 背景 / 人为撤回）；
- `D_i`：人为干扰的"目标 × 时刻 × 速度"调度族。

**场景闭包**：`Cl(C_i) = { u_{j_m}∘…∘u_{j_1}(s) : s∼O_i, u_{j_·}∈U_i }`。官方只给了闭包中的**若干样本**；评测分布 `P_test` 是闭包上的未知混合。关键结构：算子**不可交换、存在交互**——`u_obj` 换掉物体的抓取面，会放大 `u_pos` 的偏移误差；只测单轴会**系统性高估**鲁棒性。因此要用**因子设计**（2^5 全因子，或分辨率 V 的 16 轮部分因子）而不是"一次只动一个轴"。

### 1.3 评测指标：先给直觉

排行榜不是"谁分数高"，而是"在**有限次抽样**下，谁被排到前面"。这两件事的差别，就像"真实命中率"与"打 10 枪看谁赢"：后者有**估计噪声**。噪声来自三处：任务抽样、场景轴抽样、以及 N 个机器人（cluster）。降低**估计方差**（而不是降低策略本身的结果方差）能让排名更快收敛——这是本轮最实用、也最容易被忽略的杠杆。

### 1.4 评测指标：再给严谨定义

设场景 `s` 上策略 `π` 的 episode 结果为 `(χ_s, σ_s)`（成功 0/1、步骤分 0–100）。官方合成为某个单调函数 `f`（权重未知）：

```
m_f(s;π) = f(χ_s, σ_s),  f 单调不减;   M_f(π) = E_{s∼P_test}[m_f(s;π)]
```

排行榜是 `M_f` 在候选集 `Π` 上的**序**。因为 `f` 未知，定义**鲁棒序**：`π ≻ π′` 当且仅当对所有允许的 `f` 都有 `M_f(π) ≥ M_f(π′)`。若一方只在成功率上更好、另一方只在步骤分上更好，则二者**不可比**，应报 `(成功率, 步骤分)` 平面上的 **Pareto 前沿**，而不是伪造一个标量。

**排名保真（Rank Fidelity, RF）**：本地评测用有限样本给出估计 `M̂`，

```
RF = P[ rank(M̂) = rank(M) ]      （或期望 Kendall τ）
```

它和"分数估计的 MSE"不是一回事：两条策略分数差很小时，MSE 很小也可能把序排反；反之亦然。所以本地 benchmark 的目标函数应是 **RF / 两两排序正确率**，不是分数 MSE。

**配对估计（CRN）为什么有效**：对同一场景 `s` 同时评 `π` 与 `π′`，差值 `Δ(s)=m(s;π)−m(s;π′)` 的方差为

```
Var(Δ) = Var(m_π) + Var(m_π′) − 2ρ·√(Var_π·Var_π′)
```

独立抽样时 `ρ=0`；共享场景时 `ρ>0`。等方差下**有效样本量放大 `1/(1−ρ)` 倍**。本轮合成实验测得平均 `ρ≈0.62`，对应约 `2.6×` 理论效率；实测在达到 0.96 两两正确率时，独立采样约需 128 episode/策略，配对约需 32，约 **4×**。

**N 端口 = N 个 cluster**：同一机器人上的 episode 有共同偏移（标定、光照、桌面布置），存在**组内相关 ICC**。若按 i.i.d. 估方差，会低估排名不确定性；正确做法是 **cluster bootstrap / 混合效应模型**，并让本地复现也按"机器人"分组。这是 README 明说的评测结构，却几乎没人会在本地复现。

### 1.5 合流：CARE 闭环

**Contract（合约）→ Algebra（扰动代数造场景）→ Rank-fidelity Evaluation（配对 / 分层 / cluster 评测）→ Metric-aware Optimization（按官方部分分与 Pareto 口径训练）→ 回到 Contract 修谓词。**

一句话：**先把"考什么"写清楚，再把"怎么考得准"做到极致，最后才谈"怎么考高分"。**

## 2. 三个可检验假设

- **H1（评测杠杆 > 模型杠杆）**：当策略已接近公开基线时，提升排名最便宜的手段是降低**评测方差**（配对 + 分层 + cluster），而不是换更大模型。
- **H2（场景轴有交互）**：`u_obj × u_pos` 等组合的分数损失 > 各轴单独损失之和；单轴评测会高估鲁棒性。
- **H3（策略方差 ≠ 排名）**：在均值口径下，策略侧结果方差**不改变期望排名**；只有硬失败（超时、可信度异常、零分）才需要风险约束。因此不应把 CVaR 当通用优化目标。

## 3. 合成实验：两个反直觉结论

脚本 `tmp/r3_rank_sim.py` → 结果 `tmp/r3_rank_sim.json`。设定：32 任务严格按官方分值分布构造，8 个策略、8 个技能类别、共享场景难度耦合，240 次重复。**仅用于给方法排序，不是真机证据。**

- **结论 A（评测方差才是真敌人）**：达到 0.96 两两排序正确率，独立均匀采样约需 **128** episode/策略；共享场景配对只需约 **32**。等均值下策略结果方差对胜率几乎无影响（0.498–0.501）。
- **结论 B（别为"稳"牺牲均值）**：低方差策略若均值低 0.005，`N=3` 时胜率仅 0.465，`N=32` 时降到 0.392；均值高 0.01 时，高/低方差胜率几乎相同（`N=3`: 0.565 vs 0.566）。⇒ 风险敏感只该用于**硬约束**，不能替代均值。

## 4. 瓶颈假设与取舍

- **该做的**：把 `info.json` 编译成合约；用因子设计测轴交互；用"配对 + 分层 + cluster"把排名测准；用 `(成功率, 步骤分)` 的 Pareto 前沿代替单一分数。
- **不该做的**：为 32 个任务各训一个模型；把"最优步骤顺序"当主攻；用 CVaR 普遍压低方差而牺牲均值（除非有硬阈值）。
- **与 v2 的关系**：v2 的 GSO / DRF 仍是**场景与步骤分的来源**，但本轮把它们从"造数据"升级为"**可被因子设计调用的场景算子**"；v2 的 CSG 从"延迟护栏"升级为"**评测硬约束**"。

## 5. 本轮最大风险

**一句话**：整套 CARE 押在"我们用合约与因子设计造出的场景分布 ≈ 官方隐藏的 `P_test`"上；若官方评测其实只是固定 32 任务上的少量随机扰动（而非我们假设的闭包混合），那么大量场景工程与排名保真优化会退化为**精致的自我评测**，真实榜单收益有限——必须尽早用公开榜单/真机做外部校准锚点。
