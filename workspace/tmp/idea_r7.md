# 想法区 · 第 7 轮：把刀磨在树上——RSI 剪枝、打包状态，和一堂「调参无用」的课

**灵感词**：branch and bound / hyperparameter optimization / data structure
**起点**：v2.4「X-DUB/PACE-ΠA-CC*」。held-out 50 例 0.552 s / 80,463 个 OS 节点 / 0 张 PACE 表；5 个残例 0.0492 s / 6,802 节点；hard3 12 例 0.0207 s；deep 8 例 0.0456 s；45 个合成紧状态 45/45 被 ICC 关闭；38 例核心 0.120 s。它的收官风险是一句话：

> 这一轮的 2.8× 主要来自把 OS 提到 PACE 之前、从而绕开 PACE 根层约 0.08 s 的表构造，而不是来自 ICC：ICC 在 50 个 held-out 上 0 命中，真正的判决仍是 8 万节点的 OS 树；一旦换到一个 PACE 根层很便宜、而 OS 很贵的分布，CC 会比 v2.3 慢一个数量级。

这句话我同意前半句，不同意它的结论。**ICC 确实不是 2.8× 的来源；但「OS 树很贵」不是换分布才会遇到的问题，它在这一轮的数据上就已经是全部成本。** v2.4 把 OS 当成一个足够便宜的原子，只改了它的调用顺序；这一轮我不换层，只问三个问题：

1. 这棵 8 万节点的树，能不能在**节点入口**剪掉一部分？（branch and bound）
2. 同一个节点，能不能用更少的数据搬运算完？（data structure）
3. 调参到底该调什么？哪些维度是**可证明的死维度**？（hyperparameter optimization）

三个问题的答案分别是：能，RSI 剪掉 28.9% 的节点；能，打包状态让每节点便宜 1.50×；分支顺序在 NO 上是死维度，真正该调的是「剪枝强度 vs 每节点额外常数」的成本比。最后一项是本轮最像研究的部分：**不是所有让节点变少的改动都值得做**，而 HPO 的正确目标函数不是节点数。

## 一、NO 死在哪些节点：RSI

先把状态写清楚。全资格下，OS 的状态是

```text
σ = (R, A, est) ,
r_i = est_i ,   d_i = h − q_i(R) ,   c_σ(t) = |{k : A_k ≤ t}| .
```

`R` 是未调度任务，`A_k` 是机器 k 的下一次可用时刻，`est_i` 是任务 i 的最早释放，`q_i(R)` 是 i 之后的最长尾（不含 `p_i`），`h` 是公共期限。`c_σ(t)` 是 t 时刻还空着的机器数；全资格下它是精确的聚合容量。

把「所有前驱都已调度」的任务叫 ready：

```text
Ready(σ) = { i ∈ R : pred(i) ∩ R = ∅ } .
```

对 ready 的 i，定义它在当前容量里的可行起点集合：

```text
slot_σ(i) = { t : r_i ≤ t ≤ d_i − p_i ,
              c_σ(u) ≥ 1 对所有 u ∈ [t, t+p_i) } .
```

**RSI（Ready-Set Infeasibility）**：如果某个 `i ∈ Ready(σ)` 的 `slot_σ(i)` 为空，则 σ 不可行。

证明只需要一行：任何从 σ 出发的可行完成，都必须让 i 在某个 `t ∈ [r_i, d_i−p_i]` 开始；i 在 `[t,t+p_i)` 占一台机器，所以那个区间里 `c_σ(u) ≥ 1`。如果这样的 t 不存在，完成也不存在。∎

这个证明不依赖「以后容量只会更少」这种直觉，虽然直觉也对。它只依赖一件事：**i 自己的加工区间必须是当前容量里的一个槽**。所以 RSI 是节点级的 fail-first，不是分支顺序的调整。

v2.3/v2.4 的 OS 在做什么？它对每个 ready 任务算 `earliest`，如果算不出来，就把它从候选表里去掉，继续搜别的任务；它没有意识到「有一个 ready 任务已经放不下」本身就是 NO。这个差别在数据上很直接：50 个 held-out 上 RSI 命中 10,533 个节点，总节点从 80,463 降到 57,236，**−28.9%**，判决 50/50 不变。

```
RSI 不是「更聪明的排序」，是「更早的死亡判定」。
```

## 二、调参的第一课：顺序是死的

有了 RSI，下一步自然会想：既然节点还多，能不能调分支顺序？LPT、EDD、SPT、MRV、随机……这是 HPO 最顺手的维度。但这里有一个可以被证明的负结果。

**定理（NO 的序不变性）**。固定状态编码与精确 memo，且不使用 dominance。若根状态不可行，则 OS 的节点数不依赖兄弟节点的枚举顺序；它的调用数等于 1 加上根可达状态图（每个状态是 `(mask, cap, rel)`）的边数；展开的状态数等于图的节点数。

证明的骨架：`mask` 每层严格变小，所以可达状态图无环。对一个不可行根，所有可达状态都是失败的；DFS 第一次进入某状态时把它完整展开并加入 memo，之后每次再从别的父节点进入都是 memo 命中。每个可达父状态都会被展开一次（因为它失败，不会早停），展开时枚举它的所有候选子节点，所以可达状态图的每条边恰好被调用一次。兄弟顺序只改变这些边的**遍历次序**，不改变集合。∎

实测完全吻合：在 50 个 held-out 上，LPT / EDD / SPT 的节点数都是 **57,236**，时间 0.246 / 0.247 / 0.246 s。也就是说，**在 NO 上把 HPO 预算花在分支顺序上是零收益**。顺序不是完全没用：它影响 YES 的早停。50 个 `h=OPT` 的 held-out 上，LPT 4,601 节点、EDD 4,617、SPT 8,755；SPT 几乎慢一倍。所以正确说法是：

```
NO：顺序是死维度（定理）。
YES：顺序是活维度，但它只影响找到第一条成功路径的时间。
```

这条定理把 HPO 的搜索空间砍掉一维，也解释了为什么 v2.3/v2.4 里换 order 从来没有在 NO 上产生差异。真正剩下的旋钮只有两个：**pruning strength** 和 **state representation**。而 pruning 的收益不能只看节点数，要算成本：

```text
不用剪枝：N0 个节点，每节点 c0
用剪枝：  N1 个节点，每节点 c0 + ce
值得做 iff  N1·(c0+ce) < N0·c0
        iff  N1/N0 < c0/(c0+ce) .
```

这个不等式是后面所有消融的判据。它也是本轮最实用的「HPO 结论」：**节点数不是目标函数，时间是**。

## 三、把状态压进几个整数

v2.4 的 OS 每个节点要复制 `cap`（长度 h 的 list）和 `rel`（长度 n 的 list），memo key 是 `(mask, tuple(cap), tuple(rel))`。50 个 held-out 上每节点约 6.31 µs，其中很大一部分是分配、复制和哈希。

这一轮把它压成几个整数：

```text
cw = max(1, bit_length(m))          # 容量字段宽，m=3 → 2 bits，m=4 → 3 bits
rw = max(1, bit_length(max(h, max est)))   # 释放字段宽
CP = Σ_t c(t) · 2^(cw·t)            # 容量剖面
RP = Σ_{i∈R} r_i · 2^(rw·i)         # 释放向量（已调度任务的字段清零）
PC = Σ_{i∈R} pred_R(i) · 2^(4i)     # 未调度前驱计数，n≤16 → 4 bits
AV = Σ_t [c(t)>0] · 2^t             # 可用槽位图
```

memo key 就是 `(mask, CP, RP)`。`PC`、`Ready`、`AV` 都由这三个量和固定的优先图决定，所以 key 是精确的，不是哈希近似。

两个操作变成位运算：

1. **EARLIEST**：在 `AV` 里找从 `r_i` 开始、长度为 `p_i` 的连续 1。令 `x = AV >> r_i`，则
   ```text
   c = x & (x>>1) & … & (x>>(p_i−1))
   ```
   的第 s 位为 1，当且仅当 `[r_i+s, r_i+s+p_i)` 全可用；取最低位就是最早起点；最后检查 `r_i+s ≤ d_i−p_i`。这是 O(p_i) 个大整数按位操作，不是 O(h·p_i) 的 Python 循环。
2. **PLACE**：对 `[t,t+p_i)` 的每个槽减 1；若某槽减到 0，就在 `AV` 里清掉那一位。释放向量的更新只碰 i 的后继；前驱计数只减 i 的后继，减到 0 就把 j 加进 ready 位集。

`os_pack.py` 里还有一个**增量 ready 位集** `RDY`：不再每个节点扫 n 个任务，而是直接迭代 `RDY` 的位。这让节点入口的固定开销从 O(n) 降到 O(|Ready|)。

**一个必须记下来的实现陷阱。** 我第一版 `EARLIEST` 先把 `AV >> r_i` 截到 `d_i−p_i−r_i+1` 位，再找连续 1。结果 50 个 held-out 只用 **53 个节点**就全判 NO，看起来像天大的加速。它不是：截断把「起点在窗口末端、但加工区间伸到窗口外」的槽丢掉了，于是很多本来能放下的任务被判成放不下——**假 NO**。修正是先在整个 `AV >> r_i` 上找连续 1，得到起点 s 后再检查 `r_i+s ≤ d_i−p_i`。修好后节点回到 57,236。这个 bug 的教训写进产物区：**证书便宜到不合理时，先怀疑检查器，不要先庆祝。**

打包的收益是纯常数：v2.4 的 80,463 节点 0.508 s（6.31 µs/node）→ 打包后同样 80,463 节点 0.339 s（4.21 µs/node），**1.50×**。它不改变树，只改变每个节点的功。

## 四、HPO 的负结果：节点数不是目标

有了 RSI 和打包，我把能想到的「让节点变少」的旋钮都接在同一个 50 例 held-out 上，得到一张很不像论文主表的表：

| 配置 | 节点 | 时间 | 相对 RSI |
|---|---:|---:|---:|
| v2.4 OS（tuple memo） | 80,463 | 0.508 s | 2.07× |
| 打包，无 RSI | 80,463 | 0.339 s | 1.38× |
| **打包 + RSI（本轮）** | **57,236** | **0.246 s** | **1.00×** |
| + dominance memo | 74,301 | 1.709 s | 6.9× |
| + 全任务可放置性（ATPF） | 56,015 | 0.459 s | 1.87× |
| + 内部节点 EDF 松弛 | 55,512 | 0.747 s | 3.04× |
| + ready 集 Hall 割（RICC） | 50,979 | 0.662 s | 2.69× |
| + singleton forcing | 37,364 | 0.299 s | 1.22× |
| 反向 OS（时间反演） | 47,822 | 0.242 s | 0.98× |

这张表的读法不是「谁节点最少」，而是「谁在成本模型里赢」：

- **dominance** 相对 v2.4 少 7.7% 节点，但 Pareto 前沿的逐项比较让每节点贵 3 倍多；输。
- **EDF 预松弛** 只少 3.0% 节点，却要在每个节点解一次抢占式 EDF；输。
- **RICC（ready 集上的 Hall 割）** 少 10.9% 节点，但 O(r²)–O(r³) 的窗口枚举让时间翻倍；输。
- **ATPF** 少 2.1% 节点，多扫一遍所有剩余任务；输。
- **forcing** 最像赢家：少 34.7% 节点，只慢 22%。但按成本模型，`N1/N0 = 0.653`，`c0 = 4.30 µs`，实测 `ce = 3.70 µs`，阈值是
  ```text
  ce* = c0·(N0/N1 − 1) = 4.30 × 0.532 = 2.29 µs .
  ```
  3.70 > 2.29，所以 Python 里输；如果节点内核换成 C、forcing 的额外常数降到 0.5 µs，它会赢。**同一个算法在不同常数下有不同的最优配置，这不是矛盾，是 HPO 应有的样子。**
- **反向 OS** 少 16.4% 节点、快 1.6%，看起来是免费的。但它是分布相关的：50 例里反向赢 27 例，输 23 例，最好情况的 oracle 是 38,441 节点（只比反向少 20%）。我试了 maxq / maxest / sumq / sumest / S 的单阈值选择器，最好的一个（sumq≤171）是 46,276，已经是在这 50 例上过拟合的结果；再试 doubling race（64,128,256,… 交替跑两个方向），总成本 **169,728**，是单向的 3 倍。**没有便宜的方向选择器，就不做 portfolio。**

所以本轮只保留 RSI + 打包。其他的不是「错」，是「在这个常数下不划算」；这条成本模型比任何单个配置都重要。

## 六、没有免费的核心

v2.4 的最大风险是「8 万节点的序树就是证书本身」。这一轮我试了一个自然的压缩：找一个**极小不可行核心**（删到不能再删的任务子集），在核心上重跑 OS；如果核心仍然 NO，它的序树就是原实例的证书（加任务不会让不可行变可行）。

50 个 held-out 的结果：

- **20/50 是单删不可约的**：删掉任意一个任务都变可行。剩下 30 个可以删 1–5 个任务（平均删 1.08 个）。
- 贪心核心平均 **13.2 / 14.28** 个任务（−7.6%），最小 10，最大 16。
- 核心上的序树从 57,236 降到 **39,915** 节点（−30.3%）。
- 但找核心本身要 **0.716 s / 50**，是判决时间 0.288 s 的 **2.5×**。

所以核心压缩是**离线证书工具**，不是在线加速：它能把证书缩 30%，但生成证书比直接判决还贵。更重要的是，它反过来说明 v2.4 的 8 万节点不是「实现懒」：**这些 NO 在任务层面几乎不可约**，平均只删 1.08 个任务。想靠「找一个小反例」来绕开序搜索，在这批数据上没有成功。

## 七、本轮交付

- **OS-RSI 内核**：`Ready` 集上的单任务不可放置性剪枝；证明是「任何完成都必须给 i 一个当前槽」。
- **打包状态 BPK**：容量/释放/前驱计数按 `bit_length(m)`、`bit_length(max(h,max est))` 动态选字段宽；memo key 是 `(mask, CP, RP)`；`EARLIEST` 用连续 1 的位运算；ready 集增量维护。
- **序不变性定理**：NO + 精确 memo + 无 dominance 时，节点数与兄弟顺序无关。顺序只在 YES 上影响早停（SPT 在 50 个 YES 上 8,755 节点，LPT 4,601）。
- **级联不变**：仍是 `ICC → OS-RSI(B=10k) → PACE`，门仍是 `full ∧ n≤16 ∧ 0≤S≤4`；没有新增分布相关的门。
- **结果**：held-out 1.90×、5 残例 2.08×、hard3 1.41×、deep 1.34×、38 核心 1.05–1.09×、141 合计 1.63×；50/50 节点下降。
- **HPO 负结果**：dominance / EDF / RICC / ATPF / forcing 都是「节点更少、时间更慢」；forcing 的阈值是 2.29 µs 额外常数；反向 OS 的 oracle 只比单向少 20%，doubling race 是 3× 更差。
- **正确性**：1,080 组暴力对拍（m≤4）0 不一致；600 个 A≠0 随机状态打包 vs list 状态 0 不一致；70 + 45 张 YES 排程验证；53 张 ICC witness 重算；146/146 与 v2.4 同判决。
- **证书**：50 个 held-out 的极小核心平均 13.2 个任务，核心序树 39,915（−30%），但提取成本 2.5×，只能离线用。

## 八、一句话最大风险

**这一轮的 1.9× 全部来自「同一棵指数搜索树被剪掉 28.9%、每个节点便宜 1.50×」这两个常数，而不是任何新的可证明下界；一旦分布让 RSI 不触发（或 n>16 出门），剩下的就只有打包的 1.50×，而最坏情况的指数上界一点没动。**
